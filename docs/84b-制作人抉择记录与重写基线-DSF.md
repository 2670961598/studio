## 一、共同前提（制作人定调）

1. **公司是责任共同体，长期可能脱离具体人独立运行。** 这不是“多 agent 聊天室”，而是要有最终责任、任命、审计、结清、可继承的实体。
2. **单人/单层最终退化为当前 agent 工具（DSH、Claude Code 形态），可以接受。** 不强行把“一个 agent 唤子 agent”叫完整公司；低层就是“公司形状的 agent harness”，价值在权责记录，不在调用树。
3. **权力不是有/无，而是“在谁手里、是否下发、下发到哪一层”。** 未下发的权力不消失，默认归老板/宰相，但必须显式登记为“保留权力”。
4. **老板是根，宰相是投影。** 宰相不是权力来源，是老板在框架中的具体化身；老板可撤回；宰相不得借投影自授、扩权、自审。
5. **公司层级 L2–L9。** L1 不成公司；L2 最低公司；L9 最高。每层有不同必设岗位；层级越低，允许缺席越多；层级越高，部门、审计、人事等逐步必设。
6. **“内核固定”指责任内核固定，不是岗位表固定。** 固定的是：老板最终责任、宰相投影、任命/授权/审计/宪法记录、不得自授、不得同层自审。岗位表随层级展开。
7. **旧 63–82 的权责模型不再兼容。** 不是“修几句”，是重写；旧卷转历史/素材，不得与新卷双基线并存。

## 二、逐条抉择

### 抉择 1：事实源——选 A（分域权威表）

**制作人选择**：A。一个对象只有一个权威，按域切，不搞“三本账都自称事实源”。

**落地含义**：

| 域 | 权威 | 投影/索引 | 写入者 | 重建 |
|---|---|---|---|---|
| 组织、人事、岗位、章程、公司定义 | 公司 git 目录 | 面板、平台字段 | daemon/网关（唯一写入者） | 定义可重建；历史变更靠事件 |
| 当前工作流程状态、单据字段 | 协作平台（YouTrack/Taiga） | 台账事件、面板 | 只经网关写平台 | 平台是当前态权威，不是历史权威 |
| 工作事件、成本、证据、结清 | 台账（append-only 事件） | SQLite 索引、`cost_daily` 等汇总 | daemon | 事件可重建；汇总表是投影 |
| 记录视图 | 台账的记录投影 | `records` | daemon | **`records` 不是第四事实源** |
| 能力包/部署绑定 | 独立工件，不进定义包 | 绑定档案 | 部署/运维 | 按绑定档案恢复 |
| DSH 插件/公司资产 | 公司资产部（官方 84 D1a）；执行器专属资产可随公司包携带清单，但须标“专属/通用” | 资产索引、绑定档案 | daemon/部署 | 资产摘要 + 来源；不混入纯配置定义正文 |

> 官方 84 的 D1 是**明示例外**：公司定义包的“纯配置”约束不能被用来否认 DSH 插件资产；正确写法是“定义包正文纯配置 + 资产部独立 + DSH 插件专属资产 + 聚合体分 part 标类型”。不能一边保留例外、一边在 70/75 写“定义包绝不含可执行内容”。

**后果**：

- 17/02/78/80 里“三事实源”“台账不是事实源”“records 是事实面”的互斥句必须重写为“域表”。
- 平台只是“当前流程态”的权威，不是公司组织/人事/成本的权威；平台挂了，公司身份不丢。
- `records` 降为台账视图，不再另立事实面。
- 审计问“谁批准”时，答案只能落在一个域的一个权威上。

**未决**：域表的具体行、平台字段到台账事件的映射、历史数据迁移。重写第一交付物就是这张表。

### 抉择 2：最低公司——选 B，但按制作人的“层级 + 保留权力”模型

**制作人选择**：B 的精神（分层），但分层轴不是我提的 sandbox/internal/full 三档，而是**公司层级 L2–L9 + 权力保留/下发**。

**制作人模型（原意）**：

- 最开始所有权力都在老板手中；分给几个 agent、什么时候分，是老板决定。
- 有一个宰相级别的 agent 直接对接老板；对老板来说，公司大小事都找宰相对接；对公司来说，宰相是老板在框架中的具体化身。
- 公司等级高了，可以有多个宰相，老板和不同方面的负责人对接。
- 小公司允许缺席某些岗位，缺席岗位的权力归老板掌握；老板掌握也就是宰相 agent 掌握。
- 公司越大，权力越下发到部门，因为一个人不够了。这是一个演化过程，不是一次性切分。
- **内核仍然固定**；变的是“每层必须有哪些岗位、哪些权力已经下发”。

**关键修正（相对我上一轮的说法）**：

1. 不是“sandbox / internal / full”三档合法性；是 **L2–L9 的必设岗位矩阵**。
2. 层级只决定“最低必设”；**是否下发、何时下发仍由老板决定**。但一旦设岗，该岗位的权责/记录就是强制的，不能再叫“可选资产”。
3. 未设岗位的权力不能悬空，必须显式写成“保留给老板/宰相”，并进入记录；不能像旧 76 卷那样把核心位置塞进“可选目录”。
4. 单人/单层退化为 DSH/Claude Code 形态，是**允许的**；但那时它是“低层公司/agent harness”，不能宣称具备完整公司的独立审计与最终责任。

**后果**：

- 需要一张 **L2–L9 必设岗位矩阵**：每层列出“必设 / 可选 / 未设时权力归谁 / 升级触发条件”。这是重写第一优先级，不是文案。
- 旧 66/70/76 的“11 类治理位置”“默认目录可选资产”“附加推荐”必须全部重写；核心位置不能再放在可选容器里。
- 公司升级/降级要有条件与记录；不能只改一个 `level` 字段。
- L2 与 L3 的差异、何时必须设部门/审计/人事，必须可判定；否则“层级”只是标签。

**未决**：L2–L9 每层的具体必设清单；升级/降级触发器；多宰相的协调与优先级。

### 抉择 3：授权根与宰相——老板为根，宰相是投影（等效 A）

**制作人选择**：抉择 2 里的宰相 agent；补充：宰相是一层，下面只有一层 agent 时，退化为 DSH/Claude Code 那种“一个 agent 唤起子 agent”。

**落地含义**：

- **根权力在老板/设立行为**，不在宰相。宰相是九级 agent，是老板在框架中的投影/化身；老板可撤回。
- **不自授**：宰相不能给自己发根授予，不能自己任命自己，不能自己扩大自己的权限。
- **八级由老板亲自任免**；宰相只有提议权。九级宰相本身也由老板任命。
- 公司只有一个宰相时，老板通过一个接口对接；公司变大后可以有多个宰相/方面负责人，老板与不同方面对接；但任何一个宰相都不能代替老板任命八级。
- 单层退化：宰相 → 一层 agent，结构上就是“主 agent + 子 agent”；但这里主 agent 有正式的权责记录、任命、审计、台账，不只是调用树。

**任免规则（制作人原话）**：

- **+1 有评价和提议权；+2 才有任免权。**
- 八级部门，部长八级：最多提议组员到七级，不能提议到八级；而且是提议，要走人事流程。
- 八级可以任命六级（走正规流程）；七级只能给六级评价。
- 七级可以压力六级；六级也可以对七级不合理的做拒绝。形成相互发现、讨论的循环。
- 八级全部由老板亲自任命；宰相只有提议。

**按 +1/+2 推导的任免表（待重写确认）**：

| 被任免者职级 | +1 评价/提议 | +2 任免 | 说明 |
|---|---|---|---|
| 9 宰相 | 老板（唯一） | 老板 | 老板亲自；无 agent +1 |
| 8 部门负责人 | 9 宰相 | 老板 | 宰相只能提议；老板亲自任免 |
| 7 | 8 部长 | 9 宰相 | 8 只能提议；9 任免 |
| 6 | 7 | 8 | 8 任免；7 只评价 |
| 5 | 6 | 7 | 逐级下推 |
| 4 | 5 | 6 | 逐级下推 |
| 3 | 4 | 5 | 逐级下推 |
| 2 | 3 | 4 | L2 最低公司；1 级按同规则延伸 |

> 注：7 级的 +2=9 是按“+1/+2”规则推导；若制作人希望 7 级以上都由老板保留，此表要改。当前先按推导值记录，重写时确认。

**必须补的规则（否则 +1/+2 是空的）**：

1. `+2` 是否必须拿到 `+1` 的提议才能任免？如果 `+2` 可以绕过 `+1` 直接任命，`+1` 的“评价权”就是装饰。
2. `+1` 的负面评价是“否决”还是“记录在案、+2 可覆盖”？两种后果完全不同。
3. 六级拒绝七级的“不合理”要有 grounds：违法、越权、利益冲突、不可能、不安全；并要有升级到八级的记录。
4. 跳级任命（8 任 6）必须留 `+1` 评价、`+2` 决定、候选人申诉三条记录；否则就是绕过中间层。

**后果**：

- 旧 76/77 的 `parent_grant` 可空、无 `grantor≠grantee`、无 `grantor_basis_ref` 必须重写。
- 需要“任职者身份记录”（holder 本身的存在证明），不能只靠“任命关系”指向一个不证明存在的引用。
- 冷启动要有“老板/设立行为 → 首任宰相 → 首任八级”的明确顺序；不能靠手写记录或跳过校验。

**未决**：`+2` 与 `+1` 的强制关系；六级拒绝权的边界；多宰相时谁有提议权。

### 抉择 4：审计——分层审计，未下发归老板（宰相承载）

**制作人选择**：审计权没有下发时，就在老板（宰相 agent 部分）；部门审计在部长上一层。

> 注：制作人末句“抉择 4……选择 C”按上下文归入抉择 5；抉择 4 按分层审计的描述执行，不另选字母。

**落地含义**：

- **公司级审计**：老板。审计权未下发时，由宰相作为老板在框架中的投影承载；最终责任仍在老板，不在宰相。对宰相、八级、公司整体负责。
- **部门级审计**：部长上一层。八级部门由九级宰相审计；七级部门由八级审计；六级组由七级审计；以此下推。
- 审计权可以随层级下发，但**不能下发给被审计者本人**；公司级审计不下发给部门。
- 审计不是“外部第三方”的同义词；在这个模型里，它是**层级独立**：上级审下级，老板审宰相。

**后果**：

- 部门自审问题解决了：部门不能自己审自己，必须由上一层审。
- 但**顶层自审问题没有解决**：老板审宰相，谁审老板？如果老板就是所有者/制作人，公司级审计对老板是自审；如果公司未来要脱离人运行，顶层审计没有主体。
- 需要区分“审计”和“评价”：部门审计在 +1，而 +1 往往也是评价/提议者；审计与任命分离，但与评价可能同体。是否足够，要看你是否接受“评价者=审计者”。

**未决（必须回答）**：

1. 老板/宰相自身的审计由谁做？外部锚（制作人本人、董事会、外部审计服务）还是宪法法院？
2. 部门审计者与 +1 评价者是同一人，是否要再上提一层做审计？
3. 审计发现后，谁有处置权？+2 任免者，还是审计者直接冻结？
4. 审计记录、申诉、救济的记录类型。

### 抉择 5：宪法——选 C（硬核 + 软外围，按层分）

**制作人选择**：C。宪法是硬核，但要区分：公司最硬核在老板；审计在老板；部门的在部长上一层；这样分层。

**落地含义**：

- **公司硬核（老板独有，不可下发）**：制宪/修宪、公司级审计、八级任免、最终责任（解散/清算是否纳入，另行确认）。
- **部门硬核（部长上一层）**：部门章程、部门预算/资源上限、部门验收口径、部门审计；部门负责人不能自己改。
- **软外围（可进化）**：部门 SOP、提示词、局部流程、工作方法；走提案/批准/留痕，不进入硬核。
- **两种下发**：
  1. **资源/访问权**：可逐级转授，但不能超过授予范围；每一层都要有转授边和衰减记录。
  2. **人事选拔/任免权**：不是自由转授，按 +1 评价/提议、+2 任免；八级只能老板任免，宰相只能提议。
- **宪法制品**：唯一 canonical 副本、内容哈希、启动校验、缺失/篡改拒启动；不能再是 10 份模板副本 + 一句 demo 常量。
- **修宪**：老板亲批；部门硬核由部长上一层批；软外围按公司规则进化。

**后果**：

- 旧 D8/D10 的“✅ 已拍定”必须重写：保留就建判据区+启动校验；废除就删承诺并改 20 的强制项。不能继续“文档说硬、机制没有”。
- “公司可以脱离人”与“老板独有硬核”存在张力：老板不在时，制宪/公司级审计/八级任免谁接？必须有继承/代行程序，且代行者不能是宰相自己。
- 部门硬核不能由部门自己定义；必须由公司硬核授权，否则每个部门都可以自立宪法。

**未决**：公司硬核的精确清单；部门硬核的边界；老板缺席时的继承/代行；多宰相时谁保管公司硬核。

### 抉择 6：完成/证据——选 B（分级）

**制作人选择**：分级，选 B。

**落地含义**：

- **E2+（共享写入、对外通信、秘密、资金、生产、权威变更）**：完成 = 四要件（终态事件 + 非空输出 + REPORT 落盘 + 闸门 exit=0）+ 独立收割/验收。
- **E0/E1（本地、可逆、无对外）**：允许“终态 + 自报 + 抽样复核”，但“不适用”的要素要有合法表示，不能空着。
- **完成 ≠ 验收 ≠ 结清**：三个状态分开记录；终态只表示执行结束，不自动推出验收/结清。
- 证据八要素逐项给来源锚：谁采集、能否独立复采、缺失时写什么；高风险必须独立采集。

**后果**：

- 旧 77 的“完成=执行面到达某终态”必须重写；82 的追溯行统一到新口径。
- 低风险不折腾，高风险有硬证据；但“分级”必须真的按效果级执行，不能都走低档。
- “不适用”必须有记录，否则八要素会退化成“填表”。

**未决**：E0–E6 的精确边界；抽样比例；独立收割的最小主体。

### 抉择 7：台账重建——选 C（混合）

**落地含义**：

## 三、权力模型（把制作人的话落成可施工规则）

### 3.1 角色

| 角色 | 是什么 | 不是什么 |
|---|---|---|
| 老板/所有者 | 根权力持有者；最终责任；公司级审计/制宪/八级任免 | 不是 agent 职级；不在 L1–L9 的 agent 树内 |
| 宰相 agent | 九级；老板在框架中的投影；默认单一接口；高层可多个 | 不是权力来源；不能自授；不能代替老板任免八级 |
| 部门负责人 | 八级；对部门业务/资源/人事提议负责 | 不能任免八级；不能自审 |
| 中间层 | 七级至三级；+1 评价/提议、+2 任免链的一环 | 不能越级自授；不能拒绝上级合法审计 |
| 执行 agent | 二级及以下/子 agent；干活 | 不能代表公司对外承诺，除非有明确授权 |

### 3.2 三种权力，三种下发规则

| 权力 | 例子 | 下发规则 | 记录 |
|---|---|---|---|
| 资源/访问权 | 研发部长拿到某目录访问权，可转授组员 | 可逐级转授，但不能超过授予范围；每层留转授边 | `Grant / Delegation Edge` + 范围 + 期限 |
| 人事选拔/任免权 | 八级提议七级；八级任免六级 | +1 评价/提议；+2 任免；八级由老板任免；宰相只能提议 | 任命记录 + 提议记录 + 评价记录 + 申诉 |
| 审计/制宪权 | 公司级审计、修宪 | 公司级不下发；部门级在部长上一层；不得下发给被审计者 | 审计记录 + 宪法版本 + 批准记录 |

### 3.3 任免矩阵（按制作人规则推导，待重写确认）

见 §二·抉择 3 表。重写时必须把它变成：

- `candidate_level`
- `evaluator_ref`（+1）
- `appointer_ref`（+2）
- `proposal_required`（+2 是否必须有 +1 提议）
- `negative_evaluation_effect`（否决/记录）
- `refusal_grounds`（六级拒绝七级）
- `appeal_ref`（申诉）
- `effective_at` / `revoked_at`
- `basis_ref`（追到老板/设立行为/上位授权）

### 3.4 审计矩阵

| 被审计对象 | 审计者 | 备注 |
|---|---|---|
| 公司/宰相/八级 | 老板（公司级）；未下发时宰相承载 | 最终责任在老板；老板自身由外部锚/董事会/宪法程序；否则顶层自审 |
| 八级部门 | 九级宰相 | 部门级最高审计 |
| 七级部门 | 八级 | 上一层 |
| 六级组 | 七级 | 上一层 |
| 五级及以下 | 六级及以下 | 逐级下推 |

### 3.5 宪法分层

| 层 | 硬核内容 | 批准/保管 | 可软变 |
|---|---|---|---|
| 公司 | 五条不变律、红线、判据类资产、公司级审计、八级任免、最终责任 | 老板 | 章程细则、部门规定、人事、报表口径 |
| 部门 | 部门章程、预算/资源上限、验收口径、部门审计 | 部长上一层 | 部门 SOP、提示词、局部流程 |
| 班组 | 作业规范、局部检查 | 上一层 | 工作方法、工具使用 |

> “硬核”不是“永远不改”，是“不能由被约束者单方改”；老板/上一层可以按修宪/审批程序改，但必须留版本、哈希、批准记录。

## 五、重写范围与“保留/替换/退役”

### 5.1 保留

- 公司=责任共同体；最终责任；证据优先；唯一写入者；状态外置；可重建（限域）；物理外置（硬核）。
- 三事实源的分域思想（不是三本账都自称权威）。
- DSH 作为默认/主绑定执行体，但不是公司本体；公司可换执行体，但按官方 84 D1，换用其他 CLI 会失去部分 DSH 专属能力（明示代价，不写成等价）。
- R1–R31 / I-1–I-16 中仍适用的反例与不变量；重写要逐条重新映射，不能默认继承。
- 81-files 的逐文件方法、V0–V6 的验证分层、GLM A 档 6 项的冻结前收口。

### 5.2 替换

- 旧“11 类治理位置 + 可选默认目录” → L2–L9 必设矩阵 + 保留权力表。
- 旧“老板/CEO/宰相”模糊关系 → 老板根权力 + 宰相投影 + 八级老板任免 + 多宰相协调。
- 旧“审计=独立第三方/目标” → 分层审计（老板/上一层）+ 顶层外部锚（待定）。
- 旧 D8/D10 的“✅ 已拍定” → 硬核/软外围分层 + 单一宪法制品 + 启动校验 + 修宪程序。
- 旧“完成=终态” → 四要件 + 分级 + 完成/验收/结清分离。
- 旧“全部可重建” → 事件可重建、钱账限域。
- 旧“一人公司=完整公司” → 单人退化为 agent 工具；低层不强行称完整公司。

### 5.3 退役

- 旧 63–82 的权责模型段落（与新模型冲突者）退役，不双基线。
- 旧 76 的“默认目录（可选资产）”、旧 70 的“可选项包裹核心位置”、旧 78a 的“外部闸门=默认”若与新模型冲突，按新模型重写；78a 只作输入。
- 旧 00–62 作为历史/素材；不再作为施工依据。
- 旧审计（DSF 60 份、GLM 26 份）作为证据，不作为规范；新卷必须引用其 P0 并说明处置。

### 5.4 编号

- 本文件：`84b`，DSF 侧决策记录（官方 84 是宪法裁决，本文是补充）。
- 重写：`63–82 v2`（建议）；`85+` 留给新的实现/验证/迁移卷。
- 旧卷头注加“历史，非现行”；新卷头注“v2，替代旧卷 X”。

| R10 | **公司脱离人 vs 老板根权力** | 长期目标与当前模型矛盾 | 制定“宪法化/继承”路线：老板权力逐步制度化为可继承的位置，而不是永远依赖人 |

**对“审计应该还好？”的直接回答**：

- 在**部门层**，你的模型是成立的：上一层审计下一层，解决了“自己审自己”。
- 在**公司层**，它没有解决“谁审老板/宰相”。如果老板是最终所有者，这叫“所有者自审”，可以接受但必须明说；如果公司要脱离人运行，顶层审计必须有一个非宰相的独立主体，否则“独立审计”在公司层是空的。
- 所以：**分层审计解决了 80% 的部门问题，剩下 20% 是顶层锚点问题；这不是否定，是必须补的一环。**
