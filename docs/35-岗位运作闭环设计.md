# 35 · 岗位运作闭环设计（真实公司岗位运作调研 → 我们的唤起/启动体系）

> 2026-10-18 ｜ 制作人定向：「一个岗位的定时唤醒、外部 hook 唤醒，以及 agent 完成各种任务时的各种启动方式，需要完全闭环；调研所有真实公司岗位如何运作，作为参考来设定我们的公司」。
> 本文=**设计拟稿**（待批示后拆实现单）。现状基线：docs/22 唤起源六源已注册表化、docs/04-§三 D9 定时岗、18-§三 croner 调度、25-§3.4 invoke 端口——已有「系统级」唤起面；本文补的是**岗位级运作规格**：每个岗位一份完整「运作说明书」，启动方式全闭环。

## 1. 真实公司的岗位是怎么运作的（调研提炼）

真实公司里，一个岗位从来不是「等人派活」，而是**五面体**在同时运转：

| 面 | 真实公司怎么做 | 代表来源 |
|---|---|---|
| **触发面** | 五类工作入口并存：①派单（工单进队列）②例行（日报/周结/月结/季度规划，时间驱动）③事件（客户来电/告警 webhook/@提及）④升级（SLA 将破/P1 事故→上级或二线接管）⑤值守（on-call 轮值：primary/secondary/incident commander/manager-on-duty 四角色） | [分诊与 SLA](https://blog.invgate.com/ticket-triage)、[on-call 轮值模型](https://incident.io/blog/on-call-scheduling-rotation-models)、[OneUptime 值守建设](https://oneuptime.com/blog/post/2026-02-02-on-call-rotations/view) |
| **分诊面** | 工单先过**影响×紧急度矩阵**定级 → SLA 起表（30 分钟首响是常见 on-call 线）→ 路由到岗；Tier1 即时处理或升级 | [优先级矩阵](https://mizo.tech/blog/ticket-triage-best-practices-practice-matrix)、[服务台分诊](https://www.bolddesk.com/blogs/ticket-triage) |
| **升级面** | 升级触发器=SLA 风险/VIP/P1-P2；**页呼无人应答→自动升级到 secondary→manager**（轮值定「谁来应」，升级策略定「不应怎么办」——RACI 的 R 与 A 分离） | [升级最佳实践](https://www.fabiantechtips.com/post/best-practices-for-running-a-service-desk-triage-prioritisation-and-ticket-merging) |
| **节奏面** | 四级经营节奏：**日**站会（战术对齐）→**周**经营会 WBR（指标对表，Amazon 全年每周）→**月**结+经营回顾（趋势）→**季**规划 OKR+年度计划 | [Amazon 运营节奏](https://workingbackwards.com/concepts/amazon-operating-cadence)、[四级节奏建议](https://www.pedowitzgroup.com/best-cadence-for-business-reviews-weekly-monthly-quarterly) |
| **汇报面** | 每条节奏产固定产出物：日战报/周指标表/月结报表/季 OKR 对表——指标挂预算与 SLA 达成率 | [WBR 实操](https://www.basedash.com/blog/how-to-run-a-weekly-business-review-a-practical-operating-guide) |

**生产级 agent 框架的印证**（2025-2026 共识）：混合调度=cron（时间）+webhook（外部事件）+消息总线（可靠性），带持久状态与重试语义；纯「cron 打 REST」被认为是脆弱反模式（[为何 cron+REST 会失败](https://tianpan.co/blog/2026/04/17/event-driven-agent-scheduling-cron-failure-message-queue)、[Confluent 事件驱动多 agent 四模式](https://www.confluent.io/blog/event-driven-multi-agent-systems)、[Heres 自动化蓝图](https://hermes-agent.nousresearch.com/docs/guides/automation-blueprints)）——**我们 docs/22 的「源只产意图、意图进主循环」正是消息总线式，方向正确**。

## 2. 映射表：真实机制 → 我们的构件

| 真实公司机制 | 我们已有 | 缺口（本文提案） |
|---|---|---|
| 工单队列+分诊矩阵 | 定时查单源（状态白名单+泳道空闲） | **优先级=影响×紧急度**入字段；SLA 时钟（首响/办结双表） |
| 例行节奏（日/周/月/季） | D9 定时岗（cron 表达式） | **节奏档位枚举**（daily/weekly/monthly/quarterly→模板化 cron+产出物清单），不写死表达式 |
| on-call 轮值 | 无 | **值守岗**：轮值表（primary/backup）+ 在岗窗口（时区/时段）+ 页呼=mention 意图高优先级 |
| 升级链（无人应→自动升级） | 无系统化（靠人盯） | **升级策略段**：N 分钟未认领→副本给 backup→再 N→上级；SLA 将破→预防性升级 |
| @提及 | Matrix @唤醒源 ✓ | 认领语义（ack）落台账 |
| webhook 事件 | 事件源（只落单不派工）✓ | 事件→岗位订阅路由（哪个岗关心哪类事件） |
| 接力/重估 | 接力源 ✓ | — |
| 断点续跑 | 续命源（resume）✓ | — |
| **turn 中插话**（聊天式） | 无（docs/34 探针在飞） | 视探针结论定通道 |
| 产出物/汇报 | 台账+报表（docs/04-§三） | 节奏档位绑定产出物模板（周报=固定查询） |

## 3. 岗位运作规格（jobs 段扩展草案）

```yaml
jobs:
  - id: prime-patrol            # 宰相巡检（既有例）
    role: prime
    triggers:
      cadence: hourly           # 节奏档位：daily/weekly/monthly/quarterly/hourly/自定义 cron
    outputs: [态势表]            # 产出物模板 → 报表系统
  - id: qa-oncall               # 新例：值守岗
    role: qa
    triggers:
      oncall: { primary: QA-1, backup: QA-2, window: "09:00-21:00" }
      subscribe: [webhook:github-pr, mention, ticket:QA-*]   # 订阅面
    sla: { first-ack: 15m, resolve-hint: 4h }
    escalate:                   # 升级链
      - { after: 15m, unacked: notify-backup }
      - { after: 1h,  unacked: notify-prime }
    outputs: [值守日志]
  - id: fin-monthly-close       # 新例：月结例会
    role: finance
    triggers: { cadence: monthly, at: "d+1 09:00" }
    outputs: [月结报表, 预算对账]
```

要点：①`triggers` 五入口=派单隐式（在状态机里）+cadence+oncall+subscribe+escalate，**全部折算成 InvokeIntent 走既有主循环**（源注册表新增两类：cadence 档位展开器、oncall/SLA 计时器）；②SLA/升级计时器=新唤起源（tick 驱动），不直接派工；③产出物绑定报表模板（04-§三）。

## 4. 启动方式全集（闭环矩阵）

| 启动方式 | 入口 | 生命周期 | 幂等 | 现状 |
|---|---|---|---|---|
| 冷启动（派单） | ticket 意图→状态机→launch | 新 session | 单/泳道互斥 | ✓ 已有 |
| 例行启动 | cadence→schedule 意图 | 新 session（或固定例行 session） | 档位去重 | ✓ D9 |
| 事件启动 | webhook→落单→派单 | 同冷启动 | 事件去重键 | ✓（不直接派工） |
| 值守唤起 | oncall 窗口+订阅命中→高优 mention | 值守 session 长活 | 窗口互斥 | ☐ 本案 |
| 升级唤起 | SLA 计时器→escalate 意图 | 附原单上下文 | 升级去重 | ☐ 本案 |
| 断点续跑 | resume 意图 | 原 session | 续跑键 | ✓ F1-15 |
| 接力重估 | relay 意图 | 幂等提示 | 防抖 | ✓ |
| **turn 中插话** | 同单消息→运行中 session 注入 | 不新建 session | 消息序号 | ☐ docs/34 探针在飞 |

## 5. 与「9 级松绑」的关系（制作人 2026-10-18 洞察）

9 级体系本是 YouTrack 九账号时代的产物；Taiga 后账号与部门完全自由。提案：
- **等级保留为「成熟度锚」**（提示词分层/权限档/汇报深度的默认参数），**不再是账号或编制的硬约束**——任意人数、任意部门树、任意深度（建议仍守 docs/33 的浅层级与跨度参考）
- docs/04-§四的「推荐部门模板」降级为**参考模板库**（docs/33 已是第一版），公司目录 config 自由裁剪
- agent.yaml/目录 schema 校验中的等级相关硬编码改为「建议+警告」级

## 5.5 策划自循环铁则（2026-10-19 制作人令）

1. **前沿强制**：策划岗（PLN-1..6）与情报岗（INT-1）的例行产出**必须含前沿检索**——别人做过→怎么做的；没人做过→相近想法与失败教训；**闭门造车视为废件**。
2. **自循环派单**：策划每日审框架现状×前沿→自主立单（经提案流铁律 20-§十三），不等制作人指派；制作人只保留**关键审批**（动底层/违背高层抽象者必过制作人，对应呈批态）。
3. **全自动取向**：架构一切取舍偏向「单制作人+全自动运行」——审批面最小化、自愈优先、值守自动化。
4. **模型异构约束**：实现岗与 QA 岗**尽量不同模型**（同模型在相同内容上犯相同错误的相关性风险；DEV-10 跨档约束的具体化）。
