## 二、分级问题

### P0（卷间冲突 / 规范矛盾 / 违反决策 / 断链）

#### P0-1 77 卷内矛盾：payload 禁存 `until` vs REC-AUTH-07 `effective_window` 区间必填且与信封 `until` 同值

- 【定位】77-§1.8 第 1 条："`until` 只在信封出现，用于声明失效/复审终点，**不得放入 payload**"；77-§3.7 REC-AUTH-07 `effective_window`：区间必填，"声明终点时须与信封 `until` 同值，不得另存第二份可漂移时间"。
- 【问题】REC-AUTH-07 的 payload 字段是**区间**（含终点），并被要求与信封 `until` 保持同值——即强制把信封 `until` 复制进 payload，与 §1.8 的 categorical 禁止正面对撞。同型字段 REC-COR-01 `effective_window`（区间，"修正向前适用的起点"）也处于同一灰区。
- 【影响】实现者无法同时满足两条：要么 payload 带 `until` 违 §1.8，要么 `effective_window` 无法表达失效终点违 §3.7 的"必填区间"。冻结 schema 时两边必有一边非法。
- 【建议】二选一收口：修订 §1.8 为"原则上只在信封；经登记的专用类型可在 payload 存同值副本并强制一致性校验"，或将 REC-AUTH-07 的失效/复审终点改为独立语义字段（如 `reviewUntil`）并解除与信封 `until` 的同值约束；同步澄清 REC-COR-01。

#### P0-2 跨卷共用枚举两套可写入字面量，无主表裁决（STAT-E 族、义务五型）

- 【定位】76-§7.7 STAT-E："`completed`/`accepted`/`conditionally accepted`/`rejected`/`terminated`/`settled`｜仅运行记录"；77-§4.4.1："六值以本卷的中文语义名为**可写入值**（与 `verdict` 的中文即 payload 同一条纪律）"；77-§6.3："该族的登记与禁止混用见 76-STAT-E"。
- 【问题】判断结果族在 76 登记为六个英文字面量，77 的实际可写入 payload 取值却是中文（验收四取值"接受/附条件接受/拒绝/依授权终止"；结清 `settled_state` 四态"完全结清/…"——后四态甚至不在 STAT-E 六值之内），两卷均未声明映射与唯一主表。同一模式再现于义务形态：76-§3.13 `obligationType`（`action`/`maintain-state`/`avoid-outcome`/`report`/`stop`）vs 77-§7.1.1 `form`（`动作`/`维持状态`/`避免结果`/`报告`/`停止`，来源＝定义包）。77-§0.2 只裁决了 `appointment_kind` 与授权四态两个枚举。
- 【影响】按 77-§0.2 自设标准——"同一个枚举在两个卷里出现两套可写入值，等于 schema 与 payload 必有一边非法"——这是被明令禁止的状态；跨实现交换判断结果类记录时无法判定合法字面量；结清四态处于无族登记状态。
- 【建议】按 §0.2 模式为每个跨卷共用枚举补"唯一主表"裁决（一处定字面量、另一处声明同值引用）；为结清四态在 76-§7.7 补登记状态族或给出到 STAT-E 的显式映射表；义务五型同理。

#### P0-3 76 内部矛盾：`canonicalizationId` 声明为 `token`，规定值 `studio-next/jcs` 不合法态 token

- 【定位】76-§1.5.2："`canonicalizationId` + `canonicalizationVersion`｜**`token`** + 版本字面量"；76-§8.1："`canonicalizationId = studio-next/jcs`"；76-§1.2：`token`＝`[a-z][a-z0-9-]{0,63}`。
- 【问题】token 语法不含 `/`；规定值 `studio-next/jcs` 既非合法 token，也不是合法 qid（仅两段、`jcs` 不在 kind 封闭表），而多段命名空间只登记了 `.` 分隔（§1.3）。`@1` 简写（§1.5.1/§8.1）是第三种形态。
- 【影响】任何按 §1.2 校验该字段的实现都会拒收本规范自己规定的值——所有 `semanticDigest` 携带的规范化身份全部非法，`E-SYN-004` 的"未知 canonicalizationId"判定也无从谈起。
- 【建议】改值为 `.` 段形态（如 `studio-next.jcs`）等合法 token，或为该字段定义专门的标识形态并登记语法；§1.5.1、§1.5.2、§8.1 三处同步。

#### P0-4 76 验证门不可满足：强制通过 RFC 8785 数值样例/附录 B，与自身数值域规则矛盾

- 【定位】76-§1.5.1 验证要求 1："必须同时通过…§3.2.2.3 **数值样例**…以及**附录 B 的 IEEE-754 数值序列化样例**"；同节数值规则："超出安全范围的整数、任意精度 `decimal`、big integer **一律以字符串承载**"。
- 【问题】在本规范的类型化输入中，JSON 数值只可能是安全整数（小数/大整数一律字符串；§1.2 语法排除指数形式）。RFC 8785 §3.2.2.3 与附录 B 练的是 IEEE-754 双精度序列化（`1e+30`、`4.50` 一类），这些输入在域内要么被 I-JSON 前置拒收、要么必须以字符串承载而不走数值序列化——"必须通过附录 B"按文不可执行，规范未定义其适用口径。
- 【影响】`canonicalizationStatus` 的 `supported` 档（要求"实际运行并通过全部公布向量含 RFC 8785 样例"）按文不可达，D75-08 冻结—验证阶梯被卡死；各实现只能自行解释哪些向量适用，产生跨实现分歧。
- 【建议】明确数值验证的适用域，例如："附录 B 仅约束实现选择接受 JSON 小数/超界数的情形；本规范域内输入不含此类数值，附录 B 以'域外输入一律拒收'的**负向样例**形式纳入三态判定条件"，并写入 §1.5.1 的状态表。

### P1（越界 / 未定义 / 不完备）

#### P1-1 `DEF-SYN-08` 一号两义

- 【定位】76-§1.1："**文字与 schema 同源**（`DEF-SYN-08`，不是二选一）"；76-§1.2.1 标题："**精确十进制运算**（DEF-SYN-08）"。
- 【问题】同一编号挂在两条不同规范条目上；§12.3 以"同源规则（`DEF-SYN-08`）"引用时无法消歧。
- 【影响】违反 75-§2.1"编号不复用给另一语义"的纪律；追溯与 schema 冻结时的条目对照错位。
- 【建议】其一改名（如十进制运算改 `DEF-SYN-09`），并在 §0.5 段位说明。

#### P1-2 诊断码通配引用未定义：`E-SYN-*`/`E-PKG-*` 无已发布码覆盖对应拒绝情形

- 【定位】76-§8.1 限额表："解析/校验失败按 `E-SYN-*`""超限按 `E-PKG-*`"；§1.7："**未列出的码本卷不得使用**"。
- 【问题】已发布码表（§1.7）中 E-SYN-001..004、E-PKG-001 均不覆盖两类必须拒收的高频情形：标量值域越界（text 超长、integer/decimal 越界、timestamp 小数秒>9）与归档限额超限（条目数/深度/压缩比/嵌套层数等）。通配引用等于引用不存在的码。
- 【影响】这些拒绝无法产出合规诊断，§1.7"每个接受/拒绝都有可交换说明"落空；§8.1 的"诊断回报"要求不可执行。
- 【建议】在 §1.7 码表补发布对应码（如 E-SYN-005+、E-PKG-002+），或将 §8.1 改写为"按（待发布）码"并显式标注未发布状态与发布前处置。

#### P1-3 `SUBJECT-REF` 六值封闭过窄，正文所需主体不可表达

- 【定位】76-§4.4：`subjectKind` "只允许 `holder`、`appointment`、`position`、`governance-position`、`org-unit`、`joint-body` 六值"。
- 【问题】两卷正文实际需要的主体超出六值：SG-02 `assertedBy` 允许"设立主体或程序"（设立责任共同体＝kind `responsibility-community`，"程序"无 kind）；DEF-STAKE-01 `partyRef` / DEF-STAKE-02 `representativeRef` 可为外部主体；§1.5.2 `signerRef` 可为公司（`company` 不在六值）；77-§2.6 `actor_ref` 明确可为"出工段/外部主体"。
- 【影响】这些引用要么无法合法表达，要么被迫塞进 `holder` 造成"引用类型不符即拒收"；签名结构与来源结构的责任主体落不了字段。
- 【建议】扩充 `subjectKind`（补 `company`、`responsibility-community`、外部主体等并逐一登记 kind 与证明边界），或为"程序/外部主体"定义专门引用类别。

#### P1-4 76-§4.1 条 3/4 越界撰写 77 的 payload 判定规则（双源）

- 【定位】76-§4.1 条 3："专用类型优先，不造第二个身份…决定面只能作为该专用类型的一个 facet"；条 4 未知类型分场景处置——与 77-§1.7 条 2/5 几乎逐句重合。
- 【问题】payload 身份与 decision facet 规则按 76-§0.4 边界表归 77（"77 各 recordType 的 payload"），76 在信封章内整段写下 77 的判定规则，形成双源表述。
- 【影响】现值一致故暂非 P0，但任一卷单方修订（如 facet 槽位调整）即升级为 P0 漂移；违反 75-§一"必须引用而非重定义"。
- 【建议】76-§4.1 条 3/4 压缩为接口声明＋"见 77-§1.7"，删除规则正文。

#### P1-5 记录实例版本槽缺失，对象身份与 `recordId` 的多版本映射未定义

- 【定位】77-§1.2 条 2："修改产生新版本，旧版本保留"；§1.3："任何改变状态的写入必须带预期版本"；76-§4.2 信封字段表无实例版本字段。
- 【问题】信封 19 个字段中无"记录实例版本"；77 的预期版本并发、多版本对象（`contract_id`+修订号、grant"范围/期限变更出新版本"）依赖"同一对象多版本并存"，但对象身份如何从 `recordId`/`lineage.supersedes` 推出未定义——§1.2 条 6 的"投影"规则只适配单记录类型，对跨多记录的业务对象（合同、授予）无法套用。
- 【影响】并发控制与"按当时版本解释历史"（D75-14）落不到统一机制；77-§12.4.1 已将"信封必须能表达同一对象多版本并存"挂账为对 76 的前置要求，76 未应答。
- 【建议】76 信封补 `recordVersion` 槽，或显式声明"对象身份＝首版 `recordId`＋`lineage.supersedes` 版本链"；77 §1.2 条 6 补多版本对象的投影/映射规则。

#### P1-6 幂等键公式三处不一致，未声明特化豁免

- 【定位】77-§1.4："幂等键作用域＝（公司标识、对象类型、对象标识、操作类别、请求方序列）"；§3.7："幂等键＝（事实域、目标端点、新代次）"；§10.6.2："位置＋任职者＋任期起点＋拟任版本"。
- 【问题】后两个协议键与通用五元组组成不同（缺公司标识/请求方序列，混入请求内容项），且 §1.4 未授权协议自定义键式。
- 【影响】"同键/跨对象复用"的判定边界在各协议间不一致，实现者可各取所读，防重语义可能分裂。
- 【建议】在 §1.4 增补"协议可定义特化键，但必须含公司标识并可映射回五元组"的约束，或统一改写两处键式。

#### P1-7 可选边无迁移表条目，状态机封闭性被打开放又未补

- 【定位】77-§5.4 可选边："暂停 → 待验收…已拒绝 → 待验收（部分可返工）、转呈后的并行受理"；§5.3 迁移表 T01–T26 无对应行。
- 【问题】可选边没有 T 编号条目（无触发/权源/前置/证据定义）；启用它们的绑定写 REC-WORK-09 时无合法依据行，而 §5.5 的口径是表外即非法。另外"返工 → 待验收的直接重提"与 T20（返工完成并重新提交）边界未区分。
- 【影响】"迁移表＝完整合法边集合"的封闭性存疑，状态迁移判定两可。
- 【建议】为每条可选边补 T 行并标注"绑定可裁剪"；或声明"可选边启用时按最近似必选边的权源/证据要求执行"；澄清 T20 与"直接重提"的差别。

#### P1-8 GOV-POS 表误配诊断码 `E-RULE-006`

- 【定位】76-§7.2 表注："若出现此类推论，按 `E-RULE-006` 拒绝"（指"用位置审计档降低事项验收档"的推论）。
- 【问题】`E-RULE-006` 的定义（§6.12）是"可选字段未声明容忍却被当作未知使用"（typecheck），与该推论违规语义无关；违反"码只增不改义"。
- 【影响】审计违规与规则求值失败在日志上不可分辨，恰是 §1.7 要防的错配。
- 【建议】为"档位推论违规"新设 policy 相位码，或改引已定义的 policy 码（如 E-RULE-020 一类）并说明。

#### P1-9 manifest 等工件未落实 75-§4.2 的 `$schema`/`$id` 要求

- 【定位】75-§4.2："每份工件带 `$schema`、稳定 `$id`、规范版本和自身版本"；76-§2.3 manifest 字段清单无 `$schema`/`$id`。
- 【问题】manifest 只列 manifestVersion/specVersion/definitionRevisionRef/parts/aggregateDigest/signatures/extensions；§8.3/§8.4/§8.5/§9.2 各工件同样未声明稳定 `$id`。
- 【影响】跨实现引用工件缺少稳定交换身份，75-§4.2 的工件级引用纪律在 76 面上未闭合。
- 【建议】在各工件字段表补 `$schema` 与 `$id` 并规定取形（与七版本轴的挂接方式）。

#### P1-10 `REC-` AREA 的跨卷登记处未定义

- 【定位】76-§0.5："`REC-<AREA>-<NN>`｜AREA：`ENV`、`PROV`、`REF`、`CASE`、`MIG`、`LOSS`"＋"现有前缀下擅自使用未登记的 AREA，等同于伪造条目"；77-§0.2/§0.5 另用 13 个 AREA（CMD/DEC/RCP/COR/EVT/AUTH/WORK/EVD/EXC/OBL/MEM/OBS/LIFE）。
- 【问题】`REC-` 前缀跨两卷共用（75-§2.1"按对象唯一主表"），但 AREA 级登记只存在于各卷自己的表；76 的封闭列表未注明"仅本卷"，77 的 AREA 集未经 76 或 75 登记，"未登记即伪造"的裁决落点没有定义。
- 【影响】严格读 76-§0.5 可判 77 全部 13 个 AREA 为"伪造条目"；宽松读则 AREA 纪律失去约束力。
- 【建议】在 76-§0.5（或 75-§2.1）补"REC- AREA 分卷登记、各自封闭、汇总＝76-§0.5 ∪ 77-§0.5"的显式规则，或建跨卷登记表。

### P2（表述）

#### P2-1 75-§九分级口径与登记处未定义；字段"来源"列两卷不对称

- 【定位】75-§九："P0/P1 必须清零；P2 如实记录和处置"。
- 【问题】全组未定义 P0/P1/P2 判级标准、复查人与登记处；§九要求"每个字段有来源"，76 的对象/SG 字段表无"来源"列（77 有），该检查项对 76 部分不可答。
- 【影响】验收口径的可操作性与可复核性打折。
- 【建议】在 75 或 82 定义分级标准、登记位置与复核主体；统一两卷字段表列。

#### P2-2 77-§9.3 观察面 7"资源账"悬空指代

- 【定位】77-§9.3 第 7 行："资源账 + REC-EVD-05 代价账"。
- 【问题】"资源账"无 REC-/RUN- 标识；资源事实实际分散于 REC-WORK-05 / REC-EVD-01 / REC-EVD-05 / REC-EVD-06。
- 【影响】该观察面的"最小记录组"无法逐项核验。
- 【建议】改写为具体记录组合。

#### P2-3 STAT-H 与 77-§4.8 状态名措辞不一致

- 【定位】76-§7.7 STAT-H："已核验…撤回到期"；77-§4.8："来源与完整性已核验…授权撤回/到期"。
- 【问题】同一十三态两卷字面不同，未声明映射（语义相同）。
- 【影响】跨卷对照与 schema 命名时产生不必要分歧。
- 【建议】一处为字面主表、另一处标注同义映射。

#### P2-4 数据层 NFC 归一未钉 Unicode 版本

- 【定位】76-§1.1："仅当字段声明 `normalizedComparison=true` 时才按 NFC 归一后比较"。
- 【问题】§6.11 只对规则档要求声明 Unicode 版本；数据层归一的 Unicode 版本未钉。
- 【影响】跨实现对同一字段"归一相等"的判定理论上可随 Unicode 版本漂移。
- 【建议】在 §1.1 或 §8.1 为 `normalizedComparison` 钉 Unicode 版本并纳入版本轴。

#### P2-5 77-§6.4"四种取值的运行后果"表实为 5 行

- 【定位】77-§6.4.1 下方表：接受/附条件接受/拒绝（可返工）/拒绝（不可返工）/依授权终止。
- 【问题】标题与行数不一致（拒绝拆两行），易误读为验收五值。
- 【影响】低，表述层面。
- 【建议】表头注明"拒绝的两种处置形态"或拆子表。
