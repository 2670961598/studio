## 摘要

沿「身份→任职→能力→生涯」贯穿四问的结论：

1. **概念主归属（①）基本闭环**：65 的四型任职关系、任职期、接受/交接/生效条件、六面交集、职级只读接口在 69-§2.3 有唯一行、在 77-§10.6 `REC-LIFE-05` 与 76-§3.11 拟任（引用不复制）落地一致；能力面（资格/剖面/执行配置/出工段）在 71-§一/二与 77-§4.5–4.8、80-§6.5 六端口闭合良好。**但 64-§2.2 为 65 登记的 8 个新增子概念中，「任职生命周期状态」「员工绩效子类」「个人记忆子类」三个无技术承载**——其中生命周期六状态与绩效记录构成两条断链（P0）。
2. **能力声明/验证/吊销链（②）在抽象与端口层闭环、在记录层留有已登记缺口**：71-§1.2 十三态 ↔ 77-§4.8 逐态证据 ↔ 80 `TS-PORT-CAP-01..06` ↔ 07-adapters 六机制件对得上；资格认定/重认（`REC-WORK-08`+`RUN-WORK-05`）、授权撤回（`REC-AUTH-03`）齐备；但安装/挂载/探测/激活/退役**回执与 `ProbeReport` 无记录类型与字段集**（07-§七-1/2/10 已登记未关闭），十三态的「进入所需证据」在台账层悬空（P1）。
3. **身份语义在注入层（③）大幅收窄**：L0-L5 只承载「人（工号）+ 任务 + 工具自报能力」，**任职关系（任命引用/兼任归属/代理受限范围）、资格状态、禁配结论均不进入任何一层**；署名面设计已定（`actingCapacity` 区分服务/任职，G-9 关闭），但当前生产身份位是 `daemon` 占位，且落款四身份位不含任职者。
4. **E1–E12（④）每条有验证锚**（V 层级＋预期证据＋失败即禁止＋81 文件＋78-§13.5 唯一主绑定），锚的可追溯性成立；个别行的断言面窄于 65-§12.1 应然处置（E6 的「据此晋升」、E9 的「以合作方名义作最终承诺」），且 E2/E7/E8 的存储锚与 E1 不在同一条记录链上。

计数：**P0 = 2，P1 = 6，P2 = 5**。

## 分级问题

### P0-1　任职生命周期六状态机无技术承载——「暂停/离岗待结清/已退役」三态在任何技术卷中不存在

- 【定位】65-§0.5/§九：「任职生命周期状态：候选、在岗、暂停、交接中、离岗待结清、已退役」；77-§10.6.1 `effective_state`：「`pending`/`effective`」仅两值；80-§6.7 `TS-PORT-LIFE-04`：「`appoint`/`current`/`end`」仅三方法。
- 【问题】65 的六状态是 64-§2.2 登记的 65 新增子概念之一，但：69-§2.3 该行展开位置（70-§三、71-§二）未枚举六状态；77 `REC-LIFE-05` 只有 `pending/effective` 两态＋职位级 `vacancy_state`（76-§7.7 STAT-C 是治理位置四值，且明令状态与任职类型分离）；80 端口只有 appoint/end，无 suspend/resume/settle；员工离岗结清清单（在途/承诺/资源/账户/信息/记忆/授权/外部关系/救济）无记录类型——`REC-EVD-06` 结清记录是**工作**域（`work_ref` 必填）。全库 grep 证实「待结清/已退役/交接中」在 70/72/76/77/80/82 及 81-files 中零命中（77-§8.4.5 仅「任职结束」一行记忆处置散文）。
- 【影响】65-§九的核心制度——暂停期间义务继续（I-11 相关）、复职先重认、离岗两段式（待结清≠已退役）、离岗后「结清/复查有限权限按 66 保留」——全部不可表达、不可断言；E5/E7 只能从记忆与交接侧间接测试，「不得结清」「核验通过才退役」无状态可判；「暂停」在记录上只能走撤换（终止关系），与 65「暂停≠终止」直接冲突。
- 【建议】在 77-§10.6 为任职关系补一个显式生命周期状态族（可并入 `REC-LIFE-05` 的状态轴或新增迁移记录），至少覆盖 暂停（权源冻结、义务继续、复职条件）与 离岗待结清→已退役 两段式＋员工级结清清单记录；80 `TS-PORT-LIFE-04` 相应补 `suspend/resume/settle` 方法；76-§7.7 为其登记状态族；82 为 E5/E7 补对应断言。或走批示明示「v1 以 pending/effective＋撤换近似，六状态降级为制度约束」，并登记损失。

### P0-2　员工绩效（Performance Assessment）在记录层断链——77 五十类 REC 与 80 端口映射均无绩效记录

- 【定位】69-§2.3 绩效行：「技术对象在 72，评价程序在 65/66」；72-§4.4：「记录结构与归因分层（`Performance Assessment`）」；77-§7.5.2：「本卷只规定记录与归因分层，不另立绩效维度」；77-§0.5 五十类记录表中无绩效记录；80-§4.7「50 类无空档」映射与 §6 端口全集均无对应件。
- 【问题】抽象层（69/72）声明了技术对象，记录层（77）与运行时层（80）都没有落地：`REC-EVD-05` 是工作域价值评估（四本账），不是任职者绩效结论；65-§八「绩效记录随任职史保留，离岗不删除」「评价者独立、不得自评、须有校准与申诉」是记录义务，五维（结果/过程/代价/合规/价值）结论无处落盘；TR-E-06 预期证据「成本与绩效分账」中「绩效」半边没有可断言的记录目标（78-§13.5-E06 亦只给「宿主配置事实与分账证据」，把归因判定推回 65/77，而 77 无此记录）。
- 【影响】E6（配置红利误归员工）的验证锚只剩成本账一侧；65-§八的三层归因中「任职者绩效」层与「绩效用于资格维持/重认、任职变化建议」的输入接口（65-§八「绩效的使用」）无机器语义；80-§18 面板却在 API 展示「个人详情、绩效」（`80:3185`），展示面数据来源与目标记录链脱节。
- 【建议】77 增补绩效评定记录（含层别＝能力表现/任职者绩效/组织绩效、五维结论、不确定性、评价者独立性、申诉入口；复用 `decision_facet`），80 补端口映射；或在 77-§7.5.2 明示「绩效结论由 `REC-EVD-05`＋`REC-DEC-01` 组合承载」并写明组合规则，关闭断链。

### P1-1　65 的三个新增子概念未进入 69-§2.6 的映射清单——按其自订规则即「映射缺口」

- 【定位】64-§2.2（`64:52`）：65 新增子概念 8 项（含「个人记忆子类、员工绩效子类、任职生命周期状态」）；69-§2.6：「65 的任职关系类型、能力剖面、执行配置、出工段」仅列 4 项，且「新增但无法回到本节的子概念，视为映射缺口，不得进入实现」。
- 【问题】「任职生命周期状态」「员工绩效子类」两缺口已升 P0-1/P0-2；第三项「个人记忆子类」（事实/经验/技能/承诺与关系，65-§0.5/§七）同样无字段承载：77-§8.2 `REC-MEM-01` 只有 `layer`（四层）枚举，无个人层子类字段；72-§三与 77-§8.4.5 仅在处置表散文中残留「承诺与关系记忆」一词。员工记忆的取用范围规则（65-§七「按任务与角色取用，不全量倾倒」）也无注入/取用面的机器语义（与 P1-2 叠加）。
- 【影响】65-§七的四子类各自的风险控制（经验当因果、技能与资格脱节、承诺遗漏）与差异化处置（承诺与关系记忆随交接移交）只能靠散文；E12 只断言「记忆≠证据」整体面，子类行为不可分判。
- 【建议】或把三概念补进 69-§2.6 映射清单并给出承载（子类枚举字段或指回既有行的显式说明），或由 64/69 出修订说明「子类属制度描述、不进机器面」，消除自订规则下的「不得进入实现」判定风险。

### P1-2　L0-L5 注入层不承载任职关系语义——六面交集到注入层只剩「人＋任务＋工具」

- 【定位】81-files/05-§3.2 L3 行：「`L3PersonSource{person, sections[]}`……identity=工号」；同卷 grep：全篇无「任命/任职/资格/禁配」任何承载；77-§4.6.1 出工六面含「任职关系……`appointment_ref`」；65-§12.2 R5 第 4 步：「记录本次属于哪段关系、什么配置、什么授权」。
- 【问题】记录层的 `REC-WORK-06` 携带 `appointment_ref`（哪段任职关系履职），但注入层没有任何一层携带它：L3 是单人单 `position` 节，L2 是部门与署名说明，L4 是任务，L5 是 executor 自报五键能力。兼任/代理（65-§二：逐岗登记、代理不继承资格、受限范围须明示）场景下，worker 在上下文中无法看到「本次以哪段关系、什么受限范围履职」；L5 能力 JSON 是 adapter 自报（05 明言「L5 不证明能力声明为真」）。另 L3 六节解析器无归属、运行链仅 `position` 一节（05-§七 G4 已登记），「技能/画像从未进入提示词」。
- 【影响】R5（兼岗多次出工）与 E2 的执行期防线只剩记录侧事后追责，履职时点的身份边界（禁止越范围行动）在上下文面缺失；65-§四「以谁的身份做」在注入层退化为「工号＋部门」。
- 【建议】在 05/17 的层契约中给 L3 或 L4 增加「本次任职关系引用＋范围与不可为边界（只读注入，非授权）」的最小字段；同时把「注入层不产生授权」的既有纪律写成对应断言（越范围动作的拒绝锚在网关而非提示词，二者分工写明）。

### P1-3　任命幂等键两处口径不一致——80 少了「拟任版本」与位置版本

- 【定位】77-§10.6.2：「幂等键：由 位置（`position_ref` 的 ID + 版本）+ 任职者 + 任期起点 + 拟任版本 构成」；80-§6.7 `TS-PORT-LIFE-04`：「幂等/预期版本：按 `(position, holder, term)` 幂等」。
- 【问题】77 是四元组（含 `nomination_ref` 的 ID+版本与位置版本），80 是三元组。77 明言「任期起点**或拟任版本**不同即新键」；按 80 的键，同位置、同人、同任期起点的两次不同拟任（例如前一拟任被拒后重新提名）会被误判同键——要么错误去重吞掉第二次任命，要么与 77 的 `rejected_idempotency` 语义漂移。
- 【建议】80 的端口幂等键改为与 77-§10.6.2 逐字对齐（四元组），或在 80 明写「引用 77-§10.6.2 的键定义，此处为缩写」；两卷以一处为唯一主表。

### P1-4　能力回执与探测报告无记录类型/字段集——十三态「进入所需证据」在台账层悬空

- 【定位】77-§4.8 十三态表每态要求「进入所需证据」（落位记录/核验记录/探测记录/运行时暴露观测等）；07-adapters-§七-2：「安装/挂载/探测/激活/退役五类回执属于哪类记录未定义——80-§4.4 的 50 类 REC 里没有『能力回执』」；§七-1/10：CAP 六端口的类型「字段集未定义」、`ProbeReport` 无最小字段集。
- 【问题】声明→验证链在抽象（71-§1.2）与端口（80-§6.5）层闭合，但每态证据要求的载体缺席：07 自陈「按回执是端口返回值处理，不写台账、不冒充记录」。E3/E4 的锚（`TS-PORT-CAP-04` + `F-adapters-cap-probe`）因此只能断言端口行为，断言不了「探测记录可复核、历史可重建」（71-§2.2 历史配置保留当时版本的要求）。
- 【影响】H0a-H4 闭合判据中「落位记录可查、安装日志可读、探测记录含负向结果」无台账落点；跨实现交换时能力供给链证据不可随记录导出。
- 【建议】80/77 裁决回执的记录归属（新增轻量 REC 或明确挂在 `REC-EVT-01` 观测＋专用 payload），并给 `ProbeReport` 最小字段集（观测手段、证据引用、proved/notProved、时间与宿主版本）；该缺口 07 已登记，需在 80/77 侧关闭而非留在附录。

### P1-5　E2/E7/E8 的存储锚指向人事同步链（hr.ts），与 E1 的任命记录锚不在同一记录链

- 【定位】82-§五 TR-E-02/TR-E-07/TR-E-08 的「81 文件（主）」均为 `F-store-records-hr`；03-store-§F-store-records-hr：「职责：`PersonnelEventRecord` + `HrSyncPayload`……归属 52-§9.2/§11 人事同步」；TR-E-01 锚的是 `F-contract-rec-payload-lifecycle`（`REC-LIFE-05` 的 payload）。
- 【问题】`F-store-records-hr` 是 52（人事同步器：公司目录人事变动→台账）链上的件，其「非职责」明言不定义流转合法性；而 E2（拆身份避禁配）、E7（离场无交接）断言的对象是 `REC-LIFE-05`/`REC-LIFE-02`（任命与移交记录），其 payload 与写入口在 contract/lifecycle 与 `TS-PORT-LIFE-04/02`。同一组 E 反例中，E1 锚任命记录链、E2/E7/E8 锚人事同步链，两条链在目标架构里是不同事实源路径；hr.ts 不锁 type 值域（v0 明言），拿它当任命断言点会测错对象。
- 【建议】82-§五 把 E2/E7/E8 的存储锚统一到任命/移交记录链（`F-contract-rec-payload-lifecycle` 或 store 的通用 records 面），或由 80/81 明示「hr.ts 即 `REC-LIFE-05` 的存储件」并改写 03-store 该件的职责；否则按 82-§14.5 登记为跨卷冲突。

### P1-6　E 行断言面窄于 65-§12.1 应然处置——E6 缺「据此晋升」侧、E9 缺「以合作方名义作最终承诺」侧

- 【定位】65-§12.1 E6：「把配置红利记成员工能力**并据此晋升**」；82 TR-E-06 预期证据仅「成本与绩效分账；配置差异记录」。65 E9：「外部主体行使未经 66 授予的保留权，**或以合作方名义作最终承诺**」；82 TR-E-09 预期证据仅「无授权行使记录的动作被拒；拒绝审计」。
- 【问题】E6 的第二半（绩效结论→晋升决定）因晋升程序记录与绩效记录缺位（P0-1/P0-2 连带）完全无断言；E9 的承诺侧在 TR 行未出现（`REC-OBL-02` 未进该行对象列）。反例只测一半即可能「通过」，违背「覆盖表只证明章节有内容，不证明充分」的自我警告（65-§12.6 同理）。
- 【建议】TR-E-06 增补「绩效结论不经程序不得改变任命/职级」的断言（依赖 P0-1/P0-2 关闭）；TR-E-09 对象列补 `REC-OBL-02` 并断言「外部入口不产生具体承诺」。

### P2-1　`personId` 术语漂移——验证锚使用展示层 ID 名而非身份主链术语

- 【定位】82 TR-E-01／78-§13.5-E01：「工具名/CLI 账号充当 `personId`」；76-§1.3 kind 表身份词是 `holder`（「任职者/个人主体身份」）；80-§18：`personId` 是 API「稳定 `personId` + 展示名」的展示投影。
- 【问题】`personId` 在目标类型链中不存在（主链是 `holder`/`SubjectRef`/`PersonRef`）；把「工具不产生任职」的断言挂在展示层 ID 上，实现者可能把面板投影 ID 当身份判据。
- 【建议】78/82 的 E01 探针改用 `holder`/`SubjectRef` 术语，或加注「`personId` 即 `holder` 的展示别名」。

### P2-2　「外部任职」叠加形态无登记标记——`appointment_kind` 四值不含外部维度

- 【定位】65-§0.5/§二：「外部任职是有限叠加形态（第十章）」；77-§10.6.1 `appointment_kind`：「`任命`/`兼任`/`代理`/`替补`……唯一主表，不得另立英文别名」。
- 【问题】外部任职者（66 授予有限任职关系后由本册登记，范围/信息/授权/禁配受限）只能用「任命＋受限 scope」隐式表达，无「外部」维度的显式字段；65-§十对外的特殊限制（不得行使保留权、不产生最终责任）在记录面无标记可判，E9 只靠入口拒绝兜底。
