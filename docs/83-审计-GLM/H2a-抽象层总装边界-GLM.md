## 分级问题

### P1-1 责任分型的展开指针悬空：69 §2.3 指向 71-§2.1，该节无任何责任分型内容

- 【定位】69-§2.3：「`Responsibility Assignment` 分层：……| 70-§3.3、**71-§2.1**；分配程序引 66-§6.3」
- 【问题】71-§2.1 是"六面交集才能形成正常履职"（身份/任职关系/职级接口/能力资格/执行配置/本次授权），全节无 Responsibility Assignment 或任何责任类型语义；71 中实际承载共同责任表述的是 §4.5（"共同责任仍按约定和实际控制分配"）。按 69 §2.1 纪律"展开位置"应可核验，此指针落空。
- 【影响】按 69 §2.6"逐项对照"核验 58 概念覆盖时，该行的 71 侧展开无法证实；实现者循指针找不到对象定义，易自行发挥。
- 【建议】69 §2.3 该行改为「70-§3.3、71-§4.5」，或在 71 §2.1 补一句责任分型引用（指向 70-§3.3）。

### P1-2 「最终责任/对外最终责任」同时挂在两个对象族，责任类型枚举四处不一致

- 【定位】69-§2.2：「顶点/最终责任/对外最终责任 → `Responsibility Position / Control Relation / External Undertaking`」；69-§2.3：Responsibility Assignment 只列「一般/运营/管理/共同」；69-§2.5(4)：「运营、管理、共同、**最终/对外最终责任**各有……（§2.3）」；70-§3.3：「`Responsibility Assignment` 至少区分：运营/管理/**最终/对外最终**/共同」
- 【问题】同一上位概念（最终/对外最终责任）在 69 §2.2 被归给位置族对象，在 70 §3.3 又作为 `Responsibility Assignment` 的类型行出现；且 69 自身 §2.5(4) 称最终类"见 §2.3"，而 §2.3 该行并未列最终类——69 内部两处加 70 一处共四种枚举口径。
- 【影响】"一个技术对象不得兼任两种互相否定的语义"与"唯一技术主归属"在该概念上判定摇摆；两表各自修订后可能产生真冲突（位置族改了、分派表没改）。
- 【建议】显式声明互补关系：位置族对象承载"谁处在最终责任位置"，`Responsibility Assignment` 的最终/对外最终行只是对该位置的分派记录；并统一 69 §2.3 行与 §2.5(4) 的枚举（要么都含最终类并注"对象见 §2.2"，都不含）。

### P1-3 Rule Profile 求值语义双规范表并存且条目数不一致，互不引用、无主从声明

- 【定位】69-§3.5：五要求表（绑定版本化/确定且封闭/未知即拒绝/激活钉版本/共同用例）；70-§0.3：六要求表，多出「**定性不受迫**」；70 全卷仅引 `69-§3.2`/`69-§3.3`，未引 §3.5
- 【问题】69 卷首自称"本文是四者共享概念和端口的唯一总装位置"，§3.5 是共享求值语义；70 §0.3 另立一张同题材规范表，条目为 69 的超集（另"求值封闭"含"等外部 IO"，措辞亦异），两表均以"必须满足"呈现，未声明谁是主定义。
- 【影响】跨实现符合性核查只读其一即漏要求（只读 69 漏"定性不受迫"）；任一卷单方修订即产生口径分叉，距 P0 一步之遥。
- 【建议】指定 69 §3.5 为求值语义唯一主表，70 §0.3 改为引用 + 仅补公司包语境特有的"定性不受迫"（或将其上收 69 §3.5）。

### P1-4 信息域命名对象三重失锚：`Access Policy` 被 71 裸引而全体系无定义处

- 【定位】69-§2.2：「信息 | `Information Requirement / Artifact Reference / Access Policy`……| 70-§三、71-§六、72-§二」；71-§3.4：「部署责任者按 `Authority Requirement` 与 `Access Policy` 决定……（`70-§3.6/§5.2`）」
- 【问题】检索证实：三个命名对象仅在 69 出现；70 §3.6 只有信息配置的内容表述（需求/来源/时效/知悉范围/可用目的/保留规则）而无任何同名对象；71 §3.4 所引的 `70-§3.6/§5.2` 处并无 `Access Policy` 定义；72 亦无。信息域是 69 §8.3 强制核心对象面（"资源与信息"）。
- 【影响】强制核心对象无技术落点；71 的"部署供给确认"规则建立在一个未定义对象上，跨实现无法判定各自所指是否同一物。
- 【建议】在 70 §3.6 把三个对象显式命名落位（与内容对应），或 69 §2.2 行改用 70 已有表述并在 71 §3.4 处补定义引用。

### P1-5 最小交换词表对象无定义处：69 §8.1 自称是 §8.3 核心对象的下限，但双方都未在归属卷落位

- 【定位】69-§8.1：「最小共同交换词表至少包括……`Capability Profile`/`Evidence Item / Assessment Record`……这些名词是 §8.3 核心对象在交换面的**下限**」
- 【问题】检索证实：`Capability Profile` 仅存在于 69（2 处）；69 §2.3 声称其归属 71-§1.1–1.3，但 71 该范围只有一次近义表述「工作先提出**需求剖面**」（§1.3），无对象定义；`Evidence Item / Assessment Record` 在 72 只有"证据包/五类判断"的语义对应而无同名对象；且 69 §8.3 核心对象清单本身也未列这三个名词——§8.1"是 §8.3 的下限"这一自我声明不闭合。
- 【影响】跨框架交换词表是互操作的最小契约（V3 层），词表项无法落到任何卷的定义处，"能交换"不可判定；与 69 §8.1"完整清单以 §8.3 为准"的权威声明矛盾。
- 【建议】三选一收口：把三个名词加入 §8.3 核心对象清单并在 71/72 补同名定义；或从 §8.1 词表中移除/替换为各卷实际定义的对象名；或在 71 §1.3、72 §2.1/§2.2 显式标注"即 Capability Profile / Evidence Item / Assessment Record"。

### P1-6 导出/记录必带字段两处清单口径不一致；70/71 的记录对象未锚定 69 §3.1 共享语义

- 【定位】69-§8.1 记录交换行：「身份、版本、权源、来源、**双时间**、未决义务和修正链」；70-§5.3：「记录/导出格式须能表达身份状态、权威激活与代次、义务实例与未决项，否则'导出成功'不构成可交换」；72-§1.1：「记录的最小语义以 `69-§3.1` 为唯一共享源」
- 【问题】70 §5.3 的"须能表达"清单（4 项）明显窄于 69 §8.1 记录交换面（7 要素），且未引用 §8.1/§3.1 作为上源；70 的运行/迁移档案（§1.3）与 71 的出工段记录（§2.2）均未像 72 §1.1 那样显式锚定 69 §3.1 九问（双时间、扩展与未知面在两卷记录字段清单中缺席）。
- 【影响】"导出成功构成可交换"的判据在两卷各有一套下限，跨实现可各执一词；69 §3.1 作为共享记录语义的实际覆盖率被静默收窄。
- 【建议】70 §5.3 改为「在 69 §8.1 记录交换要素之上另须表达身份状态、激活与代次、义务实例」；70 §1.3 与 71 §2.2 各补一句"记录语义以 69-§3.1 为共享源"。

### P2-5 71 规范文本内嵌 Studio Next 私有实现细节（规范/实现分离的轻微渗漏）
