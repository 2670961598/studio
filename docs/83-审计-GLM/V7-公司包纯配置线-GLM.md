## 摘要

**总判：本纵向链条未发现 P0。**「公司=纯配置包」主线在规范层（69-§0.1 四否定式 → 70-§0/§1 → 75-§四 → 76-§2）贯穿一致、逐层细化无冲突；文档的自我登记纪律极好——几乎所有目标态与现状的重大差距（manifest 未实现、part 分离阻塞、秘密扫描未实现、jcs 未验证、跨框架 V3 未执行）都已被各卷自行登记为待决/迁移项并如实标注「不得声称」。剩余问题集中在**公共工件的可获取基础设施**（交换编码、namespace 登记、词表分发）与**几处归属判定的空洞**（template-asset 分界、.studio-next.yaml 包分型），以及「当前实际可传播物」（YAML 目录 + 内嵌 DSH 插件的行业模板）与 70 纯配置定义之间**已登记但无排期**的持续背离。

### P1-1 交换工件的物理编码未定；jcs@1 与现行 YAML 资产断裂，跨框架装载现行公司包的桥接缺位

- 【定位】76-§1.1「交换时使用一种声明式的、无执行的、无注释的结构化文本（本卷以 JSON 数据模型描述字段……〔选择〕）」；70-§7.1「org-config.yaml……不能独自承担完整公司语义」。
- 【问题】76 只规定了「以 JSON 数据模型描述字段」，从未规定定义包物化/发布时的物理编码；`studio-next/jcs@1` 仅覆盖 JSON 数据模型。而现行公司目录与模板的全部机读资产是 YAML（org-config/departments/.studio-next.yaml/dependencies.yaml），YAML 允许注释、锚点、多文档、1.1/1.2 语义差异——76-§1.1 编码层（「注释与尾随分隔符不允许」）按无注释文本设计，直接套用会拒收所有现行资产。YAML→JSON 数据模型的投影规则（键序、别名展开、标量类型判定）在 70/76/69-§八 均未定义，70-§4.1 只说「可沿用多文件目录，也可提供等价交换格式」。
- 【影响】按 69-§八+76 实现的框架 B 能装载**目标形态**的包（设计主张，V3 未执行），但**不能装载现行 YAML 公司包**——其「结构合法」判定实际取决于具体 YAML 解析器行为（zod strictObject + yaml 库 uniqueKeys 缺省），构成隐含的 StudioNext 实现私有耦合。该缺口未列入 76-§12.2 待决清单（第 7 条只登记「org-config 字段级映射完备性」，未覆盖语法层归属）。
- 【建议】在 76 明确定义包机读 part 的交换编码（或明示「物理编码归 78 绑定档案 + YAML 投影的规范化规则条目号」），并把「现行 YAML 公司目录的跨框架装载语义」补入 §12.2 待决清单，指明归属卷与决策主体。

### P1-2 `partType=template-asset` 与 DEF-PKG-01g「人读资产与惰性模板」的分界未定义，definition-only 子集范围不确定

- 【定位】70-§1.4 / 76-§2.3 part 类型「definition / capability / template-asset / evidence / license / unknown」；76-§2.4「只有这份子集可以被称为纯配置公司包」（只含 definition part）。
- 【问题】定义包九部件（76-§2.2）中 `DEF-PKG-01g` 为「人读资产与惰性模板」，属定义包自身部件；聚合体 part 类型又单设 `template-asset`。两卷均未给出判定标准：README/charter/prompts/org-config 是 definition part 还是 template-asset part？19-§5.5.5 只登记了 dependencies.yaml「留 definition part」与插件属 capability，未登记其余 219 件的 part 类型。
- 【影响】definition-only 子集「只含 definition 类 part」的组成随判定标准漂移：若模板资产归 template-asset，则「纯配置公司包」不含模板资产、以模板初始化的公司不完整；若归 definition，则 template-asset 类型无用途。「纯配置公司包」这一核心称谓的边界因此不可判定。
- 【建议】76-§2.2/§2.3 补一张「九逻辑部件 × partType」的映射表，并定义 template-asset 的判定标准（例如：被 `init` 消费但不是公司语义声明的骨架资产）。

### P1-3 qid 的 namespace 登记机制无数据形状、无运营位置，跨框架同一性对账悬空

- 【定位】76-§1.3「由公共命名空间登记者分配，分配后不回收、不复用」。
- 【问题】「公共命名空间登记者」是谁、登记表是什么工件、按什么流程分配、跨框架如何取得公共命名空间——76 全卷无定义；该事项也未出现在 75-§七（D4 只覆盖「公开规范维护者」）或 76-§12.2 待决清单。全卷甚至没有给出一个示例 qid 的 namespace 取值。
- 【影响】qid 是所有对象（含 Company Identity）的稳定标识；两个框架各自给同一公司分配不同 namespace，则 70-§1.5「身份主张与谱系核验……与可取得的记录对账」失去锚点，跨框架互操作的基础设施悬空。
- 【建议】在 76 增补 namespace 登记表的对象形状（可挂 REC- 或 DEF- 段），并把登记者的设立列为 75-§七 待决项（与规范公开维护者同批决策）。

### P1-4 公共词表（vocabulary）工件无数据形状与分发规则，enumRef 的可解析性悬空

- 【定位】76-§1.3 kind 表登记 `vocabulary`；§1.2「enumRef：{vocab, vocabVersion, code}，词表版本必须精确」。
- 【问题】词表对象被登记为一种 kind，但 76 没有任何小节定义词表的数据结构、发布、版本化与获取方式；无数个字段（roles、taskKindRefs、effectFace 等）依赖 `enumRef`，而「引用方必须写版本」要求词表本身可按版本取得。词表分发未定义，也未列入 §12.2。
- 【影响】跨框架交换中，框架 B 遇到 `enumRef` 引用的公共词表若无法按版本获取，只能按未知拒收——互操作在最常见的受控取值面上失效。附带：冻结 JSON Schema 工件（75-§4.1 第 2 条、76-§1.1 同源规则）在 kind 封闭表中也无条目，其作为可获取对象的身份不成体系。
- 【建议】76 补「词表工件」小节（形状 + 分发 + 与 §8.1 版本轴的关系），并登记 schema 工件的引用形态。

### P1-5 `.studio-next.yaml` 在 70 四类包分型中无归属；04-§1.4 与 D18 对其地位的表述有张力

- 【定位】70-§7.1「.studio-next.yaml｜本地挂载元信息的候选……挂载状态与公开定义/运行档案分离」；04-§1.4 表「DEF-PKG-01a 包描述（manifest 的逻辑面）｜.studio-next.yaml」。
- 【问题】该文件随模板复制、随公司目录传播，内容混合了定义描述（schema/template）与挂载状态（created_at/last_validated_at/last_validation/framework_version）。70-§1.3 四类包、76 partType 枚举均未给它位置；70-§4.1「物理布局不改变归属」只是兜底原则，未指认归属。04-§1.4 把它列为 DEF-PKG-01a 的落位（「部分实现」），D18 又声明它「不是 76 DEF-PKG-02 的 manifest」——同卷内先当落位、后称不是，未给出它的正面定义。
- 【影响】按 70「挂载状态不随公开定义传播」的口径，携带挂载戳记的该文件进入传播物是定义包边界的一处未闭合点；跨框架侧无法判定它是定义 part 还是应被排除的本地状态。
- 【建议】70-§1.3 或 76-§2 明确 `.studio-next.yaml` 的包分型归属（例如：拆为「定义描述段（进 definition part）+ 挂载戳记段（排除，类部署面）」），04-§1.4/D18 统一口径。

### P1-6 模板 schema 字面量 `studio-next/org@1` 为框架私有命名空间字面量，且未登记为公共词表或绑定档案标识

- 【定位】19-§5.5.1「目标字面量 studio-next/org@1」（模板 8 件迁移目标）；76 全卷无此字面量。
- 【问题】公司定义资产（org-config.yaml、.studio-next.yaml、README）内的 `schema:` 字面量锚定在 `studio-next/` 私有命名空间上并随包传播。它不是 76 的 specVersion 语义，也未作为公共词表登记；类似字面量还有 `studio-next/dependencies@1`、`studio-next/trust@1`、`studio-next/plugin-registry@1`（后三者属部署/能力面，前者直接写在定义资产里）。
- 【影响】跨框架框架 B 遇到 `schema: studio-next/org@1` 时应按未知必需扩展拒收（76-§8.2）还是按兼容绑定接受（§8.6）——无规则。定义资产的自我身份标识依赖框架私有命名空间，与 69-§八「同名字段、相同目录名、能读 YAML 不足以证明符合」的警告形成自我指涉的缺口。
- 【建议】在 76 或绑定档案层登记该字面量的地位（公共 schema 标识 / 或迁移期绑定标识），并给出非 StudioNext 实现的处置规则（拒收或按兼容绑定投影）。

### P1-7 行业模板 6 个 DSH 插件仍在「当前可传播物」内，分离阻塞链只登记、不排期

- 【定位】19-§2.4「这是已登记的语义冲突……本文不把『拆分』写成已定的物理动作」；§8.4「阻塞条件：76 的 part 索引文件名、78 的能力安装根路径、82 的波次三者未定」。
- 【问题】70-§0.1 已废除「包内代码例外」，但 company-game/internet 模板（现行唯一的行业分发样本，走 `company add` 通道）仍内嵌 6 个可执行插件文件（含 DSH 专属 cordis.patch.yml）。19 自己写明「不动的代价是『公司包含代码』这一事实继续存在」；W82-4 对分离波次只「占位，不排期」，阻塞上游（76 part 索引文件名、78 安装根）同样无排期。
- 【影响】「可传播公司包」的现实样本持续违反 70 的纯配置边界；若 70 获批，则在分离落地前所有经行业模板初始化/导入的公司目录都携带边界违规物，且 E-2 可执行位闸还必须为插件约定入口放行（04-§4.2）。属已登记（W76-2/W82-4/04-D18）但无 owner、无时限的开放冲突。
- 【建议】将「part 索引文件名 + 能力安装根」从「未定」升为 76/78 的显式交付物并挂决策主体与时限；在此之前在 19-§5.1 与行业包 README 中以更显著方式标注「该样本含 70 已废除的代码例外」。

## 已登记缺口的核实（不计新问题）

以下差距经核实确已被文档自身登记，登记内容与实际相符，体现链条的自我诚实纪律：

- manifest/part 索引未实现（04-D18「不得声称已支持按 part 引用/裁剪」）；
- definition-only 子集与损失报告未实现（04-D19）；
- 配置类别未声明、platform 混入公司配置（04-D20）；
- 秘密内容扫描未实现（04-D21「不得声称仓库无秘密」；19-§2.6 guard 只扫 import 不扫字符串）；
