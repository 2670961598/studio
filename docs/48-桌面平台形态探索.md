## 〇、问题陈述

Studio Next 的三个 HTTP 面（:8787 监控 / :8789 公司概览 / :8788 对外 API）与 daemon
（launchd 看护的 headless 常驻进程）已经构成完整的信息面，但**入口是浏览器 + 端口号**：
制作人要看公司，得记 URL；daemon 挂了，得开终端敲 launchctl；公司包漂移告警 ESCALATE
了，页面没开着就看不见；未来 onboard 向导（docs/36）、批准指纹 re-approve（docs/43-条款4）、
凭据授予（条款7）都是「高权限、低频、要仪式感」的动作，散落在网页 tab 里体验散。

问题因此收敛为：**要不要给这套系统一个桌面级操作台（app 图标、菜单栏常驻、系统通知、
本机进程管理），以及用什么形态做**。前置定位已由 docs/45-§三 定调且本文沿用：桌面平台
= **V 面（视图层）**——不新增事实源、不新增决策位、daemon 保持 headless，壳只是操作台。

**前沿结论**：管理本地后台进程的桌面应用，Electron（Docker Desktop）与原生（OrbStack）
都成立；AI agent 桌面操作台（Codex/Claude）清一色 Electron。Tauri 在该赛道**没有找到
同量级先例**（此为事实陈述，非优劣判断）。

### 1.4 macOS 集成机制（官方核实，2026-10-19）

- **launchd 管理的两条正规路**：① `SMAppService`（macOS 13+，Apple 官方 API）——GUI 应用
  注册 LoginItems/LaunchAgents/LaunchDaemons，plist 放 app bundle `Contents/Library/LaunchAgents/`，
  用户在「系统设置 > 登录项」批准；② 传统路——写 `~/Library/LaunchAgents/` plist +
  `launchctl` load/unload（SMAppService 之前的老机制，Apple 迁移指南确认为被替代的旧法）。
  壳（Tauri Rust 侧 / Electron Node 侧）两者都能走：SMAppService 是 Swift/ObjC API，
  非原生语言壳走绑定或直接走 launchctl CLI（Rust 绑定成熟度未核实，§七-1）。
- **分发与公证**：Developer ID 分发的 Mac 软件自 macOS 10.15 起**必须公证**（Apple 官方），
  否则 Gatekeeper 拦截；仅本机自用可绕（右键打开/ad-hoc），但 Electron 自动更新与
  safeStorage 都要求正规签名——**「只给自己用」与「对外分发」是两个工程量级**。
- **PWA on macOS**：Safari 自 macOS Sonoma/17 支持「添加到 Dock」，**任何网站无需 manifest
  亦可加**（MDN）；Chrome/Edge 要求 manifest+service worker。已安装 web app 可收 Web Push
  （Safari 16.1+，macOS Ventura 起，官方支持文档）。Safari **不支持** File System Access API
  （Chromium-only；有 OPFS 替代）——PWA 读本地文件树无门。

## 二、形态方案（四案）

> 四案共享同一个前提：daemon 永远 headless + launchd 看护（docs/45-§三「壳只是操作台」），
> 壳死了公司照跑。四案不是互斥终点：A 是 B/C/D 的公共底座，前端资产（Vue+Naive UI）四案
> 全复用——**先 A 不封锁任何后路**。

### 方案 A · 纯 Web 面板（浏览器直访，零壳）

- **技术栈**：现有 Hono panel + docs/37 已拍板的组合 A（Vue3+Naive UI+ECharts vendor 直引，
  零构建）。浏览器访问 `http://127.0.0.1:<port>`。
- **体积与内存**：零新增运行时；内存=浏览器一个 tab。
- **升级链**：**单一升级链**——面板与 daemon 同仓同部署（git pull + launchctl 重启），
  版本永不错配。这是四案中唯一没有「壳版本 × daemon 版本」协商问题的形态。
- **macOS 集成**：无——无托盘、无系统通知（页面没开就收不到告警）、无开机自启入口、
  不管理 launchd（装卸 daemon 靠 CLI/文档）。通知盲区只能靠「常开一个 tab」缓解。
- **开发工程量**：**零额外**（docs/37 路线的自然延伸；六能力全走 HTTP 面）。
- **panel 资产复用度**：100%。
- **风险**：① 端口/URL 记忆负担（且 :8787 现被旧面板占用，:8790 之类的漂移更添乱）；
  ② 多公司=多个书签，无统一入口；③ 写面 token 存浏览器（docs/28-EC-⑭ 的 X-SN-Token），
  钓鱼/exfil 面比本机壳大；④ 「app 感」弱——观感问题是制作人原始诉求的一部分；
  ⑤ 首次安装 bootstrap 缺位：daemon 没装好时没有任何引导界面（鸡生蛋）。

### 方案 B · PWA（manifest + service worker，Add to Dock）

- **技术栈**：A + web app manifest + service worker（localhost 属安全上下文，SW 可注册）；
  Safari「添加到 Dock」/ Chrome 安装。
- **体积与内存**：零壳体积；安装后独立窗口 + Dock 图标（Safari 走系统 WebKit）。
- **升级链**：面板本体仍随 daemon 升级；**SW 缓存是新增风险面**——需 network-first 策略
  防缓存陈旧挡住新面板；daemon 不在时要给明确的错误态（离线语义重新定义）。
- **macOS 集成**：Dock 图标/独立窗口 ✓；**Web Push 通知 ✓（安装后，Safari 16.1+）**——补上
  A 的告警盲区，但代价是 daemon 要实现 Web Push 协议（VAPID/推送服务，工程新增）；无托盘、
  无 launchd 管理、无本地文件访问（Safari 无 File System Access）。
- **开发工程量**：小（manifest+SW+图标+错误态，估 1-2 人日）+ 可选的 daemon 推送实现。
- **panel 资产复用度**：100%。
- **风险**：① Safari PWA 能力次生且 Apple 政策有摇摆史（iOS 17.4 EU 一度撤 Home Screen
  web app 后恢复——移动端事件，macOS 未受波及，但示风险）；② 仍是浏览器权限模型，
  六能力中进程管理/本地浏览两项实质无门；③ 「伪桌面」可能满足不了「Codex Desktop 类」
  的期望值——它长得像 app，能力不是 app。

### 方案 C · Tauri 壳（Rust 核心 + 系统 WKWebView）

- **技术栈**：Tauri 2.12.x；前端与 panel 同一套 Vue 资产。两种集成模式：
  **C1 定向壳**（webview 直接加载 daemon 的 :8787/:8789 URL——零后端改动，本质是「带托盘
  的定制浏览器」）；**C2 原生壳**（前端打进壳内、经本地 API 取数——需 daemon 开 CORS/
  token 面与版本协商）。dsh web :13800 可作第三视图嵌入（docs/36-§5）。
- **体积与内存**：安装包 ~3-10MB、idle ~40-80MB（社区基准；有反例场景）。不内嵌 daemon
  （daemon 保持独立 Node 24 + launchd），避免把 Node 运行时打进包（数十上百 MB 级，具体
  未核实 §七-6）。
- **升级链**：updater 插件（minisign 强制签名 + 静态 JSON，可挂 GitHub Releases）+ Apple
  签名公证；**双升级链**：壳一条、daemon 一条，需要兼容矩阵（壳要能管「上一版 daemon」）。
- **macOS 集成**：托盘/菜单栏（官方 System Tray）、开机自启（官方 autostart 插件）、
  launchd 管理走 Rust `std::process` 调 launchctl 或 SMAppService 绑定（后者成熟度未核实）、
  系统通知原生、漂移告警可做托盘 badge + Notification。
- **开发工程量**：**四案最大**——Rust 工具链与壳工程入仓（建议独立仓或隔离目录，不进
  daemon 零构建链）、签名公证 CI、多架构产物、WKWebView 回归测试。壳特有逻辑（进程管理/
  文件树/安装引导）用 Rust 重写，与仓内 TS 资产零复用。
- **panel 资产复用度**：前端高（同一套 Vue 页面）；后端逻辑零。
- **风险**：① 团队 Rust 经验门槛（本仓技术栈全 TS）；② WKWebView 与 Chromium 的渲染/
  行为差异需回归（Naive UI/ECharts 均支持 Safari，风险低但非零）；③ 同赛道无大先例可抄
  （§1.3）；④ webview 内存反例（tauri#5889）；⑤ Rust 生态的 macOS 深集成（SMAppService、
  Keychain）依赖第三方绑定，质量参差。

### 方案 D · Electron 壳（Chromium + Node 24）

- **技术栈**：Electron 44.9.0（Chromium 152 + Node 24——**与 daemon 同为 Node 24 LTS**）。
  同样两种集成模式（D1 定向壳 / D2 原生壳）；主进程可直接复用仓内 TS 代码（公司目录浏览
  可调 `packages/company` 校验器、进程管理用 `child_process`）。
- **体积与内存**：安装包 ~120-200MB、idle ~150-400MB（社区基准；Codex/ChatGPT 桌面被
  社区批 5GB+ 是安装后含缓存口径，未一手测量）。
- **升级链**：`autoUpdater`（Squirrel.Mac，**必须 Apple 签名**）或 electron-updater；
  同样双升级链问题。
- **macOS 集成**：Tray 官方 API、`app.setLoginItemSettings` 官方（签名公证后可靠）、
  launchctl/child_process 全量、系统通知原生、`safeStorage` 存凭据进 Keychain（官方）——
  **六项能力所需的本机集成件全部是官方一等 API**。
- **开发工程量**：中——生态最成熟（electron-builder/forge）、TS 同构、先例最多
  （Codex/Claude/Docker Desktop 同路）；需引入构建链与产物 CI（壳工程独立于 daemon
  零构建链，同 C 的隔离原则）。
- **panel 资产复用度**：前端高 + 后端 TS 部分可复用（四案最高）。
- **风险**：① 体积/内存观感（HN 社区对 Electron 的主流批评）；② 「Mac 味」要额外打磨
  （Gruber 对 Claude Desktop 的批评示警）；③ 版本 churn 快（8 周一大版、支持窗口 3 版，
  需持续跟进安全补丁）；④ Chromium 全家桶与我们「轻」的审美相悖。

## 三、六项桌面能力 × 形态支持度

> 判定口径：●=该形态下原生做好；◐=可做但需新增 HTTP 面/能力或体验打折；○=该形态做不了。
> 共同前提：六项能力的**执行点都在 daemon**（§1.1），任何形态都不改核心——差异全在
> 「UI 承载层的本机能力」。

| 能力（出处） | A Web | B PWA | C Tauri | D Electron | 说明 |
|---|---|---|---|---|---|
| 1. daemon 生命周期管理（起停/日志/升级） | ◐ | ◐ | ● | ● | Web/PWA 只能经 daemon 自身新增的受控 HTTP 端点（stop/restart+强鉴权=新增攻击面，需独立设计）；日志只能看面板已暴露的。壳可直接 launchctl/SMAppService + tail 日志文件 + 触发升级——Docker Desktop 式体验 |
| 2. 公司目录浏览与配置编辑 | ◐→● | ◐→● | ● | ● | 读面 :8789 已有；编辑=docs/28 编辑中心（草稿→批示→daemon 写回），**本来就是 HTTP 面，Web 天然支持**；schema 校验=dry-run 端点回显 issues（已设计）。壳加分：daemon 挂掉时仍可只读浏览目录源文件（charter/档案/prompts） |
| 3. 公司包 onboard 向导宿主（docs/36 M-C） | ● | ● | ● | ● | 向导设计就是 panel 路由 `/create`，四案同资产。壳的真正差异在 **bootstrap**：壳可在「daemon 都没装」时双击出现并引导安装+launchd 装卸（安装器形态）；Web 的向导入口在 daemon 起来之后才存在 |
| 4. 批准指纹 re-approve 面与漂移告警（docs/43-条款4） | ◐ | ◐+ | ● | ● | 漂移事件已走 ESCALATE+SSE；re-approve=高权限写动作（信任锚落 `.studio-next.yaml` 批准位，执行点在 daemon hot-reload）。Web 版痛点：页面没开=告警盲区。B 用 Web Push 补盲区（daemon 要实现推送协议）；C/D 托盘 badge+系统通知原生达成。所有形态都需为 re-approve 设计强确认 UX（这是安全面不是壳问题） |
| 5. MCP token/scope/审计控制台（docs/45-§二/47） | ◐ | ◐ | ◐ | ◐ | 纯 HTTP 管理面，四案功能等价（皆依赖 docs/47 立项后 daemon 侧先建 token 管理 API）。差异只在凭据展示/吊销动作的本地安全：浏览器存 token vs 壳内 Keychain（D 有官方 safeStorage；C 待核实） |
| 6. 凭据类别授予面（docs/43-条款7） | ◐ | ◐ | ● | ● | onboard 期「按类别授予+偏离最小权限画像红字警告」。交互本身 Web 可做（向导的一步）；壳加分=授予动作的仪式感（本机确认框+Keychain）与授予记录的本地锚定 |

**读表结论**：六能力中 2/3/5 本质是 HTTP 面（Web 就能做好，这正是 docs/28/36 把它们设计成
网页面的原因）；**真正只有壳能做好的是 1（进程管理）与 4 的告警触达（通知）**，加上
bootstrap 与凭据本地锚定。换言之：**桌面壳的价值集中在「管家」职能，不在「视图」职能**。

## 五、排序参考（非结论，选择权归制作人）

按不同优先目标，排序不同，不构成单选建议：

1. **以「最短可用 + 零后悔」为先**：A →（告警盲区痛了）B →（管家职能痛了）C 或 D。
   与 docs/45-§三 宰相参考稿的「Web 先行 → Tauri 壳后置（Electron 备选）」一致；
   A/B 阶段的投入在 C/D 全额继承。
2. **以「操作台完整度 + 资源占用」为先，且接受 Rust 门槛**：C（Tauri）。体积/内存/安全
   模型（能力面按 capabilities 显式授权）最契合「本机管家」定位；代价是工程量最大、
   先例最少。
3. **以「最快出壳 + 生态先例 + TS 同构」为先，且接受体积**：D（Electron）。与
   Codex Desktop/Claude Desktop/Docker Desktop 同路（制作人点名「Codex Desktop 类」，
   正主即此形态）；主进程可直接复用仓内 TS，六项本机集成件全是官方一等 API。

三条路线互斥的只有 C/D 的壳工程部分；A→B 对 C/D 永远是前置而非竞争。

## 六、决策点清单（制作人圈定）

1. **形态路线**：☐ A 纯 Web（暂不立壳）　☐ A→B（PWA 补通知）　☐ A→C（Tauri 壳）
   ☐ A→D（Electron 壳）　☐ A 先行、壳形态另议（推荐起点，四案共识）
2. **若壳：Tauri vs Electron**（§二 C/D 详比：Rust 门槛+轻量 vs TS 同构+官方集成件全+先例多）
3. **壳的权限边界**：壳对文件系统**只读、写必走 drafts/API**（守「daemon 唯一写入者」，
   建议写死进壳的设计宪法）——是否照此冻结
4. **bootstrap 职能**：壳是否承担「检测/引导安装 daemon + launchd 装卸」的安装器角色
   （能力1+3 的交点，决定壳的 MVP 范围）
5. **分发目标**：☐ 仅制作人本机（免 Apple 开发者账号，ad-hoc 签名，无自动更新链）
   ☐ 对外分发（Developer ID $99/年 + 公证 CI + 完整更新链）——**直接决定工程量级**
6. **双升级链策略**：壳版本 × daemon 版本兼容矩阵与降级行为（壳要能管上一版 daemon）
7. **告警通知通道**：☐ Web Push（daemon 实现推送协议，A/B 形态可用）☐ 壳原生通知（C/D）
   ☐ 暂不做（告警只在面板/IM 面）
8. **壳工程位置**：独立仓 vs monorepo 隔离目录（构建链纪律：daemon 侧零构建不动摇）
9. **dsh web :13800 嵌入与 attach CLI agent** 是否进 MVP（docs/36-§5 预感件）
10. **端口遗留**（前置依赖）：:8787 旧面板退役 or 新面板改固定端口（docs/36-§6 待批示，
    壳的默认 URL 也挂在此决定上）

## 七、未核实清单（宁缺毋假）

1. **Tauri 侧 SMAppService 的 Rust 绑定成熟度**——官方文档确认 API 存在（macOS 13+），
   但 Tauri/Rust 生态的绑定库质量未查证；退路是 launchctl CLI（可行，未实测）。
2. **Tauri 凭据存储现状**（stronghold / keyring 类插件的维护状态与官方推荐）——未查到
   官方一等方案；D 的 safeStorage 为官方 API 已核实。
3. **Electron 44 的确切最低 macOS 版本**——依据 Electron 38 官方博客推断 ≥macOS 12，
   38→44 之间是否再抬未逐版核实（对我们的决策影响可忽略：目标机器为新 macOS）。
4. **Codex app / 新 ChatGPT 桌面应用的实测体积与内部架构**（5GB+ 为 HN 评论口径；
   其本地 agent 进程管理细节官方未公布）——只采信到「Electron 确认」这一层。
5. **Claude Desktop 的更新机制细节**——官方未文档化，未核实。
6. **Node 24 单二进制体积**（若未来考虑壳内嵌 daemon）——未核实。
7. **WKWebView 下 Naive UI + ECharts 的渲染回归**——需 spike 实测（主流库支持 Safari，
   预期低风险）。
8. **Safari PWA 对 localhost 面板的 Web Push 实际可用性**——文档口径支持（安装后），
   未真机实测。
9. **Apple Developer 账号持有情况**——决定 §六-5 的分发路线，需制作人侧确认。
10. **:8787 旧面板退役时间表**——docs/36-§6 遗留，待制作人批示（影响所有形态的默认入口）。
