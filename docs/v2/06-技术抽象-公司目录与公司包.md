## 一、公司同一性与包分型

### 1.1 什么随包旅行

公司同一性 = 稳定身份标识 + 定义修订谱系主张，由**记录谱系**（v2/11）与分域权威表（v2/05）承载真相。公司包只携带**声明与主张**：

- 显示名、slug、git 地址、平台项目号、本地路径均为**别名或绑定**，不承担同一性。
- **当前身份状态不进包**（身份四态值集唯一主表 v2/09 ENU-02，状态真相归记录谱系）。包内可有**非权威的谱系/状态主张**；主张与可取得的记录冲突时一律以记录为准，包内主张不得覆盖记录、不得作为激活依据（治 V7-P2-1 的措辞张力）。
- 复制一份公司包只证明「拿到了相同声明」，不证明同一公司已恢复、已激活或已取得信任；分叉、恢复、迁移、新设承继的判定引 v2/03 §七与 v2/11。

### 1.2 表 1 · 包分型（PKG- 族；ID 登记 v2/09）

| 分型 | ID | 内容与用途 | 不得宣称 |
|---|---|---|---|
| 公司包 | PKG-DEF | **定义部（纯配置）＋资产部（资产清单＋资产文件）**的不可变定义修订；供校验、分享、分叉、初始化 | 含全部历史；已取得信任；已激活权威；可直接履职 |
| 分发聚合体 | PKG-AGG | PKG-DEF ＋ 可选模板资产/证据引用/许可证明等 part 的**传输组合**，按 part 清单分型（§三.7） | 整体仍是纯配置；签名校验=安全或授权 |
| 运行/迁移档案 | PKG-ARCH | 定义修订引用、记录谱系导出、未决义务与承诺、结清与移交信息；记录语义统一以 v2/11 为准，本卷不另立交换下限（治 H2a-P1-6） | 可公开传播；可被当前配置覆盖；可无主认领 |
| 部署样例 | PKG-DEMO | 无秘密的宿主/平台示例、候选端点与能力替代说明 | 可直接复制本机路径、账号、信任、权威与授权到另一环境 |

「公司包」一词在 V2 全库**专指 PKG-DEF 双成分形态**；聚合体、档案、样例不得简称公司包。传播前按知悉范围拆分（读面规则归 v2/15）：公开定义不等于公开工作历史、个人记忆、秘密、客户资料或证据。

## 二、公司包内容物边界：双成分原则

### 2.1 表 2 · 进/不进清单（唯一主表）

**定义部（纯配置）可以含**：声明、受限规则表达式（求值语义唯一主表 v2/10，本卷不重述）、提示文本、验收口径、文档、模板、数据引用、依赖引用、资产清单（清单本身是声明，属定义部）。

**资产部可以含**：Skill、MCP、插件等**一等公司资产**（84 D1a）；资产可分**通用资产**（任意合规执行环境可用）与**执行器专属资产**（如 DSH 插件——只能被目标执行器使用，84 D1）。资产文件形态不受「纯配置」约束，但受 §三.5 授权纪律约束。

**任何成分不得含**：

| 禁入物 | 归属/理由 |
|---|---|
| 秘密值（句柄、令牌、密钥、账号、本机路径） | 部署面；定义内只有秘密的**逻辑类别**声明；处置归 v2/15 |
| 当前身份状态、运行记录、任职事实、绩效 | 记录谱系（v2/11）；包内只有拟任与主张 |
| 权威激活决定、部署绑定、能力安装状态 | v2/05 分域权威表＋部署面 |
| 信任态（「本目录即权威」「已信任」类自授声明） | 信任决定只能由有权部署者/合法设立程序作出（v2/15） |
| 挂载戳记（created_at/last_validated_at 等） | 部署面；随公开定义传播前必须剥离（§四.4） |
| 安装/激活脚本、宿主命令、自动执行钩子、隐藏下载 | 定义部字节惰性（§2.2）；资产部文件不经导入自动执行，安装/加载另行授权（§三.5） |

### 2.2 字节惰性

取得、解包、结构校验、差异比较、预览、物化到工作区，一律**不执行公司包内任何文件**——这是机制要求，不是纪律口号。具体偷渡通道清单（脚本/shebang、版本控制钩子、包管理生命周期、编辑器/CI 任务、引导文本、符号链接与嵌套归档）与拒绝/剥离语义唯一归 v2/10；安全面（路径逃逸、归档炸弹、秘密扫描）归 v2/15。本卷只立两条边界：

1. 惰性排除**宿主自动执行**，不排除文本影响判断：提示文本可影响模型行为，但不是授权、资格、验收通过或事实来源（引 v2/01）。
2. 把资产放入宿主**可执行位置**（PATH、钩子目录、插件加载目录等）是独立的部署动作，须另行授权并留痕（对象、位置、时间、授权依据、撤销方式）；「读一份定义」与「装一个资产」不是同一件事，导入器不得代办（§三.5）。

## 三、资产部（ASSET-；84 D1/D1a 主载）

### 3.1 一等资产与类型枚举

Skill、MCP、插件是公司**一等资产类型**；DSH 插件是**执行器专属资产类**的代表（84 D1a）。**资产类型封闭枚举的唯一主表在 v2/09**（本卷不重述值集；新增类型走 v2/09 登记流）。资产对象三要素：类型（引 v2/09）＋**专属标记**（通用/专属；专属必标目标执行器）＋**必备性**（是否声明为必备资产）。

### 3.2 表 3 · 资产清单条目（ASSET-01；语义本卷，字段 schema 归 v2/10）

| 要素 | 语义 | 缺失时 |
|---|---|---|
| 标识 | 稳定名称＋命名空间（§八.2） | 无法定位，拒收 |
| 类型 | 引 v2/09 资产类型枚举 | 未知类型拒收，不默认忽略 |
| 内容摘要 | 摘要值＋规范化规则（规范化规则归 v2/10） | 无摘要不得进入分发 |
| 来源与许可 | 发布者、上游引用、谱系、该资产的许可声明 | 未声明标「待有权者决定」，不默认继承仓库许可（MIT 只覆盖框架仓，84 裁决三） |
| 专属标记 | 通用｜专属（＋目标执行器，如 DSH） | 缺省按通用处理并警示 |
| 必备声明 | 是否必备资产（required）＋缺失影响说明 | 缺必备资产的装载结论见 §3.4 |
| 可选性 | 对运行是否必需、缺失影响 | 聚合体缺必需 part 不得宣称完整 |

资产清单（目标文件位 `assets.yaml`，§四.1）是资产部**唯一索引**：包内每个资产文件（含 `plugins/` 下的 DSH 插件）必须有清单条目指向；分区由清单表达，不由目录名猜测（沿用 v1·70 §1.4 原则）。无清单=零资产公司（51 现状：无 `dependencies.yaml` 即零插件公司，映射一致）。

### 3.3 必备资产声明（特化公司）

特化公司（围绕 DSH 搭建的公司，84 D1 原话「别人想用，也肯定是必须有我的插件的」）可声明**必备资产**：接收方须具备相应执行器方可完整装载该公司包。必备声明是**装载语义**，不是授权语义：具备执行器也只是取得「可安装」资格，安装与使用仍走 v2/07 能力授权链。

### 3.4 传播语义：接收方缺专属执行器时的降级行为（明示）

另一环境接收同一公司包时，按成分分别判定：

| 情形 | 强制行为 |
|---|---|
| 定义部 | **必须可装**（纯配置、无私有执行依赖）；装不动即拒收并指名，不得静默降级 |
| 通用资产 | 按资产类型判定可装性；不可用的列入装载报告 |
| 专属资产＋接收方具备目标执行器 | 可装；按 v2/07 授权链安装 |
| 专属资产＋接收方**不具备**目标执行器 | **不可用，必须明示**；装载报告列出「资产不可用＋原因（缺执行器）」 |
| 必备资产不可用 | 二选一由接收方部署者**具名选择并留痕**：拒绝装载（公司声明缺则不完整）｜降级装载（定义部照装、必备资产标不可用、公司按缺资产形态运行，明示代价）。**禁止**静默忽略、禁止冒充已装、禁止以缺失资产虚构能力（对应 v2/02 §五能力缺失纪律） |

**装载报告**（可用/不可用资产面＋原因）为**目标（未证）**；现状事实：51 §七 validate 摘要已含「能力面与缺失面」（现状），V2 沿此口径扩展为资产可用性面（装配归 v2/14/16）。「不用 DSH 则专属能力受损」由此成为**结构性明示代价**（84 D1），不是文档口号。

### 3.5 资产传播≠资产授权

1. 资产随包传播不获得执行资格：安装、加载、挂载、资格认定一律走 v2/07 能力面（HCL 级授权链），不因「与定义同包」获得信任、授权或执行便利。
2. `dependencies.yaml` 的属性绑定（51 D 组现状）只能视为**需求候选生成器**：属性命中不产生插件启用权，更不证明能力资格（v1·70 §4.3 口径保留）。51 §八「依赖清单自动安装」的现状表述在 V2 收窄为：**自动落位（文件到位＋清单登记），不自动授权**；安装授权语义引 v2/07（治 DSF V08-P0-01 的「能安装当可授权」半边；51 文本修订与迁移归 v2/16）。
3. 资产升级≠公司授权更新：供给升级与公司侧授权/资格分别版本化（§八.1）。

### 3.6 事实域归属（84b 抉择 1「DSH 插件/公司资产」行）

公司资产部是**独立事实域行**：资产清单与资产文件归公司目录（权威=公司 git 目录，写入者=daemon/网关，挂单 commit）；资产索引与绑定档案是投影/部署面；资产安装状态、能力锁归部署。一对象一权威，引用 v2/05 分域权威表，本卷不另立权威声明。

### 3.7 表 4 · 聚合体 part 类型语义（字面量唯一主表 v2/09；本卷只定义判定）

| part 类型 | 判定语义 |
|---|---|
| definition | 定义部 part（表 2 左列内容＋资产清单） |
| asset | **资产部 part（资产文件本体）**——v1 的 `capability` 类型由本类型取代（84 D1a 资产正式位） |
| template-asset | 模板骨架资产：被 init 消费但**不是公司语义声明**的生成物源（§六） |
| evidence / license | 证据引用、许可证明（各自独立 part，不并入总签名） |
| unknown | **一律拒收**，只能作待审查材料隔离；不得「忽略后继续」 |

`definition＋asset` 两类 part 合起来=PKG-DEF；「definition-only 子集」不再是 V2 的核心称谓（v1 纯配置公司包的边界判定），**V2 的边界判定改按表 2 双成分清单**（治 V7-P1-2 的子集漂移：判定标准=内容物语义，不是 part 类型组合的猜谜）。

### 4.2 表 6 · 定义部逻辑部件 × part 类型

逻辑部件可合并进物理文件，不要求作者重复维护同一对象；但须有**唯一索引**与引用完整性，防「索引一套、部门一套、档案再一套」。部件×part 判定：

## 五、公司层级与组织面在包内的表达（引 v2/03）

### 5.1 拟任与事实的分界（v1·70 §3.2 口径保留重映射）

| 定义部可以声明 | 必须进运行记录的事实（v2/11） |
|---|---|
| 初始岗位、组织与**拟任**安排 | 任命是否被有权者决定、被任职者接受并实际生效（任命生效五条件引 v2/02 §二） |
| 权限/义务的规则与上限、义务定义 | 每次具体授权、转授权、行使、撤回与结清；义务实例触发与到期 |
| 资格要求与认定程序 | 某任职者在某范围/期限内是否实际被认定（v2/02 §五） |
| 能力需求与兼容约束 | 实际能力、安装/加载结果、资格与本次执行计划（v2/07） |
| 唤醒条件与期限语义（51 `jobs[]`：拟任） | 某次是否触发、是否收到、如何处理、是否逾期（记录） |

配置声明的是**拟任**，不是任命；直接改文件不产生任命、离职或结清。从新版配置读「某员工在岗」不能覆盖历史任职事实。

### 5.2 CL 级表达

`company.level`（CL2-CL9）只是**主张**：CL 判据是结构事实，以在编结构可满足的最高层判据为准（v2/03 §2.4）；「只改一个 level 字段」无效，记录与结构不符时以结构为准并纠偏留痕。包内组织面文件（org-config＋departments）必须能完整表达 v2/03 表 A 的在编结构（含空编登记、**一级单元数量 N（N≥1，默认 1；三省＝N=3 示例）与各单元域划分**），使 CL 判据可从包＋记录联合判定（**N 一级单元的字段级承载＝GAP-V2-17**：`SCH-ORG-01` 现无专字段，登记 v2/17 §4.5；MIG-05 前定形为 `unitCount`/`units[]`/`domain`/`headRef`/`vacancyState` 或记录面方案；**MIG-03 不冻结该字段**）；`level_distribution` 对账（51 C-8 现状规则沿用为投影规则）。**必设矩阵与保留权力表的唯一主表在 v2/03（表 A/表 A′）**，包内不复制矩阵本体。

### 5.3 空编与保留权力的配置形态

空编=记录事实（登记空编＋复审期限，v2/03 §2.2 注）；包内可声明空编岗为拟任形态。**一级单元缺位**同为记录事实（登记「单元缺位」组织事件；缺位期最高宰相直接管理该单元，且该单元不得新增 G8，紧急例外须最高宰相双角色记录＋外部审计抽样）。保留权力去向按表 A′ 逐行显式归属（**外部老板恒定／最高宰相承载**等），属规范恒定＋设立记录初表（v2/03 §3.1），包内章程可引用、**不得另立副本或改写归属**。禁止任何权力悬空或塞回「可选容器」（84b 抉择 2；DSF P0-3）。

### 5.4 CL2 单人退化在包面的表达（85c-Q8）

CL2 公司=「公司形状的 agent harness」：公司包仍是**完整形态的 PKG-DEF**（设立记录引用、最高宰相任职拟任、资产部俱全），价值在权责记录而非调用树；不宣称具备完整公司的独立审计与最终责任（v2/03 §一）。低 CL 公司默认 **N=1**（不单设一级单元首长，最高宰相直接管理）；产品面：**L2 卖点=DSH 插件资产＋公司包格式**（与 D1 资产护城河一致）；升级触发器=CL 结构判据达成（多角色协作/审计/权力下发需求），引 v2/03 §2.4——本卷不另立触发器表。

## 六、模板与公司包的关系（治 V7-P1-2）

**判定标准**：template-asset=**被 init 消费但不是公司语义声明的骨架资产**（脚手架、占位文件、示例结构）；凡进入公司运行语义的声明（表 6 部件）都是 definition。

- 模板是**生成物源**，不是公司包本体：init 消费模板（聚合体中的 template-asset part）产出公司目录；模板修订不自动作用于已生成的公司，已生成公司不反向定义模板（共享源—生成物单向关系）。
- 行业模板内嵌的 DSH 插件=模板携带的**资产样例**：init 时落位到 `plugins/` 资产位并登记清单（§4.5，合法）；模板缺其声明的必备资产→init 硬失败（现状登记 W04-1，迁移 v2/16）。
- 模板自身按聚合体（PKG-AGG）分发与审查；「以模板初始化」不等于「公司已设立」——设立=**外部老板**设立记录（v2/03 §3.1；最高宰相的权源由外部 `root_delegation` 授予），模板只产目录。

## 七、跨框架互操作

### 7.1 双成分可装性承诺

另一框架装载同一 PKG-DEF 时：**定义部必须可装**（纯配置、无私有执行依赖、无秘密）；**资产部分明示**——通用资产按类型可装，专属资产标执行器，缺对应执行器时按 §3.4 降级并明示。单事实域单写入者与并发互斥（互认围栏/独占交接）语义唯一归 v2/05，本卷不重述。

### 7.2 私有字面量治理（治 V7-P1-6）

`studio-next/org@1` 等定义资产内 `schema:` 字面量锚定框架私有命名空间（现状随包传播）。V2 处置：该族字面量登记为**迁移期绑定标识**——其公共 schema 标识地位、非 StudioNext 实现的处置规则（按未知必需扩展拒收，或按兼容绑定投影）唯一归 v2/10；本卷只登记问题与归属，不在正文使用该族字面量作规范值。

### 7.3 互操作前提

互操作声明以**规范、词表与共同用例的可获取性**为前提（v2/10 承载分发、v2/17 V3 层承载验证）；「能读 YAML/同名字段/相同目录名」不足以证明符合（v1·70 §5.5 口径保留）；跨框架一致以共同用例为准，不以「看起来一样」为准（求值用例规则引 v2/10）。
