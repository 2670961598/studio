## 一、问题陈述

StudioNext 最终发布形态中，协作平台（现 Taiga）与 IM（现 Matrix：Synapse + Element Web）
走什么技术路线？具体要回答四个子问题：

1. **怎么用**：API 消费 / 插件扩展 / fork 二开 / 自研替代，介入深度到哪一层？
2. **怎么改**：部署后改源码重启的合规与技术边界在哪里？
3. **怎么打包发布**：第三方组件随发行件走（再分发）还是安装器现场拉取（编排引用）？
   对外托管服务时义务如何变化？
4. **怎么演进**：每条路线三年后我们在维护什么？后悔了能不能退？

关键背景：AGPL 组件（Synapse / Element Web / taiga-front）的约束**当前并不真实存在**
（纯内部使用不触发分发义务，docs/45-§1.2），约束在未来——「是否对外托管」「框架仓是否
开源」两个未决问题直接决定它何时变真。因此本文所有许可证评估均按**修改 / 分发 / 网络
服务三形态分别陈述**，不混为一谈。

### 2.3 先例对 StudioNext 的三条可迁移结论

1. **GitLab 教训（N7）**：混合许可产品**停止再分发** AGPL 组件后，给出的出路正是「用户自行
   安装」= 我们的**形态 A（编排引用）**。即：一旦 StudioNext 出现任何闭源发行件，「随包
   分发 AGPL 组件」这条路在业界是被主动放弃的，且放弃成本（GitLab 花两个大版本迁移）很高
   ——说明**早期就按形态 A 组织发行件是低后悔选择**，与仓库是否最终闭源无关。
2. **Mattermost 教训（N8）**：发行形态（编译产物 vs 源码组合）决定许可义务的实际落点；
   且「发行件里混入非 FOSS 部分」会在开源社区侧产生真实声誉成本（目录收录争议）。
   对我们的含义：若未来开源框架仓，发行件的**纯净性**（是否只含自有+宽松许可代码）本身
   是社区信誉资产。
3. **Focalboard 参照（N9/F10）**：「只消费官方发行物、不碰源码」时，组件源码的 AGPL 与我
   们无关——该模式已被多个自托管产品验证。同理推论：**Element Web 源码 AGPL（N6 加证
   生态普遍如此）并不阻塞任何「原样使用」路线**；它只在未来「我们改它 + 对外提供网络
   服务」时才变成真约束。

## 三、候选路线（四条，每条六面）

> 通用前提（四条路线共享）：FlowPlatform 端口（docs/23）与 Matrix CS API 均为稳定契约，
> 框架核心零 `if platform`；任何路线下 daemon/适配器/公司包都是我们自己的代码。

### 路线 A · 零接触基准线：维持「编排引用 + API 消费」

**怎么用**：Taiga 全 REST API 消费（packages/taiga 适配器，已首刀 F6/F7）；Matrix 全 CS API
消费（packages/matrix 三端点 + shared-secret 开户）。前端 UI（taiga-front / Element Web）
原样使用：不修改源码、不分发，仅改运行时配置（config.json / 环境变量——配置不是衍生作品，
此为通说理解，法律层面见 §六-6）。
**怎么改**：不改第三方源码。所有定制需求走三层外环：平台自身配置项 → 官方插件挂载点
（N4）→ 我们的适配器/网关侧（署名注入、告警路由都在网关做，docs/21-§三）。
**怎么打包发布**：发行件只含我们自己的代码（daemon/适配器/公司包格式 + compose 编排与
onboard 向导），Taiga/Matrix 官方镜像由安装器**现场拉取**（docs/45 形态 A）。离线场景降级
为形态 B（原样再分发官方镜像+附许可证文本，MPL/AGPL/Apache 均允许原样分发）。
**怎么演进**：升级=换官方镜像 tag；未来任一时刻可切路线 B/C/D，不积累任何切换债务。

| 六面 | 评估 |
|---|---|
| **许可证义务** | 修改形态：无（不修改）。分发形态：形态 A 零义务（从未分发第三方代码）；形态 B 原样分发仅须附许可证与来源声明（MPL-2.0 §3.3 / AGPL §4 / Apache-2.0 §4 均允许）。网络服务形态：即使对外托管，未修改版本不触发 AGPL §13 源码公开义务（§13 义务对象是 Modified Version）——**唯一残留**：须保留许可与商标标识，不得暗示官方背书 |
| **技术可行性** | 已在运行（docs/32 真机试点、21A 部署手册全部落地）。风险点均已实测关闭：arm64 走 Rosetta（F6）、开户走邀请流（F6）、shared-secret 注册（F7）。无未决技术项 |
| **工程量** | ~0（现状即此路线）。若把「安装器现场拉取 + 离线包降级」做成产品级向导：约 **5-10 人日**（compose 模板 + 版本钉选 + 镜像清单校验 + 许可证文件随附，参照 docs/36 onboard 向导骨架） |
| **维护负担** | 最低：跟官方镜像 tag；AGPL 组件零补丁负担（不改就没有补丁）。Taiga 上游月级发版（F5）、Synapse 双周级（F2）均只影响升级节奏 |
| **风险与失败模式** | ①上游转向：Taiga 主力已移向 Tenzu（F5），若开源版停更，我们冻结在末版（可长期用，但安全修复停摆）；②Element/Synapse 许可证再变（Taiga 前端有过 MPL→AGPL 往返史，DEV-6 §1.1）——但原样使用形态下再变也不追加义务；③功能天花板：平台侧永远没有转换矩阵 guard（docs/30-§4 明示的取舍），第二道闸永远是「角色收窄+框架闸」 |
| **演进可逆性** | **满格**。零沉没成本、零锁定，可随时切 B/C/D。它也是其他三条路线的公共起点 |

### 路线 B · IM 换引擎：家服务器迁 Tuwunel（Apache-2.0），协作平台维持 A

**怎么用**：docker 里 Synapse 镜像换成 Tuwunel 镜像；Element Web 原样作客户端（CS API
标准兼容，N2 93% MSC 覆盖）；我们的 packages/matrix 客户端零改动或近零改动（login/send/sync
均为稳定 v3 端点）。开户路径不变（N1：shared-secret 注册端点官方支持）。
**怎么改**：Tuwunel 是 Apache-2.0——**任何深度修改都合法且零义务**（保留版权/许可声明即可）。
若需要它没有的 Admin 端点（22 个 not-implemented 域），可以自己补并回馈上游。
**怎么打包发布**：Tuwunel 可随发行件原样再分发甚至修改后分发（Apache-2.0 宽容）；Element
Web 仍按路线 A 方式原样引用。对外托管时：家服务器侧 AGPL 约束**整体消失**（引擎已是
Apache），只剩 Element Web 一个 AGPL 面且原样运行。
**怎么演进**：矩阵协议是开放标准，家服务器可再换（Tuwunel↔Continuwuity↔Synapse 均说标准
CS API）；主要单向点是**数据**（见风险）。

| 六面 | 评估 |
|---|---|
| **许可证义务** | 修改形态：Tuwunel 零义务（Apache-2.0）。分发形态：零义务（Apache-2.0 允许闭源组合，须附 NOTICE）。网络服务形态：家服务器侧零义务——**本路线的核心价值：提前拆掉对外托管时 IM 侧的 AGPL 雷**。Element Web 维持 A 式原样使用，义务同路线 A |
| **技术可行性** | 关键依赖已逐项核实：①CS API 三端点=稳定标准（spec 层面）；②shared-secret 开户端点 ✅（N1 官方清单）；③Admin API 兼容面 69/100 且 Users/Rooms 域覆盖我们的全部消费（N1）；④桥接/appservice 支持官宣（N3，为未来人机混聊/外桥留门）；⑤性能 9.3x（F4）。**未核实项**：Synapse 存量数据迁入 Tuwunel 的官方路径（§六-1，同谱系 Continuwuity 明言 Synapse 不可迁） |
| **工程量** | 试点（新实例、不迁数据）：换镜像+TOML 配置映射 ~2 人日；开户/三端点/频道创建回归 ~2 人日；面板告警链路回归 ~1 人日 → **约 5 人日**。带存量数据迁移（若必须）：联邦/导出导入方案设计+实施 10-20 人日且无官方背书（不建议，IM=走廊非档案，docs/21-§一 90 天保留口径下重开张更便宜） |
| **维护负担** | 低-中：上游活跃（v1.9.4，2026-10-10 发版，月 4 发）；Apache-2.0 允许我们持本地补丁不回馈。负担主要来自「非参考实现」：遇 bug 要自己在 Tuwunel 语境排查，不能照抄 Synapse 社区答案 |
| **风险与失败模式** | ①**bus factor**：文档站自述全职开发+瑞士政府赞助（DEV-6 §3），但项目 2025-02 才创建、单一核心团队——若停更，conduwuit 归档剧本可能重演（缓解：Apache 允许 fork，且 Continuwuity 同谱系备胎）；②MSC 覆盖 93%≠100%（N2），长尾功能（如媒体 quarantine，N1）缺失——我们消费面已核对无缺口，但未来需求扩张须对照官方清单；③E2EE 桥接已知问题（N3 issue #327）——我们 bot 不做 E2EE（packages/matrix 明确不做），无碍；④数据单向性：频道历史不可平移（未核实，按不可迁做预案） |
| **演进可逆性** | 代码面满格（协议标准、客户端零绑）；数据面单向（迁入后无迁回 Synapse 的官方路径——同未核实项）。综合：**可退但退时要弃数据**。按「走廊非档案」定位，此代价可控 |

### 路线 C · 协作平台深度二开：taiga-back 插件优先，fork 兜底（前端永不碰）

**怎么用**：在路线 A 基础上，向 taiga-back 注入自有 Django 插件补短板（如：平台侧转换
guard、全局活动游标——docs/30 列的两个 Taiga 原生缺口）。官方挂载机制已核实为镜像预装
contrib 插件+环境变量激活（N4）；自研插件按同构方式打包进自建镜像或 volume 挂载（细节
未实测，§六-5）。taiga-front 永不修改：补功能时优先把能力做进我们的适配器/面板
（:8789），而不是动前端。
**怎么改**：两级介入。插件级（推荐）：taiga-back 是 MPL-2.0，**自有插件是独立作品，许可
自定**（官方 contrib 插件本身即 MPL-2.0，N5）；Django app 机制下不动上游源码文件。fork 级
（兜底）：改上游源码文件，修改的文件保持 MPL-2.0 并公开该文件源码，其余部分可闭源组合。
**怎么打包发布**：插件随发行件分发无义务（自有作品）；自建 taiga-back 镜像=「修改后分发」，
MPL 文件级义务：公开被修改文件的源码即可，**不传染**未修改部分与我们的适配器。这是
MPL-2.0 与 AGPL 的本质区别（DEV-6 §1.1 纯 MPL 无 Exhibit B，可与专有组合）。
**怎么演进**：插件稳定后可回馈上游（无 CLA、走 DCO，DEV-6 §1.4），回馈后维护负担转移
回上游；fork 级则每上游发版 rebase 一次（月级节奏，F5）。

| 六面 | 评估 |
|---|---|
| **许可证义务** | 修改形态：插件级零义务（独立作品）；fork 级=修改文件以 MPL-2.0 公开。分发形态：同上，MPL 文件级，专有组合合法。网络服务形态：**MPL 无网络条款**——对外托管修改版 taiga-back 也只须公开被改文件，义务不因 SaaS 形态放大。**前端红线**：一旦改 taiga-front（AGPL）且对外提供网络服务，衍生整体须 AGPL 公开——本路线以「永不碰前端」为铁律规避 |
| **技术可行性** | 插件面存在且官方维护着 7 个 contrib 插件作参照（N4/N5）；REST API 完整（F6）意味着大部分「改」根本不需要改平台，走适配器即可。**未实测**：自研 Django 插件的挂载细节（§六-5）、taiga-back 插件 API 的正式契约程度。fork 级可行性无疑（Django 工程常规），但引入 Python/Django 运维栈到我们的发行面 |
| **工程量** | 首个自研插件（含挂载管道+自建镜像 CI）：**15-25 人日**（Django app+测试+镜像构建+上游版本钉选）；其后每个插件 3-8 人日。fork 级：起步 5-10 人日，但每次上游发版 rebase 0.5-2 人日永续支出。对比：把同样功能做进我们适配器/框架闸通常 2-5 人日且零上游负担——**二开仅在「功能必须住平台侧」时成立**（如平台原生 guard） |
| **维护负担** | 插件级：低（跟上游大版本 API 兼容性即可）；fork 级：中-高（月级 rebase + 安全修复同步，F5 上游含安全修复记录）。自建镜像引入 CI 面与供应链面（镜像扫描、依赖升级） |
| **风险与失败模式** | ①上游 API 漂移破坏插件（月级发版下真实存在，缓解：契约测试锁 API 面+版本钉选）；②Tenzu 转移致开源版投入衰减（F5），二开投资的水位线下沉——插件越重、沉没越大；③「二开冲动蔓延」：把本该做在适配器的事做进平台，违反 docs/23 平台差异收敛进适配器的哲学；④fork 级最大失败模式：rebase 积压数月后事实上变成私有分支，安全修复断供 |
| **演进可逆性** | 插件级：满格（卸载即回路线 A，数据无损——插件数据在平台库里，可留可清）。fork 级：可逆但代价随 fork 存续期增长（积压的 rebase 债）。**建议纪律：任何 fork 前先证明插件级走不通** |

### 路线 D · 内置最小平台优先：LocalFile 长成默认，外部平台降为可插拔

**怎么用**：docs/23 既定方向的加速版——LocalFile（packages/localplatform，七能力骨架已建，
F9）从「demo 模式/测试靶子」升格为**默认交付平台**：每家公司目录即协作平台（单据
=jsonl、状态=目录流转、评论=md 追加），零外部依赖、零许可证负担、随公司包整体流通
（「下载别人的公司来跑」天然成立，docs/40）。Taiga 降级为可选外部平台（org-config.yaml
改一行即可切换，docs/23-§二）。IM 侧：Matrix 协议保留（人机混聊刚需），家服务器按路线
A/B 待选。
**怎么改**：改的全是我们自己的代码——面板（:8789）补看板/单据 UI，FlowPlatform 语义按我
们需要长（**平台侧 guard 我们原生就有**：状态机本就在框架核心，docs/23-§三「状态权威
归平台侧」在 LocalFile 形态下=归框架自己，双真源问题消失）。
**怎么打包发布**：发行件只含自有代码，**协作平台零第三方组件**——最纯净的发布形态
（对照 N8 Mattermost 教训：开源社区侧零争议）。对外托管无任何许可障碍。
**怎么演进**：LocalFile 与外部平台永久并存（端口抽象保证），不排除未来某类客户需要重平台
时再挂 Taiga/Plane。

| 六面 | 评估 |
|---|---|
| **许可证义务** | 三形态全零（全是自有代码）。外部平台（若客户选装）按路线 A 口径引用。**这是唯一在「对外托管+闭源」双前提下仍全绿的协作平台路线** |
| **技术可行性** | 骨架已建（F9）；契约包平台无关测试集即验收标尺（docs/23-§三）。可行性核心不是「能不能」（文件驱动已证明），而是「够不够」：多用户并发写（文件锁/一致性）、UI 面完整度（看板/甘特/报表）、活动流性能（jsonl 全扫的扩展性）——当前设计单机单 daemon 场景成立，多人 Web 并发场景未验证 |
| **工程量** | 到「内部够用」（看板 UI+单据全生命周期+活动流，复用 :8789 面板骨架）：**25-40 人日**。到「可作对外发布默认」（并发安全+备份恢复+导入导出+面板打磨）：**60-100 人日**。依据：七能力逻辑层已有（F9），增量主要在 UI 面与运维面（对照 packages/panel 现有体量与 docs/37 技术栈） |
| **维护负担** | 全自持：无上游跟进、无第三方安全补丁——负担转化为**产品功能债**（我们自此对「看板像不像、报表全不全」负全责，这正是 Taiga 免费送我们的部分） |
| **风险与失败模式** | ①**范围蔓延=重造 PM 平台**，与 docs/06 职责边界「框架公司不做平台产品」直接冲突——本路线必须以「最小够用」为宪法，超出即触发返工；②功能天花板永久存在（甘特/燃尽/跨项目报表等用户期待面）；③竞品体验差距在对外销售场景被放大（客户拿它和 Jira/Taiga 比）；④文件形态的多人并发边界一旦突破（真人团队直接用），架构返工 |
| **演进可逆性** | 结构上满格（端口并存，随时切回外部平台），心理上单向（自有资产越多越难放弃）——但此处「难放弃」是资产锁定而非债务锁定，与其他路线的债务锁定性质相反。**退出代价主要在数据**：LocalFile→Taiga 的 export/import 工具（docs/23-§二列为独立工具，尚未建） |

## 四、对比矩阵

> ●=优 ◐=中 ○=弱/差；「许可证·外托」=对外托管+闭源双前提下的许可处境。

| 维度 | A 零接触 | B IM 换引擎 | C taiga 二开 | D LocalFile 优先 |
|---|---|---|---|---|
| 许可证·修改 | ●（无修改） | ●（Apache 零义务） | ◐（MPL 文件级） | ●（自有） |
| 许可证·分发 | ●（形态 A 零义务） | ●（Apache） | ◐（改文件公开） | ●（纯净发行件） |
| 许可证·外托 | ◐（原样用可，改则触发 AGPL） | ●（IM 侧拆雷） | ◐（back 可，front 死线） | ●（全绿） |
| 技术可行性 | ●（已运行） | ●（关键端点已核，数据迁移未核） | ◐（插件细节未实测） | ◐（并发/UI 面未验证） |
| 即期工程量 | ● ~0（向导 5-10 人日） | ◐ 试点 5 人日 | ◐ 15-25 人日/插件 | ○ 25-40 起步 / 对外 60-100 人日 |
| 长期维护负担 | ● 最低 | ◐ 上游活跃但非参考实现 | ◐ 插件低 / fork 高 | ◐ 无上游但有产品功能债 |

| 风险集中点 | 上游转向 | bus factor+数据单向 | rebase 债+前端红线 | 范围蔓延 |
| 演进可逆性 | ● | ◐（代码可退/数据不可） | ◐（插件可退/fork 难） | ●（结构可退/资产沉淀） |
| 与既定方向一致性 | ●（docs/45 形态 A 即此） | ●（docs/45-§1.3 层1） | ●（docs/45-§1.3 层2） | ●（docs/23/45-§1.3 层3） |

**排序参考（探索者视角，非结论）**：四条路线非互斥，docs/45-§1.3 分层表本就是把它们排成
介入深度阶梯：**A 是所有路线的公共底座（成本为零，无理由不保持）**；B 是时间盒最小的
确定性投资（5 人日试点拆掉 IM 侧最大不确定性，触发条件=对外托管意向明朗或 Synapse 运维
痛感出现）；C 应维持「仅当功能必须住平台侧」的触发门槛（当前两个缺口：平台侧 guard 与
全局活动游标，均有框架侧补偿方案在运行）；D 是唯一改变产品形态的路线，回报最大（发布
纯净性+协议层 guard 双真源消失）但工程量与范围风险也最大，适合在规范冲刺 v1 与面板收口
之后、以「最小够用」宪法启动。
