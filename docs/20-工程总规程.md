# 20 · 工程总规程（Studio Next 施工法）

> v1.0（呈批稿）｜ 2026-10-16 ｜ 主 PM：Kimi
> 定位：本规程是 Studio Next 施工的**最高工程规范**——怎么干、按什么顺序干、
> 每个环节过什么闸、谁过目、什么算完成。效力低于宪章与红线，高于一切临时安排。
> 制作人定调：这是一个超大、详细、高要求的工程，必须有明确的规章制度。

---

## 第一章 · 总则

1. 本工程为 AI 全自主施工、制作人终审的超大工程。一切工作以**单据**为最小工作单位，
   以**证据**为完成标准，以**文档**为开工前提。
2. 版本制度：**完成一个里程碑算一个版本**（不设周/月版本）；每个版本制作人过目才发布。
3. 顺序铁律：抽象 → 文档 → 制作人过审 → 代码 → 测试 → 合并 → 发布。倒序或跳级视为废件。
4. 适用对象：所有参与本工程的角色（制作人/主 PM/宰相/各岗 agent/worker/外部委托）。

## 第二章 · 施工依据链（按什么干）

每一行代码都必须能沿这条链回溯到依据，缺一环不开工：

```
总纲领（07）→ 需求条目（01/02/03/04/05/06）→ 技术设计（17/18）→ 里程碑（16）
→ YouTrack 单据（Epic→子单）→ 任务书（含文档章节号+冻结验收口径）→ 实现 → 证据
```

- **拆单规则**：每里程碑一张 Epic；Epic 拆到"一单一命可完成"粒度（建议单件 ≤4h 墙钟）；
  每单必填：概念归属（六名词三动词，D10）、设计文档章节号、冻结验收命令、预算帽
- **概念准入**：映射不进六名词三动词的需求退回（D10，防自洽性破碎）
- **文档修订**：实现与文档冲突 → 停手改文档（走批示），不默许代码漂移

## 第四章 · 分支与发布流程（三级晋升）

```
feature/* ──CI 全绿──▶ dev ──契约+崩溃注入全绿──▶ gray ──灰度零事故+制作人过目──▶ release（tag）
```

- 上线前的实现：bugfix-only 维护线，永不发新功能
- gray 灰度：对生产 YouTrack 只读或限定泳道跑，灰度期不设日历、只看零事故+证据
- 回退：release 出问题 gray 顶回修；上线前的维护线永远兜底
- 绝不 force push、不重写历史、不删分支（红线）

## 第五章 · 测试制度（每个环节都过闸）

**五级测试闸，层层必过：**

| 闸 | 内容 | 不过的后果 |
|---|---|---|
| T1 代码级 | vitest 单测（core 纯函数 100% 覆盖分支） | 不许进 dev |
| T2 契约级 | contract 包 cases.json（规格测试，双 runner） | 不许进 dev |
| T3 集成级 | fake YouTrack + fake CLI harness 全链路 | 不许进 dev |
| T4 验收级 | 真单端到端（冻结验收命令 exit=0）+ 崩溃注入五点 | 不许进 gray |
| T5 评审级 | 异源评审（不同 CLI/模型审 diff）+ 制作人过目 | 不许进 release |

- **测试纪律**：测试只对契约与冻结口径负责；零 LLM 打桩；
  测试不写生产日志；新增功能必须带测试进同 PR
- **探针集回归**：executor/模型/框架升级前必跑；探针与进化目标物理隔离

## 第六章 · 质量红线（违者返工+复盘单）

1. 无证据=无完成；伪造证据=事故
2. 验收命令冻结后禁改
3. 任何 agent 不伪造、不隐瞒失败；失败分类如实上报
4. 密钥永不入库；出站过扫描
5. 不杀活 worker；不动在途单的泳道
6. 文档先行——无文档章节引用的代码不收
7. 公司目录 daemon 唯一写入；人工直写是受控例外+留痕
8. 不超预算帽；预算预留-结算不落即不派

## 第七章 · 并行与泳道纪律

- 泳道=并行单元：一泳道一 worker 一 dev-xxx 分支；泳道锁防同仓冲突
- 环境准备归框架（checkout/装依赖/自检机械完成）；worker 一包到底
- 包级独立开发：adapters/contract 等有独立测试套的包可单独开泳道
- 合并窗口：合并回 dev 前 contract 全绿；merge 冲突复杂转 merge 单（制作人定取舍）

## 第八章 · 评审与过目点（制作人触点清单）

制作人的触点**只有这些**（除此之外默认不打扰）：
1. 每版本证据包过目（里程碑完成时）
2. 重装单/9 级单/宪章与红线改动——亲批
3. 三态闸门 escalate 项
4. 月报+总览阅读
5. 对外发布（GitHub 公开内容）——批准

惊动预算作为可配指标纳入定时审查岗（D9 模型）；超限自动开改进单。

## 第九章 · 变更与进化

- 一切改进走候选制品管线（观测→提案→沙箱→三态闸门→灰度→切权→复盘）
- 判据类资产（验收口径/探针/阈值/分歧判据）属宪法内核，改=制作人亲批
- 公司目录规范有前瞻性，定稿不轻改；必须改时 schema 版本迁移+daemon 执行+挂单留痕

## 第十章 · 留痕与审计

- 一切处置留证据：YouTrack 评论 / git 提交 / 台账事件（三处至少其一，关键动作三者皆有）
- 台账 append-only + rolling hash；外部调用全落 events
- 月度外审（独立视角）为兜底；内部自检连续三月可信后可降频

## 第十一章 · 异常与事故

- 卡单：断路器 N=3 自动开 bug 单；持续报错升级电路
- 事故：发现→止血→复盘（挂复盘单）→案例库；复盘不追责，追流程
- daemon 崩溃：看护拉起+状态外置无损接手；YouTrack 挂：只读降级+告警

## 第十二章 · 检查清单

**开工前**：设计文档已批准 □ 概念归属已填 □ 验收命令已冻结 □ 环境 doctor 绿 □
**合并前**：T1-T4 全绿 □ 异源评审过 □ 密钥扫描过 □ 文档同步改 □
**发版前**：灰度零事故 □ 崩溃注入绿 □ 证据包齐 □ 制作人过目 □ CHANGELOG 生成 □

## 第十三章 · 提案流铁律（2026-10-19 制作人令——核心准则，不为任何东西妥协）

> **适用域**：StudioNext **框架本体**的开发与自我修改（自研自改）——地基上的每一刀都走此流，
> 可以走得慢，必须走得稳。**框架上开办的各公司不强制**：公司内部开发流程由各公司章程自定
> （框架把提案流作为可选治理模板提供）。适用于**一切重大改动与后续功能开发**（新能力/架构
> 变更/跨包面）；小修（bug 修复、数据修复、既有单范围内的补全）走常规通道。**框架必须始终保持：高层自洽的抽象 +
> 底层逻辑闭环的代码设计。**任何进度、任何 Deadline 都不得凌驾于此。

**六步，不得跳级**：

1. **提案**——问题陈述+候选方案；不预设结论，不夹带实现。
2. **探索**——派出多个 agent 独立讨论互查（允许互相反驳）。
3. **前沿对比**——别人做过→怎么做的；没人做过→相近想法与失败教训也要查。
4. **方案定稿**——实现方案文档，必须含「不做什么」边界。
5. **验证 spike**——独立 workspace 全功能验证：每个功能点逐一过，**不是跑通一个 demo 就算**。
6. **评审过审**（制作人）→ 才允许另立实现单进队列。

**两条不可妥协的判定**：

- **验证不过 = 不应用。**不打补丁硬上、不留「以后再修」；发现与预期不符，回第 1 步。
- **审验必须区分「验证通过」与「被修到能跑」。**AI 执行者天然倾向奔着完成任务去——交付物
  中出现为绕过问题的特判、被跳过/削弱的断言、无解释的行为收缩，一概判负打回（对齐第九章
  判负闸哲学，前移到设计验证阶段）。

## 第十四章 · 全景对账纪律（2026-10-20 制作人令——文档不是白写的）

1. **施工依据链（第二章）是双向的**：下行（抽象→需求→设计→单据→代码）与**上行对账**
   （代码→单据→设计→需求→抽象逐环核对「写了的是否都干了」）同等约束力。只做下行不做
   上行=断链欠账。
2. **对账触发点**（任一即触发全景对账）：里程碑收口｜规范/重大方案冻结｜制作人拍板后
   开火前｜连续两周无对账。对账产物=断链清单（文档有、实现无、且无在队单据覆盖）+
   矛盾清单（文档间冲突）+ 补单/并单/废单处置表，落 docs 编号归档。
3. **禁止被动驱动**：编排者（宰相/主 PM）不得只按制作人点名单项提级——制作人的「指出」
   本身就是对账欠账的**事故信号**，每发生一次须复盘「该信号本应对账在第几环被拦住」并
   补机制。优先级的驱动源=文档链与里程碑表，不是最近一次对话。
4. **断链清零口径**：进入下一里程碑前，断链清单必须清零或显式降级（制作人批注「缓办」
   留痕），不许静默滚存。

## 第十五章 · 分层宪法与依赖边界（2026-10-20 制作人千文件级之问；DEV-47）

> 定位：回答制作人 2026-10-20 之问——「结构能支撑上千文件/几十万行吗？要不要考虑更长远」。
> 答案=两轴模型已备（DEV-45b 第一刀落地），缺的是**机械化的边界纪律**。本章=分层宪法：
> 让仓库以「按规则生长」替代「周期性整体重构」——vscode 百万行无整体搬家式重构的实证路径。
> 执行面=机械门禁 `scripts/guards/boundaries.mjs`（规则数据唯一源 `boundary-rules.mjs`），
> `bun run test` 前置跑——**机制保证，不是自律**（与纪律 4「唯一写入者」同源哲学）。
> 本章属判据类资产（§九）：阈值/方向表/基线清单的任何修订=提案流+制作人批。

### 一、两轴规模化模型（横轴生长 × 纵轴分层）

1. **横轴（包轴）**：`packages/*` 一包一域，水平生长。新领域=开新包（或升格，见 §五），
   不向既有包塞异域物。包间依赖方向冻结于 §二横向表——横轴的「远」由方向表管理。
2. **纵轴（层轴）**：包内 vscode 式分层（DEV-45b 五域+根入口为首批实现）。以 daemon 为
   例自上而下：`index.ts`（纯入口）→ `cli/`（人机命令面）→ `assembly/`（组合根）→
   域层（`engine/`、`control/`、`evolve/` 三域平级）→ `engine/tools/`（无状态工具亚组，
   base 雏形）→ 以下即横轴包。只准自上而下依赖；同域内互引自由。
3. **第二刀预留位（域升格为包）**：第一刀=DEV-45b 包内分域；第二刀=当某域（如 `engine/`）
   自身含 contrib 子域累计 **>40 件**、或被第二个 app/包需要共用时，该域升格为独立包
   （`packages/engine/`），横轴方向表加行。触发条件机械可判（门禁扫描 contrib 子域文件数），
   升格动作=提案流（迁移+方向表修订+门禁同步），**不设日历触发**。

### 二、依赖方向冻结（方向表=宪法内核）

**通则**：①跨层只准自上而下；②同层（同域）互引自由；③表中未列的边=违例（新边=改表=
提案流）；④反向边（下引上）一律违例。

| root | ✓ | ✗ | ✗ |
| cli | ✓ | ✓ | ✓ |
| assembly | — | ✓ | ✓ |
| control | | 同层互引 ✗ | ✓ |
| evolve | | 同层互引 ✗ | ✓ |
| engine | | 同层互引 ✗ | ✓ |
| engine/tools | | | 同层互引自由 |

**横向表（包间允许边；层位数字越大越靠上，只准高层引低层）**：

### 三、尺寸阈值（千文件级扩容的结构闸）

1. **目录 >25 文件 → 必须切子域**（开子目录分组；作用于 `apps/*` 与 `packages/*` 的
   `src/`+`test/` 全目录树）。
2. **文件 >600 行 → 必须拆**（作用于同一范围，测试文件在内——测试膨胀同样是千文件级
   风险，不留豁免面）。
3. **存量基线（ratchet，只减不增）**：立宪时已超限的文件冻结行数基线（见
   `boundary-rules.mjs` `lineBaseline`）：基线内件超基线值=违例；降至 ≤600 即可除名
   （除名随任意提交顺带办理，无需提案）。**基线值上调与新增条目=改宪法=提案流。**
4. **清偿义务**：每里程碑对账点（§十四）核对基线净变化——只许净减，不许净增；
   连续两个里程碑零清偿=对账欠账，开改进单。

### 四、contrib 模式（域平面纪律；制作人 vscode 深究令）

1. **域目录长新特性=开 `<域>/<特性>/` 子文件夹**（vscode workbench/contrib 同款），
   **禁止向域平面加散文件**。平面基线冻结（只减不增）：`engine/` 13、`control/` 2、
   `evolve/` 5、`assembly/` 1；新文件进既有平面=违例。
2. **cli/ 例外**：一命令一模块（DEV-45b §3 拆分模式），平面可随新命令生长，受 §三.1
   通用阈约束；超阈=按命令族切 `cli/<族>/` 子目录。
3. **src 根=纯入口**：根平面只许 `index.ts` + 五域目录（D2 裁定「根目录主要是入口/
   配置/启动」的机械化）；根平面任何新散文件/新顶层目录=违例。
4. 域平面基线下降（拆走/合并文件）随提交顺带改表，无需提案；上升=提案流。

### 五、base 升格路径（vscode base 层等价物）

`engine/tools/` 为雏形（无领域状态的纯工具件）。**累计 >10 件 → 升格 `packages/base`**
（横轴新包，层位 1，方向表加行）。门禁在 >10 时判违例并提示升格——升格阈值由此机械化，
不靠自觉。升格前 tools 平面自然生长（不受 §四.1 平面冻结约束，受 §三.1 通用阈约束）。

### 六、机械门禁（执行面）

1. **入口**：`bun run guard:boundaries`（= `node scripts/guards/boundaries.mjs`）；
   `bun run test` 已前置串接（`guard:boundaries && vitest`）——CI 面（README §Quickstart
   同源命令）随之自动前置。违例=非零退出=测试闸红。
2. **规则数据唯一源**：`scripts/guards/boundary-rules.mjs`（层位表/允许边/阈值/平面基线/
   行数基线全量冻结于此）；本宪章节内表格为其人文镜像——**冲突时以规则文件为准并回改
   本章**（对齐第二章「实现与文档冲突→停手改文档」）。
3. **违例编号**：BC-V1 层间向上/未冻结边｜BC-V2 src 根散文件｜BC-V3 域平面超基线｜
   BC-V4 tools 升格触发未升格｜BC-H1 包间未冻结边｜BC-H2 越界相对引用｜BC-S1 目录超阈｜
   BC-S2 文件超阈（新超限/超基线）。
4. **工具选型（宰相 2026-10-20 令「dependency-cruiser 或等价」）**：取**自研零依赖等价物**
   ——本仓方向规则=层位表+允许边白名单（表驱动），dependency-cruiser 的 regex 路径规则
   表达白名单既难审计也难与文档表格互证；且尺寸阈值（§三）它不覆盖，仍需第二机制；
   仓依赖纪律极简（3 个 devDep），为扫描器引入整棵依赖树得不偿失。等价性由本门禁测试面
   （`boundaries.test.mjs` 逐规则红绿夹具+本仓自检）背书。

### 七、不做什么（边界）

- 不做循环依赖自动修复：检出即红，修法=人拆（提交流程解决）。
- 不扫 `templates/`、`docs/`、`scripts/`（非产品 TS 面；scripts 为工具面自约束）。
- 不限外部 npm 依赖（仅管仓内边；外部依赖治理另立）。
- 不测「路径字符串引用」面（如 `BRIDGE_SRC_REL` 常量）——文档标注，不做静态分析。
