# 20 · 工程总规程（Studio Next 施工法）

> v1.0（呈批稿）｜ 2026-10-16 ｜ 主 PM：Kimi
> 定位：本规程是 Studio Next 施工的**最高工程规范**——怎么干、按什么顺序干、
> 每个环节过什么闸、谁过目、什么算完成。效力低于宪章与红线，高于一切临时安排。
> 制作人定调：这是一个超大、详细、高要求的工程，必须有明确的规章制度。

---

## 第一章 · 总则

1. 本工程为 AI 全自主施工、制作人终审的超大工程。一切工作以**单据**为最小工作单位，
   以**证据**为完成标准，以**文档**为开工前提。
2. 版本制度：**完成一个里程碑算一个版本**（不设周/月版本）；每个版本制作人过目才发布。
3. 顺序铁律：抽象 → 文档 → 制作人过审 → 代码 → 测试 → 合并 → 发布。倒序或跳级视为废件。
4. 适用对象：所有参与本工程的角色（制作人/主 PM/宰相/各岗 agent/worker/外部委托）。

## 第二章 · 施工依据链（按什么干）

每一行代码都必须能沿这条链回溯到依据，缺一环不开工：

```
总纲领（07）→ 需求条目（01/02/03/04/05/06）→ 技术设计（17/18）→ 里程碑（16）
→ YouTrack 单据（Epic→子单）→ 任务书（含文档章节号+冻结验收口径）→ 实现 → 证据
```

- **拆单规则**：每里程碑一张 Epic；Epic 拆到"一单一命可完成"粒度（建议单件 ≤4h 墙钟）；
  每单必填：概念归属（六名词三动词，D10）、设计文档章节号、冻结验收命令、预算帽
- **概念准入**：映射不进六名词三动词的需求退回（D10，防自洽性破碎）
- **文档修订**：实现与文档冲突 → 停手改文档（走批示），不默许代码漂移

## 第三章 · 版本与里程碑制度

版本与里程碑对应表（16-§四 为准）：

| 版本 | 里程碑 | 过闸要求 |
|---|---|---|
| v0.1 | 契约包+公司目录模板 | contract 绿 + init 自检 |
| v0.2 | SQLite 台账 | 删库重建演习通过 |
| v0.3 | 监控面板 :8787 | 信息覆盖：jobs/runs/workers/事件流齐备 |
| v0.4 | 首个定时岗 | 48h 无故障运行 |
| **v0.5** | **首单端到端（时间盒止点，两周）** | 真单走完全程，制作人过目 |
| v0.6 | 四家适配器 | 同一探针集四家全绿 |
| v0.7 | 公司面 :8789 | 三连问页面直答 |
| v0.8 | 唤起六源 | 接力重投零重复 |
| v0.9 | 对外 API+名片 | 越权全 fail-closed |
| v0.10 | 进化管线+健壮性 | 崩溃注入五点全绿 |
| v1.0 | 切权上线 | 连续 7 天零批示正常运转 |

- 时间盒（D7）：v0.5 两周未达 → 回议，不硬撑
- 每版本交付**证据包**（页面截图/单据流转记录/测试报告/成本账）→ 制作人过目 → tag

## 第四章 · 分支与发布流程（三级晋升）

```
feature/* ──CI 全绿──▶ dev ──契约+崩溃注入全绿──▶ gray ──灰度零事故+制作人过目──▶ release（tag）
```

- 上线前的实现：bugfix-only 维护线，永不发新功能
- gray 灰度：对生产 YouTrack 只读或限定泳道跑，灰度期不设日历、只看零事故+证据
- 回退：release 出问题 gray 顶回修；上线前的维护线永远兜底
- 绝不 force push、不重写历史、不删分支（红线）

## 第五章 · 测试制度（每个环节都过闸）

**五级测试闸，层层必过：**

| 闸 | 内容 | 不过的后果 |
|---|---|---|
| T1 代码级 | vitest 单测（core 纯函数 100% 覆盖分支） | 不许进 dev |
| T2 契约级 | contract 包 cases.json（规格测试，双 runner） | 不许进 dev |
| T3 集成级 | fake YouTrack + fake CLI harness 全链路 | 不许进 dev |
| T4 验收级 | 真单端到端（冻结验收命令 exit=0）+ 崩溃注入五点 | 不许进 gray |
| T5 评审级 | 异源评审（不同 CLI/模型审 diff）+ 制作人过目 | 不许进 release |

- **测试纪律**：测试只对契约与冻结口径负责；零 LLM 打桩；
  测试不写生产日志；新增功能必须带测试进同 PR
- **探针集回归**：executor/模型/框架升级前必跑；探针与进化目标物理隔离

## 第六章 · 质量红线（违者返工+复盘单）

1. 无证据=无完成；伪造证据=事故
2. 验收命令冻结后禁改
3. 任何 agent 不伪造、不隐瞒失败；失败分类如实上报
4. 密钥永不入库；出站过扫描
5. 不杀活 worker；不动在途单的泳道
6. 文档先行——无文档章节引用的代码不收
7. 公司目录 daemon 唯一写入；人工直写是受控例外+留痕
8. 不超预算帽；预算预留-结算不落即不派

## 第七章 · 并行与泳道纪律

- 泳道=并行单元：一泳道一 worker 一 dev-xxx 分支；泳道锁防同仓冲突
- 环境准备归框架（checkout/装依赖/自检机械完成）；worker 一包到底
- 包级独立开发：adapters/contract 等有独立测试套的包可单独开泳道
- 合并窗口：合并回 dev 前 contract 全绿；merge 冲突复杂转 merge 单（制作人定取舍）

## 第八章 · 评审与过目点（制作人触点清单）

制作人的触点**只有这些**（除此之外默认不打扰）：
1. 每版本证据包过目（里程碑完成时）
2. 重装单/9 级单/宪章与红线改动——亲批
3. 三态闸门 escalate 项
4. 月报+总览阅读
5. 对外发布（GitHub 公开内容）——批准

惊动预算作为可配指标纳入定时审查岗（D9 模型）；超限自动开改进单。

## 第九章 · 变更与进化

- 一切改进走候选制品管线（观测→提案→沙箱→三态闸门→灰度→切权→复盘）
- 判据类资产（验收口径/探针/阈值/分歧判据）属宪法内核，改=制作人亲批
- 公司目录规范有前瞻性，定稿不轻改；必须改时 schema 版本迁移+daemon 执行+挂单留痕

## 第十章 · 留痕与审计

- 一切处置留证据：YouTrack 评论 / git 提交 / 台账事件（三处至少其一，关键动作三者皆有）
- 台账 append-only + rolling hash；外部调用全落 events
- 月度外审（独立视角）为兜底；内部自检连续三月可信后可降频

## 第十一章 · 异常与事故

- 卡单：断路器 N=3 自动开 bug 单；持续报错升级电路
- 事故：发现→止血→复盘（挂复盘单）→案例库；复盘不追责，追流程
- daemon 崩溃：看护拉起+状态外置无损接手；YouTrack 挂：只读降级+告警

## 第十二章 · 检查清单

**开工前**：设计文档已批准 □ 概念归属已填 □ 验收命令已冻结 □ 环境 doctor 绿 □
**合并前**：T1-T4 全绿 □ 异源评审过 □ 密钥扫描过 □ 文档同步改 □
**发版前**：灰度零事故 □ 崩溃注入绿 □ 证据包齐 □ 制作人过目 □ CHANGELOG 生成 □

## 第十三章 · 提案流铁律（2026-10-19 制作人令——核心准则，不为任何东西妥协）

> 本流程适用于**一切重大改动与后续功能开发**（新能力/架构变更/跨包面）。小修（bug 修复、
> 数据修复、既有单范围内的补全）走常规通道。**框架必须始终保持：高层自洽的抽象 +
> 底层逻辑闭环的代码设计。**任何进度、任何 Deadline 都不得凌驾于此。

**六步，不得跳级**：

1. **提案**——问题陈述+候选方案；不预设结论，不夹带实现。
2. **探索**——派出多个 agent 独立讨论互查（允许互相反驳）。
3. **前沿对比**——别人做过→怎么做的；没人做过→相近想法与失败教训也要查。
4. **方案定稿**——实现方案文档，必须含「不做什么」边界。
5. **验证 spike**——独立 workspace 全功能验证：每个功能点逐一过，**不是跑通一个 demo 就算**。
6. **评审过审**（制作人）→ 才允许另立实现单进队列。

**两条不可妥协的判定**：

- **验证不过 = 不应用。**不打补丁硬上、不留「以后再修」；发现与预期不符，回第 1 步。
- **审验必须区分「验证通过」与「被修到能跑」。**AI 执行者天然倾向奔着完成任务去——交付物
  中出现为绕过问题的特判、被跳过/削弱的断言、无解释的行为收缩，一概判负打回（对齐第九章
  判负闸哲学，前移到设计验证阶段）。
