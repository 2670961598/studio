## 一、结论

1. 共 **17 条**：**P0 0 条、P1 6 条、P2 9 条、P3 2 条**。
2. **最严重 3 条**：
   - **L3I-01（P1）** 旧台账迁移要求把 `integrity.byteDigest` “显式标 `unknown`”，但 `Digest` 没有 unknown 变体、76-§1.8 明写“未知不是可序列化值”，且本卷同时禁止伪造与删除 `integrity`——三个可选动作全被自己堵死，历史记录无合法落笔方式。
   - **L3I-02（P1）** 五十类记录只映射到 `recordType.name`：`PayloadOf<T>` 全文只出现一次、无定义、无生产者；且“用 discriminated union 的 `recordType.name` 收窄”在 TS 里不成立（同仓 `typescript@5.9.3` 探针实跑，TS2322）。§4 的核心交付物在 payload 维为空档。
   - **L3I-03（P1）** `Err` 被 §4.3.1 定义为“确定未产生外部效果”，又被 §5.2 要求“登记未知失败 ⇒ `Err(unavailable)`”，而 §5.7 处置表对 `unavailable` 一律“退避后重试”——与 77-§11.1 的“副作用可能有”列正面冲突，按表实施会重复外部写。
3. 其余 P1：`canonicalizationId` 赋值与 76-§8.1 相反（L3I-04）、公司本地日的时区来源不存在（L3I-05）、“`matrixSessionFactory` 只传行为不传值”的论据被自己的类型签名否证（L3I-06）。
4. **P0 判 0 的理由**：逐条核对后，未发现使根命题、权责链或数据／安全边界在文本上自相否定且无正解路径的硬矛盾。L3I-01 与 L3I-03 最接近 P0，但两者都还能读出一条“与 76／77 owner 一致的正解”（改写载体／先对账），按 `_scope` 口径不升格；本报告不为好看升格，也不为克制把 L3I-02 降成 P2。
5. **本层“硬”的部分（不是问题，先记下）**：17 节点／16 层位／38 条包边／13 条纵边／域平面 13·2·5·1 与 `scripts/guards/boundary-rules.mjs` 逐项一致；50 类 `REC-*` 在 77-§0.5、80-§4.4、80-§4.7 三表**集合相同、类型名无重复**；10 类 decision facet 与 77-§1.7 封闭清单逐项一致；14 类失败与 77-§11.1 逐字一致；22 条行数基线、209 测试件、18 命令、23617 行等自称计数**全部复核为真**；§0–§5 的四态标记（目标／已有／未证）诚实，未见把目标写成已有。
6. 结构性问题集中在三处：**记录面只映射到类型名**（payload 无载体）、**错误面缺“副作用可能性”维**（处置表按 failure 一刀切）、**“唯一”清单不完整**（RunServeOpts 四处、external 两套配置面、null/undefined 三义）。
7. 可带着走：§2 的层位与边清单、§3.6 的十步启动序列、§5.1–§5.6、§5.9–§5.11 的工程惯例（不含 §5.5 条 2 与 §5.7 的处置表）。
