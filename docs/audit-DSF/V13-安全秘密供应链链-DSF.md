## 一、结论

1. 本次共报 **P0=1、P1=5、P2=1**（共 7 条）。没有一条是文风问题。
2. 最严重三条：**① 秘密出站这条质量红线（20:85/20:130）在 L1、L2 都没有对象、没有承担者、没有观察面，L3 只有目标，唯一实现只覆盖 78:1044-1052 八个出口里的三个（且只对 hrSync 路径生效），失败出口的事件名在冻结词表里不存在——「出站过扫描」不能判定成败，也就不能算已经存在（V13-01）；② 网络出口在同一卷里有两说（78:929「网域 fail-closed 白名单」vs 78:1097「网络出站＝无」），而唯一带网域收口的 seatbelt 在任务派工面不启用，`DSH_*` 环境前缀又整段透传——读者无法判定现状，只能二选一猜（V13-03）；③ 「生产泳道禁自装插件」被写成红线加双保险（06:47-48/06:79-80），但代码里没有 prod/explore 泳道、`patches` 是 `z.unknown()` 透传、`profiles/` 目录不存在、插件安装不校验摘要/签名/许可（V13-04）。**
3. 链条形态是**「L3 比 L0 诚实，L1 几乎空白」**：78 与 82 大量写「目标/未证/不得声称」，是本套文档里最硬的部分；但 L1（06）全文**零命中** 网络/秘密/密钥/沙箱/隔离，于是 20 的红线在需求层**没有对象、没有主体、没有出口**。安全这一支不是被写错，是被**没有写**——所以找不到「谁执行、失败怎么办、如何证明」。
4. 秘密这条链的语义在第 2→3 层之间发生了**对象替换**：63-§1.3 的「保密」是**义务**（63:40-44 要求义务必须有实例、期限、违约去向），到 78 变成了**部署工件**（`SecretCatalog`/`SecretProvider`）。义务实例的承担位置与违约去向在传递中消失（V13-01）。
5. 审计链的防篡改承诺与现状反向：20:118 写「台账 append-only + rolling hash」，72:46-49 把它升为「**必须能发现** 篡改、丢失、重放和未授权修正」，而主审计表 `events` 恰恰是唯一**没有** UPDATE/DELETE 触发器的台账表（`personnel_events`/`probes_runs`/`price_snapshots`/`cost_daily` 都有）；同时 78:1410 仍称 `events`「可由记录重建」，而记录三表是「目标（未建表）」（78:1396）。见 V13-02（同根 `L0-A P1-06`，本报告的增量是「可重建」的归属错与缺口漏登记）。
6. 供应链的两个「锁」都不是锁：06 的版本锁在代码里只产 gap 不阻派（`detect()` 返回 `ok:true` + gap）；插件版本约束只对**来源目录自报**的 `package.json` 生效，内容无摘要、无签名、许可未核。
7. `fail-closed` 在本链是**分叉的**：网关/stdio 的 wkey、外部 API 令牌是真 fail-closed（无 key 全拒、未配令牌全 401）；而网关签根缺省回落到**仓内公开常量**（`serve.ts:784`）——同一条「部署只能收紧」（78:109）在签根上不成立（V13-05）。
8. 可以带着走的：78-§2.4 的三分法（硬/软/不可表达）与其判据、78-§5.3（E 级与四态/风险档不得互推）、78-§12.5（哈希不证明事实）、82-§14.3（阻断级缺口）、82 的「未执行不写成通过」纪律。这些是本卷最可交班的部分，本报告不改它们。
9. 本报告**不**证明任何运行时行为：DSH 沙箱/网络/审批、worker 写域、密钥可读性均未真机取证（见 §四）。

### 2.2 六条关键断点（每条只回答：它让哪条根命题/权责/验收失效）

1. **出站秘密防线没有主体、没有失败出口**（#1/#5/#6；V13-01）：让 20-§六.4「密钥永不入库、出站过扫描」这条质量红线在 L1/L2 无承载者——它既没有对应对象，也没有承担位置。后果：**没有任何位置会因为一次泄密而被要求说明**；78:1045-1052 的 `redaction-failed`/`notify-blocked`/`unknown-shape` 三个失败出口在 `EVENT_NAMES`（30 个名字）里**都不存在**，所以「fail-closed + 留证」在台账上无表示。
2. **审计主表是全库唯一无防篡改的台账表**（#2/#10；V13-02）：让 72:46-49 的「必须能发现篡改」与 20-§六.1「伪造证据＝事故」失去机检面。触发面不对称（人事/探针/价目/成本日账都有，事件表没有）说明这不是「还没做」，而是**优先级被放错了**：被审计方的动作记录比人事变动更容易被改。
3. **网络边界在同一卷内自相矛盾**（#7；V13-03）：让读者无法判断「E3 类动作现在能不能被阻止」。按 78:929 会以为网域已 fail-closed（于是不做外部代理）；按 78:1097 会以为完全无网域（于是重复造代理，或反过来把「无网」写进符合性声明）。两种误读都会让 E3 的现状声明失真。
4. **供应链的两把锁都是软的**（#3/#4；V13-04）：让 06-§3 的「这是工具投递通道，不是治理让渡」失去机制支撑——插件装的什么内容、哪一版、许可如何，没有任何一层在装的时候校验；被装进去的插件与 agent 同进程，78-§4.7 自己写「有代码执行权即可篡改判定」（`L78-POS-01` blocking）。
5. **秘密「只以逻辑引用存在」缺可执行入口**（#8；V13-05）：让 75-D75-13 成为一条无法落地也无法验收的结论。更硬的是反例：网关签根缺省值公开在仓库里且被默认使用，等于在默认部署下 `wkey` 可被任何能读源码的一方伪造（可读性同根 `L3F-01`，本报告只报 fail-open 面）。
6. **配置托管的 L1 形状与 L3 契约互斥**（#3；V13-06）：让「人事档案式配置」这一核心工程面没有唯一形状。按 06 实现必须放宽 `strictObject`（丢掉未知键拒收这条 fail-closed 闸），按 `agentconfig` 实现则 06 的示例是废件。
