## 一、结论

- **P0 = 1，P1 = 12，P2 = 6**。整条“需求→公共语义→记录/绑定→验证”的链**在 A 侧需求 ID 上断了**：84 条需求（01 的 41 条 + 02 的 43 条）在 75–78/80/82 中只有 1 处 ID 引用（80:415 的 `F2-04`）。
- 最严重三条：
  1. **P0 组织事实源分叉**：A 说“`org-config.yaml` 唯一事实源（D1 已拍板）”（04:124），B 说“旧 org-config 只读投影 + 新定义包权威”（82:618），而同一个 D1 在 75:268 仍标“待制作人决定”。同一对象两个主表，同一决策 ID 两义两态。
  2. **P1 验收链不可验**：82 声称追溯键含“需求→对象/REC→端口”（82:54），但其键表只有 R/E/W/I/G/H（82:341-349），75-§九的审查清单也不含 01/02 需求轴（75:304）。B 可以在完全丢掉 A 需求的情况下通过自己的审查。
  3. **P1 对外面被系统性改写**：独立进程→同进程装配（C3-01）、三档凭证→单静态 token（C3-03）、端点删两个/缩窄三个/新增一个（C3-04）、派单人锚与等级封顶消失（C3-07）。
- 正面：78 对**已建模**的平台/宿主/工作区损失是诚实的（guards blocking、无 webhook、读域不可收口、无网络/进程隔离均按 `blocking/degrading` 写明）；82 对“V2–V6 全部未执行”的声明也是诚实的。问题不在“说谎”，在**漏建模后不登记损失**。
- 承接最好的一段是 02-F1/F2 的运行时主干（七相位、五门/并发闸、收割四要件、三表记录、崩溃注入、写者围栏），虽然多数被改名/重分层。
