## 一、结论

1. 本链**不成立**：组织对象（部门）在 L3 有两套**互斥的封闭形状**，部门链在最后一层断；治理位置链的"配置器"与"顶点"在 L3 只有名字没有可校验对象。
2. 计数：**P0 = 1，P1 = 6，P2 = 3，P3 = 0**。P0 不是文风问题，是 schema 无法冻结、模板与校验器必有一破。
3. 最严重三条：
   - **F01（P0）**：部门在 `76-DEF-ORG-01` 里没有"单一责任位置（负责人）"、也没有 `parent`；`81-files/19` 的部门 config 却把 `leader`/`parent` 列为必填并声明"键封闭"；现行 `validator.ts` 同样必填。66-§4.1 把"有单一责任位置"作为部门**成立条件**、66-§4.9 把它写成逻辑结论，L3 无字段可校验它。
   - **F02（P1）**：十类治理位置的**唯一设置主体**"治理配置责任者"，在 66 是强制的具名岗位，在 76 被归入"附加推荐条目·可选项"，在 82 明确"不建追溯行"，且没有任何独立性要求——`appointmentAuthorityRef` 是裸 `qid`，可被"最终责任位置"直接顶替而不会拒收。
   - **F03（P1）**：最终责任位置在 L3 只有一个裸 `qid` 字段（`DEF-FOUND-01.finalResponsibilityRef`），63-I-7 的"实质控制"无字段、无校验；82 的 `TR-I-07` 却把它映射到岗位/授权/任命三类记录，预期证据"责任者能获得信息、资源、监督、止损位"无法由任何已声明对象构造。
4. 可带着走的：11 类治理位置**本身**在 66/70/76/77/82 是闭合的（10 + 第 11 类专用设置链，见 §二 链表第 11 行）；继任链（REC-LIFE-05 代理/替补 + REC-AUTH-08 + REC-LIFE-02）是本次链条里最完整的一段。
5. "DSH team 被当部门"**未发现发生**：70-§3.1 已切断 `role`/`login`/`job` 替代岗位；78-§L78-DSH-04 与 78a-§3.7 另有明文禁止（范围外，仅作反证）。
