## 1. 结论

1. 链条断在**执行面端口的表达能力**：`TaskBrief`/`ExecutorCapabilities` 没有任何权限、沙箱、工具、审批、宿主形态维度，而 78 把「启动器 spawn 前校验 PRM」当作无插件时的唯一防线——该防线在 80/81 没有任何端口或文件（P0）。
2. 78 的 PRM 必填 `signature` 在目标形态**没有验签通道**（81 自证「生产形态下没有可用的验签器」「M6 被 G3/G17 阻断」），78/82 却未把它登记为设计缺口；两条硬规则叠加 = 位置插件生产态必然全拒（P0）。
3. 四原语对「失败/取消/超时」只保留了很窄的一面：`turn_end.reason.kind` 五值被压成 `completed` 布尔，被 kill 时无 `turn_end`，而 78-§12.2 要求导出 `kind`——导出映射不可实现（P1）。
4. 「单据指定 > 岗位绑定 > 竞标默认」的执行器选择链在 L2/L3 完全缺失，`person.executor` 只作依赖绑定属性、派发只走 `registry.pick()`；「QA 用另一家做异源监控」的设计无机制（P1）。
5. 墙钟/心跳看门狗（06-§2.2 的 `wall_s`/`heartbeat_s`）无实现、无登记；三家无预算帽的 executor 没有任何时间上界（P1）。
6. 工作区隔离只有"目录不同"：代码是员工家下 `tickets/<单>/att<N>` 普通目录（非 worktree），跨 attempt 可读、同家持久，71/78 未登记该粒度的损失（P2）。
7. 计数：**P0 = 2，P1 = 7，P2 = 5**（P3 不列）。最严重三条：V07-P0-1（权限面端口无承载）、V07-P0-2（验签不可实现且未登记）、V07-P1-1（终态差异被压缩）。
8. 未修改任何设计文档、源码、配置；未运行 `typecheck`/`test`/`guard`；未起 DSH 真机。

### V07-P0-1｜P0｜B 缺口 + F 权责失真｜执行面端口与能力声明没有权限维度；78 的「启动器校验 PRM」无落点

**位置**：`docs/06-职责边界.md:27-29`、`:89`；`docs/18-…:16-27`；`docs/78-…:101`、`:397`、`:503-508`、`:510-518`、`:589`；`docs/80-…:1913-1917`；`packages/contract/src/ports/executor.ts:10-16`、`:43-52`；`packages/contract/src/ports/kernel.ts:47-64`、`:67-88`；`docs/81-files/17-…`（全篇无 PRM 件）。

**事实**
- 06-§1 纪律：周边设施层与 agent 内部层之间「**只有四个接触点**——四原语（launch/stream/result_stats/kill）+ 配置注入 + AGENTS.md + 输出收割」，并称「只要接口不变……零感知」（`docs/06-职责边界.md:27-29`）。
- 端口实现：`ExecutorAdapter` 只有 `name/capabilities/detect/estimate/launch/stream/resultStats/kill`（`executor.ts:43-52`）；`ExecutorCapabilities` **五个布尔/枚举**：`budget_cap`/`cancel_turn`/`session_resume`/`agents_md`/`cost_native`（`:10-16`）。
- `TaskBrief` 字段集：`ticket/attempt/briefPath/workspace/AGENTS_MD/budgetCap?/resume?/credentials?`（`kernel.ts:67-88`）——**无** sandbox 模式/工作区根/工具 allow-deny/审批策略/PRM 引用/launch 形态。
- 80-§6.5 明写「目标接口只补两处，不改四原语」：`TaskBrief.planRef` + `Handle.fence`（`docs/80-…:1913-1917`）。
- 78-§0.5 修正 1 把 fail-closed 拆两段：「①有插件时插件 fail-closed；②**无插件时由启动器（框架侧）在 spawn 前校验 PRM，失败即不 spawn**」（`docs/78-…:101`）；§3.4 双重校验同行（`:503-508`）。
- 80 全篇无 PRM 端口/装配件（负向检索：`grep PRM` 仅命中"秘密不进 PRM"类注释）；81-files/17 的 assembly 文件清单无 spawn 前 PRM 校验件（见 §4 第 3 条）。

**判断**
- 78 的四条硬控制（`tools.restrict`／`tools/pre-execute`／`sandbox-policy`／`user-approval`）全部靠 PRM 下发，但**唯一的传输通道（执行体端口）没有 PRM 位**；`ExecutorCapabilities` 也没有「策略面可用／宿主形态」字段，因此 78-§8.4 第 1 条「需要强策略的岗位只允许跑在有 position 插件的宿主上」在调度层无法机械判定（`registry.pick()` 只过滤五个布尔）。
- 78-§3.4 的兜底 ② 没有任何设计落点：不是"未实现"，而是"无件可写"。真机上无插件的 CLI shell-out 形态（78-§3.4 路由表第 3 行）按定义停在供给链 4/5，到不了第 6/11 态；也就是说，**照现文实现，策略面永远不生效**。
- 06-§1 的「只有四个接触点／零感知」同时被 78 否证：要收紧工具必须进程内插件 + 新的 launch 形态（`--patch` 挂载），这不是四原语能承载的。06 未修订，L1 仍以「四原语足够」为前提。
- 这不影响"目标尚未实现"的诚实性，但影响"目标按现文能否实现"：缺的是字段/端口，不是工期。

**最小修复路径**
1. `TaskBrief` 增 `policyManifestRef?: VersionRef<string>`（PRM 三元组）+ `launchForm?: 'headless'|'web'|'sdk'|'acp'`；`Handle` 增 `policyPlane?: 'in-process'|'none'`；`ExecutorCapabilities` 增 `policy_plane: boolean`、`mid_turn_inject: boolean`（供 78-§8.4 的宿主路由机械判定）。
2. 80-§6.5 与 81-files/17 增一个 `F-daemon-engine-dispatch-precheck`：spawn 前校验 PRM（摘要/期限/引用/与部署交集）→ 失败不 spawn；把 78-§3.4 的 ①/② 两段各配一个落点。
3. 06-§1/§4 补一行修订：策略插件属"agent 内部层的受控扩展点"，界面清单由四类扩为五类；否则 06 与 78 不能同时为真。

**判断**
- 两条规则叠加（必填签名 + 验签失败即拒 + 生产无验签器）= **插件永远拒绝加载**；于是 78-§3.4 路由表第 3 行「无插件（纯 CLI shell-out）」成为唯一现实，而该行恰恰声明「全部策略段停在 4/5，不可报 drift」。工具白名单/guard/sandbox/approval 四条硬控制在设计上就不可达。
- 这不是"目标未实现"，是"目标不可实现"：81 已自证，但 78 未降级 `signature`、82 未登记 `GAP`。82-§14.1 的 P0 含「把未执行写成通过」，此处是它的镜像——把不可实现写成目标，MIG-06 的前置（验签交付通道）不在任何波次里。
- 78-§3.4 同段还有一处自相矛盾（81 已登记为 G19）：既然"仅插件侧失败"意味着插件没加载成功，就不能再「记 `position/drift`（第 13 态，**仅当插件确实加载过**）」（`docs/78-…:508`）；81-files/12:107 已明确指出该句自相矛盾。

**最小修复路径**
1. 78-§3.2.1 二选一并同改 §3.4：①`signature` 降为可选，无签名时用「启动器钉 `manifest.digest` + 插件重算」替代，并在证据里标 `unverified`；或②定义验签交付通道（随包发布的 canonicalizer 作为能力包，过 76-JCS 向量；公钥经部署逻辑引用）。
2. 82-§14.3 增 `GAP-82-14`（验签交付通道缺失，阻断 MIG-06 生效面），关闭条件=通道落地 + `P-78-08` 正反双向。
3. 删/改 `docs/78-…:508` 的 drift 句：启动器通过而插件拒绝 ⇒ 不加载 + `position/manifest-rejected`，**不记 drift**（与 81-files/12:107 一致）。

### V07-P1-1｜P1｜C 漂移 + E 不可执行｜`turn_end.reason.kind` 五值被压成 `completed` 布尔；被 kill 无 `turn_end`；78-§12.2 却要求导出 `kind`

**位置**：`docs/31-…:132-134`、`:228`；`docs/78-…:1615`、`:1627-1636`；`packages/contract/src/ports/kernel.ts:47-64`；`packages/adapters/src/streams.ts:150-168`；`apps/daemon/src/engine/engine.ts:1216-1219`、`:1257-1258`。

**事实**
- dsh 真机终态是 `turn_end.reason.kind` 五值：`completed/error/blocked/aborted/max-tokens`，`exit=0` 当且仅当 `completed`（`docs/31-…:132-133`）。
- 契约 `StreamEvent` 的 `turn_end` 只有 `completed: boolean; usage?; error?; errorCode?`（`kernel.ts:47-64`）——**无** `kind`、无 `aborted/blocked/max-tokens`。
- 解析器把五值折算成 `completed: kind === 'completed'`，只有 `reason.error` 存在时才保留 message/code（`streams.ts:152-166`）。
- 31-§7 `P-08` 真机结论：SIGTERM 后「final 空且**无 turn_end 事件**、退出码 0」，并要求「以 `turn_end.reason.kind` 为**唯一**终态判据」（`docs/31-…:228`）。
- 78-§12.2 导出映射要求 `turn_end.reason` 必带 `kind`、`error.code`（`docs/78-…:1615`）；78-§12.3 要求「崩溃/超时/被 kill → 结果标 `unknown`；生成 `REC-EVT-03`」（`:1632`）。
- 收割侧只 fold `ev.completed`（`engine.ts:1218`），`fourOk` 只看 completed/nonEmptyOutput/report/exit0（`:1257-1258`）。

**判断**
- 五种终态在端口层坍缩为两种（有 turn_end 且 completed=true / 其余），`aborted` 与 `blocked`、`max-tokens` 不可区分；被 kill 时**没有 turn_end**，只能落到"completed=false"，与模型失败同形。
- 现状代码没炸，是因为 kill 路径绕开收割走 STALL（`engine.ts:1509-1516`）；但 78-§12.3 的 unknown 面、dispose 停机、以及任何"超时后仍进收割"的路径都无法表达，78-§12.2 的导出表**不可实现**。
- 这也是验收说不清的直接原因：`GATE_FAIL` 无法区分"执行体自报失败"与"被我们终止"，断路签名与事后追责都会错配（`dispositions.ts` 的 WORKER_DEAD/wall 分支因此没有生产者，见 P1-3）。

**最小修复路径**
1. `StreamEvent.turn_end` 增 `kind: 'completed'|'error'|'blocked'|'aborted'|'max-tokens'`（`completed` 保留为派生值以兼容），dsh 适配器原样透传；其余三家按各自实探填（78-§8.3 的「拟稿按不支持处理」纪律不变）。
2. 78-§12.2/§12.3 绑定该字段；§12.3 的 `TOOL_OUTCOME_UNKNOWN` 必须给落点（写入件、`owner`/`review_by` 来源），否则该行只是口号。
3. 82-§2.3 增一条可执行断言：kill 面必须产出 `kind='aborted'` 且**不**产生 `GATE_PASS`；把 31-`P-08` 的负向固化。

### 3.3 关键断点（每条说明失效的根命题/权责/验收）

5. **看护缺失（V07-P1-3）**——失效约束：三家无预算帽 executor 的唯一时间上界不存在；"成本/时长可控"的对外承诺（06-§5 一句话）无机制。
6. **边界未修订（V07-P1-5）**——失效职责边界：06 说"不建不看不改"，78 说"进程内建策略插件"；两卷并存时，实现者与审计者会各引一卷，职责归属无法判定。
