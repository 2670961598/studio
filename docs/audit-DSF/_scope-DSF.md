# DSF 全量审计 · 范围与方法（审计脚手架）

> 审计代号：DSF（与另一侧 GLM 审计区分）。本文件只定义审计口径，不是结论，不修改任何现有设计。
> 覆盖对象：`docs/00`–`docs/82`（含 `docs/81-files/` 分包附录、`78a` 前置决策稿）。
> 审计日期：2026-10-27。

## 一、四条审计轴

| 轴 | 问什么 | 报告前缀 |
|---|---|---|
| 横向（层内） | 这一层自己是否自洽、完整、可交班 | `L0`/`L1`/`L2`/`L3` |
| 纵向（链条） | 一个对象/承诺从设定→需求→抽象→细节是否不断裂 | `V` |
| 连接（层间） | A 层的概念/ID/承诺到 B 层是承接、改写、丢失还是新增 | `C` |
| 总体 | 整套文档作为一件作品是否成立，哪些必须现在修 | `O` |

最终由 `00-审计总报告-DSF.md` 合并；`00b` 做独立复核。

## 二、层的定义（本审计使用，不替代文档自己的分层）

| 层 | 文档 | 审计重点 |
|---|---|---|
| L0 设定 | 00–08、16、20、V4-V7 蓝图、TS 迁移方案 | 根命题、边界、概念准入、宪法内核、工作方法、早期承诺 |
| L1 需求 | 01–04、06、17、18 | 需求是否可测、可验收、不越位；平台/组织/执行体约束 |
| L2 技术抽象 | 63–74 | 理论闭环、对象/不变量/反例、技术抽象是否保义 |
| L3 技术细节 | 75–82、81-files | 字段/状态/失败/退出/接口/绑定/逐文件契约/验证 |

`21`–`62` 是历史探索与决策记录，不单独作为“现行规范”，由 `C09` 审计其被吸收/废弃/悬空的情况。

## 三、严厉程度与分级

- **P0**：破坏根命题、不变量、权责链、数据/安全边界，或使整条链无法成立。
- **P1**：会导致错误实现、无法验收、关键场景无出口，或把未证写成已证。
- **P2**：一致性、清晰度、重复、可维护性问题，可后修。
- **P3**：编辑问题，不阻塞。

要求：每条发现必须有 `docs/xx.md:line` 或稳定节号；引文不超过 2 行；事实与判断分开；不确定标“未证”。不许用“感觉”“可能”代替位置。宁可少报，不可虚报。

## 四、每份子报告的固定结构

1. 结论（≤10 行；P0/P1 数量；最严重 3 条）
2. 发现表（P0→P2；ID、级别、类型、位置、事实/引文、为什么错、修复路径）
3. 覆盖核对（要求的对象/章节/ID 是否覆盖；未覆盖清单）
4. 未证与无法判断
5. 给作者的修复顺序（≤7 条）
6. 本报告没有做什么（范围限制）

## 五、审计纪律

1. **只读现有文档/代码**；只写 `docs/audit-DSF/` 下自己的报告，不改任何设计文档、源码、配置。
2. **不替作者重写**；给最小修复路径，不写“应该全部重做”。
3. **不把文档当事实**：文档说“已有/已实现/已验证”时，能查代码/测试/锁文件就查；查不到标“未证”。
4. **不把目标当现状**：75 的四态（已有/库级存在/目标/未证）必须逐条核对。
5. **不把软约束当硬控制**：persona、AGENTS.md、prompt、plan mode 只能算软限制；硬控制要有机制/证据。
6. **不忽略反例**：每个“必须/不得”都要问“谁执行、失败怎么办、如何证明”。
7. **跨层审计要建映射表**，不能只写“基本一致”。
8. **区分“必须现在修”与“可以带着走”**；不要用 P0 包装文风问题。

## 六、关键提醒

- `73`/`74`/`68` 是审查记录，不是新规范；它们自己的结论也要被审计。
- `78a` 是 78 的前置决策稿，不是 78 正文；78 已声明采纳/修正关系，需核对是否真的吸收。
- `81-files` 是 81 的分包附录，不是另一套架构；逐文件契约必须能回溯到 80 的接口。
- 现行代码与文档可能不一致；`73` 的“现状”声明要用仓内代码/测试复核。
- 文档里出现的 `210/210`、`2976/2976`、`已通过` 等全量声明，必须可复现；不可复现即降级为“当前环境未证”。
