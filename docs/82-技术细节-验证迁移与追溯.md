## 〇、一句话结论与阅读须知

〔结论〕69–81 已经把「需要什么语义、用什么对象和记录、落在哪些端口与文件」写到可施工的粒度；本卷补的是**怎么证明它成立、按什么顺序迁移、每一项追溯到哪里、哪些证据还不存在**。

本卷的结论只有三句：

1. **88 项追溯行全部存在**（R1–R31、E1–E12、W1–W12、I-1–I-16、`GOV-POS-01`–`11`、H0a–H4），但**0 项取得目标语义的证据**。少数行有现状局部等价物，已在表中标注，不得当目标证据。
2. **V2–V6 全部未执行**。V0/V1 也只有「可执行的设计」，没有本次执行记录。`GAP-82-01/03/04/05` 的**设计面**已由 78-§13.5（E/W 主绑定）、80-§6.4 末（`TS-PORT-RES-01`）、80-§6.9（端口落点）、16-§11.3（27 个端口件 F-ID）关闭；`GAP-82-02` 的**资源评估与预算映射**也已由 `TS-PORT-RES-01`、`core/src/resources/` 与 `store/src/resources/` 闭合；**关闭的是设计，不是实现**——所有目标文件在 81 里仍标「目标-新增/未实现」。
3. **D1–D6、首版任务分布/组织/时间窗/阈值/用户、loopback/LAN、`PORT_VERSION` 承诺仍由制作人决定**。本卷只写工程基线与未决缺省，不代拍板。

**读者须知**：本卷的表格不是「覆盖已完成」的清单，而是「证据待取」的清单。任何一行都不能因为「有行、有 ID、有文件」被读成「已满足」。反过来，缺少真实文件或真实端口的行必须登记为缺口，不得用「同上」「略」「等等」掩盖。

### 1.4 五种证据状态（与 75-§0.1 的四态分开用）

75-§0.1 的四态描述**语义成熟度**：已有、库级存在/未接运行链、目标、未证。本卷另用第五个词描述**验证执行状态**：

| 词 | 含义 | 本卷写法 |
|---|---|---|
| 已执行 | 有可复算的原始证据（日志、记录、命令输出、夹具摘要） | 只有引用既有负向证据时才可出现 |
| 未执行 | 设计已写、没有本次或可引用的执行记录 | V2–V6 的默认状态 |
| 不适用 | 该层对该对象不回答任何问题 | 必须给理由 |
| 已登记 | 缺口、未证项或政策门已进入登记表 | 不等于已解决 |
| 已关闭 | 有证据且经独立复核 | 本卷不产生 |

**纪律**：语义上的「目标」不等于验证上的「未执行」；「未执行」也不等于「设计错误」。两者必须分开写，防止用「目标是完整的」冒充「已经能跑」。本版新增一句：**「设计已闭合」也不等于「实现已存在」**——`GAP-82-01/03/04/05` 属前者，其目标文件在 81 中仍标未实现。

### 1.5 引用与不引用纪律

1. 引用格式统一为 `卷-§节` 或稳定 ID；**不使用绝对行号**。行号只在 81 附录内部作为现状锚点时出现，本卷不复制。
2. 每个 R/E/W/I/G/H 行必须能指出至少一个真实 `F-*` 文件；若实现落点不存在，必须同时写 `GAP-82-*`，不得伪造 `F-*`。
3. 每个 E/W 行必须写明其**主绑定**（78-§13.5，**恰一个**）；不得把 55 条（R+E+W）合并成「所有 profile 共同必做」。本卷按 76-§9.4 的铁律：一个 profile 只承担 R1–R31 全部 + 它**声明**的主绑定所覆盖的 E/W。78-§13.5 的交叉引用只作补充，**不产生第二主归属**。
4. 任何「未知但合法」的外部状态，不得写成 `Err(unsupported)`；按 78-§9.6 与 80-§6.6 的 `Ok(unverified)` 处理（见 §2.9、§12.7）。
5. 任何「当前项目测试绿」只能证明当前回归，不得写成目标设计证据（见 §13）。
6. 记录面一律写 `append(input: RecordWriteInput)`；凡出现 `append(envelope)` 形状的用例，按结构性不可实现判负（80-§6.3）。

### 2.3 V2 行为契约（独立 workspace 的真实行为）

V2 是本卷的核心，也是最容易被伪造的一层，因此把边界写死。

**独立 workspace 的定义**：

1. 不在开发主仓的工作区；每个用例一个独立目录、一个独立台账文件、一组独立端口、一棵独立进程树、一条独立本地 socket。
2. 时钟、ID、随机、外部应答全部固定注入（`REC-CASE-02`）；不得读宿主当前时间、不得随机生成 ID。
3. 从冻结夹具装载；夹具摘要先记录，运行后不得改夹具。需要改预期时，新夹具 + 新用例版本 + 变更记录（76-§9.5、72-§2.3）。
4. 外部边界（平台、CLI、DSH 会话、秘密供给、socket 对端）可以用进程外替身（`cannedExternal`、fake CLI harness、fake `SecretProvider`、fake `PeerCredentialVerifier`）；替身只替代**外部端口**，不得替代内部决策、记录、事务或状态机。
5. 内部逻辑必须真跑：Node 24 起真实进程，走真实事务、真实 SQLite、真实端口实现；不得在同一进程内 monkeypatch 内部函数来「制造」结果。

**V2 的接口前提（本版按 80 现行正文重写）**：

| 记录读 | `RecordReader.payload(ref)` 四态：`Ok(undefined)` **只**表示该信封无载荷（无 `payloadRef`）；无权读该信封 ⇒ `Err(rejected_forbidden)` + `subcause:'payload-not-authorized'`；摘要不符 ⇒ `Err`（`payload-digest-mismatch`）；不可读 ⇒ `Err(unavailable/STALL, 'payload-unreadable')` | 把「无载荷」「无权」「读不到」压成一个 `Ok(undefined)`；靠 `ref` 绕过 `knowledgeScope` |

**正断言**（每条 R/E/W 至少各一次）：

- 合法动作产生预期记录（`REC-*` 的 `recordType` 与 `recordId` 可查），整封与载荷字节可往返；
- 状态迁移是 T01–T26 中的合法边，十态不混用；
- 应拒动作被拒，且拒绝带 `failure`/`category`/`subcause`（77-§11.1 的 14 类，不改字面量）；
- 禁止副作用未发生（越权写、秘密泄露、未授权承诺、历史改写、重复外部副作用）；
- 失败能到具名接收者，带期限/复审与出口；
- 资格、授权、执行配置、验收未被互换；
- 外部影响、资源、义务实例、未兑现承诺入账；资源占用缺省时给 `gaps` 且不当「充足」；
- 重开走独立受理，结清有独立判断，不由接受推出；
- 重试/替换/重开/迁移后身份、来源、责任、修正链可核对。

**反断言**（必须同时跑）：

- 同一 `idempotencyKey` 重放不产生第二次外部效果；
- 超时后不自动重试直写，先对账；
- 崩溃后未知保持 `unknown`/`gap`/`conflict`，不默认 `observed`；
- 无授权/无任职/无合同的调用被拒；
- 平台未知但合法的状态不改写成 `Err`（见 §2.9）；
- 载荷改一字节 ⇒ `payload-digest-mismatch`，且库内零行新增；
- `append` 后 `verifySealed` 过的 wkey 其 nonce 仍可用于真实写（不得撞 `replay`）；
- 投影 `since` 与 `asOf` 同给 ⇒ `projection-source-invalid`。

**V2 判负清单（出现任一条，本轮 V2 不成立）**：

1. 只证明 `import` 成功、类型检查通过、函数被调用；
2. fake 全绿但未起真实进程；
3. 进程内 monkeypatch 内部函数；
4. 用 LLM 补全裁判或补全预期；
5. 只跑正例，不跑 `negativeVariants`；
6. 只断言最后状态，不断言 `forbiddenSideEffects`；
7. 运行后改夹具或改预期；
8. 用现有 `mise exec -- bun run test` 绿当 V2；
9. 用单测覆盖率当行为契约；
10. 把「真实进程跑通一次」外推到其他版本/宿主/任务分布；
11. 用 `events` 表或 `daemon_kv` 冒充记录事实面；
12. 用 `append(envelope)`、`RecordReader.get` 的 `Ok(undefined)` 语义混用等**旧接口形状**当目标形状。

**证据**：运行日志（含版本头与夹具摘要）、记录 ID 清单、`commitSeq`/`proofRef` 对、状态快照、禁止副作用检查结果、退出码。证据要能让未参与者复算；不能只给「通过」二字。

**不能证明**：模型真实能力、外部价值、其他宿主/版本、长期自治。

**失败停止与恢复**：任一 R/E/W 红 → 停止该批次，不修夹具、不改断言；修实现或修主卷后**全量重跑**（含已绿项），防止回归被掩盖。若是设计缺口（对象/端口/文件不存在），停止并登记 `GAP-82-*`，不得在测试里绕开。

### 2.4 V3 跨实现互操作与独立验收（两件事，分开判）

| 子项 | 回答什么 | 输入 | 证据 | 不能证明 |

| V3-INT 互操作 | 两个实现能否读写同一公司定义包、规则档、记录交换，并报告语义损失 | 第二实现；同一冻结夹具；`DEF-CONF-01` 与 `REC-LOSS-01` | 双向导入导出记录；逐项 `converted`/`unconverted`/`differences`/`lossRefs`；双方对同一 R 的判定差异 | 产品功能一致；所有语义等价；性能 |

**V3 的额外前提（本版）**：交换面要能比对，`semanticDigest` 必须跨实现一致；该条**未证**（`GAP-82-06`，JCS 仍 `vectors-published`、只有 7 条公布向量，无实现运行记录）。因此 V3 在多实现跑通前，只能声称「同实现内可比」。

**V3 的停止条件**：只有同源 fork 却声称独立验收 → 立即降级声明；发现两实现对同一 R 的判定冲突 → 记入「规范歧义清单」，回写 76/77，不得由 82 裁定谁对。

### 2.9 未知但合法的外部状态：`Ok(unverified)` 规则

这是本卷新增的**验证口径**，不是新架构；其类型面与行为面已由 78-§9.6、80-§6.6 `TS-PORT-BIND-01` 与 BIND-01 三层归属（`F-contract-port-binding` 为唯一形状源、`F-daemon-platform-binding` 为唯一宿主、平台包三纯函数）定义。

| 输入 | 必须返回 | 必须落记录 | 禁止 |
|---|---|---|---|
| 平台状态非空、合法、但不在映射表 | `Ok({platformState, verification:'unverified', workStates:[], unmappedBehavior:'observe-unmapped'})` | `REC-OBS-02`（观察缺口，一等观察；**由消费方写**，不是 `mapState` 写） | `Err(unsupported)`；映射到最近已知状态；丢弃原值；静默 |
| 平台状态为空串/畸形 | `Err(rejected_precondition)` | 拒绝审计（绑定配置/数据缺陷） | 用 `Ok(unverified)` 掩盖；用默认态兜底 |
| 已映射且可核验 | `Ok({verification:'verified', workStates:[...]})` | 视需要 | 把 `verified` 当授权/验收 |

**消费方禁令**（写入 V2/V4 断言）：`workStates=[]` 不得生成状态迁移、不得判验收通过、不得判结清；不得把平台 `closed`/`完成` 反推为 `accepted`/`settled`；推进路径读不到合法 `STAT-D` 就停在原地并报缺映射。原值必须逐字保留，视图显示未知，不得显示 0/空/绿。

## 十、迁移波次 MIG-01–MIG-07

### 10.0 全局规则

1. **波次不可跳**：每波必须出证据才进下一波；某波红则停在该波，不得“先做后面再回来补”。
2. **完整目标不裁剪**：D75-02 的完整目标不因首版发布而变成“可选”。受限实现必须标“不完整实现”、列 `REC-LOSS-01`、拒绝覆盖外事项；不得把整卷目标裁成首版默认可选。
3. **双写禁令**：没有互认围栏时**禁止并发双写**。过渡期只允许“旧写口 + 新读面”或“新写口 + 旧读面”；不得两个写口同时写同一事实源。平台/存储迁移走 `REC-AUTH-07` + 独占交接 + 迟到对账（`RUN-AUTH-03/04`）。

## 十二、探针顺序、78 全部 16 条与当前未证

### 12.1 批次规则

1. **先便宜、后真机**：能在进程内/独立 workspace 用冻结夹具证明的，排在真机前；真机（DSH/Matrix/Taiga/YouTrack）排最后，避免把外部抖动记成实现缺陷（80-D10/D11）。
2. **每批出结论才进下一批**：某批无结论（不是“红”，而是“没跑出可判定的观察”）则停，不得跳批。
3. **负向与正向同权**：只测“能用”不测“不能用”，该探针不算完成（78-§13.1）。
4. **权限差分与秘密差分单列**：不得合并成“安全通过”。
5. **探针通过不升为能力证明**：只升到“该版本、该形态、该次观察”。
6. **证据格式**照 §3.3；每条探针一个 `EVD-*`。

## 十三、当前事实与命令口径

### 13.1 标准命令

〔事实〕本仓当前的标准验证命令是：

```bash
mise exec -- bun run typecheck
mise exec -- bun run test
```

`typecheck` 等价于 `tsc --noEmit`；`test` 等价于 `bun run guard:boundaries && vitest run --passWithNoTests`（`package.json` 的 `scripts`）。`guard:boundaries` 单独运行时为 `node scripts/guards/boundaries.mjs`。

### 13.2 这些命令证明什么、不证明什么

| 命令 | 证明 | 不证明 |
|---|---|---|
| `mise exec -- bun run typecheck` | 当前工作树的 TypeScript 类型自洽；strict/可擦除/NodeNext 配置在当前代码上成立 | 文档引用正确；运行时行为；目标设计可行；V0–V6 任一层 |

| `mise exec -- bun run guard:boundaries` | 当前依赖方向与尺寸阈未越界 | 新增边是否合理；目标拆分是否已完成 |

**明确禁止**：把上述命令绿写成“目标设计已验证”“V2 已跑”“跨实现可用”“真机通过”。它们只证明**当前项目回归**，不证明目标设计。
