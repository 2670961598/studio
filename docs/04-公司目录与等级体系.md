# 04 · 公司目录与等级体系（公司 = 一个 git 目录）

> 依据：制作人 2026-10-15 定调——公司配置外置、一公司一目录、git 管理天然带历史、
> 2-9 级全面设计、报表逐级聚合、AGENTS.md 系统提示词、监控与概览分端口。
> 本文是 Studio Next 的核心数据契约之一，实施前逐节过制作人审核。

## 一、总模型：框架不变，公司 = 一个目录

- **代码（Studio Next 仓）只含框架**：调度、适配器、网关、面板引擎、契约
- **公司 = 代码外部的一个目录**，git 管理（天然带历史/审计/回滚），路径任意指定
- 框架启动时挂载公司目录：`studio-next serve --company /path/to/acme-corp`（可挂多个）
- 分发形态：给别人 = 框架包 + 公司目录模板；我们自己的公司目录永不出本机（§10 公私边界）
- **配置分两层**：框架级配置（外置 config home：`agent.yaml`=CLI 工具、`gateway.yaml`、`models.yaml` 价目表等）＋ 公司级目录（本文）

## 二、公司目录结构（契约）

```
<company-root>/                  # git 仓，代码外置
├── org-config.yaml              # 公司组织配置：名称/使命/等级/等级分布/账号映射/部门索引
├── charter.md                   # 公司章程（基础规定，改它=9 级批示）
├── README.md                    # 公司自述（使命/当前方向/战役）
├── departments/
│   └── <部门名>/
│       ├── config.yaml          # 部门章程/规定/主管/职能/泳道/汇报线
│       ├── people/
│       │   └── <工号>.md        # 人事档案（front-matter+六节，见 01-C2）
│       └── departments/         # 子部门（嵌套深度=部门层级，最长到 9）
├── reports/
│   └── <节点路径>/
│       └── <date>-<type>-<节点>-<一句话总结>.md
├── docs/                        # 公司文档库（规范/知识/案例）
├── prompts/                     # 公司级提示词片段（L1 层内容源：使命/方向/战役）
└── .studio-next.yaml            # 挂载元信息：schema 版本/挂载时间/最近校验
```

**规则**：
- 部门领导配置 = 该部门目录的 `config.yaml`（leader 字段指向工号）；部门成员 = `people/` 内档案
- 部门嵌套深度 = 该部门层级；**9 级是最长链，不是每个部门都要到 9**
- 一切内容（章程/部门规定/人事/报表）都在目录里，网页按约定读取——**目录即 API**
- git 历史 = 组织变迁史；每次人事变动/章程修改 = 一次 commit（daemon 唯一写入者代写，挂单据号进 commit message）

## 三、报表体系（逐级聚合到制作人）

> 2026-10-16 制作人定调（D9）：**一切唤起都是定时任务，挂在部门下**——报表岗、财务审查、
> 人事审查、项目审查、升级审查……全部是部门名下的定时岗，公司可自行增删调整，
> 写成极强拓展性的通用模型，不在代码里写死任何岗位。

**约定文件名**：`<YYYY-MM-DD>-<type>-<节点>-<一句话总结>.md`，front-matter：`{time, type∈daily|weekly|monthly, node, level, author}`。

> 2026-10-22 增补（130-提案 P4·批示⑥ 全批）：type 三档（daily/weekly/monthly）为**节奏档**；
> 另设 `perf-weekly`＝部长绩效周报专用值——承载绩效五指标（闸过率/打回/完成时延/工时成本/
> 证据完备度，口径冻结见 130-提案 §6.6，**caliber 版本化 F2-08**，节点=部门 path，报表行
> 落 reports 表值域）。perf-weekly 不占节奏档位、不替代 weekly：月报/周报仍是逐级聚合的
> 经营叙事面，perf-weekly 是台账复算的绩效账面（零自评，只投影不裁决）。

| 层 | 谁写 | 频率 | 内容 |
|---|---|---|---|
| 叶子节点（部门/岗位） | 各级执行 agent（1-3 级岗位） | 日报 daily | 干了什么/卡在哪/明天计划 |
| 中级部门 | 部门主管（或主管岗 agent） | 周报 weekly | 汇总叶子+进度+成本+风险 |
| 公司 | 公司负责人（宰相型） | 月报 monthly | 经营五节（公司级/部门级/人事变动/项目/方向） |
| 制作人 | 框架聚合 | 实时+月度 | 各公司月报汇总成 `总览.md`；随时看网页 |

**定时岗通用模型（D9）**：每个定时岗 = 公司目录里的一条配置
`{id, dept, cron, 岗位, 等级, 任务类型, 模型档, 预算帽, 输出}`（勘误 2026-10-17：原字段集漏列
id/dept——id=装载进 ScheduledJob.job_id 的主键、dept=挂靠部门（缺省根部门）——依据 company jobs
装载单映射表 packages/company/src/validator.ts OrgJobSchema 与模板实形），挂在所属部门节点下；
报表生成、财务审查、人事审查、项目审查、惊动预算检查、升级审查……都只是这个模型的实例。
公司可自由增设审计/审查类岗位（新岗位=新定时岗配置，走批示流后生效）。
- 聚合方向：**叶子 → 部门 → 公司 → 总览**，每层只读下层的文件按约定归并，不跳级
- 事实数字从 SQLite 台账取，文字由负责 agent 写（零自评指标）
- 网页按 `{node}/{date}-{type}` 约定直接渲染，不需要额外 API

## 四、公司等级体系（2-9 级完整设计）

**公司从 2 级起步**（1 级=1 人不成公司）；**agent 等级仍是 1-9**（1 级=最末端执行者）。
升级由**宰相定时审查**（月度定时岗）提议 → 会签 → 制作人终验。

| 等级 | 形态 | 规模参考 | 推荐部门（默认框架） | 升级触发（建议阈值） |
|---|---|---|---|---|
| 2 | 班组 | 5-8 agent | 不设部（或 1 执行部）；财务人事=负责人兼 | 日均在途单>8；泳道排队>2h；日 token 超阈 |
| 3 | 小团队 | 15-25 | 工程/质量/情报；综合岗（财务人事） | 单部门排队常态化；质量返工率>30% |
| 4 | 团队 | 40-80 | 工程/质量/情报/**人事财务（合设）**（宪章 §12.6：4 级起设人事） | 人事财务岗满载；跨部门单占比>25% |
| 5 | 部门化 | 100-250 | 工程/质量/情报/人事/财务/**对外部**（GitHub 形象/API/合作） | 财务独立核算需求；对外交互量超阈 |
| 6 | 多团队 | 250-600 | 工程按项目群拆分/质量/情报（升战略情报）/人事/财务/**审计合规** | 事业部化需求；审计压力 |
| 7 | 事业部 | 600-1500 | 每项目=事业部；集团职能：人事/财务/审计/情报/战略 | 集团化需求 |
| 8 | 集团 | 1500-4000 | 多事业部；职能层级化（部→中心）；平台泳道群 | 控股化需求 |
| 9 | 控股 | 3000-10000 | 子公司群；控股职能（战略/资本/审计）；制作人直管 | 上限 |

- 每级的默认部门框架是**推荐模板**，制作人逐个审核（做的时候审），各公司可裁剪
- 触发阈值是可进化资产（走进化管线调整）；宰相审查输出=升级建议单，不自动升级

## 六、提示词落地：AGENTS.md（持久指令化）

制作人洞察正确：普通提示词会被 auto-compact 遗忘。落地方式：

- 出工时把分层内容（L0-L5，见 01-C2）**组装生成为 `AGENTS.md`**（生态标准名，
  codex/dsh/kimi 实测原生读取；compact 后项目根指令文件会从磁盘重注入——抗压缩成立）
- **落点规则（复查 B5 修订）**：优先走各家用户级通道（$KIMI_CODE_HOME / $DSH_HOME /
  $CODEX_HOME 的 AGENTS.md；claude 用 `--append-system-prompt-file`，且需 ≥2.1.277 才原生读
  AGENTS.md——适配器须做版本能力探测，不达标明报回退）；若落仓内工作区根，不得覆盖仓内
  已有 AGENTS.md——改名或先备份，并写入 `.git/info/exclude`（不入项目仓红线不破）
- 文件标记"生成物勿手改"，每次派发重生成；分层指纹照常记账（C2-08）

## 九、公司目录规范（E1-E3 已定稿，2026-10-16 制作人拍板）

0. **模板与建议，不写死**：目录里的一切——目录结构、部门模板、报表约定、等级映射、
   定时岗配置——都是框架提供的**默认模板**，公司可以覆盖任何一项。
   框架代码零公司特定硬编码；合法性校验只校验"结构合法"，不强制"内容同款"
1. **公司目录 = 外置 git 仓**：与框架代码完全分离；V4 框架本身在全新独立目录开发（不混现 Studio）
2. **两种得来方式**：框架初始化（`studio-next init <dir>` 从模板生成）｜ 挂载现成目录——
   框架启动前**校验合法性**（schema 校验：org-config/目录结构/必填文件齐全且合规范），
   合法才可运行；**校验不合法给精确错误**（文件:行+修法）
3. **可移植**：公司目录 copy 到任何机器即可直接运行——一切公司相关都在目录内，无外部隐式依赖
4. **前瞻性纪律**：目录规范是契约级资产——定稿后不轻改；必须改时走批示流 + schema 版本迁移
   （migrate 脚本随框架发布，迁移由 daemon 唯一写入者执行、挂单留痕、可 git revert）
5. **git 操作纪律**：daemon 是公司目录唯一写入者（人事变动/报表/配置落盘都挂单 commit）；
   制作人与主 PM 可直写（受控例外）；远端镜像私有或纯本地，**永不 public**（红线）
