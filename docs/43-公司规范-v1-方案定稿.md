## 一、公司包与传播：git 网址即公司

- **一条命令安装**：`studio-next company add <git-url> [名]`——框架克隆到本地工作目录
  → **导入内容、重建本地 .git**（分发仓不带钩子等活性元数据，用户无感，见附录 A-2）
  → schema 校验 → 平台字段 provision → **建 .AIWS 员工工作区树（§五）** → 初始化完成
  即可开工。
- **同构支持**：本地路径 / tarball（离线场景）与 git-url 走同一条导入管线。
- **版本与升级**：公司包=git 仓库即天然版本；manifest 记 `schema` 版本；升级=拉取新
  版本走同一导入流 + 迁移钩子（store 已有 schema migrate 先例）。
- **传播性载体**：`templates/` 提供多行业示例公司包（互联网公司/游戏公司/内容工作室
  等，见 §三），拿来即改即用——规范的扩散靠示例不靠说教。

## 二、组织结构 schema：公司的骨架（纵向+横向）

`org-config.yaml`（结构已在运行中验证，本规范将其冻结为契约）：

- **纵向=等级**：company.level 2-9 锚定权限与模型档；level_distribution 定分布；
- **横向=部门**：departments 树（parent/leader/lanes 泳道/functions 职能）；
- **人事**：people（id/name/login/level/dept/role/skills/executor）+ 档案正文
  `people/<工号>.md`（属性面=自由字典，进提示词；行为面=插件绑定，见 §四）；
- **定时岗**：jobs（cron/role/budget/output 等，形状闸见 schema）；
- **行业差异落在资产不在 schema**：互联网公司与游戏公司用**同一张表**，差异全部表达在
  prompts/ 与 charter/（§三）——这是「规范少、上限高」的关键取舍。

## 三、提示词分层规范：每个员工收到什么

- **L0-L5 既定分层**（mission → company 战役 → dept 配置 → person 档案 → lessons →
  tools）→ 组装为 AGENTS.md + 任务书 + 分层指纹——本条直接冻结现行装配为契约；
- 公司包 `prompts/` 目录为提示词资产位；**行业模板包**（templates/）是主要传播载体：
  同 schema、不同资产，下载即可开一家「游戏公司」「互联网公司」；
- 字段分类铁则保留：给模型读的文本（自由）与给引擎执行的声明（schema 严格）分字段，
  不混装。

## 四、依赖清单与插件绑定：员工的行为面（本版新增主特性）

- 公司包提供 **`dependencies.yaml`**：**属性值 → dsh 插件**映射，支持版本号与来源：
  ```yaml
  # 示意
  bindings:
    - when: { attr: role, is: frontend }
      plugins: [{ name: dsh-web-test, version: ^1.2 }]
    - when: { attr: dept, is: 研发部 }
      plugins: [{ name: dsh-git-flow, version: 2.0.1 }]
  ```
- **框架替他安装**：onboard/初始化时读取依赖清单，缺的插件自动安装到本机 dsh 插件库
  （安装动作对制作人可见、可确认）；属性决定插件开关——员工档案属性命中即启用；
- **高等级公司特权**=更大的插件库配额（既定设想，level 锚定）；
- **热重载**：插件增删随公司配置热重载（dsh 插件 insert 铁律既定）；
- 插件可带内容寻址（name+version+hash）：**自动安装的校验顺带就是完整性保障**——
  功能与安全一体，不增加使用负担；
- **公司包内允许的代码只有一种：dsh 插件**（`plugins/` 目录）；其余一律是配置/提示词/
  架构文本。

## 五、员工工作区 `.AIWS`：组织镜像，建司即建，派发权限圈（制作人口谕）

> 之前每个**单据 attempt**有独立 workspace（证据隔离），但**员工没有常驻的家**。本节
> 把家建起来：员工在自家文件夹里可以做任意事（工具/笔记/进行中的工作/自己的 git 仓）。

- **位置与形态**：公司根目录下 `.AIWS/`（与公司 git 目录、var/ 平级，**不进 git 目录**
  ——保持 daemon 唯一写入者纪律与发行件纯净）；
- **组织镜像**：`.AIWS/<部门路径>/<工号>/`——部门层级完全镜像 org-config departments
  树（path/parent），叶子=people 逐个工号的文件夹；公司目录里 people/<工号>.md 是
  「档案文件」，.AIWS 里对应位置是「工作文件夹」——一文件一文件夹，一一对应；
- **建司即建**：init / 导入（§一）时按组织结构一次性建好整棵树；人事增删随热重载
  增量同步（新员工得新文件夹，删员工文件夹归档不删）；
- **监听排除**：`.AIWS` 与 `.git`/`.DS_Store` 同款被内容指纹与文件监听排除——员工在
  自家文件夹里的任何活动**不触发**公司配置热重载、不触发批准指纹漂移；
- **派发权限圈（阶梯）**：worker 派出时权限固定在其员工文件夹内——
  ①**cwd 圈定**（现状已有）：工作目录=员工文件夹下单据子目录；
  ②**写域圈定**（本规范新增目标）：macOS seatbelt（sandbox-exec）配置文件落盘可写
  白名单=员工文件夹（+指定产出位），读取按需放行——「权限固定在文件夹内部」的机制化；
  ③完全沙箱（远期，随 confinement 路线图）；
- **单据证据位**：每单 attempt 在员工文件夹下开子目录
  `.AIWS/<部门>/<工号>/tickets/<单号>/att<N>/`——收割四要件（终态/非空输出/REPORT
  落盘/闸门 exit=0）在该子目录断言，证据纪律不变；deliverables 从该处收账。

## 六、executor 能力面：dsh 为核心，降级提前说好

- v1 **唯一保证面=dsh**（八类事件流/steer/followup/inject 三原语/插件面全套）；
- claude/codex/kimi 等其他 executor 后续按同一契约适配；
- **提前声明**：非 dsh executor 下插件功能不可用——依赖清单同时是一份**能力声明**，
  onboard 时明示「此公司在 X executor 下损失哪些能力」，用户知情选择；
- 公司包 `requires.executor` 只声明需求（name+min version+capabilities），**解析权归
  本机制作人**（不携带命令路径/端点）。

## 七、平台面：本地增强，发行基本功能

- **本地**：我们（及任何用户）可改 Taiga/Matrix 源码自用——开源（MIT 仓）+不托管
  前提下许可证义务面干净（docs/46 路线 A 判定）；
- **发行**：编排引用官方镜像，对外只保证**基本功能**；本地补丁不随发行件走；
- 提前说好（写入发行说明）：平台增强=用户自留地，发行版不承诺。

## 八、⑤新增机制 spike（v1.1 相对 v1 的增量验证面）

原 v1 十条机制已全部 spike 验证（docs/44，双轮 1490/1490）；v1.1 新增三项须 spike：

1. **git-url 导入流**：克隆 → 剥离活性 .git → 重建本地仓 → schema 校验 → 建平台字段
   → **建 .AIWS 树** → 初始化全链（含升级=再次导入幂等；.AIWS 与 .git 的指纹/监听
   双排除负断言）；
2. **依赖清单自动安装**：dependencies.yaml 解析 → 属性绑定求值 → 插件安装/启用/
   热重载全链（含版本解析与缺失源的处理）；
3. **员工目录写域圈定（seatbelt 原型）**：worker 子进程在 sandbox-exec 配置下运行，
   断言可写=员工文件夹、越界写被拒——「权限固定」的机制化证明。

判定纪律不变：良性示例包全链绿 + 各机制端到端证据；「修到能跑」=不过。
