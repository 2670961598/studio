## 〇、先固定四个否定式

1. **公司不等于目录，目录不等于公司全部。** 公司定义可以纯配置传播；运行公司还包括历史、
   承诺、证据和未决责任。丢掉后者只复制前者，是新建或分叉，不是无损失迁移。〔结论，63-I-10/I-16〕
2. **能力不等于权，框架不等于责任主体。** 框架可以校验、执行、记录和提示，不能仅因自己
   运行就取得批准、验收、恢复、修宪或清除记忆的合法权。每个决定须能追到责任位置与授权。
3. **连接不等于理解，记录不等于真实。** MCP、A2A、CLI、git、SQLite、签名或仪表盘都可以
   成为实现部件，任何一个都不自动提供公司语义、事实真实性或独立验收。
4. **可替换不等于无条件热替换。** 更换执行体、平台或框架时，资格、在途工作、写互斥、
   历史与承诺必须连续；做不到时明示不能并走暂停、交接或终止，不得静默降级。

因此，本抽象的最小核心不是一组产品名，而是：

> **以可版本化的规范表达权责与工作语义，以可核验的记录保存决定与后果，
> 以可替换的端口供给能力，以明确的授权把三者连接成可验收、可退出、可移交的公司。**

这给出的是自治的**技术必要条件**，不是自治已经可行的充分证明。

## 一、从根命题到六个技术层面

### 1.1 六层及其不可替代性

| 层面 | 保存/提供什么 | 可以版本化传播什么 | 绝不允许它冒充什么 |
|---|---|---|---|
| **规范（Specification）** | 核心语义、符合性判据、绑定规则、扩展规则 | 规范文本、语义 schema、公开用例、版本与迁移规则 | 某家公司的授权、某框架的实现事实 |
| **公司定义（Definition）** | 使命、边界、组织、岗位、治理位置、规则、能力与资源需求、权威需求 | 不可变的定义修订及其纯配置快照 | 已发生的履职、实际资格、真实可用能力、历史承诺 |
| **公司记录（Record）** | 决定、授权行使、任职史、工作、承诺、证据、结清、权威激活代次及其修正链 | 经授权的导出、来源证明与移交档案 | 可由当前配置任意改写的“现状” |
| **能力供给（Capability）** | 模型、agent loop、工具、插件、技能、隔离与验证能力 | 能力描述、能力包、依赖锁与兼容声明 | 任职身份、资格认定、授权、完成或验收 |
| **部署（Deployment）** | 宿主、路径、账号绑定、秘密引用、资源硬上限、候选权威端点 | 部署模板或示例，不传播真实秘密与本机状态 | 公司自我扩权、跨机器天然有效的信任、公司权威激活决定 |
| **观察（Observation）** | 事件索引、监控、报表、告警、检索、记忆候选与评价视图 | 投影定义与可重放程序 | 第二事实源、外部价值、独立验收、原始历史 |

**层间规则**：定义提出需求，记录保存事实与决定，能力使行动可能，部署限制实际可用面，
观察帮助发现和解释。任一层都不能单独证明另外五层。纯配置只修饰“公司定义包”，
不被偷换成“公司的一切都是静态文本”。

**权威归属不落在部署层**：定义声明权威需求，部署只能提供候选端点，选择哪个端点、何时
切换、以哪一代激活，是公司有权位置的决定并写入记录谱系（§3.3）。因此“这个环境只能连
这个平台”是部署事实，“这家公司的事实权威在这里”是公司决定；后者不能由前者自动推出。

### 1.2 规范自身的四层

| 层 | 内容 | 谁可以改变 |
|---|---|---|
| **核心语义** | 63 的概念、五环、I-1–I-16 及其不可削弱约束 | 只走上位元治理；公司或框架无权自行削弱 |
| **公司规范** | 上述语义的可交换对象、配置语义、记录语义、规则表达式求值语义与符合性判据 | 本纲层按 63-§6.3：**本项目当前由制作人终审**；变更须版本化、独立验证并留异议位置。未来公开规范的维护位置与许可须在发布前呈审（§10.2） |
| **绑定档案** | 某类平台、执行宿主、传输或存储如何承载共同语义 | 由绑定档案的维护位置按兼容规则独立演进，不得改变核心语义；本项目当前同由制作人终审，公开维护与许可同样待呈审 |
| **实现说明** | Studio Next 或其他框架的组件、性能、默认参数、操作方式 | 各实现自行治理，不能反向成为公司合法性的来源 |

不同框架可以共享前两层，选择不同第三层，并写出完全不同的第四层。只兼容某个 CLI 的
启动参数，不因此兼容公司规范；只通过 schema 校验，也不因此通过行为符合性。

本表不写匿名的“维护程序”。任何一层都有一个可指认的维护责任位置；位置空缺时，按
§3.3 的权威登记与 63-§6.3 的元治理处理，不能由“流程本身”取得修改权。

### 1.3 对旧“六名词三动词五不变律”的修订映射

`docs/08` 提供了重要的早期抽象，但不能原样承担 63–68 的语义。新抽象作如下**显式修订**，
不暗中宣称旧文档已经说过：

| 旧抽象 | 保留什么 | 必须修订什么 |
|---|---|---|
| Company = git 目录 | 公司定义可版本化、可传播 | 公司同一性还含历史、承诺与责任承接；git 只是载体 |
| Org = 部门树 + 工号 | 组织与身份需要稳定对象 | 还要表达岗位、任职、授权、治理、集体顶点、继任与清算 |
| Work = 单据 | 工作须有外部可观察记录 | 单据只是绑定；任务合同、承诺、验收、异常和结清各有语义 |
| Executor = 黑盒 | 执行实现可替换 | 执行能力不是任职者；须补资格、配置、出工段和能力缺口 |
| Ledger = 只增事件 | 历史与可重建投影 | 台账不天然是唯一事实源；来源、外部回执和修正链不可省 |
| Contract = 契约集合 | 契约必须显式、可检验 | 规范、任务合同、授权、承诺和验收口径必须分型，不能混装 |
| 派 / 批 / 变 | 调度、决定、变更需要治理 | 读、拒绝、记录、止损和移交也有语义；批须具体责任者与独立性 |
| 五条不变律 | 状态外置、证据、唯一写入、护栏外置、可重建 | 解释为跨实现的语义约束，不是某个 daemon 或数据库的同义词 |

## 二、核心概念的唯一技术主归属

### 2.1 映射纪律

- “主归属”指**技术对象的语义、结构与正常写入规则**的家；它不是概念定义权，也不是
  程序性规则的存放处。概念定义权仍只在 63（64-§2.1 明令上位概念不得重定义），册间
  分工仍只在 64。实操程序另引：任职者绩效 `65-§八`、组织绩效与整体资源 `66-§八`、
  问责/救济/重开 `66-§六`、价值复盘 `67-§十二`。本文只回答“这个对象在技术层由谁表达、
  由谁正常写入”，不把 65/66/67 的程序搬进来。
- 规范对象、实际关系与观察视图分开。例如岗位定义不等于任职记录，资格认定不等于能力探测。
- 一个技术对象不得兼任两种互相否定的语义。尤其 `completed`、`accepted`、`settled` 不可互换。
- 下表覆盖 `64-§2.1` 列出的全部 58 个上位概念；分册新增子概念也必须能回到这里。
  逐项对照见 §2.6。归属空缺、两个文档同时自称主归属，或把程序引用冒充对象归属，均视为映射不合格。

| 证据 | `Evidence Item / Evidence Bundle`，含来源、形成时间与可复核引用 | 72-§二 |
| 价值 | `Value Assessment`，含相关方反馈、反例与不可抵销的外部损害；不由内部绿灯派生 | 72-§4.4；复盘程序引 67-§十二 |
| 问责 / 救济 | `Accountability Case / Remedy Decision`，含申辩、裁判、执行与结清 | 72-§2.5；程序引 66-§六/§6.7 |
| 历史 | 只追加修正的 `Historical Record / Receipt / Correction Link` | 72-§一 |
| 记忆 | 个人、岗位、出工、组织四种 `Memory Record`，是历史派生物而非历史替身；四层的处置授权位置分开 | 72-§三、70-§3.4 |
| 变更 / 进化 | `Change Proposal / Authorization / Verification / Activation / Review`，各阶段不可互替；"授权进行验证"与"批准激活"是两道门 | 72-§5.1/§5.2、70-§6.1 |
| 终止 | `Termination + Settlement + Acceptance of Handover`；`liquidated/dissolved` 不得原身份重新激活，只能依法新设并逐项承继，历史不删除；停机或删除不是结清 | 70-§6.3/§6.5、71-§5.6 |

### 2.5 四处必须展开而不能只列一行的语义

**（1）权与禁止。** `Authority Policy` 在定义中声明“可用/保留/禁止/未覆盖”四态与范围、
条件、期限、父子关系；`Grant / Delegation Edge` 记录具体授予、转授、行使与撤回。自主、保留与
禁止是同一策略的分类视图，不是另一套权源。四态不得合并：未覆盖不等于禁止，也不等于已授权；
无能力不等于无责任；禁止优先于效率与紧急，紧急不解除禁止（63-§6.1）。
`Authority Requirement` 只描述事实域对权威存储/写入/导出/互斥等属性的需求（§3.3），不是内部权；
`Authority Activation` 是公司有权位置对事实域端点的治理切换，与内部权或能力激活批准均不同。
三者不得因用词相近而互相证明。

**（2）义务分型。** `Obligation Definition` 住在定义包，至少含承担位置、对象、触发、完成
口径、期限或复审条件、违约去向、可否转派与父链；`Obligation Instance` 住在运行记录，至少含
承担位置实例、触发时点、期限或复审点、完成证据、逾期状态与违约去向。义务不必是工作单：
“每月向监督者报告并公示异常”可以没有工单，但必须有实例、逾期可观察与违约去向；否则审计
会显示“无异常”，移交时也没人知道还有未履行义务（72-§4.2 观察面、70-§6.5 移交清单）。
完成口径可以定性，但判断位置、证据、异议与复审必须明确（70-§3.3）。

**（3）异常。** 异常是实际或潜在状态偏离事前口径、**缺少可比口径**、**口径本身失效**、来源
真实性存疑、**缓慢漂移**，或多个局部合规累积成**整体不可接受**（63-§6.1）。技术上它不只是
一张处置表（71-§5.4）：每个责任位置必须发现、接收或转交与其信息范围相关的异常；**无人认领
的异常按既有升级链进入最终责任位置，不得归给“框架”**；发现义务只要求合理注意与可检验的
监测，不要求全知，隐瞒与应发现而未发现必须区分。跨环趋势由 §五 指定的汇总位置发现与升级。
口径失效类异常不得被当作普通返工，也不得以“未分类按高档”一句代替处理。

**（4）一般责任。** “责任”在技术层不是一个标量，也不是一个角色名。一般责任（说明、接受
评价、承担后果）与运营、管理、共同、最终/对外最终责任各有关联对象与实质控制要求（§2.3）。
任何责任记录都要能回到：具体位置、当时权源、控制与止损条件、证据与救济接口；只有头衔而
没有控制、或只有控制而无交代位置，都不合格（I-7、I-9）。

### 2.6 覆盖核对与分册子概念

| 分组 | 覆盖的上位概念（64-§2.1 共 58 项） | 计数 |
|---|---|---|
| §2.2 | 公司、使命、边界、初始宪制公设、设立责任共同体、委托主体、受益者、受影响者、监督者、相关方、权、自主事项、保留事项、禁止、资源、信息、自治、顶点、最终责任、对外最终责任、实质控制、元治理、剩余裁量、例外状态、异常 | 25 |

| §2.4 | 意图、事项、工作、结果、验收口径、自检、独立验收、事后独立审计、证据、价值、承诺、问责、救济、历史、记忆、变更、进化、终止 | 18 |

## 三、共享记录语义与事实权威

### 3.1 记录不是一张万能大表

本文只规定可交换语义，不强迫所有对象共享一个物理 schema。需要交换或长期保存的对象，
按类型携带足够的下列信息；不适用的字段必须说明“不适用”，不能拿默认值伪装：

| 语义 | 回答的问题 | 反例 |
|---|---|---|
| 稳定标识与类型 | 这是哪个任职、授权、工作、出工段或证据？ | 以员工显示名或 CLI 会话号充当身份 |
| 公司与规范版本 | 按哪套语义、哪家公司解释？ | 新版解析器改写旧记录含义 |
| 定义修订与对象版本 | 当时生效的是哪一版？ | 用最新章程追罚旧行为 |
| 来源与形成方式 | 谁观察、签署、导入或推导出它？ | 把摘要当作原始事实 |
| 有效时间与观察时间 | 何时生效，系统何时知道？ | 补录伪装成当时证据 |
| 权源或形成依据 | 状态改变凭什么合法，观察凭什么可信？ | 安装成功被解释为允许使用 |
| 关联与因果 | 属于哪件工作、承诺、父决定或修正对象？ | 只有 correlation 没有具体决定依据 |
| 知悉范围与保留规则 | 谁能读、何时复审、如何处置？ | 为审计永久收集一切私密内容 |
| 扩展与未知面 | 哪些字段可忽略，哪些不理解就必须停？ | 未识别扩展被静默丢弃后仍声称兼容 |

原始字节、规范化语义摘要与数字签名是三种不同材料。摘要证明比对对象，签名证明某个
签名主体认可过某内容；二者均不证明内容真实、安全、合法或已验收。规范不在本阶段强制
某一种序列化、哈希、密钥或签名服务，绑定档案必须声明规范化与互操作规则。

### 3.2 决定、授权、凭据和租约四分

| 对象 | 作用 | 不能证明 |
|---|---|---|
| `Decision Record` | 某责任主体在某时点作出什么判断，理由、范围和异议是什么 | 决定者有权、决定已生效或决定正确 |
| `Grant / Delegation Edge` | 权从何来，目的、范围、条件、期限与退出是什么 | 实际有能力、凭据仍有效或已完成 |
| `Credential / Capability Token` | 向技术边界证明可执行一次受限操作 | 公司权源、员工身份、验收或免责 |
| `Lease / Fencing Token / Fencing Epoch` | 让旧写入者在切换后被拒绝，协调在途互斥 | 业务批准、授权延长、权威激活代次或工作结清 |

状态改变以“请求—权源检查—决定—执行—回执—观察”连接。每步都有自己的失败与证据。
请求必须能防重，写操作须带预期版本或等价并发条件；超时且结果不明时先对账，不能盲目重试。
批准与生效分开，计划与实际分开，回执与后续外部影响分开。

### 3.3 权威需求、候选端点与激活决定

权威归属不是部署属性，而是**三层分立的公司决定**。70/71/72 与任何实现必须使用同一组术语：

| 层 | 谁表达 | 内容 | 不能冒充 |
|---|---|---|---|
| **Authority Requirement**（权威需求） | 公司定义修订 | 每个事实域要求何种权威属性：单一写入、可导出、来源可核验、保留期限、跨框架可读、是否要求围栏 | 已有可用端点、已经激活 |
| **Candidate Endpoint**（候选端点） | 部署 | 本环境可提供的平台/存储/服务及其能力、限制与实测证据 | 公司已选择该权威、已取得公司决定 |
| **Authority Activation**（权威激活） | 公司有权位置 | 就某事实域选择端点、定义切换边界、签发激活代次、冻结旧写入者 | 部署者单方变更、框架自动继承 |

- **部署者不能单方更换权威端点。** 把某事实域改指另一个项目、另一个空库或另一台机器，
  是公司决定；部署只能提供候选与硬限制，并报告“本环境无法满足该权威需求”。
- **激活与代次写入 `Record Lineage`**：谁、依据何权源、何时、把哪个事实域从哪个端点切到
  哪个端点、前一端点如何停写、哪些在途事项被迁移。激活决定本身是 `Decision Record`，
  不能被“启动参数已改”代表。
- **`Activation Generation`（治理激活代次）与 `Fencing Token / Fencing Epoch`（技术围栏令牌/围栏代）必须分开。**
  前者是治理记录，回答“哪一代权威是合法的”；后者是技术防旧写机制，回答“这次写入是否来自
  已被替换的旧写入者”。围栏有效不证明业务授权，代次合法也不自动产生围栏；两者同名混用会
  让“代次已切换”被误读为“旧写者一定写不进来”。
- **互认围栏或共同仲裁。** 权威端点必须共同认可同一围栏，或由激活决定指定共同仲裁者；
  只有一侧围栏（各写各的租约、各自围栏自己）不构成互斥。**无互认围栏时只允许独占交接**：
  旧写入者停写并留下核验，新写入者才启动；不允许并发双写，也不允许“先并行跑一段再看”。
- 跨框架运行同一家公司时，双方必须采用兼容的权威档案**并**满足上述围栏条件；格式相同但
  各自持有本地租约，仍不构成可判定的单一写入。

每个权威事实域都要能回答：

| 项目 | 必须说明 |
|---|---|
| 对象与字段范围 | 哪类记录、哪个字段或哪段状态由它负责，边界是否重叠 |
| 权威需求与候选来源 | 按哪条 `Authority Requirement` 选中该 `Candidate Endpoint`，哪些需求它不满足 |
| 权威写入路径 | 哪个服务/主体经何授权写入，其他写入如何被拒绝或识别 |
| 权威读取与回执 | 如何读到一致版本、确认写入结果、发现外部直接修改 |
| 来源与活动记录 | 如何保留原始来源、游标、顺序、丢失和冲突信号 |
| 导出与重建 | 如何导出可供另一实现理解的记录，而非只导出某数据库私有格式 |
| 围栏与仲裁 | 用何种 `Fencing Token / Fencing Epoch`，跨端点如何互认，或指定了哪个共同仲裁者 |
| 故障与移交 | 如何防双写、冻结旧写入者、确认新写入者与处理不明结果 |
| 保留与终止 | 如何结清未决记录、保存历史、处理无法访问的外部事实 |

**同一事实域同一时刻只能有一个权威写入路径。** 多产品可以各管不同事实域，也可以有只读
镜像，但不得“双写后希望一致”。权威适配器离线时，按事项选择暂缓、只读、保全或经授权的
降级路径；不得把镜像悄悄提升为权威。

当前兼容档案可以继续把某协作平台作为工作流事实权威；可移植档案也可以选择其他权威绑定。
这是显式的**公司激活决定加迁移**，不是本抽象暗中完成的持久化变更，也不是部署者的环境
偏好。若某档案不提供互认围栏，则该事实域在跨框架期间只能独占交接。

### 3.4 历史、快照、镜像与未知

- 权威历史以追加记录和外部回执为准；修正追加指向旧记录，不删除旧事实。
- 配置快照是某修订的不可变视图，不是“所有历史都可不要”。
- 镜像须带来源游标、同步时间和差异；镜像新不等于事实完整。
- 没有记录时只能写“未观察到/未知”，不能写“未发生”；证据不足不能判接受，也不能伪造否定。
- 事实源不可访问、记录冲突或游标断裂时，必须标记受损并触发对账，不得用重启或重放清空。

### 3.5 规则与谓词表达式的求值语义

定性判断不要求机器化：使命解释、价值、尊严、信任等可以保留为“由具名位置作出、有证据、
有异议与复审”的判断（70-§2.2、§8.3）。但一旦把使命判据、边界、自主/保留/禁止、任务触发、风险分档、
验收条件、异常政策或授权范围写成**可求值表达式**，它就从文本升级为规范工件，须满足：

| 要求 | 含义 | 反例 |
|---|---|---|
| 绑定版本化 `Rule Profile` | 语言语法、算子集、类型系统、标准库与求值语义各有版本号，随规范发布 | 各实现自造 DSL，同一公司包在 A 合法、在 B 越权 |
| 确定且封闭 | 同一输入在同一 Rule Profile 版本下结果唯一；禁止宿主时间、环境变量、网络、随机、文件系统与模型调用 | 规则引用 `now()` 或部署环境，同修订在不同机器给出不同授权与验收结论 |
| 未知即拒绝 | 未知构造、未知算子、类型错误、缺必需字段一律拒绝并定位；不得默认允许、降级为真或静默忽略 | 解析器跳过不认识的条件后按“未违反”放行 |
| 激活钉版本 | 定义修订与权威激活记录同时钉住 Rule Profile 版本；升级走变更、独立验证与新激活 | 解释器静默升级，改变已批准规则的含义 |
| 共同用例 | 规范随版本发布参考求值行为与共同用例，供跨实现比对与拒绝行为对照 | 只有实现私有测试，无法判定两框架等价 |

表达式求值只产生“成立/不成立/拒绝”，不产生授权、验收、责任或价值结论。`Rule Profile` 是
独立版本轴（70-§5.3 已将其与核心规范、定义修订、绑定档案等并列），符合性声明须列出所支持
的 Rule Profile 版本与拒绝行为；跨实现交换定义包时，Rule Profile 不兼容即视为不能完整解释，
而非“尽力而为”。

## 四、组件与端口：框架能做什么，不能做什么

### 4.1 端口是责任边界，不是产品清单

| 端口 | 合法职责 | 必须拒绝/明报 | 可替换实现例 |
|---|---|---|---|
| **定义目录** | 读取不可变定义修订、校验引用、提供差异 | 把草案当已批准修订；忽略必需扩展 | 文件、HTTP、内容寻址存储 |
| **定义与权威登记** | 提交定义修订与差异、登记具名批准与激活代次、按决定冻结旧写入者、提供恢复点与谱系 | **自行批准修订或激活权威**；把部署者的端点选择当公司决定；用“已提交”代表“已生效” | 文件/HTTP 登记服务、治理服务绑定、人工/AI/集体决定适配 |
| **授权与决定** | 校验授权链、登记具名决定、检查禁配与独立性条件 | 代替责任者作批准；把 token 当权源 | 本地策略面、外部治理服务、人工/AI/集体决定适配 |
| **协作与工作记录** | 承载意图、工作、评论、关联、活动游标及平台回执 | 用评论塞入无权决定；不支持的流程静默降级 | LocalFile、Taiga、YouTrack、其他平台 |
| **执行能力** | 探测能力、制定计划、启动/观察/停止执行、报告真实缺口 | 把启动或执行完成当验收；虚构暂停/恢复/热更 | DSH、其他 CLI、远程 agent loop |
| **工作空间** | 提供受限读、写、产物、临时区和交接材料 | 以 cwd 代替隔离；默认读取宿主全部秘密 | 本地目录、沙箱、容器、远程工作区 |
| **产物与证据** | 保存不可变产物、证据引用、校验材料与访问边界 | 用日志自述替代实际结果；擅自清除证据 | 文件、对象存储、签名/透明日志绑定 |
| **历史与记忆** | 追加历史、读取授权范围内记忆、提交修正/清除程序 | 记忆覆盖历史；把个人记忆自动交给继任者 | 事件存储、文档库、检索系统 |
| **信任与秘密** | 验证来源、按授权短时提供秘密、吊销与审计使用 | 秘密入包/提示词/快照；签名即信任 | 本地密钥、外部密钥管理、人工信任锚 |
| **入口与通知** | 接收外部意图/反馈、发送通知、保存送达和来源证据 | 把消息自动当承诺；通知发送当对方接受 | HTTP、Matrix、邮件、其他消息通道 |
| **观察与基础服务** | 提供只读投影、时钟、标识、健康与资源观察 | 由监控直接改写事实；以在线率证明自治 | 面板、API、指标/日志系统、测试时钟 |

端口方法由后续绑定规范冻结；本文不要求每个端口都是一个网络服务。跨实现可交换的是
**语义、失败和证据**，不是强迫自己复制当前 TypeScript 接口。

### 4.2 每次调用都带的能力与失败语义

1. 调用方说明公司、身份/任职、工作、授权依据、预期版本和请求范围。
2. 提供方先声明实际能力与兼容范围；`unsupported`、`unavailable`、`unverified` 不得合并成成功。
3. 执行结果至少区分已接受处理、已执行、结果不明、被拒绝、失败、部分完成和取消。
4. 失败须返回可否重试、是否可能已有副作用、对账入口和证据引用；不得只给一句“未知错误”。
5. 降级必须说明失去哪项履职条件、由谁批准、影响哪些口径；无法补足则暂停、改派、拒绝或终止。
6. 任何异步通知都不能替代主动对账；收到通知不等于对方已作合法决定。

### 4.3 三类配置不得混用

- **公司配置**表达“这家公司希望如何合法履职”，由公司授权程序修改。
- **部署配置**表达“这个运行环境能提供什么、硬限制是什么”，由部署责任者修改。
- **框架配置**表达“这个实现怎样装配自身”，由框架运营者修改。

部署可以收紧公司授权，不能放宽；框架可以提供更强的校验，不能替公司作决定；公司可以
声明能力需求，不能要求部署交出秘密或宿主无限权限。三者差异须在启动与每次变更时报告。

**权威激活不属于部署配置。** 部署只能提供候选端点与硬限制（§3.3）；“这家公司的事实权威
在哪里、以哪一代激活”由公司有权位置决定并写入记录。部署者改环境、换路径或换项目，最多
产生新的候选端点，不产生新的权威。

## 五、五环如何成为架构闭环

五环不是五个微服务，也不是五次自动绿灯。每环都要有具名决定、外部事实、终态和失败出口，
并各有一个可指认的责任位置；位置空缺时按 §3.3/70-§3.4 的替补与升级处理，不由框架补位。

| 环 | 责任位置（技术接口） | 技术连接 | 必须留下的可核验材料 | 强制失败/退出 |
|---|---|---|---|---|
| **价值** | 意图受理、口径定义、验收、价值复盘者；承诺规则与相对方程序（66-§9.5 只提供规则，不代行） | 意图来源 → 受理决定 → 合同/承诺 → 工作与结果 → 验收/价值评价 → 校正 | 原始意图、合同版本、资源与外部反馈、接受/拒绝/终止及理由 | 越界、无价值、不可验收或承诺不可持续时，不得继续原路径庆功 |
| **权责** | 授权/禁配求值、问责与救济位置（66-§六）、独立记录位置；叫停与恢复必须是不同主体 | 定义授权 → 任职/禁配检查 → 行动与回执 → 质询/裁判 → 救济/结清 | 当时权源、实际主体、控制关系、申辩与救济结果 | 无权、冲突或争议须限制行动；撤回包括凭据、在途和承接 |
| **能力** | 资格认定位置（71-§1.3）、执行计划锁、能力退化汇总者 | 任务需求 → 声明/实测 → 资格认定 → 执行计划 → 分段履职 → 归因与重认 | 需求、实际能力缺口、资格证据、计划锁、替换与重认 | 缺能力、退化或成本失控须缩、换、外援、拒绝或停止 |
| **组织** | 结构所有者、组织评价者（66-§八）、继任与清算位置（66-§十二） | 使命分解 → 条件性结构 → 协调与资源 → 结构评价 → 交接/撤销/清算 | 结构存在理由、成本、空编、争议终局、承接确认 | 不得新增层级掩盖协调失败；整体不可持续须缩编或终止 |
| **进化** | 变更受理、独立验证者、激活决定位置、后验评价者（四者不可合并） | 历史/异议 → 候选 → 分类与授权 → 独立验证 → 激活 → 后验/撤回修复 | 候选差异、原判据、独立结果、激活代次、后验与残余影响 | 未批准或未验证不得生效；失败不得修低判据冒充成功 |

**跨环汇总**：公司级资源、能力退化、任务结构、外部影响和未决承诺必须能合并观察。
汇总视图的责任是把异常送到指定汇总责任者与最终责任/独立监督位置，不是监控组件自行定责。

- **整体资源责任者与跨环趋势汇总者不得由被汇总的业务位置单独兼任**；报告须直达委托主体
  或独立监督位置，不得等某一环单独越线后才承认整体异常（63-§4.6(8)、66-§8.2/§8.3）。
- 汇总位置必须有答复期限、复审/升级条件与终局；逾期按 I-11 升级，不能以“已通知”结案。
- 一环完成不关闭其他环；执行完成、验收接受、承诺兑现和公司清算尤其要分开。

## 六、十六条全局不变量的架构验收条件

| 不变量 | 技术抽象必须能回答 | 明确不能采用的捷径 |
|---|---|---|
| I-1 正当性先于效率 | 每个配置、能力和动作可追使命、委托或既有义务 | 因为成本低/插件已装就自动执行 |
| I-2 事实与来源先于叙事 | 原始来源、观察时间、修正与质疑有位置 | 摘要、hash、签名或“模型说”被当作事实本身 |
| I-3 结果过程代价后果同账 | 工作关联资源、返工、外部影响、残留和未兑现 | 只统计成功交付或 token 单价 |
| I-4 权责可结算 | 权与义务都有机器可引用的主体、范围、口径、期限和退出；义务还须有实例、逾期状态与违约去向 | 只有角色名或一句“负责”；规则写了义务但从不生成实例 |
| I-5 权与能力不冒充 | 资格、配置、授权、实测四维分别返回结论 | 能调用即有权，有权即能做 |
| I-6 授权不放大可撤回 | 父链、范围交集、到期、撤回和在途处置可检查 | 子令牌比父权更大，撤配置即算完成 |
| I-7 责任匹配实质控制 | 责任者可获得信息、资源、监督与止损位置 | 只给最终责任头衔，没有实际控制 |
| I-8 验收独立性与风险相称 | 独立分类、验收位置、证据与生效时序可核验；高风险/不可逆且影响重大者须在生效前完成独立验收；**紧急止损是该时序的唯一例外** | 同一会话/同一受益方自证；未分类走低档；把止损当追认或恢复 |
| I-9 主语与共同责任明确 | 每个“系统自动”都能展开为决定、执行、监督与异常承接 | 框架/部门/委员会成为无人负责的代名 |
| I-10 主体可替换而历史承诺连续 | 身份、出工段、交接、资格和历史可跨宿主核对 | 换 CLI 或账号就重置身份与禁配 |
| I-11 异常冲突无能必有去向 | 每类失败与异常（含缺口径、**口径失效**、**缓慢漂移**、**整体不可接受**）有具名接收者、复审/期限、终局和重开规则；无人认领按升级链进入最终责任位置 | 无限待批、永久暂停、重试至死、“等待框架处理” |
| I-12 自主不得自我扩张 | 保留/禁止优先，新事项默认保留，构成性规则受保护 | 解析新字段就获得新权，插件自行提权 |
| I-13 变更有权有证有后果 | 提案、分类、授权、验证、激活与后验分段；“授权进行验证”与“批准激活”是两道门 | 配置落盘即批准生效，回滚即抹除外部后果 |
| I-14 比例与反仪式 | 控制针对错误相关性和风险，有失效信号与成本 | 以多人/多 agent 数量代替实质独立 |
| I-15 外部性不可内部抹除 | 外部反馈、受影响者异议、停止与修复能进入流程；**不可接受、不可补偿损害的认定及其授权限度不得由公司或受益委托方单独决定，须依公共规则、事前合法约定的受影响者代理或独立裁决确认；无合法依据时不得作为可接受风险；争议期间不得抵销**（认定程序落点见 70-§2.5、72-§4.4） | 内部全绿抵销不可接受损害；公司自行把损害归类为“可补偿” |
| I-16 终止必须结清承接 | 在途、承诺、资源、信息、记忆、**外部关系**、救济与残余承接均有接收和核验；承接者失能或空缺时依预设规则再指定并公示，未完成前不得宣称清算完成 | 删除目录、停止进程或账号注销即清算；“无人可指定”消灭义务 |

这些判据可以被结构校验和行为用例支持，但不能全部化约为静态 schema。尤其独立性、外部
影响、价值与实质控制，必须保留有理由的判断和异议位置。

**I-8 的唯一时序例外**：63-§6.1 的紧急止损路由。仅当延迟将造成更大不可逆损害时，现场
责任主体可在预设紧急边界内先做保全与止损，立即留证、通知并接受事后独立复核。该先行
(a) 不构成对原高风险动作的追认，(b) 不等于恢复决定，(c) 不推广到普通高风险决定，
(d) 原动作本身仍须独立验收。无预设紧急边界时，只能采取不进入禁止或保留权限的保全与升级。
技术实现必须能把“紧急止损”与“已验收生效”“已恢复”区分记录（71-§5.5）。

| R31 自评低风险 | 66 | 70-§3.4 | 71-§5.2（按档执行）、72-§2.2（验收记录） | 独立风险/可逆性分类；未分类、存疑或争议按高档，交付方不得自评降档 |

## 八、跨框架符合性与最小互操作

### 8.1 “实现同一规范”至少意味着什么

| 层 | 必须符合 | 不足以证明符合的材料 |
|---|---|---|
| **语义** | 共享概念、状态/决定含义、失败与退出、默认保留及不可削弱约束；核心对象见 §8.3 | 同名字段、相同目录名、能读 YAML |
| **配置** | 读取声明的支持版本与扩展，拒绝未知必需面，给出可定位诊断；规则表达式须按 §3.5 钉住 `Rule Profile` 版本并拒绝未知构造 | 忽略陌生字段后“成功启动” |
| **行为** | 在共同反例和正常/失败路径上产生等价责任语义与证据 | 单元测试只验证自家函数返回 |
| **记录交换** | 保留身份、版本、权源、来源、双时间、未决义务和修正链 | 只导出当前快照或某数据库转储 |
| **能力协商** | 明报实际支持/不支持/未验证，降级不改变授权与验收 | 用“类 DSH”“支持 AI”做模糊宣传 |
| **迁移与退出** | 可冻结旧写入者、导出、核验接收、保留历史并停止继续影响 | 复制目录后删除旧公司即宣称迁移 |

具体 conformance profile 可以裁剪不必要**绑定**（如 DSH 插件、某平台字段、某传输），
但**不能裁剪核心对象、核心反例与记录交换语义**（§8.3）。例如不携带 DSH 的框架不必实现
DSH 插件，但若公司需要某项只有该插件提供的能力，它必须给出替代能力或明示不能，不能丢掉
依赖后仍宣称完整运行。框架不必支持所有可选组织形态，但遇到不支持的形态须拒绝激活而非
误解释。

**共同规范保证最小共同语义，不要求组织结构同构。** 部门数量、职级名称、岗位范式、权责原子粒度、
禁配具体配对和能力分带都是设计选择；不同公司可以合法地形成不同结构。跨框架需要互相理解的是
权源、责任、证据、工作状态、失败与退出，而不是复制同一张组织图（63-§三、§0.2）。

最小共同交换词表至少包括：`Authority Policy`、`Obligation Definition / Obligation Instance`、
`Grant / Delegation Edge`、`Position Definition / Holder Identity / Appointment Relation`、
`Capability Profile / Qualification / Execution Plan`、`Evidence Item / Assessment Record`、
`Memory Record`、`Exception Record`、`Authority Requirement / Candidate Endpoint / Authority Activation`。
这些名词是 §8.3 核心对象在交换面的**下限**，不替代核心对象、核心反例与记录交换要求；完整清单以
§8.3 为准。词表只规定语义，不规定各公司必须设置的岗位、部门、职级或禁配配对。
具体目录若用于交换，必须携带命名空间、稳定标识、版本、定义、来源、兼容条件与冲突处置；
未知必需目录不得静默忽略，未覆盖不得默认允许。57–60 的具体目录只可作候选模板资产，
不因数量或历史取得强制核心地位。

### 8.2 公开扩展而非私有后门

- 扩展具有命名空间、版本、必需/可选标记、权能影响和数据知悉范围。
- 不理解可选展示扩展可以忽略；不理解影响权责、证据、承诺、工作语义或秘密的扩展必须拒用。
- 私有扩展不自动获得跨框架语义；要成为共同规范须经过公开修订与用例验证。
- 扩展不得改写核心标识、把禁止改允许、把未完成改完成，或通过嵌套文本绕过扫描。
- 实现能力 advertisement（能力广告/自述）只描述实现，不是公司授予它的权力，也不是其
  内容已经安全验收。

### 8.3 强制核心符合性 profile 与辅助面

“符合规范”不能只等于“能读 schema”。规范随版本发布**强制核心符合性 profile**，其内容至少：

| 面 | 核心内容（不可裁剪） |
|---|---|
| 核心对象 | 公司身份/状态与定义修订谱系、记录谱系；相关方（含受影响者与代理/异议通道）；治理位置、拟任与实际任命；权与禁止四态、授权与禁配；**义务定义与义务实例**；承诺规则/具体承诺/公开承诺；岗位/任职/资格/执行配置与执行计划；工作合同、验收口径、验收与独立性（含定性判断的具名位置、证据、异议）；资源与信息；异常及发现/接收/升级；**四层记忆**；**联合组织与合并/分立**；终止、清算与残余承接；权威需求—候选端点—激活决定 |
| 核心反例 | **R1–R31 全部保留为共同核心反例**，任何 profile 不得以“可选”“本期不含”“不可脚本化”为由跳过；不符合即为不符合，不得改称“部分符合” |
| 补充反例 | 员工册 E1–E12、工作册 W1–W12（68-§3.3）归**绑定档案的用例集**，用于验证具体失败路径；它们不新增概念层，也不替代 R1–R31 |
| 记录交换 | 身份、版本、权源、来源、双时间、未决义务、修正链与结清状态 |
| 规则表达式 | 所支持的 `Rule Profile` 版本、拒绝行为与共同用例（§3.5） |
| 最低验证 | **V0–V4 是符合性最低层**（72-§7.1）：文本/结构、语义/权责、行为契约、跨实现互操作与独立验收（含记录交换）、迁移/故障/安全；V5 按绑定档案在真机核验；V6 是独立的现实自治评估，不进入“符合规范”的声明 |

- 符合性声明必须引用 profile 版本并列出排除项；**排除核心项即不得称“完整符合”**，
  只能称“不完整实现”并明示损失（72-§7.3）。
- 定性、独立性与价值判断不要求脚本裁判，但必须是可检验结构：由具名位置作出、有证据要求、
  有异议位置、有复审与记录；把定性验收留给“操作习惯”不算实现。
- **框架生成框架如要接管本公司运行，不只是“生成成功”**：须完成旧写入者冻结/围栏、导出核验、
  承诺与记忆移交、接收确认与迟到副作用对账（72-§1.4、§5.3、70-§6.3/§6.4），并以 V4 验证
  退出与回滚；否则只能作为候选或只读实现，不得宣称“可替换”。

**最小内核就是上表的核心对象、规则表达式与记录交换语义，不再另设较窄清单。**
**辅助面**包括定时唤醒、IM、面板、报表、缓存、快捷 CLI、指标聚合、推荐派工和自动学习。
辅助面可以提高效率，但不得绕过内核。

移除 IM 不应使权源消失；移除面板不应使事实改变；替换 CLI 不应使员工历史清零；移除某个
插件可能使工作无能，但不能把无权变成有权。反之，辅助面再丰富也不能补偿内核缺失。

### 9.2 参考实现必须保持的依赖方向

- 共同语义可以进入 contract；纯判定逻辑可进入 core；具体适配只依赖公共语义，不互抄实现。
- daemon/组合根负责把授权、工作、能力和事实端口接起来，不把跨域语义偷塞给某个适配器。
- `apps/boot` 是组合根，不是另一个权威状态机；监控/API 是读/入口面，不是旁路写入者。
- 现有机械规则以 `scripts/guards/boundary-rules.mjs:78-142` 为准；未来需要改方向表时，
  走工程提案与制作人审批，不能借“技术抽象”绕过。
- Node 24、Bun、TypeScript、SQLite、包数和端口只属于当前实现说明，不进入跨框架核心规范。

### 9.3 建议的目标装配，不绑定进程数

```text
外部意图/反馈       公司定义修订          能力包与宿主
      │                    │                     │
      ▼                    ▼                     ▼
 入口与来源核验 ──→ 授权/决定与工作治理 ←── 能力协商与资格
                           │                     │
                           ▼                     ▼
                    工作编排与开工门禁 ──→ 出工/出工段执行
                           │                     │
             ┌─────────────┴─────────────┐       │
             ▼                           ▼       ▼
      权威事实与回执                 只读投影     工作区/产物/证据
             │                           │       │
             └──────────→ 验收、问责、学习、结清与移交 ←──────────┘
```

图中的“授权/决定与工作治理”不是自动批准机，“编排”不是权责顶点，“投影”不是事实源。
箭头表示合法输入输出，不表示调用方可以越过网关直写。实际实现可拆成多进程，也可在单进程
内分模块；只要权源、写互斥、故障语义与证据等价，进程数量不构成核心差异。

“权威事实与回执”由哪一端点承载，是图中“授权/决定与工作治理”作出的 `Authority Activation`
结果，不是部署装配的副产物；把箭头改成“默认连本地库”即等于偷偷改变公司权威（§3.3）。

## 十、本阶段不做什么与呈审门

### 10.1 不做什么

1. 不定具体 YAML/JSON 字段、SQL 表、HTTP 路由、函数签名或 npm 依赖。
2. 不承诺当前 DSH 已支持运行期插件热插拔、任意 agent loop 切换或无损跨宿主续跑。
3. 不强制所有公司采用部门、职级、常驻员工、某一协作平台或某一数据库。
4. 不把 MCP/A2A/AGENTS.md、签名、hash、W3C PROV 或 OTel 当作现成的公司权责规范。
5. 不用逻辑闭合代替真实探针、互操作、崩溃恢复、安全与任务分布内的自治验证。
6. 不在本文决定规范/公司包许可证，不替相关方接受公开承诺，不自动发布任何配置或历史。
7. 不把当前实现缺的能力反向从理论删除，也不为迁就现状默许历史、承诺或独立性丢失。
8. 不要求所有定性判断机器化；也不把“写了表达式”当成“已获得授权或已通过验收”。
9. 不把“框架能生成另一个框架”当成“可替换当前框架”；生成物流程须另走迁移、围栏与接收确认。

### 10.2 本阶段必须呈审的选择

- 公司定义包严格纯配置，可执行 DSH 插件改为独立能力包；是否保留仅用于传输的聚合包。
- 权威档案由对象/字段显式声明：`Authority Requirement` 字段集、候选端点的能力描述格式、
  激活记录与 fencing 的互认方式，以及当前平台权威与可移植记录绑定如何分阶段共存。
- `Rule Profile` 的公开范围：语言与算子集、参考求值器与共同用例随哪个版本发布；哪些判据
  保留为定性判断。
- 规范、公司模板与实例公司内容的分层许可和公开传播条件；**当前维护位置是本项目制作人**
  （63-§6.3），公开维护程序与分层许可是未来呈审事项，不擅自预选许可证，也不预设“必然公开”。
- 强制核心符合性 profile 的版本号与声明格式（排除项如何披露）。

### 10.3 通过的含义

本组文档通过，只表示：

- 63–68 的必要概念有唯一、互不矛盾的技术承载；
- 纯配置传播、跨框架替换、工作失败和终止不再依赖口号；
- 当前实现与目标的距离可检验，后续 spike 和实现单有明确上位依据。

它不表示技术细节已冻结、当前框架已经实现目标，也不表示现实自治已经被验证；技术必要条件
的成立不构成现实自治的充分证明（72-§7.4）。
制作人批准后，仍须按 `docs/20` 完成具体提案、探索、独立验证和实现审查。

### 10.4 跨卷接缝判据

- 权威需求、候选端点、激活决定与围栏分属定义、部署、公司记录和技术互斥，部署不能单方换权威。
- 义务定义与实例、异常发现与接收、各类责任与贡献可分性都有明确对象，不能只存在于提示词。
- 能力声明、资格、执行计划、本次授权与实际生效分别举证；安装不冒充挂载，配置热重载不冒充在途热替换。
- 工作主类型、验收与恢复分档、紧急止损、结清与重开保持理论语义，不由平台字段或执行终态重定义。
- 四层记忆各有归属和处置授权，监控失效显示未知/受损，不成为第二事实源或匿名叫停者。
- 反例的治理主答归 `64-§四`，技术主承载归本文 §七；二者不能互相替代或借技术映射重新分配权责。
- 强制核心符合性、真实能力探针和现实场景自治评估分层，低层通过不冒称高层成立。

跨卷事实、审查发现、返修和验证证据统一见 `docs/73-技术抽象-现状对照与审查记录.md`，不在各卷
分别维护相互可能过期的审查状态。
