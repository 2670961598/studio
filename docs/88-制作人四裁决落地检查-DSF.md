## 二、最高行政层（N 个单元；三省只是示例）：R1 动笔前要钉死的 8 件事

“三省”是例子，不是规格。规范化为：**最高行政层有 N 个平级单元（N≥1），每单元一个头**；N=1 退化为单宰相/harness；N>1 老板直通各单元，不设唯一接口。N 不是现在要你选的数字；它是公司配置参数，默认 N=1，老板可按需增减。

| # | 必须回答 | 为什么 | 建议默认（供讨论，不是结论） |
|---|---|---|---|
| 1 | **N 的默认值与增长规则** | 不能写死 3；也不能每家公司都必须多单元。N 是参数，默认值和“何时增设”才是规范 | 默认 **N=1**；老板可按需增设；不设框架硬上限（由公司配置/管理跨度决定）；增设/撤销=组织变更记录；CL2-CL3 默认 N=1，CL4+ 老板可增设，不强制 3 |
| 2 | 单元头衔/等级/名称 | 决定表 A/B/C、`REC-LIFE` 岗位、G8 任免链 | 头衔=“最高行政单元负责人”；等级=公司最高 agent 等级（当前 G9）；名称示例：省/事业部/中心，**不入规范**。G9 是等级，不是唯一岗位 |
| 3 | 域边界与重叠 | 一个对象只能有一个权威；两个单元管同一域会双主表 | 一单元一域；域不重叠；跨域事项升级；不许一个对象两个单元权威 |
| 4 | G8 由谁 +1、谁 +2 | 现表 B：G8 的 +1=G9、+2=老板；多单元后“哪个单元”必须写死，否则跨单元部门无主 | 部门归属单元 → 该单元头提议 → 老板任免；跨单元部门由老板指定主单元；N=1 时即现单宰相链 |

| 6 | 单元冲突/跨单元事项谁终裁 | 老板直通多单元，不等于多单元自动一致；没有规则会出现多个口径 | 老板终局；日常跨单元由“主单元”牵头；重大事项单元会签后老板批；不许单元各自对外承诺 |

## 三、根交接与外部撤权（C 双轨；不是“防宰相”）

先按你的澄清定调：**对外，人类老板是根；对内，最高宰相 agent 就是老板本人。** 它持密钥、以老板身份签发，这是设计。要补的不是“防它拿钥”，而是“外部根有没有真的交给它、交了什么范围、怎么收回”。

1. **`root_delegation`（外部→最高宰相）**：范围、期限、可撤回、密钥指纹/公钥、老板签名或离线批准件；启动时验。它回答“凭什么它是内部老板”。
2. **`operating root key`（最高宰相）**：以老板身份签内部硬动作；内部不再设第二个“批准老板”。子 agent 只能拿 scoped key，不能拿 root key。
3. **`revocation/rotation key`（外部老板）**：撤权、换钥、收回 root；撤权必须能枚举并停用后代/凭据（接 I-6/P0-12）。这是外部老板对内部老板的唯一硬控制。
4. **哪些动作保留给外部老板**：默认只保留“任命/撤回最高宰相、换 root key、外部审计/清算”；宪法修宪默认也由最高宰相（它就是内部老板）。若你要外部对宪法保留否决，另加 `external_veto`；不特别说就不加。这样“宪法硬核在老板”里的“老板”就是最高宰相，内部没有更高者——自洽，但必须明写。
5. **内部“不得自授”分两层**：子 agent 不得自授；最高宰相对下授予不叫自授（它就是老板），它的权限来自 `root_delegation`，超出范围=外部可撤回的违约，不是内部程序非法。
6. **P0-4 状态与负向用例**：17 §六.2 从“已解”改“部分解（内部顺序已解·外部交接证明待 R1）”；负向：无 root_delegation 的“最高宰相”、撤权后旧 root 签名、子 agent 持 root key、root 超范围。

**一句话**：不是“密钥不能给宰相”，而是“密钥给的是最高宰相，给的动作要有外部交接证明，收回要有外部撤权证据”。
