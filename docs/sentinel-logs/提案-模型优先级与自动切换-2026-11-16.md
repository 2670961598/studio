## 1. magpie：可借鉴设计（原文证据）

**取源说明**：`raw.githubusercontent.com` 直连被 reset；改用 ghproxy 镜像成功取到 README/reference
（`https://ghproxy.net/https://raw.githubusercontent.com/yetone/magpie/main/README.md`、
`.../docs/reference.md`）；官网 intent 文档 `https://usemagpie.ai/docs/intent` 直接可取。仓库主页
`https://github.com/yetone/magpie`。以下为原文要点，未取到的点标“未知”。

- **形态**：本地网关 `127.0.0.1:3425`，同时说 OpenAI Chat/Responses、Anthropic Messages、Gemini，做格式翻译；
  单机 app/Docker/远程共享；**MIT**；README 明确“supports DeepSeek Harness (dsh)”并会改 dsh profile。
- **订阅池化**：把各 agent 已登录的订阅（Claude/ChatGPT/Copilot/Gemini/Grok）或 API key、本地模型统一为
  provider；同一 provider 可加多个账号，额度耗尽时换账号。
- **routing group**：多个模型（跨 provider）作为一个 `group/<id>`；组可嵌套；模式有
  `smart`（有额度的订阅中“最早重置”优先）、`order`（首个能答就用，不能答换下一个）、`rotate`（逐轮）、
  `usage`（最少使用）、`pace`（按周剩余/小时）、`weight`（加权平滑）、`fast`（近期首 token/速度）；
  `stays=` 控制会话粘性（auto/session/turn/off/strict）。
- **失败/冷却**：429（额度耗尽）按重置时间/Rest-After/窗口读取 resting，默认 15m、上限 8d；
  短限流按 Retry-After（最多 1h）或 1m 起倍增到 30m；out of credit 30m；其他失败 1m 起倍增到 10m；
  同一请求在未发送首段前可立刻切下一个候选；401/403、模型不服务也 rest；安全拒答不 rest，可换源重问。
- **意图路由**：每个 turn 用一个小分类模型读最新消息选 intent，按规则把请求先派到对应模型，其余成员留作 failover；
  分类器失败/超时=无 intent 规则，按原组路由；超时全局默认 8s。
- **配额/计费/审计**：按 key/账号读余额与 5h/weekly/monthly 窗口；usage 记录实际 provider/account；
  网关 key 可做客户端级 token/cost 限额；usage 可按 provider/account/agent/模型统计并 OTLP 导出；
  gateway→gateway key 鉴权、轮换、限制模型/账号。
- **部署/许可/治理**：Docker、远程 magpie、LAN 共享；MIT；**仓库不接受 PR**（README 明示），
  上游是个人/小团队项目，长期治理与兼容性需自担（这是接外部网关的主要非技术风险）。
- **明确未知**：magpie 对 **Zcode CODING PLAN 订阅**、**KimiCode 订阅**、**opencode-go 订阅**作为
  provider 的精确支持面（README 支持 Kimi Code agent 与 Zhipu GLM provider，但“订阅 vs API key”边界未逐项确认）；
  其配额度读取/重置策略在非 Claude/ChatGPT 订阅上的覆盖度未取原文逐条确认。

## 2. 两路线对比

| 维度 | A. daemon 内建多源路由（推荐） | B. 接外部网关（magpie 类） |
| --- | --- | --- |
| 控制/审计 | 选择、失败、冷却、价格全在自有 engine/台账；事件词/面板可复用 | 网关内部决策，daemon 只见 group/模型名；需网关 usage API/审计桥 |
| 价格/预算 | 每源价目→预算预留/收割成本/work_records.model 精确归属 | 网关给出 list/实际 provider，但 daemon 需适配解析；COST_RECON 要新增桥接 |
| 来源兼容 | 逐源适配（dsh provider/Kimi adapter 真 CLI）；已有 opencode-go 直连证据 | magpie 支持 dsh，但对 Zcode/KimiCode/opencode-go 订阅的精确支持未逐项证实 |
| 故障面 | 仅 daemon 代码；失败可回退单源=现状 | 新增常驻进程/端口/密钥池；单点、部署/升级/日志/网络都是新面 |
| 密钥面 | 各源 key 仍在 daemon/宿主既有 secret 面 | 所有源 key 集中到网关；网关 key 再分发给 daemon |
| 并发/在途 | 在 dispatch 选源；在途 worker 不换源，重试/新单用下一源；maxInflight/泳道不变 | 网关可在请求内切换（更强），但与 daemon 的 attempt/work_record/预算/验收归属脱节 |
| 实施量 | 中（parser+selector+失败分类+价格+测试） | 小改 daemon，但网关部署/运维/审计桥成本高；依赖上游治理 |
| 适用 | 我们要“同一套台账+预算+验收”内闭环 | 多 agent/多工具共享订阅池、愿意接受外部网关 |

**推荐：A（内建）作为 MVP；B 作为后续可选模式**。理由：我们最稀缺的是**可审计的成本/配额归属和
与四要件/验收/台账的一致性**，magpie 的路由模式（order/smart/stays/failover）很有参考价值，但其
usage/价格/配额数据在网关侧，接进来需要额外桥接且引入单点与上游治理风险；A 可用较小改动复用
task-34 热切与现有事件/价目/预算链，先覆盖“同档多源优先级+429 降级+冷却+审计”。

## 3. 设计草案（A：daemon 内建）

### 3.1 models.yaml schema 草图（strict 向后兼容）

```yaml
tiers:
  high:
    # 兼容：若省略 sources，则 provider/model/price 视为单源（priority 0，id=default）
    sources:
      - id: glm-zcode
        provider: glm
        model: GLM-5.3
        priority: 10                 # 越小越优先
        price: {inputPerM: 1.1111, outputPerM: 3.8889, cacheReadPerM: 0.2778}
        quota: {kind: monthly, limitUsd: 0, resetAt: null}  # 0=不探测/仅审计；先不做自动探测
        cooldown: {baseMs: 60000, maxMs: 28800000, circuitAfter: 3}
      - id: go-kimi
        provider: opencode-go
        model: kimi-k3.1-pro
        priority: 20
        price: {inputPerM: 2, outputPerM: 10, cacheReadPerM: 0.2, cacheWritePerM: 2}
        quota: {kind: monthly, limitUsd: 15, resetAt: null} # 先只登记/告警，不主动探测
    strategy: priority              # priority|order（MVP 只 priority；组内可用 weight/pace 后续）
```

- 解析器把单源旧形归一到 `sources[]`；指纹包含整组源（热切原子替换）。
- 价格按 source 存（不是 tier 单值）；price snapshot 记录 source id/挂账。

### 3.2 选择算法（MVP）

1. 候选=该 tier 的 sources，按 priority 升序（同级按 id 稳定排序）；过滤 `cooldownUntil > now` / circuit open 的源。
2. 预算预检：用**候选源价格**估算并 reserve；超帽=拒绝该源（不换更贵源偷偷超预算；可配置 allowBudgetUpgrade=false）。
3. 选择第一个可用源；把 `source.id` 写入 DISPATCH note（`;modelsrc=<id>`，不新增契约/事件词）。
4. 在途单不切换；失败重试/新单重新选择（attempt 级隔离，work_records.model=实际源 provider/model）。
5. 全部源不可用：fail-closed `DISPATCH_FAIL note=ALL_MODEL_SOURCES_UNAVAILABLE;tier=..;tried=..`，不无限重试；
   同拍只尝试一次，下一拍按冷却/半开再试。

### 3.3 失败分类与降级

| 类别 | 处理 |
| --- | --- |
| 429 quota/allowance exhausted | 按 reset/Retry-After/窗口读取 rest（默认 15m、上限 8d）；未发首段前立即换下一源；记 `ESCALATE` note `MODELSRC_REST;...` |
| 5xx / 网络超时 / 连不上 | 指数冷却 1m→2m→…max 10m（可配 8h）；连续 N 次 circuit open；记 `ESCALATE`/`DAILY_ALARM` |
| 401/403/余额不足 | 冷却并告警（配置问题不静默换源当兜底）；换源前记明原因 |
| 400/请求畸形/安全拒答 | **不换源**（同一请求换源也坏；拒答由上层处理）；fail-closed |
| parse/流中断 | 不自动换源重跑（可能已计费/产生副作用）；按现有 WORKER_DEAD/STALL 处置，下一 attempt 选源 |
| 全部失败 | 可读错误 + 一次 DAILY_ALARM（不刷屏）；tier 保持现状（单源退化） |

### 3.4 冷却/恢复/审计/面板

- 冷却状态：source id→`cooldownUntil, consecutiveFailures, lastErrorClass, lastServedAt`；
  half-open：冷却到期后下一请求试一次，成功清零，失败翻倍（上限 8h）。
- 审计：复用既有事件词，**不新增事件名**：DISPATCH note 带 `modelsrc=<id>`/`fallbackFrom=<id>`；
  rest/全部失败走 `ESCALATE`/`DAILY_ALARM`；work_records.model=实际 provider/model；price_snapshot per source。
- 面板/健康：只读 getter 暴露各 tier/source 状态（可用/冷却到/连续失败/最近服务），复用 ops/health 面；不新增 schema。
- 热切：models.yaml 重载原子替换 source 表；在途 worker 不变；下一 spawn/重试用新优先级；单源配置=退化现状。
- 对 maxInflight/泳道/预算：不改变并发/车道；预算预检按源价；混合日注明来源分布（COST_RECON 可对账）。
- 与验收：source 切换不得改变验收口径；失败/降级留痕可查；`waived`/HOLD 不受影响。

### 3.5 验证清单

- 两源优先级：A 429→B 成功、A 冷却期跳过、到期 half-open 恢复；全失败 fail-closed 可读错误；
- 价格归属：work_records.model/price_snapshot 为实际源；日闭/COST_RECON 无重复计费；
- 在途不串源：切换期间在途单继续旧源；新 attempt 用新源；
- 热切：改 sources 后秒级生效，在途不动；单源回退=现状；
- 429/quota/5xx/超时/401/400 分类各一测；告警去重；预算超帽不换更贵源；
- 现有 verify:v2/四要件/验收闸不回归。

## 6. 风险与回退

- 失败分类误判导致降级/重试风暴；缓解：默认保守、max attempts、去重告警、冷却上限。
- 价格/配额混合口径导致 COST_RECON delta；缓解：per-source price+work_model 归属、日闭注明、先 observe。
- 多源 API 兼容差异（KimiCode adapter 未真验、opencode-go session header）；MVP 只接已验证 provider。
- 热切与在途：source 只影响下一次 spawn/重试；在途 worker 不换源。
- 回退：sources 配成单源/删除多源即退化为现状；不做自动 fallback=只保留优先级列表不启用降级。
