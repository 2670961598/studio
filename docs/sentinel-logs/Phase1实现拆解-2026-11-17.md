## 〇、结论
- **关键路径**：A 骨架 → B Transport → C sidecar 业务 → D daemon 适配 → G 双跑/回滚；E 历史迁移、F 最小面板在 B/C 接口冻结后并行。
- **3 批 low-intensity**：Batch1 地基（A+B+C 最小+mock）→ Batch2 集成（C 完整+D+E/F 并行）→ Batch3 双跑/回滚/verifier；总 33–45 人日，0.4–0.5 FTE≈8–12 周。
- **首单= A+B 最小闭环（mock sidecar）**：7–9 人日，不接生产/不迁数据；先证“Unix socket+Transport v1+错误码+health/rooms/messages/read”可跑，再由 C 替换 mock。
- **实现方不自验**：每批 builder 交证据，独立 verifier 按模块验收表签字；双跑/回滚脚本必须可重复执行。

## 二、依赖图与分批
```
A 骨架 ─┬─> B Transport(mock) ─┐
        └─> C 业务(内存→SQLite) ─┴─> D daemon 适配 ─> G 双跑/回滚/verifier
                                  ├─> E 历史迁移（导出/map 可早并行）
                                  └─> F 最小面板（接口冻结后）
```
- **Batch 1（地基，约 12–15pd）**：A＋B mock＋C 最小 rooms/messages/read；Transport DTO/错误码 v1 冻结；只跑测试/mock，不接生产。
- **Batch 2（集成，约 16–20pd）**：C 完整 wake_lease/audit + D + E/F 并行；staging 双跑（sidecar 主、Matrix 只读）；每完成一块即 verifier 点验。
- **Batch 3（验收，约 5–8pd）**：G 全量双跑≥7天、回滚演练、指标报告、独立 verifier、制作人签收；不达门槛不进 P2。
- **low-intensity**：0.4–0.5 FTE + AI；Batch1 3–4 周、Batch2 4–6 周、Batch3 1–2 周（含等待）≈8–12 周；不阻塞运维，月度 gate。
- **并行边界**：A/B/C 可并行；D 必须等 B+C 媒体/错误码冻结；E 只读导出可早做、导入等 C schema；F 等 B/D 鉴权；G 从 Batch1 维护脚本，最终串行。

## 四、风险/前置
- **插件仍在开发**：Batch 1 前冻结 Transport v1（DTO/错误码/socket framing）和 wake claim/ack 语义；加版本 `transport:v1`，字段只增不改；未冻结的字段不进入实现。插件大改→暂停/只做 mock。
- **许可/canonical**：Phase0 已获制作人 vendor 授权（`vendor/workbench-core/PROVENANCE.md`）；Phase1 继续用同一 vendor 树 sha，需明确 canonical 仓/升级流程；上游变更=人工 diff+重跑 80/133/84，不自动跟随。
- **生产不改**：P1 只 staging/本地；launchd plist 不 load 生产；Matrix 只读回退；不双写；无需动 Docker。
- **运行时**：daemon Node 24 LTS vs vendor 基线 Node 25.6.1——首单先验证 Node 24 兼容；不兼容则 sidecar 独立 pin Node，但需运维评估。
- **风险**：消息丢失/重复（lease）、sidecar 崩溃/升级、cursor 密钥、历史导入丢消息、自研面板运维面、插件未来接口变化。
- **暂停**：双跑漏/重无法归零、回滚>10min、sidecar 稳定性不达标、插件大改、许可/版本变化、人力<0.3 FTE。
