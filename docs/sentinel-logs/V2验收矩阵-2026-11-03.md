## 〇、判定口径（不采信任何 agent 自述）

**四步验证法**，四条全过才可判「已验证」：

1. **代码落仓**：`git log --oneline -5 -- <路径>` 有对应提交；关键标识在**生产路径**的引用数 > 0（`grep -rn … apps/*/src packages/*/src | grep -v test`；=0 即未接线）。
2. **门禁**：`mise exec -- bun run verify:v2` exit=0 且失败集空；`node scripts/scan-repo-secrets.mjs --json` newHits=0。
3. **真机接线**：启动日志／`ledger.sqlite`（events/daemon_kv/records/work_records/sessions）／端口探测（8788/8789/8791）／sqlite 表计数——证明能力在生产链路上真被调用，而非只有代码。
4. **红→绿**（适用时）：构造对应负向/缺证场景，改前红、改后绿，原始输出归档（17 §五「交付方自报仅线索」；AGENTS.md §五.3）。

**三档判定**：**通过**（四步全过）｜**不通过**（有证据表明行为不符，或「被修到能跑」）｜**证据不足**（缺任一必需证据）。
**状态词**：未交付｜已交付未验证｜已验证｜未过｜待裁（本矩阵严格取这五值；「部分腿已落」写在证据列）。

**逐单归因原则（Lead 2026-11-03 确认，硬口径）**：每一单必须有**自己的 patch sha＋全树 `diff -rq` 零差异＋门禁原始输出＋真机证据**；**绝不接受合并绿证代单证**。验收时按单归因——同批多单合并落仓时，各单证据须可单独追溯。
