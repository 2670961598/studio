## 〇、结论
- **推荐 sidecar 架构**：daemon 仍是唯一主控/台账写入者；新起一个本机 `workbench-service`（loopback HTTP/Unix socket）持有 issues/chat 两个 SQLite；daemon 通过既有 `FlowPlatform`/Matrix face 适配器调用。**不选 daemon 内建**（进程耦合、升级/回滚/权限隔离差）。
- **复用方式**：Phase0 起按**源码快照 vendor + thin service wrapper**；不把插件当运行时服务，也不在 daemon 里直接 import 宿主路径。**许可/来源未落地前不 vendor**（Workbench 无 LICENSE、无 git；快照 sha256 可钉，但不能替代授权）；备选=按公开 DTO/接口 clean-room 适配（工作量大）。
- **不抄边界**：sidecar 只做**业务服务**；认证/身份/人事/注册器仍由我们 daemon/wkey/公司目录提供；Workbench 的 principal/membership 只作内部技术 ID，**不作为权源**；sidecar 不对外暴露，必须经 daemon/panel 鉴权。
- **路线**：Phase0 PoC（5–8pd）→ Phase1 聊天服务（30–45pd）→ Phase2 单子双轨（60–90pd）→ Phase3 切 Taiga → Phase4 关 Docker。**只替一个关不掉 Docker**；Phase4 必须两者 parity+迁移+回滚演练都过。
- **总估 90–130 人日**（低强度 0.5 FTE ≈ 10–14 个月含验收等待），不阻塞日常运维；每阶段独立验收、独立回滚。

## 一、架构定位

### 1.1 进程模型：sidecar（推荐）
```
daemon (单写者：ledger/company git/事件)
  │  内部 HTTP/Unix socket + 短时 token（仅 loopback）
  ▼
workbench-service（每公司一实例）
  ├─ issues.db   ← Workbench issues 内核（单子/流程/审计）
  └─ chat.db     ← Workbench collab 内核（房间/消息/wake）
```
- **优点**：与 daemon 生命周期解耦；DB/迁移/崩溃隔离；可独立备份/回滚；不污染 daemon 单写者纪律；未来可整体替换为插件宿主服务（同一 transport）。
- **代价**：多一个本机进程/端口/健康检查/启动顺序；由 guardian/launchd 托管，daemon 启动时 fail-closed 探活。
- **不选内建**：daemon 已承载七相位/台账/公司 git；内建会把 issue/chat 存储、迁移、UI 依赖塞进同一进程，升级/回滚/权限隔离都变差；插件未来若提供服务也无法平滑换实现。
- **边界**：sidecar **只**写自己的 `issues.db`/`chat.db`；不写 ledger、不写公司 git、不写 .AIWS；daemon 仍写事件/工时/成本/记录。

### 1.2 复用方式、许可、版本钉
- **推荐**：vendor **源码快照**到本仓（如 `services/workbench/upstream/`，保留上游目录结构与 tests），外面包一层 `workbench-service` 适配层；只调用包的 public DTO/接口，不 fork 内部 store（必要 fork 需文件级 diff 记录）。
- **不用 daemon 直接 import 宿主路径**：生产部署树不能依赖 `<workbenchRoot>`；vendor 后纳入我们构建/测试/部署。
- **许可/来源（硬前置）**：Workbench 无 `.git`、根/包均无 `LICENSE`，包 `license:null`、`private:true`；`verification/snapshot.txt` 只有 sha256 快照（例：collab `service.ts` `6e536e...`）。**无书面授权不得复制**；需制作人确认代码归属/许可，或取得 Workbench 作者书面许可后 vendor。无许可则只能 clean-room 按 DTO 重实现（Phase1/2 各 +30–50% 工作量，且需独立测试）。
- **版本钉**：`UPSTREAM.md` 记录源码树 sha256、Node 版本（Workbench 基线 `v25.6.1`、包 `0.1.0`）、验证快照时间；升级=人工 diff+重跑 80/80/133/133/84/84，禁止自动跟随。
- **依赖策略**：sidecar 只用 Node 标准库 + 两包源码；不引入 Workbench 插件/DSH 运行时；服务层自己的 HTTP/鉴权/日志/配置独立实现。

### 1.3 与 Workbench 插件未来的关系
- daemon 侧定义 `WorkbenchTransport v1`（issues/chat 两组 DTO + cursor + 错误码），sidecar 实现它；**未来插件若提供服务，只需换 transport 实现**（sidecar → 插件宿主服务），daemon/adapter 不变。
- 等插件“完全结束”设 **plugin-freeze checkpoint**：冻结其 DTO/API 版本，跑兼容矩阵；若插件设计更先进，优先把 sidecar 的 wrapper/transport 靠过去，**不重写 daemon 契约**。
- 接口留白：不把 Workbench 内部表/字段名泄漏给 daemon；daemon 只认我们的 `WorkbenchPort`/`FlowPlatform`；升级/迁移不硬切。

### 1.4 不抄边界与契约面
- **不迁**：Workbench 的权限矩阵/principal/membership/roles、认证/登录、人事/组织、注册器。
- **权源不变**：daemon 的 wkey/网关、公司目录、任职闸门/accountability 仍判权；sidecar 的 actor 只是内部技术标识；所有入口经 daemon/panel 鉴权，禁止浏览器/外部直连 sidecar。
- **公司目录边界**：公司 git 仍是组织/人事/章程事实源；sidecar DB 放 `<companyDir>/var/workbench/`（运行时，不入 git）；不新增公司目录结构。
- **契约**：目标是 **`packages/contract` 零改动**；通过适配层实现现有 `FlowPlatform` 与 Matrix source/notify/HR/conversation 结构接口。若缺字段/能力必须动契约，按提案流另批，**不在本路线图偷改**。
- **多公司**：每公司独立 sidecar 实例/DB/端口（先 2 家最简单）；公司级 token 由 daemon 注入；不允许共享 actor/房间命名空间。

## 三、数据迁移与回滚
- **单子**：优先保留公开 `studio-dev-N`（`key`=旧串；`external_ref` mapping 到内部 UUID）；Taiga 自定义状态/type/dept/level/lane/字段进**公司级映射表**，不可映射项显式豁免，不压缩不猜；评论导入 author/时间/reply；附件导出到 sidecar 文件存储+元数据（或制作人明确接受不迁）；Taiga history 只作迁移注释/审计，不伪装原生事件。台账 `ticket_mirror` 是投影，切后重建；events/work_records/AIWS 引用不动。
- **聊天**：MXID→actor、room_id/alias→room、成员/owner/canBroadcast 映射；历史按时间导入，旧历史不重放 mention；read cursor 以导入末 seq 为基线；DM 保留；外部 Element/手机端无等价物（P1 明确接受内部聊天 UI）。
- **双跑/双写**：**不做跨平台双写**（避免两个事实源）；Taiga/Matrix 唯一写，Workbench 只读影子+定时比对；冻结后一次性切；变更 delta 用导出/导入补齐。
- **工具**：`workbench-migrate`（导出→校验→导入→diff）、`workbench-snapshot`（Taiga pg_dump+体积、Matrix DB/房间导出、sidecar DB 备份）、`workbench-compare`（单数/状态/评论/附件/message/seq 哈希）；所有工具只读写本地，产物落 `/tmp` 或 company var，可重复运行。
- **回滚**：每阶段保留前态快照；P1/P2 停 sidecar 即回 Matrix/Taiga；P3 切回 `platform: taiga`+Taiga 只读；P4 不删 Docker 镜像/卷，30 天后才清。回滚必须演练并留下证据，不接受“理论上可回”。

## 四、与现有验收体系结合
- 每阶段**独立验收**：P0/P1/P2/P3/P4 各自 verifier 报告 + 制作人签收；不与 V2 28/28 混算，不覆盖既有验收。
- **功能验收**：P1 聊天矩阵（mention/DM/reply/mention_all/read/wake/notify/HR/conversation/重试/去重）；P2 单子矩阵（create/transition/fields/comments/activity/links/KB/guards/ID/evidence）；P2/P3 数据迁移矩阵（counts/hash/status/comments/attachments/ID/mirror/refs）。
- **回归门槛**：每阶段 `verify:v2` 绿、typecheck/test/guard 绿；daemon 七相位/派发/收割/日闭无回退；无新增事件词/契约变更（若需=提案流）。
- **证据**：迁移脚本、快照 sha256、diff 报告、双跑日志、回滚演练录像/命令、独立 verifier 签字；低强度期间按阶段门禁，不按日历强推。
