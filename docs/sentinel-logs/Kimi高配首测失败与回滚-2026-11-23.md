# Kimi via DSH 高配档首测失败、回滚与修复（2026-11-23 14:00-14:2x）

## 一、事件
- 14:00 批：为验证 `high→dsh+kimi-coding/k3.1-pro`，用 `modelTierTickets` 把新单 LOCAL-296~300 强制 high；LOCAL-297 实际执行 `dsh-high`（dispatch note `tier=high@dsh-high`）。
- 结果：worker 启动即失败 `llm-pi-ai: no credential for provider route "kimi-coding"; its profile resolves KIMI_API_KEY, which is not set`；连续 4 次 attempt GATE_FAIL → `CIRCUIT_BREAK`（自动开 bug 单 LOCAL-298）。全程无数据丢失（单回滚为新单，熔断半开后续重试）。

## 二、根因（已在 deploy 树代码确认）
- `execute.ts` 的 `routingActive` 仅当 `adapter.name === 'dsh'` 成立；tier 执行器名是 `dsh-high`/`dsh-mid`/`dsh-low` 时 **routing 面不激活** → `routedSource` 恒 undefined。
- 但 tier overlay（`var/tmp/dsh-tier-high.yml`，由 models.yaml 热切写成 kimi-coding/k3.1-pro）**仍然生效** → dsh worker 走 kimi-coding provider；
- 而 KIMI_API_KEY 注入条件用的是 `provider: routedSource?.provider` → undefined → 不注入 → pi-ai 找不到凭据必败。
- 一句话：**注入门控只认 routing 源，没认 tier overlay 生效源**（文档 §4 触发条件描述也不完整）。

## 三、立即处置（已执行）
1. 回滚：移除 `modelTierTickets` 强制覆盖；`tierExecutors` 恢复 `{"high":"kimi","mid":"dsh","low":"dsh"}`（high 回 Kimi CLI——其默认模型已是 3.1 Pro，等价质量档）。
2. `launchctl kickstart -k gui/$(id -u)/io.studionext.daemon` 重启；daemon 健康（现 pid 50223，14:17:27 启动；期间 14:16-14:17 连续两次重启，一次为我们的 kickstart，另一次 reason=unknown 已记录待查）。
3. 生产恢复中档/低档正常（dsh+GLM），高配档暂时走 Kimi CLI（默认 3.1 Pro）。

## 四、修复（worker 进行中）
- `execute.ts`：注入 provider 取 `routedSource?.provider ?? tierCatalog 中当前 tier 的 provider`（tier 覆盖路径也能命中 kimi-coding）；无 tier 解析/非 kimi provider 时不注入（保持 fail-safe）。
- 新增测试：(a) dsh-high + tier provider=kimi-coding → 注入；(b) tier=glm → 不注入；(c) routedSource 回归；(d) 无 tier → 不注入。
- 文档 §4 触发条件更正 + 本事故注记。
- 修复部署后：先干跑单元/集成测试 → 重新启用 high→dsh → 用 **单张测试单**（非批量强制）验证 4 项硬证据（routing/model/cost/无 key 泄漏）→ 通过后再退役 Kimi CLI。

## 五、教训
- 新增"模型源注入"类能力必须覆盖 **routing 源与 tier overlay/executor 路由两条生效路径**，测试矩阵缺一即现场必败。
- 生产切换前应先用单张测试单验证，不应直接对新批次批量强制档（本次代价：LOCAL-297 四连败+熔断开单，无数据损失但有噪音）。
- 待查：14:17 的 daemon 二次重启 reason=unknown（另立 P2 观察）。
