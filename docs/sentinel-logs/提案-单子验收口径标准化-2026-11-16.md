# 提案：单子类型 × 验收口径标准化（测试层 / 功能验收层）

> 任务：task-38（提案单，不含实现）；2026-11-16 制作人问「所有单子都有测试，验收呢？策划自己提的也应验收」。
> 关联：`提案-策划产出评审闸-2026-11-16.md`（task-37，评审卡引用本提案的 `acceptance_criteria`）、`提案-策划提案自动建单-2026-11-16.md`（task-36，建单必须带本提案字段）。本文不改契约/schema/事件词。

## 0. 结论先行

测试（代码正确性）与验收（功能符合意图）是两层：前者已有 `verify:v2` 门禁链；后者目前只在部分单靠独立 verifier/Lead 真机自证，**缺统一强制字段与 CLOSE 前闸**。建议：按单子类型定义验收口径矩阵；每单强制 `acceptance_criteria`；功能类改动 CLOSE 前必须有验收结论；验收结论/证据/签收入既有报告与台账（优先复用 four-piece/QA/事件词，不新增审批层）。

## 1. 现状差距

| 层 | 现状 | 缺口 |
| --- | --- | --- |
| 测试层（代码） | 落仓改动走 `verify:v2`（guard + margin + typecheck + test:v2 ≈2570 用例 + hr-gate-audit + v2-suite-manifest + old-test-ledger + secret scan） | 只证明代码/契约回归正确，不证明功能达到任务书本意 |
| 单票质量验收 | 收割四要件（completed/输出非空/REPORT/gate exit0）+ QA_PASS + CLOSE | 报告类成立；功能类「四要件绿但功能不符」仍可能发生 |
| 功能验收层 | 个别单靠独立 verifier（如 task-35）+ Lead 真机证据 + 验收单；无统一强制 | 无结构化验收标准；无 CLOSE 前强制校验；无分级签收与证据字段 |
| 策划自提单 | 日报/plan.md 产出，尚无自动建单（task-36） | 若建单不带验收标准，会把缺验收的提案带入派发 |

## 2. 单子类型 × 验收口径矩阵

| 单子类型 | 必要验收口径 | 判据/证据 | 签收 |
| --- | --- | --- | --- |
| 报告/巡检/策划类 | 收割四要件 + QA_PASS + 产出被采纳/决策依据可核（引用来源报告、数据窗口、结论可复现） | REPORT + summary + QA_PASS + 采纳记录（Lead/制作人批注或下游引用） | Lead + QA；重大决策加制作人 |
| 代码/功能类 | `verify:v2` 门禁 + 按 `acceptance_criteria` 真机/端到端验证 + 独立验证方 + 回归证据 | verify 输出 + 真机证据（命令/日志/文件/DB 只读快照）+ verifier 结论 | 低风险=Lead+verifier；中风险=ENG-0；高风险/契约面/对外=制作人 |
| 提案类 | 评审闸 task-37 通过（评分卡/去重/采纳 P0-P2）+ 立项批准 | triage 报告 + 批准记录 + 去重键 | 评审岗 + Lead；立项按金额/风险分级至制作人 |

**叠加而非替换**：现有四要件语义、QA_PASS、verify:v2 均不变；验收层只增加「是否达到任务书意图」的强制出口。

## 3. 每单强制 `acceptance_criteria`（可测/可复现）

建单模板（CLI/平台网关）与 task-36 自动建单必须携带以下结构化字段（建议放 issue 描述的固定 JSON 代码块，或 `<companyDir>/reports/...` 任务书 frontmatter；不改平台 schema/契约）：

```json
{
  "acceptance_criteria": [
    {"id": "A1", "check": "改 models.yaml 后 reload，daemon pid 不变", "evidence": "ps/log", "verifiable": true},
    {"id": "A2", "check": "下一次 spawn 的 worker overlay 含新 model", "evidence": "文件/进程命令行", "verifiable": true}
  ],
  "verification_mode": "code|report|proposal",
  "risk_level": "low|medium|high",
  "evidence_required": ["verify:v2 exit0", "真机日志", "只读 DB 快照"],
  "signoff_level": "lead|eng0|producer"
}
```

- 缺 `acceptance_criteria` 或不可测（无判据/无证据方式）→ 建单拒绝/退回补料（task-36 强制）；存量为空单在 CLOSE 前 HOLD。
- 例：报告类可写「结论与来源报告数据窗口一致；被 Lead/制作人引用为决策依据」；代码类必须含真机命令与预期输出/回归命令。
- 验收标准由提单人写、任务方确认；变更验收标准需重新签收。

## 4. 证据留痕与分级签收

- 验收结论四态：`pass` / `return`（退回返工）/ `need-evidence`（待补证）/ `waived`（制作人显式豁免）；含验收方/时刻/证据引用。
- 留痕：优先复用既有 REPORT/summary + GATE_PASS/QA_PASS note + `acceptance` 报告段落；若必须新增事件词，另报提案批（本提案不擅自扩契约）。
- 面板：单据详情增「验收」栏（标准/证据/结论/签收人）；CLOSE 前若功能类无 `pass/waived` → HOLD。
- 分级：低风险 Lead+verifier；中风险 ENG-0（主管）；高风险/契约面/对外/超预算 制作人；制作人保留一票否决/插队。

## 5. 门禁接线点（实现阶段）

1. **建单模板/网关**：`acceptance_criteria` 必填校验（CLI/平台网关/task-36 统一入口；缺=拒绝）。
2. **收割 CLOSE 前**：读取单据验收块，功能类验证 `pass/waived` 才允许 CLOSE；缺→HOLD/ESCALATE（复用既有事件词与 HOLD 语义）。
3. **面板/报表**：验收覆盖统计（有标准/已验收/退回/待补）随日报呈现。

## 6. 不做什么

不新增冗余审批层（复用 QA/verifier/acceptance/主管岗）；不要求报告类单做代码测试；不改四要件/QA/verify 语义；不把「测试绿」当功能验收；不自动改平台 schema/契约。

## 7. 风险与回退

- 风险：标准形式化导致填表负担/走过场；验收方与实现方同体重叠；HOLD 卡住主链。缓解：模板/示例、抽查、验收方独立、功能单才设 CLOSE 闸；观察一周统计误伤。
- 回退：验收字段/面板只读观察先上；CLOSE 前闸默认观察（只记不拦），稳定后开启强制；开关关闭=回到现状四要件+QA。

## 8. 验证清单（实现后）

- 缺验收标准的单被拒/退回且原因可查；功能单 CLOSE 前无验收结论=HOLD；`waived` 仅制作人可写并留痕；
- 报告类单仍按四要件+QA 通过（不回归）；`verify:v2`/收割主链不改；面板/报告可查覆盖；开关关闭=零行为。
