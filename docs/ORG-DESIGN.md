# 组织架构设计（ORG-DESIGN）— 纵向分级 × 横向分部 × 交叉负责

> 状态：v2（制作人 2026-09-29 第二轮决策已吸收：批/干错位分权矩阵、团队等级制、
> 全流程联签、谁派出谁验收、人事系统、升级流程——细节见下；剩余关键问题见第六节）
> 来源：制作人 2026-09-29 构想——"单子分等级，高等级派低等级；纵向等级、横向职能/部门；
> 类三省六部但不照抄：三省直报制作人管方向性/破坏性/高成本/前沿，六部管执行全流程；
> 部门交叉管理（每部至少一个上级，上级对下级完全负责）；多项目并行各编各制；
> 框架强制'高级别管低级别+交叉'总纲，内部可调。STUDIO 率先按小团队改造。"
> 执笔：宰相（ZCode）。

## 一、核心概念

### 1. 纵向：单据等级（派生权 + 审批分权 的统一度量）【v2 定稿】

- 每张单有**等级**（1-9）。**批/干错位一格**（制作人定则）：每层领导「干 [X, X+2]，批 [X-1, X+1]」
  ——批的下限恰好=下属干的上限，派活与审批无缝衔接：

  | 层 | 干（领单） | 批（放行） | 派出 |
  |---|---|---|---|
  | 制作人 | — | **9 必亲批**；8 个别看（制作人评论=高权重指令，非亲批也影响走向） | 只发 9 级（多为探索） |
  | 高层（三省） | 7-9 | 6-8 | 给中层派 6 |
  | 中层 | 4-6 | 3-5 | 给执行层派 3 |
  | 执行层 | 1-3 | 1-2（组内小组长） | — |

- **派生规则**：等级 N 的单可派生 <N 的子单（父子链 `父单` 字段）；**子单等级上限=派单人的批上限**（制作人派的 9 级单，我拆的子单最高 8；我派的 6 级单，中层拆的最高 5）——天然防越级
- **终验收=谁派出谁验收**（制作人定则，v2 新增）：单据带 `派单人` 字段；
  中间环节按等级分权流转（含全流程联签），**最终验收锁定派单人本人**——
  制作人派的 9 级单，宰相全程主理，最后验收仍归制作人
- **升级流程**（v2 新增）：团队扩容由该项目最高负责人提议 → 最高领导层会签
  （≥3 级团队三人签）→ 制作人终验收 → 团队升一级

### 2. 横向：部门（职能实体，主管+成员 agent+可承接的单类）

- 部门 = 主管 agent + 成员 agent 池 + 职能定义（承接哪类单）
- **交叉管理**：部门配置 `上级` 列表（可多个三省/部门）——上级对下级完全负责；
  上级派**跨部门任务**时，由涉及部门共同决定、共同推进（联签+共担）
- 部门有自己的泳道/资源（对接现有 lane 机制）

### 3. 三省（战略层，直报制作人）

- 只设少量（小团队 1 个，大团队 2-3 个），职责：方向性/破坏性/高成本/前沿探索类
  战略单的**发起**与向上汇报；**三省的定时任务挂在 ZCode（宰相）+制作人交流面**（制作人原话：
  "三省的都在 zcode 和我交流"）
- 宰相（ZCode）= 三省之首：框架治理总纲、跨项目协调、向制作人总汇报

### 4. 六部（执行层，框架内自主推进）

- 职能裁剪自制作人举例：成本审计、人员安排、前期准备、中期施工、后期收尾、测试
- **框架内定时**自主运转，无需制作人过目；**六部中挑 1-2 个进 ZCode 汇报面**
  （制作人原话："六部可能也挑一两个进入 zcode 我来看看"）——被选中者的简报进宰相日报
- 对上级完全负责；无勾心斗角设定（利益结构由单据等级+联签机制固化）

## 二、与现有机制的映射（全部向后兼容，旧规则=新引擎特例）

| 现有机制 | 新架构下成为 |
|---|---|
| L0-L3 交付深度 / G1-G4 治理重量 | 统一等级：L0→1、L1→2、L2→3、L3→4；G1→5、G2→6、G3→7、G4→8（映射期双轨） |
| delegated_approvals（GAMES 无条件等） | 分权配置的"项目级豁免"条目 |
| producer_only_lanes（三消 core 亲批） | 分权配置的"部门级亲批"条目（core 部门全等级亲批） |
| 单据级「亲批」叮嘱 | 保留，最高优先级锁定 |
| Epic 单 | 等级 ≥7 的战略单（父子链的父端） |
| 探索泳道（explore） | 情报/前瞻部门的专属资源通道 |
| 泳道（lane） | 部门的资源配额（部门可拥有多条泳道） |
| 提示词版本化/自评/复盘/报告 | 六部中"质量部"的职责包 |

## 三、org schema（唯一事实源：kernel/org.yaml）

```yaml
version: 1
projects:
  STUDIO:                      # 每项目独立编制（多项目并行，各编各制）
    scale: 小团队               # 3-10（模板名，可自定义偏离）
    sheng:                     # 三省（直报制作人；定时任务在 ZCode 交流面）
      中枢省: {agent: ZCode(宰相), 职责: 框架治理总纲/跨项目协调/向上总汇报}
    bu:                        # 六部（裁剪为 3-4 部，小团队版）
      工程部: {主管: ZCode兼, 上级: [中枢省], 职能: 开发/修bug/重构, 泳道: [explore]}
      质量部: {主管: 自评引擎, 上级: [中枢省], 职能: 测试/复盘/案例库/报告, 进ZCode汇报面: true}
      情报部: {主管: 巡逻引擎, 上级: [中枢省], 职能: 前沿扫描/知识库/评估}
    approvals:                 # 分权引擎配置
      producer_min_level: 7    # ≥7 制作人亲批
      cross_bu_cosign: true    # 跨部门联签
      exemptions:              # 项目级豁免（兼容旧规则）
        - {范围: 全部, 规则: 宰相可批 <7 且非跨部}    # STUDIO 全权（制作人 09-29 授权）
    # 其他项目示例：
  GAMES:
    scale: 中团队
    sheng: {…}; bu: {…}; approvals: {…豁免: 业务单 GAMES 专岗无条件…}
  POLY:
    scale: 中团队
    approvals:
      exemptions:
        - {范围: 部门=core工程部, 规则: 全等级制作人亲批}   # 三消 core 收紧的迁移
```

单据模型变更（YouTrack 字段）：`部门`（多值枚举）、`等级`（1-9）、`父单`（链接）。
evolve 流程保留（org.yaml 修改走治理提案+VERIFIED+制作人批——org 是治理核心）。

## 三点五、人事系统（v2 新增）

- 框架为**每个项目提供 agent 档案**（org.yaml 内 `agents:` 段）：身份/部门（可多属=交叉任职）/
  职责/定时任务/上级——单源事实，人事与组织同源
- **团队等级制**（制作人定则）：团队等级=最高自主领导层。2级（3-10人）→3级（10-30）
  →4级（30-100，起推荐人事部管控编制与成本）→…→9级（集团公司，终极目标）。
  管理幅度推荐 3-4，允许至 10；全部推荐非强制
- STUDIO 现状=**2 级团队**（宰相直管执行层），按升级流程演进

## 四、标准编制模板（docs/org-templates.md，推荐非强制）

- **3-10 人（小团队）**：1 省 + 3 部（工程/质量/情报），主管多兼任；进化路径：
  做满 2 周期 → 质量部独立主管 → 增设计部
- **20-50 人（中团队）**：2 省（战略/运营）+ 5 部（工程/质量/设计/情报/交付），
  交叉：每部挂 1-2 省；进化路径：按项目数扩副本→交付部拆分
- **100+ 人（大团队）**：3 省 + 6-8 部 + 部门内分组（组=最小单元，主管一层）；
  进化路径：项目群→事业部制
- 通用总纲（所有项目必须遵守）：高级别管低级别；每部至少一个上级；跨部门联签；
  战略级三省发起+制作人批

## 五点五、数据层决策与职责边界定则（v2.1，制作人 2026-09-29 指令）

**框架 × YouTrack 分工（定则）**：
- **框架（studio-daemon + kernel/）聚焦 agent**：人事（org.yaml 编制/agent 档案/定时任务/交叉任职）、
  干活（worker 执行/沙箱验证闸/记账/巡逻引擎/报告）——"人与活"
- **YouTrack 聚焦流程流转**：单据状态机/等级/批示/评论/联签/知识库 Articles——"流程与记录"
- 组织架构数据归属：编制与人事=框架侧（org.yaml）；单据与流转=YouTrack（字段：部门/等级/派单人/父单）

**数据层决策（实测驱动，2026-09-29）**：
- 实测：events 882 行（日增~150，一年~5.5 万行）、全量解析 5-10ms；runs 增长主因是哨兵空转
  （已修，回落 ~300/天）；worker 归档 916M 为文件形态（本就不适合进 DB）
- **结论：当前不引入独立数据库**。所有数据已在 BigDisk（/Volumes/BigDisk/Studio/kernel）
- **随 P1-P2 组织架构引入 SQLite 查询层**（标准库零部署，单文件 kernel/metrics/studio.db，
  天然在 BigDisk）：JSONL 保持 append-only 账本源，SQLite 承载部门/等级/派单人聚合查询、
  人事档案、timeline 索引（组织架构带来的结构化查询是确定需求）
- **触发线兜底**（任一命中即全量切 SQLite 查询层）：events>5 万行 / 任意账本查询>500ms /
  多项目 events 合计>20 万行
- 远期（多项目大规模扩张后）再评估独立 DB 服务（Postgres 级）——远超当前需要

## 五点八、迁移策略：不停产 + P2 影子模式（制作人问询后定则，2026-09-29）

破坏性分级：P1 零（纯新增）/ P2 高（审批命脉）/ P3 中 / P4 低。
**不停产**（业务项目在跑，停框架=全线停；设计本为语义兼容——旧三机制=新引擎豁免特例）。
P2 影子模式：新引擎并行计算（shadow）→ 每笔审批新旧各算一遍只记不干预 →
分歧自动报警复盘 → **零分歧 3 天切权**（org.yaml `approvals.engine: shadow|org|legacy`，
切权=改配置+优雅重载）→ 旧审批代码保留不删（一键回滚 legacy，分钟级恢复）。
P2 期间框架其他主线暂停，时间线/记账盯流转异常。

## 五点九、YouTrack 深度利用与账号等级制（制作人 2026-09-29 定则）

**不重复造轮子——改用 YouTrack 原生能力的地方**：
| 我们在自建的 | 改用 YouTrack 原生 |
|---|---|
| 父单文本字段（P1 刚建） | 原生 issue links（Subtask/Depend）：树视图/依赖/板面原生支持（P3 切换，文本字段转冗余兼容） |
| 代码层状态机 guard | Workflow JS（on-change 平台级强制——宪章 §2 承诺过一直未做，P2/P3 补上） |
| 部门视图 | Saved Searches + 多块 Agile 板（按部门/等级） |
| 时间线可视化 | Dashboards（报表组件） |
| 工时记账 | Time tracking 字段 |

**账号=等级，职能是正交维度（制作人 2026-09-29 第二轮修正）**：账号**只带等级、不带定位**——
login 名仅为历史标识（保 token），等级语义以 org.yaml accounts 表为准（deputy=9…game=1 可调整）；
职能/岗位/部门归 agents 人事档案维度，与账号解耦。账号是**等级权限锚点**（YouTrack 原生角色
按等级配，平台级强制+代码引擎双保险）；个体身份靠评论署名协议 `[项目·个体名·部门] 正文`。
**团队等级=单据上限（制作人 09-29 二次纠偏定则）**：等级 N 团队 → 单据区间 1~N，越团队等级即越级
（STUDIO=2 级团队 → 活全在 1-2 级；4-6 级"主力战力"是 4 级以上团队（有中层，30-100 人）的区间）。
不同级别团队干不同复杂度的内容：2 级=简单直接实现，3 级=多轮设计，往上逐级复杂。
制作人派的 9 级单（如 STUDIO-55 构想）不受团队等级限制（战略级直派）。

## 六、决策记录（制作人 2026-09-29 三轮全部敲定）

1. **终验收=派单人，铁律定死**（制作人原话："派出人是起点和终点，必须是这样"）——
   单据生命周期：派出（起点）→ 等级分权中间流转（含全流程联签）→ 派单人终验收（终点）。
   制作人派的 9 级单：宰相主理全程，终验必归制作人；宰相派的子单终验归宰相。
2. **等级渐进启用**：从 1-2 级起步，逐步拓展 1-3、更高——不一次性铺满 1-9；
   存量无迁移压力（org.yaml `渐进启用: [1,2]` 段控制，拓展即改配置）
3. **STUDIO 2 级编制确认**：宰相直管三执行组（工程/质量/情报），无中层，慢慢扩
4. **项目迁移**：框架（P1-P3）迁移完之后，三消与 GAMES 两项目改造接入（制作人确认）
5. 宪章 v3 呈批时点：P2 审批引擎落地后（默认，未获异议）
