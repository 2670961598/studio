# 40 · 公司规范提案（Company Spec v1）——提案阶段【未定稿，无结论】

> 提案流铁律 20-§十三 第一阶段产物（2026-10-19 立项，制作人定向：「定义公司规范是当前最重要的事」）。
> 本文档**只陈述问题、范围与待决问题**——所有结论须经 ②探索 ③前沿对比 ④方案定稿 ⑤验证 spike ⑥过审后才成立。
> 原始动机：框架抽象里「公司=可从网上下载的模型，本地跑起来」——要让第三方设计的公司能在任意
> StudioNext 实例上安全运行，规范是前提。**我们处在定义规范的位置，先想清楚再落字。**

## 一、问题陈述（为什么必须有一份规范）

1. **可移植性**：别人做好的「公司模型包」（组织+章程+提示词+岗位+插件清单）下载即跑——
   没有规范就没有生态，只有「我家目录结构」。
2. **安全性**：公司包会携带插件要求——可能出现**奇怪甚至危险的插件要求**（如要求装某来路不明的
   CLI 插件、要求网络全开、要求读取超出工位的路径）。没有声明与审查规范=任意代码执行入口。
3. **异构适配**：我们适配多种 CLI（dsh/claude/codex/kimi）、多平台（Taiga/YouTrack/LocalFile）、
   多 IM（Matrix/…）——各家的能力与要求不同，公司包声明什么、框架协商什么、缺能力时怎么降级，
   需要一张**要求矩阵**而不是逐个 hack。
4. **版本演化**：框架自身不断进化（schema 版本已有 v1），规范必须带版本与迁移策略——旧公司包
   在新框架上的兼容承诺怎么给。

## 二、规范应覆盖的面（范围清单——待探索后定形状）

| # | 面 | 待决问题（示例，非结论） |

## 三、候选方向（开放，探索阶段定）

- A. **最小规范**：只定 manifest+安全声明，其余沿用现行目录约定——快，但可能约束不住异构。
- B. **全量规范**：公司包=完整自描述（含平台无关流程声明），框架负责落地——优雅，但工程量大、
  过度设计风险。
- C. **分层规范**：核心层（必填/安全）+可选层（平台/IM/插件按需声明）——折中，但层间交互复杂。
- （以上仅候选，不预设倾向。）

## 四、探索计划（下一步：铁律 ②③）

1. **前沿对比**（探索 agent-1）：业界有没有「agent 组织包/可下载 agent 团队」的相近规范——
   AGENTS.md 生态、MCP server 分发与安全审查、A2A/agent card、LangGraph deployment 配置、
   AutoGen Studio 导出格式、composio 工具 schema、ChatDev/MetaGPT 的项目模板机制——做过怎么做的，没做过的想法。
2. **红队审视**（探索 agent-2，对抗视角）：专攻本提案第二节清单的安全面——一个恶意公司包
   能干什么？声明机制哪里会被绕过？「harmless 声明」的造假面？
3. 两路独立产出后在方案定稿阶段合流（④），随后验证 spike（⑤）用「做一个最小公司包+一个
   恶意样本包（只用于测试）」双向验证。

## 五、本提案的边界（不做什么）

- 不改现行公司目录语义（那是后续实现单的事）
- 不预设 schema 字段名/格式细节（探索后定）
- 不覆盖「框架自身开发流程」（20-§十三已治）
