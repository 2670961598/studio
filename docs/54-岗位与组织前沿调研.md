# 54 · 岗位与组织前沿调研：从「定时 + hook」到「义务 + 授权 + 编排」

> 性质：前沿调研（探索件，不是实现单；不构成实现承诺）。
> 方法：公开资料实读 + 本仓设计/代码对照；外部事实给链接，仓内事实给文件/章节。
> 结论先行：**「定时 + hook」不是太简单，而是层次混在一起。** 它是一个合格的 v1
> 触发器层，但不是岗位模型，也不是组织模型。前沿的共同方向不是更多 cron/hook，
> 而是四层分离：**义务（obligation）→ 编排（workflow）→ 授权（authority）→
> 身份/生命周期（identity）**。岗位不是 cron job；组织不是 department 列表；
> 治理不是 dashboard。

---

## 〇、直接回答三个问题

**1）定时 + hook 是否太简单？**
- 作为一周 v1：不简单，够用。它把「什么时候唤起」这件事做得确定性、可审计。
- 作为「自治理组织」：太简单。它只回答了「何时唤起」，没有回答「岗位必须做什么、
  谁能批准、做不好怎么办、经验怎么积累、多个岗位怎么交接」。
- 更准确地说：不是「量」不够，是「层」不对。cron/hook 是触发器；岗位是责任；
  组织是权威与协作结构。三者不能压成一层。

**2）有更前沿的吗？**
有，而且不是一家：

| 层 | 前沿代表 | 解决什么 |
|---|---|---|
| 编排/耐久执行 | Temporal、Restate、DBOS、Inngest、Camunda/Zeebe、CMMN | 长流程、重试、超时、人工等待、恢复、补偿 |
| 岗位/角色模型 | MOISE+、OperA、AGR、OMNI、Actor 模型 | 角色、组、使命、规范、邮箱、监督 |
| 组织设计 | VSM、Team Topologies、Holacracy、Sociocracy、DAO | 层级/团队类型/圆圈/同意/quorum |
| Agent 管理 | Workday ASOR、Microsoft Agent 365/Entra Agent ID、IBM 数字劳工 | 注册、身份、生命周期、绩效、退役 |
| 授权/审批 | EP-QUORUM、OPA/Cedar、二人规则 | 多方可信批准、职责分离、策略即代码 |
| 身份/协议 | Entra Agent ID、A2A、MCP | 代理身份、发现、任务协议、工具协议 |
| 记忆/学习 | Generative Agents、Workday AI memory | 记忆流、反思、检索、可信记忆 |
| 组织仿真 | AgentSociety、Concordia | 上线前模拟组织/政策/瓶颈 |

**3）最该借什么？**
如果只借三件：
1. **义务/SLA 模型**（CMMN / MOISE+ 的 norm）——把「岗位必须做什么」变成一等公民，
   而不是一条 cron。
2. **耐久工作流 + 事件总线**（Temporal / Inngest）——把 hook 升级为有 schema、
   幂等、可重放的事件；把长流程从 daemon tick 里拿出来。
3. **授权图 + quorum**（EP-QUORUM / OPA）——让岗位真正能批准/打回/调预算，
   且不能同一进程替三个身份签字。

# 第一部分 · 诊断：四个东西被压成了一层

## 1.1 当前设计实际是什么

| 当前件 | 实际语义 | 它不是什么 |
|---|---|---|
| `jobs`（cron） | **时间触发器**：到点唤起一个岗位/模型 | 不是义务，不是岗位，不是绩效 |
| `hooks`（mention/webhook/data-change） | **事件触发器**：外部事件落单/派发 | 不是事件总线，不是工作流 |
| `FSM`（单据状态机） | **单据状态迁移**：待办→派发→证据→复验→交付 | 不是通用工作流（无 DAG/并行/补偿/人工任务） |
| `org-config` | **组织静态配置**：部门/岗位/等级/汇报线/定时岗 | 不是岗位运行时，不是授权图 |
| `daemon` | **唯一写入者 + 调度器 + 状态机 + 收账** | 不是组织本身 |

这套东西在 [17-§2](17-整体技术设计.md) 和 [35-§3/§4](35-岗位运作闭环设计.md) 里
是自洽的：源只产意图、意图进主循环、主循环按状态决策。作为 v1，它的确定性、
可审计、预算/断路/收割四要件都是真优势。

## 1.2 但它把四组概念压成了一层

### 混淆一：触发器 ≠ 义务

cron 回答的是「什么时候唤起」，不是「这个岗位欠什么」。
真实岗位不是「每天 9 点被叫一次」，而是持续背负一组义务：

- QA 必须在 4 小时内给出复验结论；
- 财务必须在每月 3 日前完成对账；
- 部长必须在提案进入「待批」后 24 小时内批准/打回；
- 人事必须在员工入职当天完成建号/权限/频道；
- 值班岗必须在告警 15 分钟内 ack，否则升级。

这些是**义务（obligation）**：有对象、有截止时间、有违约后果、有绩效。
cron 只是检查义务是否到期的一种方式；hook 只是触发义务的一种事件。
把义务压成 cron，会导致：
- 岗位不被唤起就不存在；
- 没有「欠账」概念，只有「下一次运行」；
- 没有 SLA/升级/绩效；
- 无法回答「这个岗位今天应该做什么、欠了什么」。

### 混淆二：事件 ≠ hook

hook 是一个回调；事件是一个有类型、有版本、有 schema、有幂等键、可重放的事实。
当前 webhook/mention/data-change 是「落单」的触发器，但没有统一的：
- 事件 schema/版本；
- 幂等键与去重；
- 顺序/因果；
- 重放/死信；
- 消费者注册/订阅。

结果：每加一个 hook，就多一条隐式契约；事件多了以后，无法回放、无法排障、
无法做「如果当时这个事件晚到 5 分钟会怎样」的分析。

### 混淆三：岗位 ≠ 定时任务

这是最本质的简化。当前 `jobs[]` 的一条配置大致等于一个岗位的全部：
`{id, dept, cron, role, level, type, model_tier, budget_cap, output}`。
它没有：
- **mandate**：这个岗位拥有什么；
- **authority**：它能批准/打回/调预算/人事什么，额度多少；
- **obligations**：它必须产出/复核什么，SLA 多少；
- **interfaces**：向谁汇报、谁向它汇报、和谁联签、对谁 veto；
- **memory/skills**：它知道什么、会什么；
- **performance**：怎么衡量它干得好不好。

一条 cron 配置是「岗位的一个触发器」，不是岗位。岗位是持久的责任包；
job 只是它的一种唤醒方式。

### 混淆四：FSM ≠ 工作流

FSM 适合单据状态；工作流需要：
- DAG/并行分支/汇合；
- 定时器/超时/升级；
- 人工任务/审批；
- 补偿/回滚；
- 依赖/前置条件；
- 重试/幂等/恢复。

当前 FSM 能表达「待批→已派发→证据就绪→复验通过→已交付」，
但表达不了「等 QA + 财务 + 法务三方都过，且任意一方超时则升级」这种真实流程。
这不是 FSM 的错；是把 FSM 当工作流用。

## 1.3 结论：不是加更多 cron，而是加三层

```
现在：  triggers (cron/hook) + FSM + org-config  →  daemon
目标：  obligations  →  workflows  →  authority  →  identity
        （欠什么）      （怎么走）     （谁能批）     （谁在干）
```

下一节按「岗位」「组织」「编排」「企业 agent 管理」四条线看前沿。

## 1.4 一句话评分（按当前实现，不按愿景）

| 维度 | 当前实现 | 评价 |
|---|---|---|
| 触发器 | cron + mention/webhook/data-change + escalate/relay/resume/freshness | **够用**（v1） |
| 义务 | 无 `obligations` 一等模型；jobs 代替 | **缺** |
| 编排 | FSM + tick；无 DAG/并行/补偿/人工任务 | **弱** |
| 授权 | daemon 独占状态推进；worker 六动作；无 quorum | **缺** |
| 身份 | 工号/岗位/人事档案 | **有基础**，缺 agent 版本/生命周期/access review |
| 组织设计 | 部门/等级/汇报线/relations | **有骨架**，缺团队类型/交互模式/治理节奏 |
| 记忆/学习 | lessons 空；无 per-agent memory/skill | **缺** |
| 绩效/退役 | personnel_events 有类型；无执行链 | **弱** |
| 事件 | hook 落单；有 dedupKey，但无统一 schema/版本/重放 | **弱** |

结论：**触发器层及格，岗位/组织/授权层不及格。** 这不是「再加几个 cron」能解决的；
需要补的是模型，不是配置项。

# 第二部分 · 岗位前沿：从「定时任务」到「岗位运行时」

## 2.1 MOISE+：角色、组、使命、规范

MOISE+ 是多智能体组织的经典模型，把组织分成三层：

- **结构（structural）**：角色（role）、组（group）、角色间链接（link）；
- **功能（functional）**：使命（mission）、目标（goal）、计划（plan）；
- **道义（deontic）**：规范（norm）——义务（obligation）、许可（permission）、
  禁止（prohibition），以及违反后的制裁。

它的关键洞见：**角色不是一段 prompt，而是一组抽象行为 + 规范**。
一个角色可以被分配到一个组，承担一个使命，受一组规范约束。
这正好补上当前「岗位 = cron 配置」的缺口。

可借：
- 岗位合同 = role + mission + norms；
- 部门 = group；
- 战役/目标 = mission；
- 章程/红线 = norm（义务/许可/禁止）；
- 违规 = 事件 + 制裁（降级/停派/复盘）。

来源：[MOISE+ 论文](https://dl.acm.org/doi/10.1145/544741.544858)、
[MOISE+ 组织模型资料](http://www.pa.icar.cnr.it/cossentino/paper/eumas_2011_moise.pdf)。

## 2.2 OperA / AGR / OMNI：组织与交互协议

OperA、AGR（Agent-Group-Role）、OMNI 都在回答同一个问题：
**多个 agent 如何在一个组织里合法地交互？**

它们共同提供了：
- 组织模型（角色、组、依赖、权威）；
- 交互协议（请求、承诺、通知、拒绝）；
- 规范与制裁；
- 电子机构（electronic institution）——规则可执行、可审计。

可借：
- 岗位之间的交互不应该只是「评论/工单」，而应该有**协议**：
  request / propose / accept / reject / escalate / delegate；
- 每个协议有前置条件、后置条件、超时、失败处理；
- 交互记录进 ledger，可审计。

来源：MOISE+ 论文及其组织模型资料（见 §10）；OperA/AGR/OMNI 是经典组织模型，
本文只借概念，不绑定具体实现。

## 2.3 Actor 模型：邮箱、监督、let-it-crash

Actor 模型（Erlang/Akka/Orleans）对「岗位运行时」有直接启发：

- 每个 actor 有一个**邮箱（mailbox）**，按顺序处理消息；
- actor 可以有**监督者（supervisor）**，定义重启/停止/升级策略；
- **let-it-crash**：局部失败不要拖垮全局，由监督树处理；
- **位置透明**：actor 在本地/远程/云上无差别；
- **背压**：邮箱有界，满了要拒绝/降级，而不是无限堆积。

映射到 Studio：
- 每个岗位 = 一个 actor，有 inbox；
- 部门 = 监督树；
- 岗位失败 = 重启/换人/升级，不是 daemon 全局异常；
- 消息 = 事件/任务/审批请求；
- 邮箱 = 岗位收件箱（当前只有 queue 投影，没有 per-position inbox）。

可借：邮箱、监督树、let-it-crash、背压。**不必**重写整个 daemon 为 actor 运行时；
先把「岗位 inbox + 监督策略」做成逻辑模型即可。

来源：[Akka Actor 模型](https://doc.akka.io/libraries/akka-core/current/typed/guide/actors-intro.html)、
[Orleans 虚拟 actor](https://learn.microsoft.com/en-us/dotnet/orleans/overview)。

## 2.4 CMMN：案例管理，比 BPMN 更适合知识工作

CMMN（Case Management Model and Notation）是为**知识工作/自适应流程**设计的：
- **Case file**：案例的所有信息；
- **Task**：人类任务、流程任务、决策任务；
- **Milestone**：里程碑（达成条件）；
- **Sentry**：进入/退出条件（entry/exit criteria）；
- **Discretionary item**：由人决定是否执行的可选任务；
- **Stage**：阶段，可嵌套。

它和 BPMN 的区别：BPMN 适合「路径已知、重复执行」的流程；CMMN 适合
「路径部分未知、由人判断、以案例为中心」的工作。AI 公司的岗位工作大多属于后者：
- 「这个提案要不要批」——milestone + sentry；
- 「QA 必须在 4 小时内复验」——human task + SLA；
- 「等三方会签」——sentry + milestone；
- 「如果超时则升级」——sentry + escalation。

可借：
- 用 CMMN 的 **milestone/sentry** 表达岗位义务的达成条件；
- 用 **discretionary item** 表达「部长可以决定是否加一道审查」；
- 用 **case file** 表达单据的完整上下文（现在散在 ticket/REPORT/summary）。

来源：[OMG CMMN 1.1](https://www.omg.org/spec/CMMN/1.1/)。

## 2.5 企业 Agent 管理：岗位的「HR 化」

这一块是 2025-2026 最明显的前沿：把 agent 当员工管理。

### Workday Agent System of Record（ASOR）

Workday 把 AI agent 纳入组织结构和 workforce 管理：
- 单一系统记录所有 agent（自建/伙伴/第三方）；
- 记录 owner、role、skills、使用情况、成本、价值；
- agent 与员工并列，进入组织结构和 workforce planning；
- 生命周期：引入、治理、衡量、改进、退役；
- 支持 MCP、A2A、OpenTelemetry。

它的核心话术是：「你不可能管理你看不见的东西」「像管理员工一样管理 agent」。
可借：
- agent registry（谁、属于谁、什么 role/skills、成本、绩效）；
- 把 agent 放进组织结构，而不是只放在 jobs 列表；
- 生命周期与绩效，而不是只统计 token。

来源：[Workday ASOR GA](https://blog.workday.com/en-au/managing-ai-powered-future-of-work.html)。

### Microsoft Agent 365 / Entra Agent ID

Microsoft 把 agent 当**一等身份**：
- **Agent 365**：observe / govern / secure 三支柱；registry、access control、
  visualization、interoperability、security；
- **Entra Agent ID**：每个 agent 有独立身份、sponsor（负责的人）、blueprint（模板）、
  生命周期（provisioning/deprovisioning、access review、owner attestation）；
- agent 没有自己的凭据，由 blueprint 代取 token；
- 支持 RBAC/ABAC/Conditional Access；
- 与 Purview/Defender 集成做数据安全/威胁检测。

可借：
- **每个岗位/agent 一个稳定身份**，不是共享账号；
- **sponsor**：每个 agent 有一个对人类负责的人；
- **blueprint**：同类 agent 的模板（权限、角色、能力）；
- **生命周期**：入职、权限评审、离职/退役；
- **owner attestation**：定期确认「这个 agent 还有必要吗、权限还对吗」。

来源：[Agent 365 概览](https://learn.microsoft.com/en-us/microsoft-agent-365/overview)、
[Entra Agent ID](https://learn.microsoft.com/en-us/entra/agent-id/agent-identities)。

### IBM 数字劳工生命周期

IBM 的说法更直接：digital worker 要像人一样 **hire → credential → deploy → retire**。
几个值得注意的细节：
- 4,000+ digital workers、450+ active projects；
- **没人用的 agent 会被 decommission**：不给 token，让它「饿死」；
- 用 **workflow-centric assessment**（没见过的 workflow 问题 + 另一个 agent 评分）
  来认证 agent 技能，而不是让 agent 背题；
- 强调「agent 管理」与「HR 管理」同构。

可借：
- **预算即生命周期**：不用的岗位/agent 自动减预算、降频、退役；
- **认证**：不是自评，而是用未见过的任务 + 异源评分；
- **退役**：agent 不是永久资产，要有日落机制。

来源：[SiliconANGLE/IBM 数字劳工生命周期](https://siliconangle.com/2026/05/20/managing-digital-worker-lifecycle-enterprise-ibmthink/)。

### ServiceNow AI Control Tower：一个反面教材

TheCUBE 对 15 家 ServiceNow 客户的访谈给出一个很有价值的警告：
- AI governance 实际分三层：
  1. **治理工作流/问责**（inventory、owner、approval、exception、remediation、audit）；
  2. **AI 生命周期证据**（model version、lineage、validation、bias、drift）；
  3. **运行时强制执行/安全**（拦截、阻断、撤销权限）。
- ServiceNow 最强的是第 1 层；第 2 层常由别家生成；第 3 层在 14/15 家客户那里
  是外部/定制/人工/有限路径/未验证。
- 有安全从业者估计，只有 30%-40% 的 AI 活动能经过 ServiceNow 控制路径。
- 「kill switch」被过度宣称。

教训：
- **不要做「只有 dashboard 的控制塔」**；没有运行时强制，治理只是事后工单；
- **不要把「可观测」当「可治理」**；
- **不要过度宣称**「端到端」。

来源：[TheCUBE 对 ServiceNow AI Control Tower 的客户访谈分析](https://siliconangle.com/2026/10/17/servicenow-ai-control-tower-selling-a-penthouse-while-building-the-frame/)。

### 2.5.1 对 Studio 的最小映射

| 企业 agent 管理概念 | 代表 | Studio 对应 | 缺口 |
|---|---|---|---|
| Agent registry | Agent 365 / Workday | `people` + `departments` | 无 agent 版本/能力/生命周期状态 |
| Sponsor | Entra Agent ID | 汇报线/制作人 | 无显式「对人负责」字段 |
| Blueprint | Entra Agent ID | 岗位模板/公司模板 | 无模板版本/权限基线 |
| Skills | Workday ASOR | `people.skills` 标签 | 无 SKILL.md/技能库/认证 |
| Performance | Workday ASOR / IBM | ledger 可复算 | 无绩效视图/退役判据 |
| Retirement | IBM | `personnel_events` 退 | 无预算饥饿/自动退役 |
| Access review | Agent 365 | 无 | 无定期权限复核 |
| Owner attestation | Agent 365 | 无 | 无「这个岗位还有必要吗」的定期确认 |

这张表说明：不是「没有概念」，而是「概念散在 people/ledger/jobs 里，没有形成生命周期」。

### 2.5.2 Agentic Enterprise Blueprint：四层参考架构

Enterprise Intelligence Lab 的《Agentic Enterprise Blueprint v1.0》（技术笔记，非标准，
只作参考架构）把企业 agent 系统拆成四层：

1. **Agent Roles**（角色）；
2. **Orchestration**（编排）；
3. **Control Gates**（控制闸门）；
4. **Human Oversight**（人类监督）。

并覆盖身份/访问、工具/数据治理、记忆/上下文、多 agent 协调、工作流集成、安全、
可观测、可靠性、人机决策权、生命周期治理，以及 bounded autonomy（有界自治）。

这几乎就是本文建议的四层（Company Spec / Institutional / Orchestration / Execution）
的企业版表述。它说明：**「四层分离」不是学术偏好，而是企业实践也在收敛的方向。**
对 Studio 的启发：
- 当前设计主要覆盖了 Orchestration + 部分 Human Oversight；
- **Agent Roles 只到配置层，Control Gates 只到 FSM/验收闸门**，没有形成授权/quorum 语义；
- 「bounded autonomy」需要授权图/quorum/预算/审计一起成立，不是一句口号。

来源：[Agentic Enterprise Blueprint v1.0](https://zenodo.org/records/21349962)。

## 2.6 岗位运行时的最小模型

把上面的东西收敛成一个可实现的模型：

```
Position {
  id, name, dept, level
  mandate:      它拥有什么（职责边界）
  authority:    能批准/打回/调预算/人事什么；额度/条件/quorum
  obligations:  必须产出/复核什么；SLA；违约后果
  interfaces:   reports_to / supervises / peers / veto / 联签
  budget:       钱 / token / 时间
  memory:       有界、按岗位/项目 scope、可审计
  skills:       SKILL.md / 能力标签 / 认证
  performance:  从 ledger 复算，不自评
}
```

```
Inbox ← 时间触发（cron）
      ← 事件触发（webhook / mention / state change）
      ← 义务触发（SLA due / review required / 定期对账）
      ← 委派（上级/同级）
      ← 升级（下级/异常）
```

```
Loop: claim → plan → propose action → authority/policy check
      → execute → evidence → ledger → learn
```

关键：**Inbox 是岗位的，不是全局队列的**。当前 `todo_queue` 是全局投影；
需要 per-position inbox（可以是投影，不必是新事实源）。

# 第三部分 · 组织前沿：从「部门列表」到「治理架构」

## 3.1 Viable System Model（VSM）：组织的五系统

Stafford Beer 的 VSM 把任何可存续系统分成五个递归子系统：

- **System 1**：执行单元（做业务）；
- **System 2**：协调（避免振荡、共享资源、排程）；
- **System 3**：控制/优化（资源分配、绩效、内部调控）；
- **System 3\***：审计（独立抽检，不经过 System 3 的汇报链）；
- **System 4**：情报/适应（看外部、看未来、研发）；
- **System 5**：政策/身份（宗旨、宪法、终极决策）。

还有两个关键概念：
- **algedonic signal**：疼痛/警报信号，可以绕过层级直接上达；
- **requisite variety**：管理复杂度必须与业务复杂度匹配，否则失控。

映射到 Studio：
- 部门 = System 1；
- 调度/泳道/共享资源 = System 2；
- 预算/绩效/断路 = System 3；
- 独立审计岗 = System 3\*（当前没有真正的独立审计，只有复验）；
- 情报岗/规划岗 = System 4（当前有策划/情报岗的雏形）；
- 宪法/制作人 = System 5。

可借：
- 用 VSM 检查组织是否缺层：有没有 System 3\*？有没有 System 4？
- 把「升级」设计成 algedonic signal，而不是普通工单；
- 用 requisite variety 解释「为什么 9 级不是越多越好」：管理层级要匹配业务复杂度。

来源：[Viable System Model](https://en.wikipedia.org/wiki/Viable_system_model)、
[Stafford Beer 的 VSM 资料](https://www.systemswiki.org/index.php?title=Viable_System_Model)。

## 3.2 Team Topologies：团队类型与交互模式

Team Topologies 给出四个团队类型：

- **Stream-aligned**：对齐业务流，端到端交付；
- **Platform**：提供内部平台/服务，降低认知负荷；
- **Enabling**：帮助其他团队提升能力（教练/专家）；
- **Complicated-subsystem**：处理高复杂度子系统，需要专门团队。

三种交互模式：
- **Collaboration**：高带宽、短周期、共同解决问题；
- **X-as-a-Service**：一方提供服务，另一方消费；
- **Facilitating**：一方帮助另一方学习/改进。

可借：
- 部门模板不要只按「工程/质量/情报」分，而按团队类型分；
- 定义部门之间的交互模式，避免所有跨部门协作都变成「开会/联签」；
- 平台团队 = 框架/工具/基础设施；enabling = 培训/审计/教练；
- 用「认知负荷」解释为什么要限制部门数量和接口。

来源：[Team Topologies Key Concepts](https://teamtopologies.com/key-concepts)。

### 3.2.1 岗位分类（可直接用于公司模板）

| 类型 | 主要职责 | 应有权威 | 主要指标 | 对应 |
|---|---|---|---|---|
| 执行岗 | 产出交付物 | 提议、执行、提交证据 | 吞吐/一次通过率/成本 | Stream-aligned |
| 协调岗 | 排期、派发、升级 | 分配、调整优先级、升级 | 周期时间/在途数/阻塞时长 | Team lead / PM |
| 治理岗 | 评审、审计、合规 | 批准/打回/veto | 闸过率/漏检率/复验时延 | Enabling / System 3* |
| 平台岗 | 工具、基础设施、标准 | 设标准、发版本、封禁 | 可用性/交付 lead time | Platform |
| 情报岗 | 外部扫描、规划、研究 | 提议、立项建议 | 机会命中率/预测偏差 | System 4 |

这张表比「部门名列表」更能指导岗位设计：先定类型，再定权威/义务/指标，
最后才是部门归属。

## 3.3 Holacracy / Sociocracy：自治理的机制

Holacracy 的核心不是「没有老板」，而是：
- **角色（role）**：不是职位，是一组持续更新的责任；
- **圆圈（circle）**：角色的集合，有治理会议；
- **治理会议（governance meeting）**：调整角色/政策，不是讨论具体工作；
- **Lead Link / Rep Link**：圆圈与上层/下层的连接角色；
- **同意（consent）**：不是全体一致，而是「没有有理有据的反对」。

Sociocracy 类似：
- 圆圈、**同意决策**、**双链接（double-linking）**；
- 角色与使命；
- 反馈/评估。

可借：
- **角色可以细粒度更新**，不必每次都改组织架构；
- **治理会议**与**工作会议**分开：一个改规则，一个干活；
- **双链接**：部门与上级/下级之间的代表关系，避免信息断层；
- **同意**：不是投票多数，而是「无重大反对」；适合 agent 组织的快速决策。

注意：这些是**人类社会技术**，不能照搬仪式；借的是机制（角色、圆圈、同意、
双链接、治理节奏），不是开会形式。

来源：[Holacracy](https://www.holacracy.org/how-it-works/)、
[Sociocracy For All](https://www.sociocracyforall.org/)。

## 3.4 DAO 治理：提案、quorum、timelock

DAO 治理机制（不看 crypto 部分）：
- **提案（proposal）**：任何重大变更先提案；
- **quorum**：达到最低参与/同意门槛才生效；
- **timelock**：生效前有延迟，给反对/退出留时间；
- **delegation**：可以把投票权委托给代表；
- **执行**：链上/链下执行，有审计。

可借：
- 重大变更（宪法/预算/人事/权限）走提案 + quorum + timelock；
- timelock 不是拖延，是给「反悔/退出/审计」留窗口；
- delegation 可以映射为「制作人授权给宰相/部长」。

不借：token 投票、链上资产、投机治理。

来源：[OpenZeppelin Governor](https://docs.openzeppelin.com/contracts/4.x/governance)。

## 3.5 组织模型的最小集合

把经典理论收敛成 Studio 可实现的几个原语（不新增六名词，作为 Org 的扩展面）：

| 原语 | 来源 | 当前对应 | 缺口 |
|---|---|---|---|
| Role | MOISE+/Holacracy | 岗位/工号 | 无 authority/obligations |
| Group | MOISE+/VSM | 部门 | 无团队类型/交互模式 |
| Mission | MOISE+ | 战役/OKR（prompt L1） | 无正式目标树 |
| Norm | MOISE+/章程 | 章程/红线 | 无违反/制裁机制 |
| Circle | Holacracy/Sociocracy | 部门 | 无治理会议/双链接 |
| Authority | 组织理论/EP-QUORUM | FSM + 六动作 | 无授权图/quorum |
| Obligation | CMMN/MOISE+ | jobs | 无 SLA/欠账/绩效 |
| Interface | Team Topologies | relations（联签/下游/共享泳道） | 无交互模式/协议 |
| Audit | VSM S3\* | 复验岗 | 无独立审计链 |
| Intelligence | VSM S4 | 情报/策划岗 | 无外部扫描/情景规划 |

# 第四部分 · 编排前沿：从 cron/hook 到耐久工作流

## 4.1 Temporal：耐久执行

Temporal 的核心：
- **Workflow**：确定性编排逻辑；
- **Activity**：有副作用的步骤，可重试/超时；
- **Timer/Signal**：长时间等待、人工审批；
- **Event history**：每次执行的事实记录，可重放；
- **Continue-as-new**：长流程不无限增长历史。

它解决的核心问题是：**checkpoint 不是耐久执行**。进程死了，checkpoint 还在，
但「谁来决定从哪继续」没人管；Temporal 把「恢复」变成运行时责任，而不是应用代码。

对 Studio 的启发：
- 主循环 tick 适合「调度/状态决策」，不适合长流程；
- 长流程（等审批、等外部系统、等测试、等人工）应该用 durable workflow；
- 人工等待不应该占着进程/拍；应该是 timer/signal，成本为零；
- 每个 step 的输入/输出/重试/超时要可观测、可回放。

来源：[Temporal + LangGraph 耐久执行](https://temporal.io/blog/temporal-langgraph-plugin-durable-execution)、
[Temporal 文档](https://docs.temporal.io/)。

## 4.2 CMMN/BPMN/DMN：流程、案例、决策

- **BPMN**：适合路径已知、重复执行的流程；有网关、事件、补偿。
- **CMMN**：适合路径部分未知、以案例为中心的知识工作；有 milestone/sentry/
  discretionary item。
- **DMN**：决策表，把「什么条件走哪条规则」从代码/流程里分离出来。

对 Studio 的启发：
- 单据状态机（FSM）保留，用于「单据生命周期」；
- 岗位工作用 CMMN 的 milestone/sentry/obligation 表达；
- 路由/审批/优先级用 DMN 决策表表达，可测试、可版本化；
- 不要把所有东西塞进一个 FSM。

来源：[OMG CMMN](https://www.omg.org/spec/CMMN/1.1/)、
[OMG BPMN](https://www.omg.org/spec/BPMN/)、
[OMG DMN](https://www.omg.org/spec/DMN/)。

## 4.3 事件驱动：hook 的升级版

hook 的问题不是「不好用」，而是「不是事件」：
- 没有 schema/版本；
- 没有幂等键；
- 没有顺序/因果；
- 没有重放/死信；
- 没有消费者注册。

事件驱动架构的最小要求：
- **事件类型 + schema + 版本**；
- **幂等键**（至少一次投递 + 消费端去重）；
- **Outbox**（本地事务 + 可靠发布）；
- **死信/重放**；
- **订阅/消费者注册**；
- **可观测**（事件 id、correlation id、causation id）。

对 Studio 的启发：
- 把 mention/webhook/data-change/state-change 统一成 `Event`；
- 事件进 outbox/ledger，消费者（岗位）订阅；
- 重放事件可以重建/调试；
- 不要让每个 hook 直接调用 daemon 内部函数。

来源：[Transactional Outbox](https://microservices.io/patterns/data/transactional-outbox.html)、
[CloudEvents](https://cloudevents.io/)。

## 4.4 调度：cron 之外

当前 cron 只按时间触发；真实组织还需要：
- **优先级**（pinned/priority/age）；
- **截止时间**（SLA/EDF）；
- **依赖**（前置任务/产物）；
- **资源**（机器/模型/预算/泳道）；
- **抢占**（高优任务可以打断低优）；
- **公平**（防止某个岗位饿死）；
- **容量**（并发/队列/背压）。

可借：
- 优先级 + 截止时间 + 资源约束的调度器（不需要一步到位，先把 SLA/priority 加进去）；
- 用队列论（Little's law）做容量规划；
- 用「最早期限优先（EDF）」或「最小松弛优先（LLF）」做简单 SLA 调度；
- 用 per-position inbox + 全局资源池，避免全局队列看不到岗位欠账。

### 4.4.1 触发器的完整分类

「定时 + hook」只覆盖了前两类：

| 类型 | 例子 | 当前 | 缺口 |
|---|---|---|---|
| 时间 | cron、日历、班次 | 有（cron + 时区/DST 豁免） | 节假日/轮值/on-call 未成模型 |
| 事件 | webhook、mention、state-change | 部分（落单） | 无统一 schema/重放/死信 |
| 义务 | SLA 到期、必须复核、依赖满足 | 弱 | 无 `obligations` 一等模型 |
| 委派 | 上级/同级/外部委托 | 部分（assignee） | 无 delegation/accept/reject 协议 |
| 升级 | 超时、异常、越权 | 部分（escalate） | 无授权链/quorum，升级只到人 |
| 资源 | 预算/容量/配额 | 部分（budget gate） | 无 capacity-aware 调度 |
| 人工 | 制作人直接指令 | 有（CLI/IM） | 无统一收件箱/审计 |

结论：当前是「时间 + 事件 + 部分升级」；缺的是**义务、委派、资源**三类。
这正是「感觉太简单」的来源——不是 cron 不够多，而是触发器类型不全。

来源：[Queueing theory / Little's law](https://en.wikipedia.org/wiki/Little%27s_law)。

## 4.5 授权与审批：EP-QUORUM / OPA

### EP-QUORUM

EP-QUORUM 是一份个人 IETF 草案，定义「高风险 agent 动作的多方批准谓词」：
- **distinct humans**：k 个不同的人类批准者，不能一人多槽；
- **roles**：每个批准者有角色；
- **threshold/ordered**：阈值或顺序链；
- **fail-closed**：任何一项不满足即不通过；
- **window**：批准窗口；
- **action-bound**：每个签名绑定到具体动作；
- **anti-rubber-stamping**：记录批准者查看/签署的时间，识别秒批；
- **不宣称防合谋**：只提高单点失败成本，并让行为可归因。

可借：
- 高风险动作（调预算、改权限、合并、对外发布）走 quorum；
- 每个批准者有独立身份/独立 session；
- quorum 排除同一 executor/同一进程；
- 批准窗口/超时只升级，不放行；
- 记录批准延迟，识别橡皮图章。

这正是 Studio「联签」缺的东西。对照当前：`gateway` 无 quorum；自审指出会签三人
可以是同一 daemon 定时岗、同进程替三个身份签字（[复查报告](复查报告-2026-10-16.md) B10）。
EP-QUORUM 的 **distinct humans + distinct keys + action-bound + fail-closed** 正是
对这个问题的机制化。

来源：[EP-QUORUM IETF 草案](https://datatracker.ietf.org/doc/draft-schrock-ep-quorum/)
（个人草案，未获 IETF 背书；本文只借机制，不宣称其为标准）。

### OPA / Cedar

策略即代码：
- 把「谁能对什么做什么、在什么条件下」写成可测试的策略；
- 决策与执行分离；
- 策略版本化/审计；
- 支持 RBAC/ABAC。

对 Studio 的启发：
- 授权图不要硬编码在 FSM 里；用策略引擎评估；
- 策略可测试（单元测试/回放）；
- 每次决策记录策略版本 + 输入 + 结果；
- 先做简单的策略表，再考虑 OPA/Cedar 级别的引擎。

来源：[Open Policy Agent](https://www.openpolicyagent.org/docs/latest/)、
[Cedar](https://www.cedarpolicy.com/)。

# 第五部分 · 身份、协议、记忆、仿真

## 5.1 身份：Agent 需要自己的身份证

Entra Agent ID 的关键点：
- agent 是特殊 service principal，有独立 id/display name/sponsor/blueprint；
- agent 没有自己的凭据，由 blueprint 代取 token；
- 支持生命周期（provision/deprovision/access review/owner attestation）；
- 支持条件访问/RBAC/ABAC；
- 单租户，不能跨租户。

对 Studio 的启发：
- 工号/岗位 ID 是稳定身份；不要让多个 agent 共用同一个账号；
- 每个 agent 有 sponsor（对人负责）；
- 每个 agent 有 blueprint（模板：角色/权限/能力）；
- 生命周期：入职/权限评审/离职/退役；
- 凭据不落在 agent 自己的 env 里；由 daemon/网关代取短命令牌。

来源：[Entra Agent ID](https://learn.microsoft.com/en-us/entra/agent-id/agent-identities)。

## 5.2 协议：A2A 与 MCP 的分工

A2A（Agent2Agent）是 agent 之间的协议：
- Agent Card：发现/描述 agent；
- Task：任务生命周期（submitted/working/input-required/completed/failed/canceled）；
- 消息/artifact；
- 与 MCP 互补：MCP 是 agent→tool，A2A 是 agent→agent；
- Linux Foundation，Apache-2.0。

对 Studio 的启发：
- 岗位之间的交互不应只是评论/工单，而可以是 A2A task；
- Agent Card 可以作为岗位名片（能力/权限/联系方式）；
- 但不要为了协议而协议：先把内部协议（request/propose/accept/reject/escalate）
  定义清楚，再映射到 A2A。

来源：[A2A Protocol](https://a2a-protocol.org/latest/)。

## 5.3 记忆：Generative Agents 的记忆流/反思/计划

Generative Agents 的架构：
- **Memory stream**：完整记录经历；
- **Reflection**：定期把记忆合成更高层反思；
- **Planning**：基于记忆做计划；
- **Retrieval**：按相关性/时间/重要性检索。

对 Studio 的启发：
- 岗位记忆不是「聊天记录」，而是「经历 + 反思 + 可检索」；
- 需要定期 reflection（复盘/教训）；
- 需要按任务检索，而不是全量注入；
- 记忆要有边界/过期/审计（Workday 也在研究可信记忆）。

来源：[Generative Agents](https://arxiv.org/abs/2304.03442)、
[Workday AI memory](https://blog.workday.com/en-au/how-do-we-ensure-ai-memory-trustworthy-enterprise.html)。

## 5.4 仿真：上线前先模拟组织

AgentSociety 支持 30,000 个 LLM agent 的大规模仿真，带真实环境与并行交互。
Concordia 提供社会仿真的构建块。

对 Studio 的启发：
- 公司配置（org-config）可以在上线前跑「组织仿真」：
  - 这个部门会不会成为瓶颈？
  - 这个审批链会不会死锁？
  - 这个预算/人力配置能不能撑住这个目标？
- 仿真不需要真跑生产；用 LLM agent + 合成任务即可；
- 仿真结果可以作为「组织设计」的证据，而不是拍脑袋。

来源：[AgentSociety (ACL 2025)](https://aclanthology.org/2025.acl-industry.94/)、
[Concordia](https://github.com/google-deepmind/concordia)。

## 5.5 组织即代码（Org-as-Code）

ODL（Organizational Definition Language）等项目在尝试「用代码定义组织」：
角色、团队、政策、流程。这个方向与 Studio 的「公司=git 目录」高度一致。
可借：
- 组织定义应该是声明式的、可版本化的、可测试的；
- 但不要依赖某个早期工具；先把自己的 schema 做稳。

来源：[ODL](https://github.com/co-crea/odl-lang)。

## 6.1 不建议借的

1. **完整 BPMN/CMMN 引擎**：概念可借，引擎太重；Studio 的 FSM + workflow 子集够用。
2. **完整 Actor 运行时重写**：借 mailbox/supervision/backpressure，不必换运行时。
3. **DAO token 投票**：借 proposal/quorum/timelock，不借币。
4. **学术 MOISE+ 引擎**：借本体（role/group/mission/norm），不必实现形式化引擎。
5. **「控制塔」式 dashboard**：ServiceNow 的教训——没有运行时强制，治理只是工单。
6. **Agent registry 只做 inventory**：没有生命周期/绩效/退役，就是资产清单。
7. **组织架构图没有授权/quorum**：那是 persona theater，不是组织。
8. **用 cron 表达一切**：时间只是触发器之一；义务/事件/委派/升级都是触发器。

# 第七部分 · 目标架构：四层分离

```
┌─────────────────────────────────────────────────────────────┐
│ Company Spec（声明式，git 可移植）                          │
│  org / roles / authority / obligations / policies / budgets │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ Institutional Kernel（制度内核）                            │
│  identity/registry · authority graph · policy engine       │
│  ledger · memory · performance · audit                     │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ Orchestration Kernel（编排内核）                            │
│  event bus · durable workflows · scheduler · queues        │
│  SLA/timers · human tasks · retries/replay/compensation    │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│ Execution Kernel（执行内核）                                │
│  executor port · workspaces · tools/MCP · sandbox          │
└─────────────────────────────────────────────────────────────┘
```

**关键判断**：当前 daemon 把 Institutional + Orchestration 混在一起。
这不是错，但会导致：
- 状态机/授权/调度/账本耦合，改一个动全身；
- 无法替换编排引擎；
- 无法独立测试授权/义务。

建议：
- **Company Spec**：声明式，不存运行时状态；
- **Institutional Kernel**：回答「谁有权、谁负责、证据在哪、学过什么」；
- **Orchestration Kernel**：回答「什么时候、按什么顺序、失败了怎么办」；
- **Execution Kernel**：回答「在哪跑、用什么工具、怎么隔离」。

# 第八部分 · 演进路线（建议）

| 阶段 | 交付 | 验收 | 风险 |
|---|---|---|---|
| **0（现在）** | 保留 cron/hook；补事件 schema/幂等；加 `obligations` 配置；加 per-position inbox 读模型 | 每个岗位能看到「欠什么」；事件可重放 | 低 |
| **1（2-4 周）** | 一条耐久工作流（ticket→plan→build→review→merge）；SLA timer；人工任务；重试/恢复 | kill 后恢复；审批等待不占进程；超时升级 | 中 |
| **2（4-8 周）** | Agent registry/identity；position contract；策略表/授权图 v0；quorum v0 | 每个 agent 有身份/sponsor；高风险动作需 2 方；同一进程不能多签 | 中高 |
| **3（8-12 周）** | 记忆/反思；组织仿真；A2A；绩效/退役 | 同类返工下降；组织配置仿真；岗位间协议 | 高 |

**如果只能做三件**：
1. **义务/SLA 模型**（让岗位有「欠账」）；
2. **耐久工作流/事件总线**（让长流程可靠）；
3. **授权图 + quorum**（让岗位有实权且可信）。

# 第九部分 · 结论

### 9.0 五条前沿共识

| # | 共识 | 含义 |
|---|---|---|
| 1 | Agent 不是 prompt，是 identity + lifecycle | 独立身份、sponsor、权限、评审、退役 |
| 2 | 岗位不是 job，是 authority + obligations + interfaces + budget + memory | 定时只是触发器之一 |
| 3 | 组织不是部门列表，是 roles/groups/missions/norms + 治理节奏 | 部门只是容器，规范才是制度 |
| 4 | 工作不是 hook，是 event + durable workflow + human task | 事件有 schema/幂等/重放；长流程可恢复 |
| 5 | 治理不是 dashboard，是 runtime enforcement + evidence + quorum | 能拦截、能追责、能多签，才算治理 |

1. **「定时 + hook」不是太简单，是层次不对。** 它是触发器层；岗位是责任层；
   组织是权威/协作层。三层不能压成一层。
2. **前沿的共同方向是「四层分离」**：义务 → 编排 → 授权 → 身份。
   Temporal/CMMN 管编排，MOISE+/VSM/Team Topologies 管组织，
   Workday/Agent 365/IBM 管身份/生命周期，EP-QUORUM/OPA 管授权。
3. **最该借的三件**：义务/SLA、耐久工作流/事件总线、授权图/quorum。
4. **最不该做的三件**：把 cron 加得更复杂；把组织画得更大；
   把「控制塔」做成 dashboard。
5. **一句话**：**岗位不是定时任务，组织不是部门列表，治理不是 dashboard。**
   先把「义务、授权、身份」做成机制，再谈「自治理」。
