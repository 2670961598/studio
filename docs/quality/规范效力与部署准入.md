# 规范效力、迁移模式与部署准入（GOV-01）

> 归属：task-160 / GOV-01（框架 + studio-dev；Kimi 总审 P0-06/P1-01，制作人 2026-11-28 批准）。  
> 定位：统一规范效力、实现现状、部署准入与迁移模式的唯一口径与机读入口。**不改动任何生产 yaml、不修改契约冻结面、不启用 V2 enforce。**

## 1. 核心原则：`spec-final` ≠ `deployment-eligible`

- **文档正文只引用，不再多处重复维护“是否已落 / 是否可部署”状态**；唯一机读事实源落于 `docs/quality/governance/` 四张 JSON 表。
- **规范定稿（`final`）** 只表示规范文本经复查与签认冻结，不自动推导“实现已闭合”或“可无条件上线”。
- **历史段落不重写**：旧卷/旧切片出现与现行口径冲突时，按惯例保留历史原貌并追加「失效区间注记 / 历史快照」指向机读表与上位权威。

## 2. 机读三表与迁移模式表

| 文件 | 职责 | 关键字段 |
|---|---|---|
| `docs/quality/governance/spec-registry.json` | 规范效力表 | `id`、`status`（`final\|draft\|partial\|open`）、`authorityDoc`/`authoritySection`、`authorityRole`（DOM-05 仅可 `projection`）、`deployEligibility`（`eligible\|conditional\|blocked`） |
| `docs/quality/governance/implementation-registry.json` | 实现状态表 | `specId`（与 spec 表 1:1）、`state`（`implemented\|partial\|not_implemented`）、`recordsAuthorityModel`、`evidence`（`commits`/`files`/`tests`/`note`；无证据不得标 `implemented`） |
| `docs/quality/governance/deployment-admission.json` | 部署准入表 | `targetProfile`、`requiredSpecIds`、`fingerprints`（commit/Node/CLI/schema/contract/lockfile/config）、`checklist`（8 类）、`currentDeployments`、`exemptions` |
| `docs/quality/governance/migration-modes.json` | 迁移模式表 | 逐公司/逐面 `legacy\|shadow\|enforce`、`upgradeCriteria`、`productionYamlModified=false`（只读治理登记，禁改生产 yaml） |

## 3. `legacy / shadow / enforce` 定义与升级条件

| 模式 | 语义 | 允许条件 / 升级门槛 |
|---|---|---|
| `legacy` | 旧轨运行：以既有收割四要件与运行规则为准，不产生新面强阻断 | 既有基线面 |
| `shadow` | 影子观察：新面伴随运行并产出完备性报告/观测指标，拒写或缺失留痕但不阻断主链路 | 新面写口与观测接入后进入；**studio-dev 默认 `legacy → shadow` 过渡** |
| `enforce` | 强态阻断：必备记录或不变量缺失直接 fail-closed 拒迁移/拒收口 | 须在 `migration-modes.json` 该面登记具名批准 `enforcementApproval`（`{ticket,approvedBy,approvedAt}`），通用或「暂缓 enforce」豁免不得替代；禁止 `open`/`blocked`/`not_implemented` 项强启 |

### V2 enforce 暂缓的裁决依据

依据 `docs/sentinel-logs/全面Review拆分-2026-11-28.md` §7（制作人 2026-11-28 10:30 裁决）：
1. **V2 records 暂缓 enforce**：studio-dev 维持 `legacy → shadow` 观察，待 **FIX-05**（CAP-02/AUTH-02/接受回执/LIFE-01/04/EVD-01 生产者与回退返工状态边闭环）与 **ARCH-01**（跨进程写者 fencing + PRB-14 当前 commit 取证）完成后，再逐公司报制作人批准切换 `enforce`。
2. **概念不混用**：`acceptanceEnforce`（收割四要件与验收闸）自 2026-11-17 已 enforce，与 `v2-records` enforce 相互独立；`migration-modes.json` 分面单列，禁止混推。
3. **扩量与 agy 禁令**：V2 闭环前不扩公司/泳道/daemon 写者/生产执行器；`SPEC-ENU-88-AGY` 标为 `deployEligibility: "blocked"`，严禁进入部署准入面。

## 4. 部署准入清单（对应 `scripts/ops/deploy.mjs`）

| # | 类别 | 对应检查点与脚本锚点 | CI 静态校验 | 部署窗口核验（`deploy.mjs` / 旁证） |
|---|---|---|---|---|

| 3 | `cli` | 生产执行器绑定版本（`dsh`/`kimi`）；未认证执行器（`agy`）保持禁用 | 阻断 `deployEligibility=blocked` 进入 `requiredSpecIds` | 启动日志与探针核对启用执行器清单 |
| 4 | `schema` | SQLite store schema 版本（当前 v17）与迁移文件一致、兼容回滚 | 校对最新迁移文件 `version: 17` | 无破坏性迁移或附回滚方案 |
| 5 | `contract` | 冻结 JSON Schema 工件零漂移（74 类 / 13 AREA） | 校对 `packages/contract/artifacts/index.json` sha256 与计数 | 同 commit 跑 `bun run contract:check` |

| 7 | `health` | 重启后新 pid 替换旧 pid，`/healthz` 返回 `200` 且 `ok=true`、`chain.ok=true` | 校验 checklist 覆盖项存在 | `deploy-health.mjs` 轮询至新 pid 就绪，失败自动回滚树与 state |

## 5. CI 门禁与显式豁免流程

### 5.1 命令用法

```bash
# 独立运行（人类可读输出；任一违例 exit 1）
bun run verify:admission
node scripts/verify/spec-admission.mjs

# 机器可读 JSON 输出（CI / 自动化消费；支持 --now YYYY-MM-DD 注入时钟）
node scripts/verify/spec-admission.mjs --json

# 文档与治理联合门（v0-doc-check + spec-admission）
bun run verify:docs
```

### 5.2 检出违例类（fail-closed）

- `MISSING_TABLE` / `INVALID_JSON` / `SCHEMA_INVALID`：缺表、坏 JSON 或字段/枚举非法；
- `RECORDS_AUTHORITY_CONFLICT` / `DOC_RECORDS_AUTHORITY_CONFLICT`：records 权威与 DOM-05 投影口径冲突；
- `SPEC_FINAL_DRAFT_CONFLICT` / `DOC_FINAL_DRAFT_CONFLICT`：final/draft 冲突或非 `final` 条目冒用 `eligible`；
- `IMPL_STATUS_CONFLICT` / `DOC_IMPL_STATE_CONFLICT`：无证据宣称 `implemented`、同条矛盾状态或文档已落/未落无失效注记；
- `THREE_TABLE_MISMATCH`：三表与迁移表引用不闭合或文件不存在；
- `UNAPPROVED_ADMISSION_OPEN_PARTIAL` / `BLOCKED_SPEC_ADMITTED` / `ENFORCE_UNMET_PREREQ`：未获批准的 `open/partial/draft` 或 `blocked` 项进入准入面，或前置未满开启 `enforce`；
- `EXEMPTION_INVALID` / `EXEMPTION_EXPIRED`：豁免缺原因/批准人/到期日或已过期；
- `DEPLOY_CHECKLIST_INCOMPLETE` / `DEPLOY_FINGERPRINT_MISMATCH`：部署清单缺类，或 commit/tree（`git rev-parse`，git 不可用时 fail-closed）、CLI 启用态（`agy` 未批准不得 `production`）、`configDigest.yamlDigests` sha256、`contractArtifacts`/`lockfile`/`storeSchema`/`nodeRuntime` 任一缺失或漂移。
- `IMPL_STATUS_CONFLICT`（伪证据）：`implementation-registry.json` 中 `implemented`/`partial` 的 `evidence.files`/`tests` 必须相对仓根真实存在（目录/文件按声明类型校验），不存在一律 FAIL。

### 5.3 显式豁免流程

1. 任何 `open` / `partial` / `draft` 规范或非 `implemented` 实现进入 `requiredSpecIds`，必须在 `deployment-admission.json` 的 `exemptions[]` 登记：
   - 必填：`id`、`specId`、`reason`、`approver`、`approvedAt`（`YYYY-MM-DD`）、`expiresAt`（`YYYY-MM-DD`），并建议附 `trackingTask` 与 `mitigation`。
2. **无豁免或 `expiresAt < 当前日期` 一律 fail-closed（exit 1）**；禁止口头豁免或无限期豁免。
3. 豁免到期前须由对应任务关闭并移出豁免，或重新走制作人审批延期并更新 `approvedAt`/`expiresAt`。
