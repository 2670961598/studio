# 验收闸门超时配置与调优（acceptanceTimeoutMs；task-138）

- 状态：已实现（task-138；设计面=docs/17-§6 验收闸门超时位别注记）。
- 一句话：daemon.yaml 可配**公司级**验收闸门超时 `acceptanceTimeoutMs`（整数毫秒，1000..3600000）；
  缺省不配＝60s 旧语义**零行为变化**；启用＝加键+重启，回滚＝删键+重启。

## 0. 背景与问题

2026-11-26 哨班实证（docs/sentinel-logs/哨班-2026-11-26-2215.md）：`ACCEPTANCE_GATE_TIMEOUT_MS`
固定 60s，而重载公司的冻结验收命令（如整仓 `node --test`，194 个测试文件）在负载高时必超 60s
→ 超时判 `exit=124` → GATE_FAIL → 断路器熔断 → 半开重派循环——每次完整 worker 跑 10-30 分钟、
占用并发槽，队列极慢。根因＝超时是**公司无关的编译期常量**，验收负担重的公司无法自调。
本单把它升为公司级配置（fail-closed 校验，不静默取默认）。

## 1. 字段说明（daemon.yaml）

```yaml
# 冻结验收命令（既有键，真验收闸门形态开关——本单不新增开关语义）
acceptance: "cd .AIWS/repos/workbench-plugin && node --test"

# 验收闸门超时：逐条冻结验收命令的执行上限（ms）
acceptanceTimeoutMs: 300000
```

- 键：`acceptanceTimeoutMs`，可选；**整数毫秒**，闭区间 **1000..3600000**（1s..1h）。
- **非法值＝配置错误 fail-closed**（启动即报错退出，不静默取缺省）：0、负数、非数字、字符串、
  带小数点、超范围（如 500、3600001、`"300000"`）——报错形如
  `daemon.yaml：acceptanceTimeoutMs 须为 1000..3600000 的整数（实得 …）`。
- **缺省不配置＝60s**（真源＝`apps/daemon/src/engine/gate.ts` 的 `ACCEPTANCE_GATE_TIMEOUT_MS`；
  配置文档不复制数值，以代码常量与启动日志为准）。
- 上限 1h 封顶：超时是收割相位的挂死兜底，不是长任务授权面——超过 1h 的验收命令应拆条
  （命令间短路语义归命令文本自身，闸门只认逐条退出码）。

## 2. 生效路径（单一生效值双消费）

```
daemon.yaml acceptanceTimeoutMs
  → serve/config 解析即验（CONFIG_INVALID fail-closed）
  → ServeConfig.acceptanceTimeoutMs
  → buildServeRuntime 装配（assembly/serve/runtime.ts）
      ├─ createAcceptanceGateRunner(…, timeoutMs)   # 收割闸门：逐条命令 runShell 超时
      └─ createDefaultMergeRunDeps({…, timeoutMs})  # 合并跑门禁（202-P2 引擎亲跑，同一值）
```

- 同一值喂两张门：收割四要件第 4 条的闸门命令执行，与合并跑（merge）门禁——不出现「收割等
  60s、合并跑等另一值」的双源漂移。
- 缺省链：不配该键 → `undefined` 下传 → `gate.ts` / `merge/default-deps.ts` 各自兜底同一常量
  `ACCEPTANCE_GATE_TIMEOUT_MS`（60s）——缺省值真源唯一，不在配置层复制。

## 3. 启动日志（核对面）

启动时固定输出一行，供公司验收人员核对生效值与来源：

```
[serve] 验收闸门超时=300000ms（来源=daemon.yaml）     # 配置了 acceptanceTimeoutMs
[serve] 验收闸门超时=60000ms（来源=缺省）             # 未配置（60s 缺省）
```

- 修改后**需重启 daemon 进程**生效：daemon.yaml 只在启动时解析装配（公司目录热重载不含
  daemon.yaml 本体）。
- 回滚＝删键＋重启（回到 60s 缺省，零行为变化）。

## 4. 何时调大 / 何时不调

- **调大**：验收命令是真跑整仓测试/构建的重载命令，且台账出现 `GATE_FAIL` note 携
  `exit=124(timeout)`——这是超时判负的直接证据，先看证据再调，不凭感觉。
  workbench 类形态（验收命令=整仓 `node --test`）经验值 **300000**（5 分钟）。
- **不调**：验收命令是轻量检查（`test -s`、lint 单文件）——调大只会推迟挂死暴露，无收益。
- **不治根**：超时调大治「误杀慢验收」，不治「验收本身慢」——验收慢应在公司仓侧优化
  （分条命令/并行化/瘦身测试集），不要用超大超时掩盖。

## 5. 风险与边界（如实）

- **挂死等待上限**：配 `T` ms 后，一条挂死的验收命令最多等 `T`（+2s 杀组宽限）才判负——
  期间该单收割相位被占住（拍有界设计内的兜底等待）。**逐条独立计时**：N 条命令最坏总等待
  ≈ N×T；上限 1h 即单条最坏 1h。调大前想清楚「真愿意等这么久吗」。
- **误判红→熔断链**：超时与验收失败同走 GATE_FAIL 面（断路/半开重派既有语义不变）——调大
  只减少超时误判，不改变判负后的任何链路行为。
- **不碰四要件**：超时不是新要件，是要件 4「闸门 exit=0」的执行边界；判据、事件词、
  契约、schema 零变更。
- **双门同值**：合并跑门禁同吃该值——公司若只想要收割闸门放宽而合并跑收紧，当前不支持
  （单一生效值是有意设计，防双源漂移；有真实需求再立单）。

## 6. 验收人员操作步骤（checklist）

1. 看证据：面板/台账查该单 `GATE_FAIL` note 是否含 `exit=124(timeout)`。
2. 估上限：验收命令单次真跑耗时 p90 × 2 起步，不超 3600000。
3. 改配置：编辑该公司 daemon.yaml，加/改 `acceptanceTimeoutMs: <毫秒>`（整数、1000..3600000）。
4. 重启：停 daemon → 起 daemon（受权重启通道同效）。
5. 核对：启动日志找 `[serve] 验收闸门超时=<ms>ms（来源=daemon.yaml）`——没这行或来源=缺省，
   说明键没写对（键名拼错会在启动时以「未知配置键」明报拒绝，fail-closed 不静默）。
