# 自研业务向模型能力评测基准：规范设计（benchmark v1）

> 状态：v1（LOCAL-299 设计稿；冒烟实证见 §8）。姊妹文档：`model-eval.md`（评测台的用法与口径）。
> 依据：docs/17 §2（主循环七相位）、§6（收割四要件）；docs/20 §十五（尺寸阈与目录切分）。
> 一句话：评测台负责「跑」，本规范定「怎么比才算数」——任务集、评分体系、控制变量、统计协议、局限与威胁。

## 0. 结论

- 基准 = **6 个业务任务族**（评测台已有 fixtures 与判定器）+ 本规范的**评分 / 控制 / 统计**口径；不另起炉灶，只做加法（`scripts/ops/model-eval/benchmark/`）。
- **硬门先于软评**：确定性检查决定一格是否通过；盲评 rubric 只描述质量高低。格分 = 0.7 × 确定性分 + 0.3 × 盲评总分 / 12。
- **设施与能力分离**：供应商侧失败（限流、过载、鉴权、额度）不计入模型分，重试后仍缺则单列；模型侧失败（拒答、预算内未完成）计 0。
- **冒烟（reps = 2）不下优劣结论**；正式对比要求 reps ≥ 3、设施侧缺格 ≤ 10%、盲评 ≥ 2 人且 κ ≥ 0.4。
- 冒烟实证：GLM-5.4、GLM-5.3 × 6 任务 × 2 次全部产出样本并出报告（GLM-5.4 有 3 格在 300 s 预算内未完成，计 0；§8）；Kimi、DeepSeek 本轮因设施侧原因（鉴权过期 / 月度额度）未产生样本，如实列为缺口。

## 1. 目的、定位与原则

### 1.1 要回答的问题

在本公司真实业务任务上，各候选模型（Kimi 3.1 Pro / DeepSeek 4.1 Flash / GLM-5.4 / GLM-5.3 等）的适配度如何——哪个模型更适合哪一档工位（high = verifier / 综合 / 决策；mid = 主力 worker；patrol = 巡检岗）。结论须**带区间、可复现、可审计**。

### 1.2 不回答的问题

- 通用能力排行榜：任务集只有 6 族，代表不了「模型整体强弱」。
- 单次抽样的名次：n 小、区间宽是常态，名次只在区间分开时才有意义。
- 安全红队、价格谈判、供应商评测：不在本基准范围。

### 1.3 设计原则

| 原则 | 含义 | 落在哪 |
|---|---|---|
| 硬门先于软评 | 能用脚本判的绝不用人判；人只判脚本判不了的 | §3.1、§3.2 |
| 设施与能力分离 | 供应商抽风不算模型不行，但也不能悄悄抹掉 | §5.3、§5.6 |
| 先到先得 | 同一格多次运行取**第一个有效样本**，不存在「挑最好的一次」 | §5.4 |
| 控制变量可核 | 跑前留指纹，批次间不一致就不合并下结论 | §4.4 |
| 结论不超出口径 | 冒烟只说「能跑 / 口径成立」，正式才说「谁强」 | §5.8 |

### 1.4 与评测台的关系

| 能力 | 评测台（`model-eval.md`） | 本规范补充 |
|---|---|---|
| 任务集与 fixtures | 6 个任务、`prompt.md` + `fixtures/` + `check.mjs` | 任务族定义、新增任务准入（§2） |
| 判分 | 确定性检查（0.7）+ LLM 裁判（0.3） | 人工盲评 rubric 与一致性门槛（§3）；LLM 裁判降为过渡替身（§3.6） |
| 运行 | `run.mjs`：隔离工位、事件流、脱敏、`report.json` | 多批次合并、重试规则、指纹（§4、§5.4） |
| 统计 | 逐格分、逐模型均值、档位排序 | 区间、配对比较、失败分类、结论闸（§5） |
| 局限 | §8 列了样本小、裁判有偏、隔离有限 | 逐项威胁—影响—缓解表，标注本次是否已发生（§6） |

## 2. 任务集

### 2.1 六个任务族

全部是「给材料 → 在工位里干活 → 留下可检查的产物」，对应主循环里 worker 的真实形态（docs/17-§2：采集 → state-diff → 派发 → 收割 → 合并 → 回收 → 落账/心跳；本任务集覆盖的是「派发 → 收割」这一段）。

| 族 | 任务 | 业务场景 | 输入（只读） | 期望产物 | 硬门要点（`check.mjs` 必过项） |
|---|---|---|---|---|---|
| 工单闭环 | `t01-ticket-report` | 巡检岗按任务书出巡检报告与跟进计划 | 任务书、健康快照、额度状态、事件尾日志 | `REPORT.md` + `deliverables/plan.md` | 验收命令 exit 0；`REPORT.md` 有效字符 ≥ 300、含巡检日期与任务编号；结论 / 证据 / 下一步三小节；证据 ≥ 3 条且关键事实命中 ≥ 3；结论须为「告警」；`plan.md` 是计划表格；fixtures 未改 |
| 代码修复 | `t02-bugfix` | 修复「日闭窗口」的闭开区间缺陷 | 最小 TS 包（`src/`、测试、`package.json`） | 工作树内的修改 | `node --test` 全绿且用例数不减；测试文件、`package.json`、README 未动；无新增 / 删除文件；改动 ≤ 30 行（附加项：只动 `src/window.ts`） |
| 信息综合 | `t03-research` | 三份材料综合出「本周平台风险 Top3」 | 周报、事件台账、额度快照（各带出处标记） | `report.md` | 关键数字命中 ≥ 3；出处标记 ≥ 3 处且覆盖 ≥ 2 个来源；编号风险 ≥ 3 条；fixtures 未改（字数、排序、「建议关注」节为附加项 / 盲评） |
| 中文公司语境决策 | `t04-triage` | 值班分诊：按规程条款对请求逐项判定 | 分诊规程（G-01 ～ G-08）、在途单、请求 | `decision.md` | 判定行、逐项覆盖、条款引用；被拒的动作不得出现在下一步；下一步含补证据动作（D-120 事实核对、风险段为附加项） |
| 工具链多步 | `t05-toolchain` | 写脚本统计滞留单并生成 CSV / JSON | `tickets.json` | `stats.mjs` + `out/*.csv` + `out/summary.json` | CSV 值全对；`summary.json` 值与键序全对；脚本存在；输入未改、无新增依赖（期望值由判定器从原件重算；字节级规范、缩进、可重跑为附加项） |
| 长上下文抗漂移 | `t06-longctx` | 1.3 万字纪要汇编里答 3 问，抵制相近干扰条目 | 纪要汇编（同一主题有早中晚多条记录） | `answer.md`（7 行） | 六个事实项（拍板人 / 条件 / 根因 / 措施编号 / 上限 / 处理）各一条必过；关键事实只在材料中部，首尾放同类干扰项（依据章节、7 行格式为附加项） |

六族分别压的是六种不同的失效方式：**编造**（t01、t03）、**作弊**（t02 改测试到通过）、**越权与失仪**（t04）、**格式纪律**（t05）、**被干扰材料带偏**（t06）、**任务书纪律**（全部：只读写工位、不联网、做完即停、不生成多余文件）。

### 2.2 工位与 fixtures 布局

- 每一格（模型 × 任务 × rep）一个全新工位目录，由评测台从任务原件复制；`fixtures/` 是只读输入。
- 两种布局：**只读输入型**（t01/t03/t04/t06：`fixtures/` 原样放工位，产物写在工位根）；**工作树型**（t02/t05：fixtures 摊到工位根，判定器比对「相对原件改了什么」）。
- 公司级指令（`AGENTS.md`）以 `user_level` 注入，同一批次内对所有模型一致。

### 2.3 每份任务书必带的约束

只读写当前工作目录、不联网、不装依赖、做完即停、不生成任务书以外的文件。这些约束本身就是被测内容：合规性维度（§3.3）与判定器里的「受保护文件未变」「无多余文件」检查据此判分。

### 2.4 新增任务的准入清单

1. 业务侧能说清「这一族压的是哪种失效方式」，且与现有六族不重复。
2. `prompt.md` + `fixtures/`（脱敏，不含密钥、真实人名、内网地址）+ `check.mjs`，遵守评测台的 `check(ctx)` 契约。
3. **必过项 ≥ 3**，且至少一项是反作弊面（受保护文件哈希、产物白名单、用例数不降）。
4. 导出 `rubric`（业务质量要点），供裁判与盲评参考。
5. 离线测试进 `scripts/test/model-eval-checks.test.mjs`；用至少一个模型试跑 2 次确认可完成（否则先调预算而不是放宽判定）。
6. 进 `fingerprint.mjs` 的指纹范围（自动，无需额外操作）。

### 2.5 任务集的覆盖缺口

目前没有：多轮协作（派发 → 追问 → 返工）、跨文件大规模重构、真实仓库量级的代码修复、带真实工具副作用的运维任务。补齐前，结论只覆盖「单轮、工位内、留产物」的业务任务。

## 3. 评分体系

### 3.1 两层结构

```
格（模型 × 任务 × rep）
 ├─ 第一层 确定性检查 check.mjs（权重 0.7）── 决定「过 / 不过」与确定性分 det ∈ [0,1]
 │    必过项（required）任一未过 ⇒ 该格 TASK_FAIL（样本有效，分记 det）
 │    全部必过项通过          ⇒ 该格 OK（det 可因附加项 < 1）
 └─ 第二层 盲评 rubric（权重 0.3）── 只描述「差在哪里、好在哪里」，总分 b ∈ [0,12]
      格分 = 0.7 × det + 0.3 × b / 12
```

### 3.2 确定性检查的写法规则

- 检查项分**必过**与**附加**；必过项是硬门，附加项只调分。权重由各任务 `check.mjs` 自定并写进文件头注释。
- 能对着输入核实的才判：字数、小节、表头、哈希、测试结果、条款编号。判不了的留给盲评。
- 反作弊面必设：测试文件与配置文件哈希不变、产物白名单、用例数不降、改动行数上限。
- 判定器自身出错（`checkError`）不是模型的错：该格记 `HARNESS_BUG`，不计分，修后重跑（§5.3）。

### 3.3 盲评 rubric（人工）

全文见 `scripts/ops/model-eval/benchmark/rubric.md`。要点：

| 维度 | 0–3 分问什么 |
|---|---|
| 正确性 `correctness` | 结论 / 数据 / 修改对不对，能否对着输入逐项核实 |
| 完整性 `completeness` | 任务书要求的交付是否齐，有无要求外夹带 |
| 合规性 `compliance` | 是否只做授权的事：工位、权限、格式、范围；有无泄密 |
| 可读性 `clarity` | 业务同事能否直接用：结构、中文表达、粒度 |

- 总分 0–12，只打整数；拿不准取低一档并写 `notes`。
- **匿名**：`blind.mjs build` 把有效样本格（OK / TASK_FAIL）的产物打乱编号（`S-001`…），模型身份留在 `mapping.json`，评审不得打开；同种子同顺序，可复现。
- **≥ 2 人独立评分**，先各自用 2 条条目试评对齐锚点，不互看、不商量。
- 入包的是模型产物与任务书原文；产物里出现**任务书里没有的**品牌词，会被 `leak-scan.json` 标为可疑，须人工复核是否自报身份（任务材料本身提到的路由名、冷却源不算泄漏）。

### 3.4 一致性与仲裁

- 报：完全一致率、|Δ| ≤ 1、|Δ| ≤ 2（Δ = 两评审总分差），以及三档（≤ 4 低 / 5–8 中 / ≥ 9 高）Cohen's κ。
- 门槛：κ ≥ 0.67 高、0.4–0.67 中，可用于正式对比；κ < 0.4 回到锚点校准后重评。
- 跨评审总分极差 > 2 的条目进**仲裁**（第三人或合议），只定争议条目，不回改无争议分。
- 单人评审的汇总一律标 `singleReviewer`，不得用于正式对比。

### 3.5 折分

- 格分 = 0.7 × det + 0.3 × (盲评总分 / 12)。模型侧失败格恒为 0，不折主观分。
- 未做盲评时只用确定性分（`stats.json → scoring.mode = 'det'`），报告须照录折分模式。

### 3.6 LLM 裁判的定位

评测台自带的 `--judge` 只是盲评的**过渡替身**：裁判偏好冗长工整的产物，且可能与被测同源。规则：裁判固定不随被测变；`judgeSelf = true` 的格不折裁判分；折了裁判分（`mode = 'det+judge'`）的结论必须注明「未经人工盲评」。

## 4. 控制变量

### 4.1 变量表

| 变量 | 要求 | 现状 / 取值 | 证据 |
|---|---|---|---|
| 执行壳（dsh）版本 | 批次间固定 | 同一版本；不一致不合并 | `fingerprint.mjs --env` |
| 评测台代码（`run.mjs` / `judge.mjs` / `lib/`） | 批次间固定 | 树哈希 | `fingerprint.json → harness` |
| 任务书、fixtures、判定器 | 批次间固定 | 每任务：原件 / 渲染后 / check / fixtures 四个哈希 | `fingerprint.json → tasks` |
| 模型标识 | 显式 `provider/model` | 如 `glm/GLM-5.4`、`kimi-coding/k3.1-pro` | `report.json → rows[].modelId` |
| 温度 / 采样参数 | **应固定** | **未固定**：执行壳未暴露，按供应商默认 → 威胁 T2 | 人工登记（报告模板 §1） |
| 提示词 | 固定 | 渲染后字节的 sha256（= 模型实际看到的） | `fingerprint.json → tasks.*.promptRendered` |
| 单格超时 | 固定 | 300 s（评测台默认） | `report.json → config.timeoutMs` |
| 重复次数 | 冒烟 ≥ 2；正式 ≥ 3 | 照录 | `report.json → config.reps` |
| 裁判 | 固定且不同源，或关闭 | 冒烟 `none` | `report.json → config.judge` |
| 工位 | 每格全新目录，跑完留档 | `work/<task>__r<n>/` | 产物目录 |
| 并发 | 同批一致；优先各模型**串行** | 首轮两模型并发，观察到过载与贴线超时（§8） | 运行日志 |
| 运行时间窗 | 记录起止 | 照录 | 报告模板 §1 |
| 凭据 | 每模型只注入其所需 key；不入报告 | 子进程 env 隔离 + 报告脱敏 | 评测台 `overlay.mjs`、`redact.mjs` |

### 4.2 执行壳与隔离

- 所有模型走**同一条**调用链：评测台 → dsh headless profile → 供应商；评测台不认识任何一家的专有接口。
- 三层隔离：**进程级**（每格一个独立子进程、独立工位）；**配置级**（每格独立 overlay，`DSH_HOME` 指向隔离目录）；**凭据级**（子进程只拿到该模型所需的 key）。
- 已知缺口：被测模型的工具不在内层沙箱里（headless profile 为全权限），「只读写工位」靠任务书约束 + 判定器事后核对。含敏感数据的机器不得无人值守跑。

### 4.3 提示词

任务书用 `{{include:fixtures/…}}` 引用材料，评测台渲染后再发给模型。指纹对**原件**与**渲染后**各记一个哈希：原件变说明任务书改了，渲染后变说明「模型看到的字节」变了——后者才是控制变量的真正锚点。

### 4.4 指纹（`model-eval-fingerprint/v1`）

- 范围：评测台代码（不含 `tasks/` 与分析工具 `benchmark/`）、每个任务的四项哈希、评测台全树哈希。不含绝对路径，可随报告归档。
- 用法：跑前 `fingerprint.mjs --out <outDir>/fingerprint.json`；统计时 `stats.mjs --fingerprint <file>` 比对当前评测台；多批次各带指纹时逐对比较，不一致的批次在 `stats.md` 头部**加粗提示**，不得合并下结论。

### 4.5 运行窗口

同一批比较尽量在同一时间窗内跑完；跨窗（如跨天、跨供应商发版）须在报告里登记，并在「局限」里评估影响。

## 5. 统计协议

### 5.1 记号

- **格** = 模型 × 任务 × rep；**批** = 一次 `run.mjs` 运行 = 一份 `report.json`。
- **格分** s：折分后的格分（§3.5），未折分时为确定性分。
- **有效格**：产生了可归因于模型的结果（OK / TASK_FAIL，以及计 0 的模型侧失败）。
- **缺格**：设施侧或评测台侧失败导致的空格，不进能力均值。

### 5.2 重复次数

| 口径 | reps | 能说什么 |
|---|---|---|
| 冒烟 | ≥ 2 | 可运行、口径成立、设施缺口在哪；**不说谁更好** |
| 正式 | ≥ 3（时延类结论建议 ≥ 5） | 按配对差区间读优劣（§5.7） |

每格独立运行、独立工位；不把同一 rep 的多次重跑当作多个样本（见 §5.4）。

### 5.3 失败分类

| 类别 | 触发 | 归属 | 计分 | 处置 |
|---|---|---|---|---|
| `OK` | 必过项全过 | 样本 | det | — |
| `TASK_FAIL` | 有必过项未过 | 样本 | det（可 > 0） | 盲评看「差在哪」 |
| `SAFETY_REFUSAL` | 拒答 / 被拦 | 模型 | 0 | 记为模型侧失败 |
| `BUDGET` | 达 max tokens | 模型 | 0 | 同上 |
| `BUDGET:timeout` | 同格累计 ≥ 2 次超时仍无有效样本 | 模型 | 0 | 时限预算内未完成 |
| `LIMIT:timeout` | 首次超时 | 设施（待复核） | 不计 | 重试 |
| `PROVIDER_ERROR:quota / rate_limit / server / network / auth` | 额度、限流、过载、网络、鉴权 | 设施 | 不计 | 重试 ≤ 2；仍缺则单列 |
| `PROVIDER_ERROR:bad_request` | 请求被拒 | 设施（待归类） | 不计 | 人工看日志；上下文超限改判模型侧 |
| `HARNESS_BUG` | 判定器异常 / 评测台故障 / 报告结构坏 | 评测台 | 不计 | 必须修后重跑 |
| `UNKNOWN` | 其余（解析失败、中止…） | 未知 | 不计 | 人工看日志归类 |

归属决定两件事：进不进能力均值（样本 / 模型侧进，其余不进）、阻不阻塞结论闸（只有设施侧与评测台侧缺格阻塞）。

### 5.4 多批次合并

1. 多份 `report.json` 按 `generatedAt` 排序；格键 = `模型|任务|rep`。
2. **第一个有效样本定稿**（先到先得）；之后的同格结果记为 `extraRuns`，不替换、不平均。
3. 无有效样本时取最后一次尝试的类目；其中 `LIMIT:timeout` 累计 ≥ 2 次改判 `BUDGET:timeout`（模型侧，计 0）。
4. 补跑只针对缺格所在任务整任务重跑（评测台不支持按 rep 选）；已有有效样本的格不受影响。

### 5.5 区间

| n（每模型每任务的有效格数） | 报什么 |
|---|---|
| 0 / 1 | 不给区间 |
| 2 | 只报极差 [min, max] |
| ≥ 3 | 双侧 95% t 区间 mean ± t₀.₉₇₅,ₙ₋₁ · s / √n（df > 30 用 1.96 近似） |

样本方差为 0 时区间退化为一点，照实报。时延报中位数与 p90（最近秩法）。

### 5.6 两种口径

- **能力口径**（主口径）：缺格不计，均值只看有效格——回答「模型做出来时做得怎样」。
- **可用性口径**（对照）：缺格按 0 计入——回答「把它放上线，期望拿到什么」。
- 两口径都把模型侧失败计 0。两口径差距大 = 该模型受设施影响重，报告里必须点出。
- **硬门通过率**（统计表里的「全过率」）：有效格里必过项全部通过（类目 `OK`）的占比；附加项未过只扣分，不算失败。

### 5.7 配对比较

- 只比**共同任务**（双方都有有效格的任务），逐任务报均值差与领先 / 平 / 落后。
- 配对差 = 同任务同 rep 的格分之差；对配对差报区间（口径同 §5.5）。
- 判读：无共同任务 → `no-overlap`；任一方某任务有效格数 < 正式 reps → `insufficient`；区间含 0 → `indistinguishable`（分辨不出）；区间不含 0 → `distinguishable`。
- `indistinguishable` **不是**「一样」，只是「这组样本分辨不出」。

### 5.8 结论闸

| 条件 | 门槛 |
|---|---|
| 级别 | reps < 3 ⇒ 冒烟；否则正式 |
| 进推荐 | 预探可用且任务覆盖 ≥ 60% |
| 允许下优劣结论 | 正式口径 **且** 设施侧缺格比例 ≤ 10% **且** 有效模型 ≥ 2 **且**（折了主观分时）盲评 ≥ 2 人且 κ ≥ 0.4 |

闸门不过时，报告只写「可运行 / 口径成立 / 缺口」，不写名次。

### 5.9 报告必填项

按 `scripts/ops/model-eval/benchmark/report-template.md`：结论闸、控制变量登记（含温度是否固定）、可用性与覆盖、模型 × 任务、配对比较与区间、失败分类与人工定性、盲评与一致性、局限勾选、原始数据索引（`report.json` 的 sha256）。

## 9. 与主循环的对接

- **对 docs/17-§2（七相位）**：本基准是「派发 → 收割」的可重复实验。`t01` 的任务形态与验收命令就是主循环 worker 的形态（工位 + 任务书 + `REPORT.md` + `deliverables/plan.md`），因此基准结论可直接解释为「该模型当 worker 靠不靠得住」，而不是抽象分数。
- **对 docs/17-§6（收割四要件）**：评测台的收割同样要求终态 + 非空输出 + 产物落盘 + 判定可核；本规范把「闸门 exit = 0」细化为确定性检查，并补上「设施侧失败不是 worker 的错」这一中性处理。
- **对选型的意义**：档位排序（high / mid / patrol）只在结论闸放行后使用；冒烟阶段只回答「哪个模型现在能进正式对比」。
