## 4. 流程与治理缺口

| 治理面 | 已有有效机制 | 缺口与风险 |
|---|---|---|
| 验收 | 四要件、缺验收标准拒派、close 前 pass/waived+证据，能挡住假完成；11 月 26 日历史点待验收为 0 | 缺少本次可核验的待验收时序和 aging；供给错误被记成闸门失败；REPORT+exit=0 后缺终态仍需整单重跑。waived 的审批人、时效、范围及当前积压均**未核验**。 |
| 记录 | issue 首尾可见完整状态推进；事故库修复后链校验 PASS；当前 issue 文件数与队列总数一致 | CSV 无表头、时间口径混用；`done/CLOSE/已交付`缺本评审可核验的对账桥；Archived 被报未知；有产物无 REPORT；usage/cost 空文件。单日/单时点健康不能替代连续投影完整性。 |

## 5. 对框架设计的反馈（从运营反推）

> 以下是运营需求与建议，不断言框架代码一定没有实现；落地前应由框架负责人对照现有设计与契约核实。

1. **把“错误分类—重试决策”提升为核心契约，而非适配器散点特判。**统一识别 5 小时/7 天/月限额、速率限制、401、429、502、529、缺凭据、缺 adapter、worker dead；决策至少区分“等待 reset”“供给级熔断”“切换供给”“人工处理”“可重试”。用契约测试冻结同一错误在不同泳道和定时岗下的行为。
2. **将 attempt 租约、终态写入和证据复验做成幂等闭环。**每次 attempt 有唯一 ID，STALL/WORKER_DEAD/boot recovery 共用同一收口键；重复事件不得重复回退或增加 attempt。若 REPORT 与 gate exit=0 已存在，仅补终态时应走“复验并完成”，不得默认重跑模型，也不得绕过四要件。
3. **建设供给与成本一体化的调度控制面。**provider/lane 维度发布健康、reset-at、剩余预算、实际 token/成本；同源故障按 fingerprint 全局暂停。定时岗需要预算感知、jitter、去重/合并与降级策略，避免固定 cron 在配额耗尽时同步撞墙。
4. **把重启恢复从“能重派”提升为“可证明无损”。**除崩溃注入外，验收应覆盖重复收口、在途证据复用、台账完整性、服务自启/停驻持久化、备份恢复演练。关键数据库和 Docker 卷要有明确 RPO/RTO、最近可恢复点和负责人，而非只验证备份任务曾 PASS。
5. **提供面向运营的稳定投影与权限/升级数据模型。**每日快照至少含待验收量及 aging、当前 attempt、重试原因、供给、成本、告警 ACK、阻塞 owner/SLA；归档、waive、人工恢复必须带操作者/审批关联。事件与 CSV 使用明确时区和版本化 schema，使 `done→复验→交付→成本` 可对账。
