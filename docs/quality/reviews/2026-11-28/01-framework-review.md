# StudioNext 框架本体独立评审

> 评审对象：当前只读快照中的框架规范、质量专题与指定哨班记录。  
> 证据纪律：下文区分“规范要求”“文档自报实现”“历史日志观察”。本批未读源码、未执行测试，因此凡涉及真实代码行为均为**未核验**；历史日志只证明当时记录，不外推为当前仍存在。“未见/缺少”仅指授权阅读面，未读卷中是否另有补偿设计仍为**未核验**。  
> 严重度：P0＝可能破坏核心事实/权限/状态不变量，切权或扩展前必须关闭；P1＝显著影响可靠性、成本或治理；P2＝局部可观测性、运维与文档质量缺口。

## 结论摘要

框架的优点很明确：契约先行、纯函数核心、适配器四原语、fail-closed、租约 epoch、幂等/回滚意识、证据边界和负向用例均有较强设计。问题不在“没有制度”，而在**多套制度与实施状态同时存在，且关键不变量尚未形成同一条可验证执行链**。

当前快照最宜被解读为“既有生产链 + V2 规范 + 若干已接切片”的迁移态，而不是一个已经完成 V2 一致性闭环的系统。两个最优先事项是：①在 V2 权责记录缺账时，不再把旧四要件直接当作完整 V2 收口；②把“唯一写入者”从部署约定升级为跨 SQLite、平台网关和公司 git 的 fencing 机制。其后才是增加模型、执行器或泳道容量。

## 2. 缺陷清单（P0–P2）

### P0-1：V2 权责记录链可不完整甚至零写，而旧四要件仍允许完成/收口

**证据**

- `framework/docs/17-整体技术设计.md:98` 明示记录写失败“不打断拍”，事件面照旧；`:275-278` 又规定记录落在四要件判定之后、不是判据，前件未落即拒写。
- 同文 `:105,118-131` 自报 LIFE-01 只有拟任面，LIFE-04/EVD-01 等待多个前件；八族在缺省无决定事实注入时 fail-closed。`:276` 更直写“本轮前件未落故零写”。
- `framework/docs/v2/11-技术细节-运行记录与行为契约.md:884-887` 则把生效任命、证据包、独立性和结清引用列为强制不变量。
- `framework/docs/v2/05-技术抽象-总规范与框架总装.md:124-126` 规定 DOM-03 事件是历史权威、records 是投影；所以不能把“事件已有”自动当成“V2 权责记录已证”。

**影响**：运行面可以出现 GATE_PASS/CLOSE，规范面却没有足够的任命、授权、独立收割、验收或结清材料。事件回放能重建部分技术轨迹，但不能补造当时不存在的权源与独立判断。若直接切到 V2 强态，又可能因前件生产者未就位而全面停摆。

**修复方向**：先定义 `legacy / shadow / enforce` 三态及逐公司迁移条件；补齐 CAP-02、AUTH-02、接受回执等关键生产者，再给每条 CLOSE 生成记录完备性证明。enforce 后，必需记录缺失必须阻断相应迁移；事件与记录用同事务 outbox/同事务句柄衔接。历史欠账只能标“未知/待补证”，不得回填成当时已授权或已独立验收。

### P0-2：唯一写入者缺少已验证的跨进程 fencing，单写仍是拓扑假设

**证据**

- `framework/AGENTS.md:69` 要求唯一写入者由“机制保证，不是自律”。
- `framework/docs/v2/05-技术抽象-总规范与框架总装.md:132-134` 明示无互认围栏时只允许独占交接，而围栏/激活代次机制仍为“目标（未证）”。
- `framework/docs/quality/lane-capacity.md:33,68` 的租约簿是进程内存态，明确不做跨进程分布式租约；`framework/docs/17-整体技术设计.md:71` 的合并租约也把跨进程互斥留作后续。
- `framework/docs/v2/17-验证矩阵与追溯.md:568` 规定 PRB-14 未过不得宣称台账单写；同文 `:32` 记录 V6 仅 1/26 executed。当前 PRB-14 是否后来补跑，**未核验**。

**影响**：守护重启重叠、误起第二实例、灰度并行或网络分区时，旧写者可能继续向 SQLite、协作平台或公司 git 产生副作用。进程内 epoch 能防本进程迟到释放，不能阻止另一个进程持新 epoch 后旧进程继续写。

**修复方向**：引入带单调 fencing token 的写者代次；SQLite 在事务内检查代次，平台网关和公司 git 写口也拒绝旧代次。启动第二写者默认拒绝；接管须“旧写者停写/隔离→新代次激活→在途对账→新写”。必须有两进程互斥、 stale writer、崩溃接管、外部写回执未知的负向实测。

### P1-1：平台回退/返工/重开与 V2 记录桥不闭合，形成系统性历史缺口

### P1-6：验收超时与重试策略会放大确定性故障，且缺少整单总 deadline

**证据**：`framework/docs/quality/验收超时配置与调优.md:74-82` 明示 N 条命令最坏约 N×T、单条可到 1 小时，收割与合并共用一值，超时会进入 GATE_FAIL/熔断链；`framework/docs/17-整体技术设计.md:314-320` 的半开会再次派发。该专题 `:9-13` 已记录 60 秒误杀重载验收的历史根因。

**影响**：慢测试、环境挂死和确定性超时可能被当成可重试质量失败，反复消耗 worker、泳道与模型额度；调大超时只是把占用时间拉长。  
**修复方向**：分离“测试断言红、基础设施超时、资源争用、环境错误”；增加逐命令、整单验收、整 attempt 三层 deadline 和排队时长。确定性超时不得在配置/环境未改变时自动重跑；合并与收割可共享默认值，但应允许受审的位别覆盖。

### P1-7：泳道容量只限制 worker 数，不限制验证子进程与下游验收容量

**证据**：`framework/docs/quality/lane-capacity.md:38-40,52-53` 只给泳道 1–8 槽并提示多写/长跑风险。`framework/docs/sentinel-logs/2026-11-03.md:513-517` 记录高负载时大量 vitest/tsc/bun 争用；`:541,561,569` 又记录待验收从 20 增至 24，而过闸继续发生。`framework/docs/sentinel-logs/2026-11-02.md:92-100` 将验收权收回单一 Lead。

**影响**：扩容会把瓶颈从派发转移到 CPU、IO、验证和人工验收，反而提高超时、陈旧 diff、WIP 与批量粗审风险。  
**修复方向**：建立宿主级 CPU/内存/IO/测试并发预算，重验证走独立队列与缓存；派发器纳入验收队列长度、最老等待时长和评审者容量。验收可委派给符合独立性规则的池，不靠单人硬扛。

**影响**：进程健康可掩盖无可用模型、记录长期拒写、队列积压或调度暂停；告警噪音被“预期化”后容易形成无责任人窗口。  
**修复方向**：增加 readiness/SLO 面，至少覆盖可用源、最老队列、记录 refused/recon 差异、孤儿、验收积压、配额耗尽时间。每类告警必须有 owner、ack、升级期限和关闭证据；角色不调查可以，但交接未确认不得视为已处理。

### P2-1：路由健康已有 healthz 字段，但专用面板与操作视图未接

**证据**：`framework/docs/quality/model-routing.md:147-162,242-244` 自报 healthz 已有源状态、面板专用视图未接，宿主 E2E 也曾待复跑。

### P2-2：个别运行文案自相矛盾，削弱告警可信度

**证据**：`framework/docs/sentinel-logs/2026-11-03.md:325` 记录“457ms 超阈值 3600000ms”的矛盾文案；真实原因是 interrupted 即时收口。  
**影响/修复**：运维可能按错误原因调参；将触发原因结构化为枚举，展示值只在对应原因存在时输出，并为每类 note 加格式契约测试。

### P2-3：回退说明有备份意识，但缺少统一的兼容性与完整性凭证

**证据**：`framework/docs/20-工程总规程.md:57-63` 给出发布层级和高层回退描述，`framework/docs/17-整体技术设计.md:141-142` 给出 supervisor 拉起与切权重启；模型/执行器专题主要以恢复备份并重启为回退，例如 `framework/docs/sentinel-logs/Kimi-DSH切换执行记录-2026-11-23.md:20-23`。V2 对记录类型已有“同主版本只增可选字段”的好约束（`framework/docs/v2/11-技术细节-运行记录与行为契约.md:900`），但未在所读发布规程中形成统一门禁。

**影响/修复**：代码可回滚不代表 SQLite schema、事件词、公司包、配置和在途会话可回滚；发布物应携带 backup digest、schema/contract 兼容区间、在途处置与回滚后验证命令，回滚演练不能只看进程重新在线。

### P2-4：依赖与 CLI 供应链准入仍偏薄

**证据**：`framework/docs/20-工程总规程.md:290-295` 明确分层门禁不限外部 npm 依赖；`framework/docs/quality/agy-adapter.md:198-213` 仍有多项真实 CLI 行为未证。  
**影响/修复**：边界门禁管不住恶意依赖或上游 CLI 突变；增加依赖 allowlist、锁文件审查、SBOM/来源摘要、版本支持窗口和升级前差分探针。此项不是现有依赖已有漏洞的证明。

## 3. 流程与治理缺口

| 领域 | 已有控制 | 主要缺口 | 应形成的闭环 |
|---|---|---|---|
| 验收 | 四要件、QA、T1–T5、制作人触点 | 旧四要件与 V2 权责记录脱钩；final 与部署准入易混；验收积压无背压 | 按公司声明迁移模式；每单可出示验收独立性、记录完备性、当前 commit 验证和准入批准 |
| 记录 | append-only、哈希链、幂等、对账 | 写失败不断拍、回退边拒写、对账差异只留痕；文档状态陈旧 | 同事务 outbox/投影；差异产生有 owner 的异常；关闭须给补偿证据与期限 |
| 权限 | wkey、选择链、root/scoped 分离、fail-closed | 跨进程围栏、整树撤回、agy 沙箱与真实权限形态未证 | 权限与 binding certification 绑定；撤回必须给后代停用证据；第二写者和旧代次实测拒绝 |
| 配额 | 任务/公司预算、冷却、断路、微调用三帽 | 共享额度池未一等建模；订阅成本/剩余量申报；CPU、测试进程和评审容量无统一配额 | provider/account/pool + host + reviewer 三层容量；剩额未知不显示健康；超限有预防性暂停 |
| 告警 | ESCALATE/DAILY_ALARM、healthz、哨班 | liveness 被误用风险、噪音归档、交接无 ack/SLA、部分问题仅日志 | severity/owner/ack/deadline/escalation/close-evidence 全字段；根事故与症状单分组，不以归档替代恢复 |
| 回滚 | 配置备份、重启回退、gray/release、公司目录失败回滚 | DB/事件/契约/在途工作的联合回滚未证实；恢复备份缺统一 digest 与适用窗口 | expand→migrate→contract；旧新双读或明确禁窗；回滚后跑数据、平台、在途与路由四组核验 |
| 升级 | Node 升级前同版验证、适配器探针、契约冻结 | 工具链 Node 24 与生产实测 Node 25 存在运行时差；组合兼容矩阵与 V6 覆盖不足 | 每个发布绑定实际生产 Node、CLI、契约和 schema；当前生产版本也进 CI/canary，不只验证下一主版本 |
| 事故 | 发现→止血→复盘，断路自动开单 | 供给故障形成多症状 bug 单后再归档，容易弱化根事故；哨班“不调查”若无接管确认会断链 | 一根事故多症状关联；止血、根因、恢复、后验各自有证据；未确认接手不得结束上报责任 |

## 4. 架构风险与建议不变量

| 风险面 | 评审判断 | 必须补的不变量/验证 |
|---|---|---|
| 状态一致性 | 平台当前态、DOM-03 历史、DOM-05 records 和旧四要件处在迁移双轨；记录拒写与平台动作可分离 | 同一语义迁移有唯一 ID、预期版本和幂等结果；外部效果未知时不得假成功或盲目重放；V2 enforce 下无必备记录不得收口 |
| 并发 | 逐租约 epoch 是良好改进，但 lane/merge 簿仍进程内；跨进程 fencing 未证 | 所有外部写都校验单调代次；两个 daemon、旧 worker 迟到、TTL 到期、重启接管均不造成双写或误释放 |
| 单点 | daemon、宿主、协作平台与单 Lead 均可能成为瓶颈；supervisor 只解决拉活 | daemon 可接管且 fencing 安全；平台故障只读有 SLO；宿主资源隔离；验收有可委派且独立的容量池 |
| 多公司隔离 | V2 有按公司与知悉范围隔离要求，所读实现卷主要是 slug、company-dir、db 等装配描述。共享/每司进程与 DB 的边界、KV/缓存/会话主键和跨司授权测试**未核验** | 所有 key/query/route/job/routing-state/session/artifact 都带 tenant；默认跨司拒绝；以两公司同名单号、同工号、同模型源、同泳道做负测 |
| 升级兼容 | 记录类型只加可选字段是好基础；但生产 Node 与工具链不同版，DB/契约/配置/在途联合兼容未形成一张矩阵 | 发布物声明可读/可写最低版本；旧 binary 能安全打开新库或明确拒绝；回滚不丢在途；当前生产运行时参与验证 |
| 路由/模型控制 | 优先级、冷却、预算预检和换源审计较完整；共享池、真实 wire model、凭据续期与探针资格仍弱 | 配置模型与实际 wire model 不同必须标未知/漂移；同一 pool 联动熔断；新源须过同版本真机 canary；在途不串源且 token 可安全续期 |
| 可观测/成本 | healthz 与事件链较强，但 readiness、配额预测、历史钱账对账和人工队列不足 | 任何“健康”均可分解到供给、调度、记录、验收四子态；成本能解释到 provider/model/pool/价格版本，未知不得写成零 |

## 5. 可拓展方向（按优先级）

1. **证据驱动的运行准备度与策略控制面**：把规范、实现、探针、部署、记录完备性变成同一张可查询证据图；公司可按策略选择 legacy/shadow/enforce。它先解决“能否安全开功能”，后续所有扩展都复用。
2. **可靠执行内核：fencing + durable command/outbox + 可恢复状态桥**：不急于微服务化，先把单写、外部副作用、崩溃接管和记录事务做成可替换内核。未来无论单机、双机或分布式 worker 都受益。
3. **供给/成本/算力/验收容量统一配额代理**：把模型 quota、订阅成本、宿主测试资源和评审队列作为不同资源类型纳入同一调度接口，支持背压、预约和公平性，避免单纯加泳道。
4. **签名化 Executor/Provider 插件 SDK**：复用四原语、能力声明与契约包，提供版本化 binding、真机探针包、故障分类和最小权限沙箱。新 CLI 不需改主循环，且未认证插件只能实验运行。
5. **多公司只读控制塔与可移植公司包**：在每司写面保持独立的前提下，扩展跨司只读聚合、证据导出、策略包签名分发和迁移预检。先做 tenant 隔离与只读扩展，不提前建立多主写入。
