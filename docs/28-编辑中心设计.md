## 〇、范围与总链路

编辑中心 = :8789 公司概览的第六个 tab（C1-12）：**网页编辑公司目录**（人事档案、
org-config、部门 config），全链 = 网页录入 → 草稿 → 三档批示 → daemon 单点写回 →
三处留痕（平台单 / 目录 git commit / 台账 personnel_events+APPROVE）。

```
制作人/主PM ──:8789 编辑端点（POST 只产草稿与批示动作）──┐
制作人（平台直批，中文自由批示）──────────────────────┤
                                                          ▼
            ┌──────────────── daemon（唯一写入者）────────────────┐
            │ 审批队列（SQLite drafts 表=工作态镜像）               │
            │   批示落点=平台「人事单」（经网关建单/评论/迁移）      │
            │   档② = 既有派发链唤起部门 leader agent 审单          │
            │   冷静期 = D9 人事定时岗（24h 未批自动批，D2 引用）   │
            │ 写回器：锁→基线复核→dry-run 校验→落盘→复验→          │
            │          git commit 挂单号→personnel_events→镜像→收口 │
            └──────┬──────────────────────────────┬───────────────┘
                   ▼                              ▼
        公司 git 目录（组织事实源）      SQLite 台账（可重建投影 + 留痕）
                   └──:8789 读面热读（不重启，C1-07）──┘
```

四条铁律（全部既有拍板，本设计零新增红线）：
1. **永不直接写文件**（00-§二.2）——网页是录入面，保存不生效、显式标"未生效"（C1-05）；
2. **daemon 单点写回**（C1-07、20-§六.7：公司目录 daemon 唯一写入，人工直写=受控例外+留痕）；
3. **personnel_events 必挂单**（C1-06/F2-06：无单号拒绝——列级 NOT NULL 已备，
   `packages/store/src/records.ts` PersonnelEventRecord.ticket）；
4. **目录契约不轻改**（04-§九.4 前瞻性纪律）——本设计不动公司目录结构（§一选型理由之一）。

## 一、数据面：编辑草稿的存储与结构

### 1.1 存储形态三案对比

| 维度 | 案 A：公司目录内 `.drafts/`（或 `.studio-next/` 下草稿区——同属目录内新分区，判定相同） | **案 B：SQLite drafts 表（推荐【拟稿 EC-①】）** | 案 C：daemon 内存+导出文件 |
|---|---|---|---|
| 目录契约 | **破坏**：04-§二 目录树无此区，收编即改契约（04-§九.4 不轻改）；校验器须加忽略规则 | **零变更**：草稿不进目录 | 零变更 |
| git 历史 | 陷两难：gitignore 则草稿不可审计；入库则污染"组织变迁史"（04-§二：git 历史只记已生效事实） | 公司 git 保持纯净=只记已生效事实 | 不入 git，审计面弱 |
| 崩溃安全 | 文件落盘，但多文件草稿无事务 | WAL+事务，崩溃无损 | **daemon 重启即丢** |
| :8789 读面 | panel 须读公司目录文件（破"panel 不碰目录"注入纪律，见 overview 首刀头注） | WAL 单写多读，panel/daemon 同库并存安全（与 :8787 同款，server.ts 头注） | 跨进程读需另开通道 |
| 与 personnel_events 原子性 | 异构（文件 vs 库），无联合事务 | 同库：状态迁移同事务收口 | 无 |
| 台账先例 | 无 | **有**：jobs 调度表（17-§2，store v3）与 daemon_kv（store v4）已开"运行时状态表落台账"先例 | 无（kv 时代已被 v4 收编） |
| 可移植性 | 草稿随目录走 | 草稿留台账；目录 copy 不带草稿（草稿=未生效工作态，非组织事实，**可丢但须如实上报**） | 同左且更弱 |

**推荐案 B**，决定性理由三条：目录契约零变更（铁律 4）；运行时状态表已有 jobs/daemon_kv
两代先例（store/src/ledger.ts 头注 v3/v4 段）；公司 git 历史语义纯净（草稿不是变迁，生效才是）。
案 A 被否的主因是契约破坏而非技术不可行；案 C 被 v4 吸收面（kvGet/kvSet 头注"接管关系"）
的历史走向直接证伪——运行态终会要求持久化。

**语义声明**：drafts 表是**运行时工作态**（同 jobs），不是 append-only 台账事实；append-only
只记生效后的事实（personnel_events / events）。台账若损毁重建：已生效变动无损（git commit +
personnel_events 皆在），未生效草稿丢失=可接受事故，如实上报、可重录（对齐 F2-01 可重建投影）。

### 1.2 草稿结构：全文快照为源，diff 为派生视图【拟稿 EC-②】

**取全文快照，不存 diff 补丁**——对齐 git 心智（git 对象即全量快照，diff 永远是比对视图）：

- `apply` = 整文件写入，**无补丁应用失败面**（无 fuzz 匹配、无行号漂移问题）；
- 前值快照即乐观锁基线（§5.3）与 C1-05 验收口径本体（"含前值快照可逐字 diff"——diff 由
  基线快照与新快照**派生**，展示层逐字渲染，落库不存补丁）；
- 回滚（写回失败面 §3.2）= 恢复前值快照，同样整文件、无逆补丁。

### 1.3 草稿记录形状（drafts 表，store migration v5【拟稿 EC-⑱】）

```
drafts 表（示意，列名冻结候选；实现单走 store 迁移单）
  id            TEXT PK   -- ULID（daemon 侧 id.ts 既有 ULID 生成）
  company       TEXT      -- 公司 slug（多公司分区，对齐 events.company）
  rev           INTEGER   -- 乐观版本号（§5.3 同草稿并发编辑闸）
  status        TEXT      -- editing|pending|approved|applying|applied
                           --   |rejected|withdrawn|conflicted|invalid（状态机见 §2.5）
  kind          TEXT      -- 编辑类型枚举（§1.4）
  person_id     TEXT NULL -- 目标工号（部门/组织类草稿为 NULL）
  intent_prev   TEXT NULL -- 标量前值（"2" / 部门 path / 工号 / null…）
  intent_next   TEXT NULL -- 标量新值
  reason        TEXT      -- 理由（不可信文本：原文落库，展示转义、批示预检见 §5.1）
  author        TEXT      -- 编辑者（制作人 opengames / 主 PM 工号——C2-13 编辑者限这两人）
  ticket        TEXT NULL -- 平台人事单号（submit 时经网关建单回填；applied 前必非空）
  tier          INTEGER NULL -- 批示档 1|2|3（submit 时按 §2.2 矩阵定档）
  approver      TEXT NULL / decided_at INTEGER NULL    -- 批准人 / 批示时刻
  reject_reason TEXT NULL
  base_head     TEXT      -- 草稿创建时公司目录 git HEAD（目录级基线，§5.3）
  files         TEXT      -- JSON 数组：[{path, base_sha8, base_content, new_content}]
                           --   目标文件相对路径 + 前值全文 + 基线指纹 + 新值全文（EC-②）
  created_at / updated_at INTEGER
  applied_at INTEGER NULL / git_commit TEXT NULL / personnel_ids TEXT NULL
                           -- 生效回填：时刻 + commit 哈希 + 落账的 personnel_event id 集
```

索引：`(company, status)`（编辑中心列表页）、`id` 主键。量级=人工编辑频度（日级），远低于
events，无规模前瞻压力（17-§12 口径顺带满足）。

### 1.4 编辑粒度：结构化意图，不开"任意文件任意内容"口【拟稿 EC-③/④】

**客户端不给文件内容，只给结构化意图**（zod strictObject 校验，与 company 校验器同纪律）；
目标文件集与 new_content 由 **daemon 按意图现算**（草稿创建时读当前文件做前值快照+渲染新值）。
只有档案描述节文本一种自由文本入口。这把不可信面从"任意字节"压到"标量+一段文本"。

| kind（草案枚举） | 目标文件（联动写） | 意图字段 | person 事件 | 档 |
|---|---|---|---|---|
| person.create | 档案新文件 + org-config people 索引行 | 全套 front-matter 初值 | 入 | ③ |
| person.retire | 档案 + 索引行 status | status→retired | 退 | ③ |
| person.pause / person.resume | 档案 + 索引行 status | status 停/复 | 停/复 | ③ |
| person.level | 档案 + 索引行 level（level_distribution 联动） | level 数字 | 升/降（按方向） | ③ |
| person.dept | 档案**挪树** + 索引行 dept | dept path | 调 | ② |
| person.reports_to | 档案 + 索引行 reports_to | 工号或 null | 线【EC-⑪】 | ③（上下级） |
| person.role / person.name | 档案 + 索引行 | 文本 | 无（EC-⑩） | ② |
| person.dispatch-attrs | 档案 + 索引行（skills/side_effects/executor） | 受控枚举/数组 | 无（EC-⑩） | ②（影响派工面） |
| person.body-text | 档案正文描述节（定位/职责/技能本体/表现画像四节） | 节文本（唯一自由文本口） | 无（EC-⑩） | ① |
| dept.config | departments/<部>/config.yaml | 章程/主管/职能/泳道/relations | 无（EC-⑩） | ③ |
| org.structure | org-config departments 段（增删/层级） | 结构条目 | 无（EC-⑩） | ③（编制） |
| org.company / org.jobs / org.accounts / org.yt | org-config 对应段 | 段内字段 | 无（EC-⑩） | ③（分布/定时岗/账号锚/映射=编制面） |

**不可编辑项【拟稿 EC-④】**：工号（主键永不变，C1-02/C2-04 文件名=工号，改名=删旧建新两单）；
login（账号=等级锚点，04-§五——v0.7 编辑面禁改，换锚是平台侧操作走线下）；schema 版本
（迁移归 daemon 唯一执行，04-§九.4）；档案 `<!--AUTO-->` 受管区（机器只写，越界红灯，C2-04）；
自述段（只本人写，C2-12——编辑中心不提供入口）；**charter.md（v0.7 不开网页口**——04-§二
"改它=9 级批示"，本设计取更保守线：章程编辑走线下 9 级批示流+受控直写例外，不进编辑中心）。
描述节里的"做过的事"归系统机械归集（C2-12），同样不开网页口。

联动自洽：person.* 草稿的多文件联动（档案+索引）保证 C2-05 双检（悬空/孤儿）在 dry-run
（§3.1 第 3 步）永远不因编辑自身引入而翻红；level 联动改 level_distribution（分布=实数校验，
validator.ts crossRules）。

## 二、批示流：三档、触发矩阵与落点

### 2.1 三档口径（引用 C1-07，零重设计）

档① **描述类自批**（提交人即批准人）｜档② **职责/部门主管签**（部门 leader）｜
档③ **等级/上下级/编制/预算制作人亲批**。三档审批链**可配置可测**（C1-07 验收）：
档位判定表是框架默认模板，公司目录可覆盖（04-§九.0 模板不写死；落位=org-config 新增可选段
`approval_tiers`，形状归实现单【拟稿 EC-⑦ 附带】）。

### 2.2 触发矩阵

kind→档的逐行映射见 §1.4 表末列（与 personnel_events type 同表给出）。归属依据：
C1-07 的三类原文——描述类（档案四节正文）→①；职责/部门（dept/role/name/派工属性）→②；
等级/上下级/编制/预算（level/reports_to/status/入退/org.* 全族）→③。
**超出 C1-07 字面需自定归属的行**【拟稿 EC-⑦】：skills/side_effects/executor→②（参与派工
匹配与安全分级，非纯描述）；name→②（入署名与档案展示）；status 停/复→③（编制面保守归③）。

### 2.3 批示动作的落点：平台人事单为流程证据，daemon 队列为工作态【拟稿 EC-⑤】

| 方案 | 形态 | 判定 |
|---|---|---|
| A 草稿即平台单（状态全在平台） | :8789 只产单，批示=平台状态迁移 | 流程证据最纯，但**双入口双写**（:8789 与平台各写一份状态）违背 D1 单源精神；草稿正文（全文快照）塞平台单体态笨重 |
| **B 混合（推荐）** | **草稿工作态=drafts 表（daemon 唯一写）；批示落点=平台「人事单」**：submit 时经网关建单（issues.create），批示动作=网关评论（comments.add，署名自动注入）+状态迁移（transition，控制面做）；:8789 批示与平台直批**双入口汇于同一状态机**（daemon 从活动流感知平台侧批示，17-§2 采集相位既有通道） | 流程事实归流程事实源（YouTrack=流程+工作知识，17-§1）；工作态归 daemon；**单一写入者不破**（两入口最终都由 daemon 落墨） |
| C 纯内建队列（不建单） | 批示只落 drafts 表 | **违 C1-06/F2-06**：生效无单号即拒——单必须存在；且批示过程脱离平台=流程证据旁落，违 20-§十 |

推荐 B。对齐验证：**"一切处置留证据"**（20-§十：关键动作三处皆有——批示=单评论、生效=git
commit 挂单号+personnel_events、状态=APPROVE 事件）；**04-§五 网关哲学**（一切平台操作走
网关、署名自动注入、控制面自身也过网关——17-§7）；**平台可替换**（23：FlowPlatform 端口，
YouTrack/LocalFile 皆可承接——建单/评论/迁移/活动流四能力都在 `packages/contract/src/ports/
platform.ts` 七能力内，编辑中心零平台硬编码）。

单型与字段：type=可配（org-config yt 段映射，缺省 `org`）；标题=「<type 中文> <工号/节点>
<prev>→<next>」；描述=理由+派生 diff+草稿 id；assignee=档② 目标部门 leader 工号 / 档③ 缺省
制作人锚。**平台不可达**（未配置/离线）时 submit 如实失败、草稿停在 editing，**不静默降级**
（C2-01 精神；LocalFile 实现是离线正解而非降级）。

### 2.4 档②的批准人是 agent：复用既有派发链【拟稿 EC-⑥】

部门主管=leader 工号指向的 agent（04-§二）。档②不造新审批机制：**人事单就是一张单**，
走主循环既有派发-收割链（16-§四 v0.5）——submit 后 daemon 产 ticket 意图（22-§二 定时查单
即可覆盖；唤起源零新增）→ leader agent 被派发审单（任务书含草稿 diff，L4 层，注入面过
sanitize §5.1）→ agent 经 wkey 网关落批示评论（GATEWAY_ACTIONS 含 comment，`packages/
contract/src/ports/gateway.ts`；**状态推进不在 agent 白名单**——批示生效的迁移永远由 daemon
控制面执行，17-§7）→ daemon 收割/活动流感知批示词（中文自由批示 LLM 回退解析，17-§7 既有）
→ 驱动状态机。制作人可提权代批（approver 记制作人，如实留痕）。

### 2.5 草稿生命周期状态机（daemon 内单点迁移）

```
editing ──submit（建单+定档）──▶ pending ──批示（档①即时自批）──▶ approved
   │                              │   ▲                            │
   │                              │   └── 冷静期自动批（D9，§2.6）  │ apply（§3 九步）
   └─withdraw（作者撤回，pending 前可）│                             ▼
                                  ├──reject──▶ rejected          applying ──▶ applied
                                  └──冲突/预演红──▶ conflicted / invalid
conflicted/invalid/rejected ── 作者改基线重开（新草稿，不做三方合并 §5.3）──▶ editing
```

档①提交即自批：submit 请求内 daemon 连续完成建单→自批评论→approved→apply（对提交人透明，
证据链同构——单号照样存在，C1-06 不打折）。status 迁移全部由 daemon 单点执行且同事务更新
drafts 行；applied 为终态（append-only 精神：生效不可撤销，改错=新草稿反向改，C1-06）。

### 2.6 冷静期（引用 D2/D9，零重设计）+ 一处细化【拟稿 EC-⑧】

## 三、写回面：daemon 单点写回

### 3.1 生效九步（顺序冻结候选）【拟稿 EC-⑨】

apply 全程持有**公司目录写锁**（daemon 进程内互斥队列——单 daemon 进程内天然串行，锁防
future 多 apply 并发；git index 自身另有锁）。一步红即停，处置见 §3.2：

1. **取锁**：公司目录 apply 互斥锁（同公司串行；不同公司并行）；
2. **基线复核**：逐文件重读磁盘，`sha8(current) == files[].base_sha8` 且目录 HEAD ==
   base_head——不等→`conflicted`（§5.3）；
3. **dry-run 校验**：内存文件映射（当前目录+草稿新值）跑 `loadCompanyDirectory(files,
   {strictFiles:true})`（packages/company/src/validator.ts + multifile.ts，目标契约面已备）——
   红→`invalid`，issues（文件:行+修法）原样回给编辑面；
4. **落盘**：每文件 temp 写+rename 原子替换；多文件=全部先写 .tmp 再逐个 rename（窗口最小化）；
5. **复验**：重读磁盘全量再跑一次校验（防 temp/rename 半途与并发外部直写——受控例外存在，
   20-§六.7）——红→恢复前值快照→abort（此时尚无 commit 无落账，目录回到原状）；
6. **git commit**（simple-git，company/src/init.ts 既有先例）：message 首行
   `org: <type|kind> <工号/节点> <prev>→<next>（<单号>）`，body 含 draft id/approver/
   批示摘要【拟稿 EC-⑫】——挂单号进 commit message 是 04-§二 冻结规则；
7. **personnel_events 落账**：person 类草稿按 §3.3 映射拆行写入（appendPersonnelEvent 已备，
   幂等规则已备）；id=**确定性派生 `pe-<draft_id>[-<n>]`**（复合变动拆多行加序）——失败重试
   幂等（EC-⑨）；同时 events 落 APPROVE（冻结枚举既有成员，17-§3，零契约变更）；
8. **镜像同步**：`syncCompany(newSnapshot)` 更新 people/departments 镜像（ledger 已备；扩展列
   不清不覆盖的既有语义正好护住 status 等字段）；
9. **收口**：drafts 行→applied（回填 applied_at/git_commit/personnel_ids，同事务）；
   经网关在人事单落证据评论（commit 哈希+personnel_event id）并关单迁移——网关失败不回滚
   生效（§3.2 第 9 行），重试归人事定时岗巡检。

**git→ledger 顺序论证**（EC-⑨ 核心）：若先落账后 commit，commit 失败=台账出现未发生的变动
（append-only 无法收回，**无中生有**）；先 commit 后落账，落账失败=事实已生效、投影滞后，
可幂等补记——"SQLite=可重建投影、组织事实源=git 目录"（17-§1/§3）的既定分层决定顺序。
daemon 崩溃在 6-7 之间：重启后人事定时岗对账（commit 有单号、personnel_events 无对应行→补记，
确定性 id 保证幂等）——对账归 D9 人事岗的一个实例，机制同 docs/26 回填对账思路。

**热读不重启**（C1-07 引用）：overview 读面 snapshotProvider 每请求重读目录（首刀既有设计），
写回后下一请求即见新组织；prompt 侧 L2/L3 下次装配自动取新内容，分层指纹 `p.<工号>.<rev>`
随之变化（C2-08）——配置化热更（D2）在编辑中心的兑现即此，无需任何 reload 动作。

## 四、API 面：:8789 编辑端点草案【拟稿 EC-⑬】

### 4.1 承载形态

编辑端点由 **daemon 进程内嵌的 :8789** 承载（daemon 常驻时以 createOverviewApp+编辑路由起
服务）。独立 `studio-next overview` 子命令（dev 首刀 ba3bf0a）保持**只读**：编辑端点注册但
无注入服务→`503 {ok:false, error:"编辑面需 daemon 常驻进程"}`（如实降级不臆造，overview
首刀降级面同款风格）。注入纪律沿首刀先例：panel 不 import daemon/company 写面——daemon 实现
`EditingService` 接口注入 overview app（同 OverviewCompanySource.snapshotProvider 形状），
panel 只做 HTTP 薄壳+转义渲染。

### 4.2 端点清单（全部 `/api` 前缀 JSON + 一个 HTML 页；写端点全 POST）

| 端点 | 法 | 鉴权 | 形状与语义 |
|---|---|---|---|
| `/<slug>/edit` | GET | 无 token（读面） | 编辑中心 HTML 页：草稿列表+状态+批示积压（暗色风格沿 overview views.ts 基线） |
| `/<slug>/drafts` | GET | 无 token | `?status=&kind=&person=` 过滤；返回草稿行（含派生 diff 摘要，不含全文快照） |
| `/<slug>/drafts/:id` | GET | 无 token | 详情：意图+前值/新值全文+逐字 diff+批示链（单号/批准人/时刻） |
| `/<slug>/drafts` | POST | token | 建**结构化草稿**：`{kind, person_id?, intent…, reason, base_head}`——daemon 现算 files[] 快照与派生 diff 并回显预览（§1.4：不给文件内容） |
| `/<slug>/drafts/:id` | PUT | token | 改 editing 态草稿（唯一自由文本节/意图字段）：带 `expected_rev`（§5.3 乐观锁） |
| `/<slug>/drafts/:id/submit` | POST | token | 提交批示：建单（经网关）→定档→pending；档①连续自批进 apply（§2.5） |
| `/<slug>/drafts/:id/approve` | POST | token+档位校验 | `{comment?}`；daemon 经网关落批示评论+迁移→apply（§3） |
| `/<slug>/drafts/:id/reject` | POST | token+档位校验 | `{reason}`（必填）→rejected+单上落驳回评论 |
| `/<slug>/drafts/:id/withdraw` | POST | token（仅作者） | editing/pending 态撤回→withdrawn |

**只信息+触发**（任务口径）：GET=信息；POST/PUT 只收草稿与批示**动作**，端点永不触达文件
写——落盘全部经 daemon 内部写回器（§3）。任务书最小集之外新增 PUT/submit/withdraw 三端点
（EC-⑬ 呈批：C1-05"保存不生效"要求草稿可保存≠提交；撤回权归作者）。

错误形状：`kernel.ClassifiedError` 风格 `{ok:false, error}`，HTTP 码 400（形状）/401（无凭证）/
403（档位越权）/404（未知 slug/id）/409（乐观锁冲突）/503（降级/平台不可达）——沿 overview
首刀 configInvalid+404/500 既有风格收编。

### 4.3 鉴权（引用 D4/D5，细化拟稿 EC-⑭）

- **读面无 token**：D5 人事档案全公开=信息面不限；:8789 缺省绑定 127.0.0.1（04-§七 受众
  制作人/内部；与 :8787 同款缺省）——**局域网暴露=显式配置+强鉴权**（D4 保守缺省精神平移，
  :8789 是内部面不是对外 API，不引 C3 三档凭证体系，不越界设计）。
- **写面 token**：`X-SN-Token` 请求头（**非 cookie**——无经典 CSRF 面）；令牌落**框架级
  ports.yaml 既有令牌位**（17-§4：8787/8788/8789 绑定与令牌——配置位已存在，用法为拟稿）；
  库存哈希+last4（C3-03 凭证先例的内化）。角色两枚【EC-⑭】：`producer`（制作人——全档

## 五、安全面

### 5.1 网页输入=不可信（三道闸，prompt 包先例对齐）

先例：`packages/prompt/src/sanitize.ts` sanitizeUntrusted（剥离命令形态行+引用块包裹+声明

1. **入口闸**：zod strictObject 形状校验（未知键拒收，validator 同纪律）+文本长度帽（单字段
   ≤64KB、请求体 ≤256KB——C3-08 webhook 帽先例内化）；
2. **渲染闸**：草稿一切文本进 HTML 经 escapeHtml（overview views.ts 既有基线；md 原文进
   pre 块同款）；diff 视图对 base/new 两侧同样转义；
3. **批示预检【拟稿 EC-⑯】**：submit 时对自由文本跑 isCommandShapedLine 扫描（sanitize.ts
   已导出"供测试与面板复用"——复用点即此），命中行数随草稿展示给批准人+落检测事件
   （C2-10"记事件"口径向编辑面延伸；事件复用 APPROVE note 承载，零新事件名）。档②审单
   agent 的任务书含 diff——L4 注入面 sanitize 照常兜底（纵深防御，双层）。

### 5.2 批示权限模型（谁能批哪档）

| 主体 | ①描述类 | ②职责/部门 | ③编制/等级/上下级 |
|---|---|---|---|
| pm token（主 PM） | 建+自批 | 建不可批 | 建不可批 |
| producer token（制作人） | 建+批 | 建+提权代批（approver 记制作人） | **亲批**（唯一人批通道） |
| 部门 leader agent | — | **签**（派发链审单，§2.4） | — |
| 无 token | 只读（D5） | 只读 | 只读 |

越权批=403+落事件（fail-closed，C3 验收精神内化）。档位判定在 submit 时点冻结进草稿行
（tier 列）——防"先提交低档再改内容"：内容变更（PUT）必回 editing 态重新 submit 重定档。

### 5.3 并发编辑冲突：乐观锁双粒度【拟稿 EC-⑮】

- **文件级**：files[].base_sha8（草稿创建时目标文件内容指纹）——apply 第 2 步复核；
  **目录级**：base_head（草稿创建时公司目录 git HEAD）——submit 时复核（两草稿先后改同区，
  后者 submit 即冲突预警、前者 apply 后后者必 conflicted）。
- **同草稿并发编辑**：drafts.rev 乐观版本号——PUT/submit/approve 带 `expected_rev`，失配
  409（多标签页互踩的最小诚实解）。
- **冲突处置：驳回重开，不做三方合并**（v0.7）——复杂合并转 merge 单、制作人定取舍
  （20-§七 既有纪律平移）。conflicted 草稿保留供人看差异，重开=以新基线新建草稿。
- **与受控直写的竞争**：制作人/主 PM 手改文件是受控例外（20-§六.7）——本设计不禁止它，
  只保证它在 apply 复验（§3.1 第 5 步）与 C1-08 漂移看门狗（config/网页/代码三方比对）里
  都被看见。

### 5.4 审计面（最小面，零契约变更【拟稿 EC-⑰】）

草稿审计源=drafts 表行本身（status/tier/approver/ticket/git_commit 全程可回放）+平台单
评论链+git commit——**不新增 DRAFT_* 事件前缀族**（17-§3 事件枚举 v1 冻结；新增前缀=契约
变更走批示，v0.7 不必）。events 只落既有成员：批示=APPROVE、人事生效=APPROVE（note 带
commit 哈希）。若后续要求端点级调用审计（对齐 C3-13 内化版），届时再呈批扩枚举。
