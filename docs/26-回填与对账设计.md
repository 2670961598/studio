### 1.2 事件账本形状（S1 详表，映射的输入面）

- **全键集**（20401 行逐行统计）：`ts / pid / issue / event / actor / attempt / note / tokens /
  cost_usd / duration_ms / usage{input_tokens, output_tokens, cache_creation_input_tokens,
  cache_read_input_tokens}`。**没有** id／company／level／dept／correlation_id／causation_id／
  size／payload_hash；`cost_cny` 代码里有、数据里 0 行。
- **ts 两种格式**：ISO `T` 分隔 14 行（全部是 2026-09-15——bash 内核时代导入），空格分隔 20387 行
  （Python daemon `time.strftime("%F %T")`，写入端 `studio-daemon/studio/metrics.py::append_event`）。
  两种都缺时区标识——按制作人机器本地时区解析（**待验证**： Asia/Shanghai 假设需在回填工具里
  显式声明）。
- **attempt 值分布**：0 → 20250 行（写入端缺省 0）；1/2/3 → 77/43/31 行。contract 要求 ≥1。
- **event 类型分布（今日实测）**：SHADOW_DIFF 16147（79.2%）｜LLM 1979｜APPROVE 446｜DISPATCH 357｜

## 二、回填范围界定

**回填**（入库）：S1 事件账本全量 → `events` 表；S2 done.json 全量 → `work_records`；S4/S3 的
会话索引（session_id → archive 相对路径）→ `sessions`（最小面）；S14 组织事实 → people 锚定表
（经公司目录 org-config 流程，非本工具直写）。

**不回填、只清点对账**：S6 闸门证据（文件侧证据体，F2-03 结果体分离——库内只存 size/hash/
路径引用，正文永不入库）；S8 运行记录（无成本列、含 76%+ 空转噪音，定时岗流水与 events 的
PATROL/DAILY_ALARM 重叠——是否回填为独立表**待拍板**，默认不回填）；S9-S12（提示词版本/自评/
报表——报表是可重建投影，F2-01）；S10 战役目录（公司目录范畴，走 org 流程不走本工具）。

**明确排除**：S5 wire（不存在）；YouTrack 权威侧（F2-10 活动流方案另接，回填不碰平台）。

## 三、对账口径设计（F2-13「先对账」的落地规格）

### 3.1 对账报告的定义

回填工具在**写入任何行之前**，先对快照产出一份对账报告（JSON＋人读 MD 双产物），含四组校验。
**全部校验只读快照**，不碰在跑的旧系统。

### 3.2 A 组 · 源内自洽（数字必须两两相符）

| # | 校验 | 今日实测基线 | 不符时含义 |
|---|---|---|---|
| A1 | events 行数 ＝ Σ 事件类型分布计数 | 20401 ＝ 20401 ✓ | 有行不含 `event` 键（坏行）——实测 0 行 |
| A2 | 完全重复行数（去重预案） | 1550 行 | 回填后因确定性 id 自动幂等跳过（§4.1），**去重数必须写进对账报告**（不静默丢弃，F2-13 验收口径） |
| A3 | ts 格式清点：T 形态＋空格形态＝总行数 | 14＋20387＝20401 ✓ | 存在第三种格式 → 坏行分类 |
| A4 | done.json 单号唯一（无同号多份） | 212 份＝212 单号 ✓ | 出现同号多份 → 口径破坏，硬停 |

### 3.6 对账不通过的处置（设计决策点 D-列表入 §七）

- **硬停面**（不产出回填）：A1/A4 破坏（账本或 done 结构性损坏）；快照哈希与回填时点不一致
  （快照后旧系统又写——重新快照重来，快照只认拷贝件）。
- **清单面**（不阻塞，差异入清单继续回填）：B2/B3/B7/B8 全部、D1 锚不进的行。F2-13 验收口径
  「差异入清单不静默丢弃」——**默认不阻塞全量回填**（差异是已知系统性欠账，阻塞无收益）；
  是否对某类差异（如旁路单）设阻塞档，**待制作人拍板**（§七-3）。
- 每条差异记录：单号/行号、差异类型（枚举见 §6）、源侧原文、处置动作。

## 五、回填工具规格（不实现，冻结命令面）

```
studio-next ledger backfill --from <旧kernel快照目录> --company <slug> [--dry-run] [--report <目录>]
```

步骤（每步产物与失败面）：

1. **快照拷贝**：`--from` 必须指向**已拷贝出的快照**（红线：旧系统零写入，工具拒绝直接指向
   活目录——启动时探测 daemon 心跳文件 mtime，新鲜则报错退出）。快照侧记总行数＋SHA-256，
   写入对账报告头部（快照时刻/指纹）。
2. **解析**：逐行 JSON.parse（两种历史格式都合法 JSON）；坏行 → 拒收清单（实测 0）。
3. **映射**：按 §4.1/§4.2 映射表逐条变换；锚定表（§4.3）作为配置文件随工具版本冻结。
4. **契约闸**：映射产物逐条 `validateEventRecord`；work_records 逐条 `WorkRecordSchema`。
   过不了 → 按分类进拒收清单，不截断（§4.1 总策略）。
5. **对账报告**：§3 全部 A/B/C/D 组校验＋数字表（含与本文档基线的对照栏）；JSON＋MD 双产物。
   **`--dry-run` 到此为止**（只产报告不写库）。
6. **写入**：events 走 `appendEvent`（先闸后插，幂等语义已备：同 id 全列一致跳过）；work_records
   走工具层查重（issue+started_at 已存在且内容一致 → 跳过；不一致 → 报错停）——store 的
   insertWorkRecord 无内置幂等，**拟稿缺口记档**（是否给 store 补 work_records 同 id 幂等闸，
   随实现单批示）。
7. **commit 计数**：输出 `{read, mapped, appended, idempotent_skipped, rejected, deduped}` 六元组；
   六元组自洽式 `read = appended + idempotent_skipped + rejected`（deduped ⊆ idempotent_skipped
   的完全重复子集）。六元组与对账报告一起落盘。
8. **收尾**：回填后跑 `dumpEvents` 再生 JSONL，行数＝库内计数（F2-11 单向派生首次对齐）；
   抽检 N=20（F2-13「抽检一致率 100%」）随机行人工比对源侧原文，结果写进报告。

**幂等性总述**：三层——①事件确定性 ULID（同内容同 id）＋appendEvent 幂等跳过；②work_records
工具层查重；③全流程可重跑（重跑时第一层的 appended 全变 idempotent_skipped，计数变化可预期）。
