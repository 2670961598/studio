# 90 · 自主存活架构（Autonomous Survival Architecture）

> 制作人 2026-11-01 令（照录）：「我们本身公司之后是要脱离人完全自主运行的……至少要保证
> 自己绝对不会出问题，自己能修复自己，**至少有一个最小的东西能够守护全公司去运行**，例如
> 研发部门的网络被切断了，是由运维来修复的，在真实的公司中就是这样的。」

## 一、设计原则（三层不可缺一）

1. **最小守护核（Guardian Core）**：一个极小的、永远存活的监护体——类比 Unix 的 PID 1 /
   生物的脑干。铁律：①代码面极小（小到不会坏）②零业务依赖（不依赖 Taiga/Matrix/模型/
   Docker——它们全是它的被监护对象）③只做「监护+拉起+上报」，不做业务④自身存活由更底层
   机制保（launchd/systemd/看门狗）。
2. **分层存活**：守护核（永生）→ 公司运行时 daemon（可重启）→ 岗位/worker（可断可换）→
   外围设施（容器/平台/网络——全部假设会坏，坏了由下层修）。
3. **自修复阶梯**（逐级升级，能自动不人工）：
   - L0 自动重启：进程死→launchd 拉起；容器死→restart policy 拉起（秒级，无人参与）
   - L1 自动绕行：部件坏→走备用通道（例：网关认证坏→exec 隧道直连；主平台坏→localfile 降级）
   - L2 运维岗修复：OPS-1 巡查发现→按 runbook 修/立修复单（分钟级，公司内部消化）
   - L3 宰相哨升级：跨层故障/无法自愈→宰相诊断处置+呈制作人
   - L4 制作人：仅物理级/授权级/doctrine 级（**最小人集**——目标趋零）
4. **绝不假设任何部件永生**：守护核自己也要被看门狗盯着（launchd 保隧道与守护进程的
   先例）；单点必须有备用拉起路径。

## 二、场景推演（制作人例：研发部网络被切断）

1. 守护核/ops 岗巡查发现：研发部 worker 心跳/tick 停走（或平台连不通研发工位）；
2. L2 运维岗诊断：定位断点（本机网络/路由/容器/隧道层）→ runbook 修复（重建隧道/
   重启面/改路由）；
3. 修不好→L3 宰相哨：切降级面（研发部工作转 localfile/备用通道）+立单修复+呈报；
4. 修复后自动回归主面（幂等 ensure 收敛）。
**要点**：部门级故障不拖垮全公司（隔离），修复是运维的**职责**而非恩惠——与真实公司同构。

## 三、现状盘点与落成形态（2026-11-04 更新，studio-dev-697）

**已有**：launchd（隧道✓）、容器 restart 策略✓、exec 隧道绕行✓（L1 实例）、OPS-1 每时岗✓（L2）、
宰相哨 2h+调查督导✓（L3）、断路/半开自愈✓、公司 schema 四连校验✓；**守护核 MVP 已落成**：

   **指数退避重启**（initial/multiplier/maxMs）→ **crash-loop 刹车**（`windowMs` 内 ≥`maxRestarts` 次

   纯逻辑单源=`packages/core/src/survival/guardian.ts`（退避/刹车/健康判据；零 IO、零 import，测试单点）；
   脚本只做 IO/进程编排（spawn/探针/日志/信号）。
2. **daemon liveness：`GET /healthz`（apiPort，缺省 8788 环回）**：进程存活＋**tick 前进**
   （最近一拍时戳 ≤ max(30s, 5×tickMs)）＋**events 哈希链摘要**（120s 节流复算、10min 陈旧上限；链断/过期=不健康，body 带 `chain.fresh`/`reasons[]`）；
   健康 200、异常 **503**（fail-closed，不谎报）；**不新增契约面/PORT-**，liveness 非 readiness，
   不承载业务读数（docs/17-§2）。
3. **迁移**：手工 nohup daemon → launchd `io.studionext.daemon`（RunAtLoad/KeepAlive 保 guardian；
   `ops/launchd/` 模板与安装/演练步骤见 `ops/launchd/README.md`）。

**仍开放**（进化方向）：

2. 运维修复自动化仍归 OPS-1 runbook 逐类沉淀（v0.1 见 §五）；

## 五、运维 runbook（v0.1，studio-dev-697；OPS-1 首使命起点）

> 每条=「症状 → 判定 → 处置 → 升级」；所有命令只读优先，处置后必须留一行证据（时间/命令/结果）。
> 禁止：不经判定直接 kill -9；伪造健康；改资料库/契约面。

### RB-01 daemon 进程死亡（guardian/launchd 已自动拉起）
- 症状：`/healthz` 连不上；`guardian.jsonl` 有 `restart` 行；launchd 状态 `running`。
- 判定：等 60s 再看 `/healthz`（200=已自愈）；若反复 restart，看 crash-loop 告警与 daemon stderr 日志尾部。
- 处置：不手工拉起（guardian 负责）；保留日志；反复崩溃→RB-02。
- 升级：连续 crash-loop 刹车（`guardian.jsonl` 有 `crash-loop brake`）→ L2 OPS-1 诊断→L3 宰相。

### RB-02 daemon 挂死（进程在、tick 停走）
- 症状：`GET /healthz` 503（`tick.advancing=false`，`ageMs` 超阈）；guardian 将按连续失败重启。
- 判定：`curl -s http://127.0.0.1:8788/healthz | jq`；看 `tick.ageMs`/`chain.ok`；看 daemon 日志末 50 行。
- 处置：guardian 自动 SIGTERM→SIGKILL→退避重启；人工不抢跑；若 chain.ok=false→RB-04。
- 升级：重复挂死（同一天 ≥3 次）→ L3 宰相（附 guardian/daemon 日志路径）。

### RB-03 鉴权/凭据面故障（平台 401/403、token 失效）
- 症状：tick 日志出现平台鉴权错误；`/healthz` 仍 200（进程健康）。属**业务面**故障，不自动重启。
- 判定：定位是 taiga/matrix/模型哪个凭据；核对 `credentials/` 与 env（不回显密钥）。
- 处置：按 L1 绕行（平台切换 localfile 等既有降级面）或更新凭据后重启 daemon（部署窗口）。
- 升级：凭据无法获取→L4 制作人（授权面）。

### RB-04 events 哈希链异常（chain.ok=false）
- 症状：`/healthz` 503 且 `chain.ok=false`；`openLedger` 启动期也可能直接拒启。
- 判定：`/healthz` 的 `chain.error`/`events`；以只读命令复算链（store 审计面）。
- 处置：**停写并保留现场**（不手工改库）；备份库文件；按 docs/v2/15 SEC-FC-04 报告。
- 升级：立即 L3 宰相→L4 制作人（可重建投影=events 重放，落仓前须批准）。

### RB-05 网络/隧道断开（研发面不可达）
- 症状：worker 派发失败、平台/网关超时；daemon 进程与 tick 正常（`/healthz` 200）。
- 判定：本机网络/路由/隧道层（`launchctl` 隧道进程、`curl` 平台地址）。
- 处置：重建隧道/切备用通道（L1）；OPS-1 立修复单；不重启 daemon 掩盖网络故障。
- 升级：部门级不可达>15min→L3（降级面：研究转 localfile）；>1h→L4。

### RB-06 guardian 自身异常
- 症状：launchd 显示 `io.studionext.daemon` 反复重启 guardian；`guardian.jsonl` 无心跳行。
- 判定：`launchctl print gui/$(id -u)/io.studionext.daemon`；看 `guardian.err.log`。
- 处置：guardian 零依赖应极少崩；核对配置路径/权限（launchd 环境 PATH 最简）。
- 升级：L2 OPS-1 修配置；仍崩→L3（守护核代码缺陷走框架开发单）。

## 六、部署形态：运行代码只来自部署树（studio-dev-708，2026-11-04）

### 6.1 事故与根因（为什么需要本形态）

2026-11-04 18:44 实测：launchd/guardian 自动拉起 daemon 时，**主工作区正有 builder 未提交的 705 代码**
（`run.ts` modified＋`reports-commit.ts` untracked）→ 运行中的 daemon 直接加载并执行了**未验证代码**，
产出公司目录 commit `2895949`（206 件报表；数据面无害）。此前手工部署同样会加载工作区未提交代码，
**守护核自动重启放大了风险面**。根因：**daemon 从主工作区直接运行**，重启即加载工作区当前状态。

制作人方向：公司要自主运行、不能依赖人；部署必须正规（版本/里程碑/已提交代码）。

### 6.2 冻结原则

1. **运行与施工分离**：主工作区（`<workRoot>/StudioNext`）只用于施工，**可以脏**；
   运行中的 daemon 只执行**部署树**（`<workRoot>/StudioNext-deploy`，独立 clone/worktree）里的代码。
2. **部署树固定在「已验证 commit」**：目标 commit 必须是 Lead commit 并过门禁的提交；
   部署状态文件记录 `targetCommit` + `tree`（git tree sha1）digest，作为「已验证事实」。
3. **fail-closed 启动**：guardian 起 daemon 前执行 `daemon.preflight`（`deploy.mjs check`）——
   部署树不干净 / HEAD≠已验证 commit / tree digest 不符 / 依赖缺失 → **拒绝启动**（告警+重试），绝不「带脏启动」。
4. **不动 daemon 业务逻辑/契约**：本形态只改守护核/部署面/文档；daemon 代码本身零改动。
5. **不重写历史**：迁移不做 amend/rebase；事故 commit `2895949` 保留。

### 6.3 部署树

- 位置：`<workRoot>/StudioNext-deploy`（**必须在主仓之外**；`deploy.mjs` 拒绝部署树 == 主仓或在主仓内）。
- 形态：推荐 `git clone --no-checkout <主仓> <部署树>`（独立对象库最稳）；`git worktree` 亦可（共享对象，快）。
- 依赖：部署树内 `bun install --frozen-lockfile`（`node_modules` 缺失或 `bun.lock` 变化时由 `deploy.mjs` 自动执行）；
  **不**把主工作区 `node_modules` 软链进部署树（workspace 包软链会指回主工作区代码，破坏隔离）。
- 只读纪律：**首次允许一次显式 checkout 到目标 commit**（`git clone --no-checkout` 后索引为空、
  `git status` 呈全部 staged deletions，属预期态；不先 checkout 则 `deploy` 会按「部署树不干净」拒绝）；
  **此后禁止手工 checkout/pull/改文件**，一律走 `deploy.mjs`（state 才会与事实一致，preflight 才放行）。

### 6.4 部署流程（部署窗口）

```
主仓：commit 已验证代码 + 门禁 exit 0（Lead）
  → deploy.mjs deploy --repo <主仓> --deploy <部署树> --ref <已验证 commit sha>
     ⓪ 漂移预检：部署树 HEAD ≠ state.targetCommit（上次失败残留态）→ exit 2 拒绝重启并给恢复指令
     ① 校验：主仓目标 commit 存在、部署树干净（不覆盖未提交改动）、部署树≠主仓
     ② checkout：部署树 `git checkout --detach <sha>`
     ③ digest：HEAD==sha ∧ tree == 主仓 <sha>^{tree} ∧ 工作树干净 ∧ 入口文件齐
     ④ 依赖：（node_modules 缺失或 bun.lock 变化）bun install --frozen-lockfile
     ⑤ **state-first 落盘**：写 <部署树>.deploy-state.json（status=deploying；targetCommit/tree/previousCommit/deps=新；
        health=pending）——**必须在重启前**，否则 guardian preflight 读旧 state 与部署树 HEAD 互锁
     ⑥ 重启：launchctl kickstart -k gui/<uid>/io.studionext.daemon（guardian 重启→daemon 从部署树起；
        窗口内 preflight 读到 deploying 态且树/state 一致 → 放行）
     ⑦ 验证：轮询 GET /healthz 至 200∧ok=true∧**pid≠部署前 pid**（超时=部署失败）
     ⑧ 收尾：state 写回 status=active（health.pid/waitedMs/probes/deployedCommit）
  → guardian preflight 在每次启动前复读 state：不一致即拒绝启动
```

- **回滚**：同一命令 `--ref <上一 commit sha>`（state 记 previousCommit）；不重写历史。
- **失败处置**：①–④ 失败 → 未重启，直接按提示修复；⑦ health 失败 → **自动回滚部署树到上一 commit＋恢复上一版 state**
  （preflight 可放行旧代码自动恢复），exit 4 报「daemon 可能已停」＋恢复指令；⑤/⑥ 之间 kickstart 抛错 → state 停 deploying
  （树/state 仍一致，可重跑 deploy 或 kickstart 续）。

### 6.5 guardian preflight（B 兜底）

- `guardian.json`：`daemon.cwd=<部署树>`、`daemon.command=[node, apps/boot/src/main.ts, <company>/daemon.yaml]`、
  `daemon.preflight=[node, <部署树>/scripts/ops/deploy.mjs, check, --deploy, <部署树>, --state, <state.json>]`、
  `daemon.preflightRetryMs=30000`。
- 语义：每次起 daemon 前跑 preflight；非 0 → `guardian.jsonl` 记 `preflight-failed`（含 exitCode/output 截断）→
  隔 `preflightRetryMs` 重试；**不 spawn daemon**。恢复正常后自动继续（`preflight-ok`→`daemon-start`）。
- **部署窗口语义（ref=717）**：deploy 在重启前先写 `status=deploying` 的 state（target/tree=新），preflight 校验
  「部署树 HEAD == state.targetCommit ∧ tree digest 一致 ∧ 树干净 ∧ 依赖齐」→ 窗口内自然放行；部署完成写
  `status=active`。因此 **state 不存在/漂移才 fail-closed**，部署窗口不再互锁。
- 效果：builder 施工期主工作区脏**不影响**运行；守护核自动重启也安全；部署树被手工改脏/漂移则**停而不带脏跑**。

### 6.6 演练与验收（部署窗口，ref=708 交付后由 Lead 执行）

1. **脏工作区隔离**：主工作区留任意未提交改动 → 重启 guardian/daemon → `/healthz` 200、daemon 命令行与 cwd 指向部署树、
   运行代码**不含**脏改动（`git -C <部署树> status` 空、`git -C <部署树> rev-parse HEAD`==state.targetCommit）。
2. **部署更新生效**：部署树更新到新 commit → 重启 → `/healthz` 200 且新行为生效；回滚旧 commit → 再次 200。
3. **preflight 拒绝**：部署树 `touch` 未提交文件 → `launchctl kickstart -k` → `preflight-failed` 且 **无** `daemon-start`。
4. **正常重启**：部署树干净时 kill -9 daemon → guardian 自动拉起（`daemon-start`），证明「不依赖人、不乱跑工作区」。

### 6.7 不做什么

不改 daemon 业务逻辑/契约/既有测试断言；不新建平台；不动 studio-dev 运行进程（演练由 Lead 配合）；
不重写公司 git 历史；不把部署状态/凭据写进仓库。

### 6.8 多公司部署形态（studio-profit 等）

同一套「部署树 + 已验证 commit + preflight」机制可复用到**多公司**，但**守护实例按公司隔离**：

- **代码部署树共享**（推荐）：所有公司 daemon 跑**同一部署树**的同一已验证 commit（代码同源、升级一致）；
  每公司只差公司目录/配置（`<companyDir>/daemon.yaml`）与运行数据（台账/工作区）。
- **守护实例独立**：`guardian` 语义是「一号一 daemon」，因此每公司一个实例——
  独立 launchd label（如 `io.studionext.daemon`＝studio-dev、`io.studionext.profit`＝studio-profit）、
  独立 `guardian.json`（daemon.command 指同一部署树入口 + 该公司 daemon.yaml；health.url 用各自 apiPort）、
  独立 `paths.logDir/pidFile/alertsFile`；**deploy-state 推荐共用一份**（共享同一部署树：部署一次、全实例同版本），
  重启按实例分别 `launchctl kickstart`。
- **部署脚本扩展**：`deploy.mjs deploy` 当前按「一个部署树 + 一个 launchd label」重启；
  多实例时可在部署后对每个实例执行 `launchctl kickstart -k`（或后续单给 `deploy.mjs` 加 `--label` 多次/`--labels a,b`）。
  本单（708）**先交付 studio-dev 部署隔离**；studio-profit 守护化（含其 SIGBUS/WAL 事故面）**拆后续单**，不扩本单范围。
- **隔离边界**：每公司 apiPort/healthz/DB/公司目录互不串；共享代码树时，部署树的 commit 是唯一版本源，
  state 的 `targetCommit/tree` 对所有实例一致。

## 七、发布控制面（studio-dev-719，2026-11-04）

> 定位：把「已验证 commit → 部署窗口 → 部署树」的人批流程固化为**可审计 CLI**；不建岗位、不改
> deploy.mjs/daemon/契约。脚本：`scripts/ops/release.mjs`（只 spawn 调 deploy.mjs CLI；本工具不 import
> 也不修改它）；三形状 schema：`scripts/ops/release-request.schema.json`；记录落点：`docs/releases/`。

### 7.1 角色与审批

- **执行者**（授权操作者）：采集真实 gates 输出（`verify:v2` PASS 行）→ `plan` → `request` → 交审批。
- **审批人**（制作人或其授权代理人）：对 request 的 `version/targetCommit/tree/gatesDigest` **全等**批准，
  产出 approval（`approver/approvedAt/expiresAt/commentRef`）。审批过期=拒；任一项不等=exit 2 且不部署。
- **边界**：审批是「人批」事实，不由 daemon 代签；工具不写台账 events/records（发布记录是 docs 产物，
  部署事实仍只在 deploy.mjs state）。
- **发布岗 REL-1**（studio-dev-720，2026-11-04 制作人批；公司目录 `departments/综合部/people/REL-1.md`，
  2 级/综合部/reports_to=PRIME-0/executor=dsh）：**准备权与执行权分离**——REL-1 **只准备发布材料**：
  `release.mjs plan/request` 的实例、checklist、`docs/releases/<version>.md` 记录草稿与 tag 计划；
  **不得**执行 `deploy.mjs`/`release.mjs execute`/`git tag`/`git push`，**不得**代签审批或伪造
  `gatesDigest`；**执行仍由授权操作者**（宰相/代签）跑 719 `execute`；**审批仍由制作人或授权代理人**。
  REL-1 的边界错误按「越权发布」事故处理；其 P1 特权执行泳道（723）另批，P0 不授予。

### 7.2 版本、tag 与记录

- `plan`：解析目标 commit/tree、部署树现状、checklist；`gatesDigest` 只从真实 verify 输出文本按
  `sha256("verify:v2@<commit>:"+最后一条 PASS 行)` 计算（不跑 verify、不猜、不伪造）。
- `request/approve-check`：绑定校验通过才允许 `execute`；失败 exit 2 且零 deploy 调用（可 spy 证）。
- `execute`：approve-check → `deploy.mjs deploy --repo --deploy --ref <targetCommit>` → 写
  `docs/releases/<version>.md` → 本地 **annotated tag**（`git tag -a <version>`）；**默认不 push**，
  输出 push 命令；`--push` 显式才推（已推送 tag 重发需制作人批，禁止 force push）。
- `record/tag/status`：可独立复跑；`status` 聚合 deploy.mjs status + 最近 release 记录 + tag 存在性。

### 7.3 回滚

- `rollback --to <prevCommit>`：只调用 deploy.mjs `deploy --ref <prevCommit>`（不重写历史），成功后写
  `docs/releases/rollback-<短 sha>.md`（含 `rolledBackTo/fromCommit/deploy.health`）；失败给恢复指令。
- deploy.mjs 自带「失败回滚上一 commit + state 一致」语义（718/717 硬化，§6.7）；本工具不绕过它。

### 7.4 版本纪律（制作人 2026-11-04 令）

1. **大版本结束才重新**：版本号切换（v0.x→v0.y）只在当前里程碑验收结束后进行，不在施工中途改版本。
2. **完成单优先当前版本**：已完成单优先进入当前版本发布批次；未完成单不得「借发布夹带」。
3. **下版本预研只留自己工作目录或推新分支**：预研代码/文档不得混入当前版本主分支发布树。
4. **发布必留证**：每次 release 必须有 request+approval+record+tag 四件；缺一即发布流程未完成
   （与 17-§3 证据断言同精神：无证据=无完成）。
5. **与 §六 衔接**：发布=部署树切到已验证 commit（deploy.mjs）；发布控制面只负责「人批→部署→记录→tag」
   的编排与留痕，不改变「运行代码只来自部署树」的铁律。
