# 90 · 自主存活架构（Autonomous Survival Architecture）

> 制作人 2026-11-01 令（照录）：「我们本身公司之后是要脱离人完全自主运行的……至少要保证
> 自己绝对不会出问题，自己能修复自己，**至少有一个最小的东西能够守护全公司去运行**，例如
> 研发部门的网络被切断了，是由运维来修复的，在真实的公司中就是这样的。」

## 一、设计原则（三层不可缺一）

1. **最小守护核（Guardian Core）**：一个极小的、永远存活的监护体——类比 Unix 的 PID 1 /
   生物的脑干。铁律：①代码面极小（小到不会坏）②零业务依赖（不依赖 Taiga/Matrix/模型/
   Docker——它们全是它的被监护对象）③只做「监护+拉起+上报」，不做业务④自身存活由更底层
   机制保（launchd/systemd/看门狗）。
2. **分层存活**：守护核（永生）→ 公司运行时 daemon（可重启）→ 岗位/worker（可断可换）→
   外围设施（容器/平台/网络——全部假设会坏，坏了由下层修）。
3. **自修复阶梯**（逐级升级，能自动不人工）：
   - L0 自动重启：进程死→launchd 拉起；容器死→restart policy 拉起（秒级，无人参与）
   - L1 自动绕行：部件坏→走备用通道（例：网关认证坏→exec 隧道直连；主平台坏→localfile 降级）
   - L2 运维岗修复：OPS-1 巡查发现→按 runbook 修/立修复单（分钟级，公司内部消化）
   - L3 宰相哨升级：跨层故障/无法自愈→宰相诊断处置+呈制作人
   - L4 制作人：仅物理级/授权级/doctrine 级（**最小人集**——目标趋零）
4. **绝不假设任何部件永生**：守护核自己也要被看门狗盯着（launchd 保隧道与守护进程的
   先例）；单点必须有备用拉起路径。

## 二、场景推演（制作人例：研发部网络被切断）

1. 守护核/ops 岗巡查发现：研发部 worker 心跳/tick 停走（或平台连不通研发工位）；
2. L2 运维岗诊断：定位断点（本机网络/路由/容器/隧道层）→ runbook 修复（重建隧道/
   重启面/改路由）；
3. 修不好→L3 宰相哨：切降级面（研发部工作转 localfile/备用通道）+立单修复+呈报；
4. 修复后自动回归主面（幂等 ensure 收敛）。
**要点**：部门级故障不拖垮全公司（隔离），修复是运维的**职责**而非恩惠——与真实公司同构。

## 三、现状盘点与落成形态（2026-11-04 更新，studio-dev-697）

**已有**：launchd（隧道✓）、容器 restart 策略✓、exec 隧道绕行✓（L1 实例）、OPS-1 每时岗✓（L2）、
宰相哨 2h+调查督导✓（L3）、断路/半开自愈✓、公司 schema 四连校验✓；**守护核 MVP 已落成**：
1. **守护核＝`scripts/guardian.mjs`（launchd 托管）**：极小、零业务依赖（仅 node 标准库+fetch），
   只做「监护/拉起/上报」：起 daemon 子进程 → 每 `probe.intervalMs` 探 `GET /healthz`（超时/非 200/
   字段不符=失败）→ 连续 `failuresBeforeRestart` 次失败或子进程退出 → SIGTERM 等 drain → SIGKILL →
   **指数退避重启**（initial/multiplier/maxMs）→ **crash-loop 刹车**（`windowMs` 内 ≥`maxRestarts` 次
   失败：长退避 `brakeMs` + 告警，不无限重启）→ 告警写 `guardian.jsonl`（可选 webhook；失败不炸）。
   守护核自身由 **launchd `KeepAlive`** 保活（`io.studionext.daemon`，与旧代 `com.studio.daemon` 区分）。
   纯逻辑单源=`packages/core/src/survival/guardian.ts`（退避/刹车/健康判据；零 IO、零 import，测试单点）；
   脚本只做 IO/进程编排（spawn/探针/日志/信号）。
2. **daemon liveness：`GET /healthz`（apiPort，缺省 8788 环回）**：进程存活＋**tick 前进**
   （最近一拍时戳 ≤ max(30s, 5×tickMs)）＋**events 哈希链摘要**（120s 节流；785 起 **checkpoint+delta**：启动/回退全量一次，之后只验新增链行，旧前缀由 tip 锚定——不宣称每次全量密码学验证；10min 陈旧上限；链断/过期=不健康，body 带 `chain.fresh/mode/sinceSeq`/`reasons[]`）；
   健康 200、异常 **503**（fail-closed，不谎报）；**不新增契约面/PORT-**，liveness 非 readiness，
   不承载业务读数（docs/17-§2）。
3. **迁移**：手工 nohup daemon → launchd `io.studionext.daemon`（RunAtLoad/KeepAlive 保 guardian；
   `ops/launchd/` 模板与安装/演练步骤见 `ops/launchd/README.md`）。

**仍开放**（进化方向）：
1. 降级面未系统化（主平台坏→localfile 的切换是手动的——需预案化）；
2. 运维修复自动化仍归 OPS-1 runbook 逐类沉淀（v0.1 见 §五）；
3. 存活 SLO（守护核可用性>99.99%／检测时延／重启恢复时延）待制作人定标；
4. guardian 的 Matrix 告警出口为可选项（webhook 先留口，失败不炸）。

## 五、运维 runbook（v0.1，studio-dev-697；OPS-1 首使命起点）

> 每条=「症状 → 判定 → 处置 → 升级」；所有命令只读优先，处置后必须留一行证据（时间/命令/结果）。
> 禁止：不经判定直接 kill -9；伪造健康；改资料库/契约面。

### RB-01 daemon 进程死亡（guardian/launchd 已自动拉起）
- 症状：`/healthz` 连不上；`guardian.jsonl` 有 `restart` 行；launchd 状态 `running`。
- 判定：等 60s 再看 `/healthz`（200=已自愈）；若反复 restart，看 crash-loop 告警与 daemon stderr 日志尾部。
- 处置：不手工拉起（guardian 负责）；保留日志；反复崩溃→RB-02。
- 升级：连续 crash-loop 刹车（`guardian.jsonl` 有 `crash-loop brake`）→ L2 OPS-1 诊断→L3 宰相。

### RB-02 daemon 挂死（进程在、tick 停走）
- 症状：`GET /healthz` 503（`tick.advancing=false`，`ageMs` 超阈）；guardian 将按连续失败重启。
- 判定：`curl -s http://127.0.0.1:8788/healthz | jq`；看 `tick.ageMs`/`chain.ok`；看 daemon 日志末 50 行。
- 处置：guardian 自动 SIGTERM→SIGKILL→退避重启；人工不抢跑；若 chain.ok=false→RB-04。
- 升级：重复挂死（同一天 ≥3 次）→ L3 宰相（附 guardian/daemon 日志路径）。

### RB-03 鉴权/凭据面故障（平台 401/403、token 失效）
- 症状：tick 日志出现平台鉴权错误；`/healthz` 仍 200（进程健康）。属**业务面**故障，不自动重启。
- 判定：定位是 taiga/matrix/模型哪个凭据；核对 `credentials/` 与 env（不回显密钥）。
- 处置：按 L1 绕行（平台切换 localfile 等既有降级面）或更新凭据后重启 daemon（部署窗口）。
- 升级：凭据无法获取→L4 制作人（授权面）。

### RB-04 events 哈希链异常（chain.ok=false）
- 症状：`/healthz` 503 且 `chain.ok=false`；`openLedger` 启动期也可能直接拒启。
- 判定：`/healthz` 的 `chain.error`/`events`；以只读命令复算链（store 审计面）。
- 处置：**停写并保留现场**（不手工改库）；备份库文件；按 docs/v2/15 SEC-FC-04 报告。
- 升级：立即 L3 宰相→L4 制作人（可重建投影=events 重放，落仓前须批准）。

### RB-05 网络/隧道断开（研发面不可达）
- 症状：worker 派发失败、平台/网关超时；daemon 进程与 tick 正常（`/healthz` 200）。
- 判定：本机网络/路由/隧道层（`launchctl` 隧道进程、`curl` 平台地址）。
- 处置：重建隧道/切备用通道（L1）；OPS-1 立修复单；不重启 daemon 掩盖网络故障。
- 升级：部门级不可达>15min→L3（降级面：研究转 localfile）；>1h→L4。

### RB-06 guardian 自身异常
- 症状：launchd 显示 `io.studionext.daemon` 反复重启 guardian；`guardian.jsonl` 无心跳行。
- 判定：`launchctl print gui/$(id -u)/io.studionext.daemon`；看 `guardian.err.log`。
- 处置：guardian 零依赖应极少崩；核对配置路径/权限（launchd 环境 PATH 最简）。
- 升级：L2 OPS-1 修配置；仍崩→L3（守护核代码缺陷走框架开发单）。

### RB-07 依赖链故障恢复（Docker/Matrix/Taiga；studio-dev-774，2026-11-04 事故后新增）

- **症状**：daemon 反复退出且 `guardian.jsonl` 出现 `health-fail`→`crash-loop-brake`；Matrix 登录 500
  （如 `Problem storing device`）；:8008/:9000 不可达；`docker` 无响应（Docker.raw 所在盘 I/O error）。
- **分层判定（自下而上，先证据后动作）**：
  1. **外置盘 I/O**：`log show --last 2h --predicate 'eventMessage CONTAINS "I/O error"'`（或控制台）看
     SCSI I/O error / `apfs_pagein`；`diskutil info <盘>`；先停写保数据，别在坏盘上继续跑 Docker。
  2. **Docker daemon**：`curl -s --unix-socket /var/run/docker.sock http://localhost/_ping`（>3s 无响应=
     VM 卡死，区别于「容器未起」）；`docker ps`；确认 Docker.raw 所在盘。
  3. **容器**：`docker inspect -f '{{.State.Running}}' synapse taiga`；未起→`docker start <name>`。
  4. **Matrix**：`curl -fsS http://127.0.0.1:8008/_matrix/client/versions`；登录失败先分 5xx（依赖故障，
     774 起 daemon 有限退避重试 3×30s）与 401/403（凭据/权限，fail-fast 不重试）。
  5. **Taiga**：`curl -fsS http://127.0.0.1:9000/api/v1/`。
  6. **daemon**：`curl -fsS http://127.0.0.1:8788/healthz`；`launchctl print gui/$(id -u)/io.studionext.daemon`；
     `guardian.jsonl` 看失败序列与刹车原因。
- **恢复顺序（人工标准作业）**：①停写保数据 →②Docker 卡死则强杀 Docker.app 后重开、等 `_ping` OK →
  ③起容器 synapse/taiga 并确认 :8008/:9000 →④kickstart guardian（daemon 会自行登录退避重试）→
  ⑤确认 `/healthz` ok=true 且 pid 变化 →⑥最后恢复 profit daemon。
- **自动化（host 侧独立 watchdog）**：`scripts/ops/infra-watchdog.mjs`（launchd
  `io.studionext.infra-watchdog`）探测 docker/Matrix/Taiga/studio-dev healthz/profit 进程，连续 N 次失败
  记 `infra-alerts.jsonl` 并按配置自动执行上述「docker kill+reopen / docker start / kickstart guardian」；
  恢复动作带冷却与小时上限，`--alert-only` 可切只告警。生产安装见 `ops/launchd/README.md` §7。
- **案例（2026-11-04 23:00）**：USB 外置盘 I/O error（SCSI I/O error＋`apfs_pagein` error 22）→ Docker
  Desktop VM 卡死（Docker.raw 在该盘）→ Synapse(:8008)/Taiga(:9000) 全挂 → studio-dev daemon Matrix 登录
  500「Problem storing device」连续崩溃 ×5 → guardian crash-loop-brake 15min → daemon 停 ~16min（profit 同停）；
  恢复=人工 bootout guardian→强杀 Docker→重开→bootstrap guardian→重启 profit。教训：①外部盘承载 Docker.raw
  是单点（#712 迁移评估见 774 REPORT）；②依赖链瞬态不得让 daemon 直接 crash-loop（774 登录退避）；
  ③guardian 只管 daemon，Docker/Matrix/Taiga 需 host 侧独立 watchdog。
- **升级**：I/O error 反复→存储故障 L3（盘/线/供电，先备份再迁移）；依赖链>15min→OPS-1＋L3；
  数据损坏→停写并按备份恢复流程处理，不带病重启。

## 六、部署形态：运行代码只来自部署树（studio-dev-708，2026-11-04）

### 6.1 事故与根因（为什么需要本形态）

2026-11-04 18:44 实测：launchd/guardian 自动拉起 daemon 时，**主工作区正有 builder 未提交的 705 代码**
（`run.ts` modified＋`reports-commit.ts` untracked）→ 运行中的 daemon 直接加载并执行了**未验证代码**，
产出公司目录 commit `2895949`（206 件报表；数据面无害）。此前手工部署同样会加载工作区未提交代码，
**守护核自动重启放大了风险面**。根因：**daemon 从主工作区直接运行**，重启即加载工作区当前状态。

制作人方向：公司要自主运行、不能依赖人；部署必须正规（版本/里程碑/已提交代码）。

### 6.2 冻结原则

1. **运行与施工分离**：主工作区（`<workRoot>/StudioNext`）只用于施工，**可以脏**；
   运行中的 daemon 只执行**部署树**（`<workRoot>/StudioNext-deploy`，独立 clone/worktree）里的代码。
2. **部署树固定在「已验证 commit」**：目标 commit 必须是 Lead commit 并过门禁的提交；
   部署状态文件记录 `targetCommit` + `tree`（git tree sha1）digest，作为「已验证事实」。
3. **fail-closed 启动**：guardian 起 daemon 前执行 `daemon.preflight`（`deploy.mjs check`）——
   部署树不干净 / HEAD≠已验证 commit / tree digest 不符 / 依赖缺失 → **拒绝启动**（告警+重试），绝不「带脏启动」。
4. **不动 daemon 业务逻辑/契约**：本形态只改守护核/部署面/文档；daemon 代码本身零改动。
5. **不重写历史**：迁移不做 amend/rebase；事故 commit `2895949` 保留。

### 6.3 部署树

- 位置：`<workRoot>/StudioNext-deploy`（**必须在主仓之外**；`deploy.mjs` 拒绝部署树 == 主仓或在主仓内）。
- 形态：推荐 `git clone --no-checkout <主仓> <部署树>`（独立对象库最稳）；`git worktree` 亦可（共享对象，快）。
- 依赖：部署树内 `bun install --frozen-lockfile`（`node_modules` 缺失或 `bun.lock` 变化时由 `deploy.mjs` 自动执行）；
  **不**把主工作区 `node_modules` 软链进部署树（workspace 包软链会指回主工作区代码，破坏隔离）。
- 只读纪律：**首次允许一次显式 checkout 到目标 commit**（`git clone --no-checkout` 后索引为空、
  `git status` 呈全部 staged deletions，属预期态；不先 checkout 则 `deploy` 会按「部署树不干净」拒绝）；
  **此后禁止手工 checkout/pull/改文件**，一律走 `deploy.mjs`（state 才会与事实一致，preflight 才放行）。

### 6.4 部署流程（部署窗口）

```
主仓：commit 已验证代码 + 门禁 exit 0（Lead）
  → deploy.mjs deploy --repo <主仓> --deploy <部署树> --ref <已验证 commit sha>
     ⓪ 漂移预检：部署树 HEAD ≠ state.targetCommit（上次失败残留态）→ exit 2 拒绝重启并给恢复指令
     ① 校验：主仓目标 commit 存在、部署树干净（不覆盖未提交改动）、部署树≠主仓
     ② checkout：部署树 `git checkout --detach <sha>`
     ③ digest：HEAD==sha ∧ tree == 主仓 <sha>^{tree} ∧ 工作树干净 ∧ 入口文件齐
     ④ 依赖：（node_modules 缺失或 bun.lock 变化）bun install --frozen-lockfile
     ⑤ **state-first 落盘**：写 <部署树>.deploy-state.json（status=deploying；targetCommit/tree/previousCommit/deps=新；
        health=pending）——**必须在重启前**，否则 guardian preflight 读旧 state 与部署树 HEAD 互锁
     ⑥ 重启：launchctl kickstart -k gui/<uid>/io.studionext.daemon（guardian 重启→daemon 从部署树起；
        窗口内 preflight 读到 deploying 态且树/state 一致 → 放行）
     ⑦ 验证：轮询 GET /healthz 至 200∧ok=true∧**pid≠部署前 pid**（超时=部署失败）
     ⑧ 收尾：state 写回 status=active（health.pid/waitedMs/probes/deployedCommit）
  → guardian preflight 在每次启动前复读 state：不一致即拒绝启动
```

- **回滚**：同一命令 `--ref <上一 commit sha>`（state 记 previousCommit）；不重写历史。
- **失败处置**：①–④ 失败 → 未重启，直接按提示修复；⑦ health 失败 → **自动回滚部署树到上一 commit＋恢复上一版 state**
  （preflight 可放行旧代码自动恢复），exit 4 报「daemon 可能已停」＋恢复指令；⑤/⑥ 之间 kickstart 抛错 → state 停 deploying
  （树/state 仍一致，可重跑 deploy 或 kickstart 续）。

### 6.5 guardian preflight（B 兜底）

- `guardian.json`：`daemon.cwd=<部署树>`、`daemon.command=[node, apps/boot/src/main.ts, <company>/daemon.yaml]`、
  `daemon.preflight=[node, <部署树>/scripts/ops/deploy.mjs, check, --deploy, <部署树>, --state, <state.json>]`、
  `daemon.preflightRetryMs=30000`。
- 语义：每次起 daemon 前跑 preflight；非 0 → `guardian.jsonl` 记 `preflight-failed`（含 exitCode/output 截断）→
  隔 `preflightRetryMs` 重试；**不 spawn daemon**。恢复正常后自动继续（`preflight-ok`→`daemon-start`）。
- **部署窗口语义（ref=717）**：deploy 在重启前先写 `status=deploying` 的 state（target/tree=新），preflight 校验
  「部署树 HEAD == state.targetCommit ∧ tree digest 一致 ∧ 树干净 ∧ 依赖齐」→ 窗口内自然放行；部署完成写
  `status=active`。因此 **state 不存在/漂移才 fail-closed**，部署窗口不再互锁。
- 效果：builder 施工期主工作区脏**不影响**运行；守护核自动重启也安全；部署树被手工改脏/漂移则**停而不带脏跑**。

### 6.6 演练与验收（部署窗口，ref=708 交付后由 Lead 执行）

1. **脏工作区隔离**：主工作区留任意未提交改动 → 重启 guardian/daemon → `/healthz` 200、daemon 命令行与 cwd 指向部署树、
   运行代码**不含**脏改动（`git -C <部署树> status` 空、`git -C <部署树> rev-parse HEAD`==state.targetCommit）。
2. **部署更新生效**：部署树更新到新 commit → 重启 → `/healthz` 200 且新行为生效；回滚旧 commit → 再次 200。
3. **preflight 拒绝**：部署树 `touch` 未提交文件 → `launchctl kickstart -k` → `preflight-failed` 且 **无** `daemon-start`。
4. **正常重启**：部署树干净时 kill -9 daemon → guardian 自动拉起（`daemon-start`），证明「不依赖人、不乱跑工作区」。

**实测记录（2026-11-04 19:52–19:56，studio-dev，Lead 执行）**：
- 部署树 `<workRoot>/StudioNext-deploy` clone 于 `5377edb`（`--no-checkout`→显式 `checkout --detach`→`bun install --frozen-lockfile` 90 包）；
  `deploy.mjs deploy --ref 5377edb` → `OK`、tree `b5abbfd5…`、`health=ok pid=51906`、state 落盘。
- **脏工作区隔离 PASS**：主工作区 11 个未提交改动（builder #707 seg1＋hotfix #713）期间，daemon 从部署树运行、
  `git -C <部署树> status` 空、HEAD==state.targetCommit，`/healthz` 200（tick 前进、链摘要 fresh）。
- **preflight 拒绝 PASS**：部署树 `echo >> README.md`（1 项脏）→ `launchctl kickstart -k` → `preflight-failed(exitCode=2,
  output=部署树不干净…)`、**无** `daemon-start`、healthz 不可达（fail-closed）；`git checkout -- README.md` 恢复后
  kickstart → `preflight-ok`→`daemon-start`→`/healthz` 200。
- **state 缺失 fail-closed PASS**：临时移走 state 文件跑 `deploy.mjs check` → exit 2「部署状态文件缺失…未经部署脚本记录的树不允许启动」。
- **kill -9 演练 PASS**：`kill -9` daemon(53328) → guardian 记 `restart-scheduled(attempt=1, backoff=2000ms,
  lastReason=child-exited(SIGKILL))` → `preflight-ok`→`daemon-start(53665)`→`/healthz` 200。
- **首装顺序（鸡生蛋，ref=717 后已消除）**：deploy 在重启前先写 `status=deploying` state，故 guardian 即使已带
  preflight，也可直接 `deploy.mjs deploy`（窗口内 check 通过）；state 完全缺失时仍 fail-closed（预期），先跑一次
  `deploy.mjs deploy --skip-restart` 即可落 state。该口径已同步 `ops/launchd/README.md` 第 1 节。
- **717 state-first 实测（2026-11-04 21:3x，本机）**：部署新 commit → state 先 `deploying`（target/tree=新）→
  guardian `preflight-ok`→`daemon-start`（新 pid≠旧 pid）→ state `active`（health.pid=新）；health 失败回滚与
  漂移预检由隔离窗口测试覆盖（verifier 独立探针 19/19）。

### 6.8 多公司部署形态（studio-profit 等）

同一套「部署树 + 已验证 commit + preflight」机制可复用到**多公司**，但**守护实例按公司隔离**：

- **代码部署树共享**（推荐）：所有公司 daemon 跑**同一部署树**的同一已验证 commit（代码同源、升级一致）；
  每公司只差公司目录/配置（`<companyDir>/daemon.yaml`）与运行数据（台账/工作区）。
- **守护实例独立**：`guardian` 语义是「一号一 daemon」，因此每公司一个实例——
  独立 launchd label（如 `io.studionext.daemon`＝studio-dev、`io.studionext.profit`＝studio-profit）、
  独立 `guardian.json`（daemon.command 指同一部署树入口 + 该公司 daemon.yaml；health.url 用各自 apiPort）、
  独立 `paths.logDir/pidFile/alertsFile`；**deploy-state 推荐共用一份**（共享同一部署树：部署一次、全实例同版本），
  重启按实例分别 `launchctl kickstart`。
- **部署脚本扩展**：`deploy.mjs deploy` 当前按「一个部署树 + 一个 launchd label」重启；
  多实例时可在部署后对每个实例执行 `launchctl kickstart -k`（或后续单给 `deploy.mjs` 加 `--label` 多次/`--labels a,b`）。
  本单（708）**先交付 studio-dev 部署隔离**；studio-profit 守护化（含其 SIGBUS/WAL 事故面）**拆后续单**，不扩本单范围。
- **隔离边界**：每公司 apiPort/healthz/DB/公司目录互不串；共享代码树时，部署树的 commit 是唯一版本源，
  state 的 `targetCommit/tree` 对所有实例一致。

## 七、发布控制面（studio-dev-719，2026-11-04）

> 定位：把「已验证 commit → 部署窗口 → 部署树」的人批流程固化为**可审计 CLI**；不建岗位、不改
> deploy.mjs/daemon/契约。脚本：`scripts/ops/release.mjs`（只 spawn 调 deploy.mjs CLI；本工具不 import
> 也不修改它）；三形状 schema：`scripts/ops/release-request.schema.json`；记录落点：`docs/releases/`。

### 7.1 角色与审批

- **执行者**（授权操作者）：采集真实 gates 输出（`verify:v2` PASS 行）→ `plan` → `request` → 交审批。
- **审批人**（制作人或其授权代理人）：对 request 的 `version/targetCommit/tree/gatesDigest` **全等**批准，
  产出 approval（`approver/approvedAt/expiresAt/commentRef`）。审批过期=拒；任一项不等=exit 2 且不部署。
- **边界**：审批是「人批」事实，不由 daemon 代签；工具不写台账 events/records（发布记录是 docs 产物，
  部署事实仍只在 deploy.mjs state）。
- **发布岗 REL-1**（studio-dev-720，2026-11-04 制作人批；公司目录 `departments/综合部/people/REL-1.md`，
  2 级/综合部/reports_to=PRIME-0/executor=dsh）：**准备权与执行权分离**——REL-1 **只准备发布材料**：
  `release.mjs plan/request` 的实例、checklist、`docs/releases/<version>.md` 记录草稿与 tag 计划；
  **不得**执行 `deploy.mjs`/`release.mjs execute`/`git tag`/`git push`，**不得**代签审批或伪造
  `gatesDigest`；**执行仍由授权操作者**（宰相/代签）跑 719 `execute`；**审批仍由制作人或授权代理人**。
  REL-1 的边界错误按「越权发布」事故处理；其 P1 特权执行泳道（723）另批，P0 不授予。
  **不接执行类单据（studio-dev-775/C2/C3）**：派工面排除本岗（daemon.yaml
  `autoAssignExcludePeople: REL-1`／`autoAssignExcludeRoles: 发布岗`，core pickAssignee 排除后
  空集=all-excluded 顺延不回退缺省人）；另设监控（`executionGuardRoles: 发布岗`＋
  `executionGuardKeywords: deploy;release;tag;push;发布;上线;部署;回滚`）——受监控岗位被指派
  含执行关键词单据 → **ESCALATE 拒派人工复核**（防绕过 719 审批执行原始发布命令）；
  REL-1 人事档案同步回写「不接执行类单据」边界。

### 7.2 版本、tag 与记录

- `plan`：解析目标 commit/tree、部署树现状、checklist；`gatesDigest` 只从真实 verify 输出文本按
  `sha256("verify:v2@<commit>:"+最后一条 PASS 行)` 计算（不跑 verify、不猜、不伪造）。
- `request/approve-check`：绑定校验通过才允许 `execute`；失败 exit 2 且零 deploy 调用（可 spy 证）。
- `execute`：approve-check → `deploy.mjs deploy --repo --deploy --ref <targetCommit>` → 写
  `docs/releases/<version>.md` → 本地 **annotated tag**（`git tag -a <version>`）；**默认不 push**，
  输出 push 命令；`--push` 显式才推（已推送 tag 重发需制作人批，禁止 force push）。
- `record/tag/status`：可独立复跑；`status` 聚合 deploy.mjs status + 最近 release 记录 + tag 存在性。

### 7.3 回滚

- `rollback --to <prevCommit>`：只调用 deploy.mjs `deploy --ref <prevCommit>`（不重写历史），成功后写
  `docs/releases/rollback-<短 sha>.md`（含 `rolledBackTo/fromCommit/deploy.health`）；失败给恢复指令。
- deploy.mjs 自带「失败回滚上一 commit + state 一致」语义（718/717 硬化，§6.7）；本工具不绕过它。

### 7.4 版本纪律（制作人 2026-11-04 令）

1. **大版本结束才重新**：版本号切换（v0.x→v0.y）只在当前里程碑验收结束后进行，不在施工中途改版本。
2. **完成单优先当前版本**：已完成单优先进入当前版本发布批次；未完成单不得「借发布夹带」。
3. **下版本预研只留自己工作目录或推新分支**：预研代码/文档不得混入当前版本主分支发布树。
4. **发布必留证**：每次 release 必须有 request+approval+record+tag 四件；缺一即发布流程未完成
   （与 17-§3 证据断言同精神：无证据=无完成）。
5. **与 §六 衔接**：发布=部署树切到已验证 commit（deploy.mjs）；发布控制面只负责「人批→部署→记录→tag」
   的编排与留痕，不改变「运行代码只来自部署树」的铁律。

## 九、每人 key 与提交签名（studio-dev-721，2026-11-05）

> 制作人令：**每个人有自己的 key；提交时验证 key 和作者；commit log 带工号和 key 指纹；验证通过才允许提交**。
> 本节的「提交」指进入框架主仓/公司目录的新 commit（历史 commit 按范围豁免——校验脚本只验指定 range/新提交）。
> 密钥托管位置：公司目录 **`docs/keys/`（在 `company/` git 仓之外，永不入仓）**，目录既有 README 为安装约定。

### 8.1 密钥形状与托管

- 每岗一把 **ed25519 SSH key**：`docs/keys/<工号>.key`（私钥，**600**）＋ `docs/keys/<工号>.pub`（公钥，644）；
  生成器 `scripts/ops/gen-worker-key.mjs` 同时写 `docs/keys/<工号>.json`（id/name/email/指纹/算法/comment，**不含私钥**）。
- 公钥 comment 固定 `<工号>@studio-next`；指纹口径 `ssh-keygen -lf -E sha256`（`SHA256:...`）。
- 私钥**永不**入 git/台账/日志/REPORT；`scan-repo-secrets` 兜底扫描；密钥轮换=新 key 覆盖同名文件（旧指纹从 registry 移除，历史提交按 range 校验不追溯）。
- 外部代行人/审计人 key 放 `docs/keys/external/`（同权限纪律，另行登记，不占工号）。

### 9.2 commit 约定（作者 = 工号）

- **作者身份**：`git -c user.name="<工号>" -c user.email="<login>@studio-next.local" commit ...`
  （login=org-config `people[].login`；**不得**用他人身份或机器缺省身份提交新 commit）。
- **commit message 末尾 trailers**（`git interpret-trailers` 兼容，按序）：
  ```
  Studio-Worker: <工号>
  Studio-Key: SHA256:<公钥指纹>
  ```
  历史/无工号提交（如外部既有仓库）按 range 豁免；新提交缺 trailer=校验失败。
- **可选更强的 SSH 签名**（GitHub Verified 路径）：`git -c gpg.format=ssh -c user.signingkey=docs/keys/<工号>.key commit -S ...`；
  公钥登记到 GitHub 后显示 Verified。721 先以「trailer+指纹+作者」为**必过**，签名为**推荐**（CI 可加 `--require-signature` 收紧）。

### 9.3 校验面（三处，同一脚本）

- **提交前（本地钩子）**：`scripts/ops/install-git-hooks.mjs --repo <repo> --keys-dir <companyDir>/docs/keys`
  安装 `commit-msg` 钩子 → 每次 commit 校验「作者↔registry、trailer 齐全、指纹一致、工号已登记」，未过即拒。
- **CI/PR（722 落地）**：`node scripts/ops/verify-commit-keys.mjs --repo . --range <base>..HEAD --keys-dir <keys>`
  → 任一 commit 不合法即红。
- **人工抽查**：`--range <a>..<b> --json` 输出逐 commit 结果与失败原因。
- 校验失败分类（fail-closed）：`worker-missing`（缺 Studio-Worker）/`key-missing`（缺 Studio-Key）/
  `worker-unregistered`（工号不在 registry）/`key-mismatch`（指纹不符）/`author-mismatch`（作者邮箱≠registry）/
  `signature-missing`（`--require-signature` 下未签名/验签失败）。

### 9.4 落地步骤与例外

1. 制作人/宰相在 host 上执行 `gen-worker-key.mjs` 为在册工号生成 key（私钥只留本机 600；公钥/指纹登记 GitHub）。
2. 各岗配置本地 `git config user.name=<工号> user.email=<login>@studio-next.local`；安装钩子。
3. 首轮可 `--allow-range` 仅校验新提交（历史豁免），团队 key 未齐前钩子可 `--no-verify` 临时绕过，但 **CI 必红**（722 起）。
4. 制作人/宰相自身提交同样需登记自身工号 key（建议 `PRIME-0`/`PRODUCER-0`），不得借用他人 key。
5. 例外（外部审计/代签）走 `docs/keys/external/` 登记+制作人批，不得占用员工工号。

## 十一、CI required checks 与分支保护（studio-dev-722，2026-11-05）

> 目标：把「本地门禁 → GitHub required check → 分支保护」固化为可复跑、可回滚的治理面；
> 不碰 daemon/部署树/公司目录。脚本：`scripts/ops/required-checks.mjs`；workflow：
> `.github/workflows/required-checks.yml`；配置命令：`ops/ci/github-protection.md`（Lead 用 admin token 执行）。

### 11.1 本地一键 required checks

- `node scripts/ops/required-checks.mjs` 串四处：**verify:v2**（有 bun=`bun run verify:v2`；无 bun 按 package.json
  分解 guard/margin/typecheck/typecheck:v2/test:v2/hr-gate-audit/v2-suite-manifest/old-test-ledger）＋
  **verify:docs**（v0-doc-check）＋**scan-repo-secrets**＋**verify-commit-keys --range**（721）。
- 失败即红：输出逐 check PASS/FAIL/SKIP 摘要（可 `--json`）；`--only`/`--list`/`--dry-run` 便于排障。
- 可选 **pre-push** 钩子：`node scripts/ops/install-git-hooks.mjs --repo <repo> --keys-dir <keys> --with-pre-push`
  （推送前跑一键；耗时=全量 V2，团队可按需安装；`SKIP_REQUIRED_CHECKS=1` 可临时跳过）。

### 11.2 GitHub Actions workflow（CI 平台分层，2026-11-05 裁决）

- 触发：`push`/`pull_request` 目标 `dev`；`permissions: contents: read`；**不引用自定义 secret**。
- **required job `required-checks`（ubuntu，平台无关子集）**：checkout(fetch-depth 0) → Node 24 →
  `node scripts/ops/required-checks.mjs --range <event.before..HEAD 或 origin/<base>...HEAD> --only verify:docs,scan-repo-secrets,verify-commit-keys`；
  **不再在 ubuntu 跑 verify:v2**（macOS 专属 seatbelt/dsh/localplatform/channel 权限用例是平台性差异，不是缺陷）。
- **informational job `verify-v2-informational`（非 required，`continue-on-error: true`）**：ubuntu 跑
  `bun install --frozen-lockfile && bun run verify:v2`，仅提供信号；其红不阻断合并/不进入分支保护 context。
- **完整 verify:v2 是本地 macOS 落仓前门禁**：verifier 每次全量跑；CI 平台边界不改变该制度。
- required status check context 仍为 **`required-checks`**（job name 不变；strict=false/务实模式见 11.3）。
- 提交校验（`verify-commit-keys`）为 required 子集之一，但**务实模式默认=SKIP 不阻断**：
  registry 在场只表示「可运行」，不等于「强制」；未设 `REQUIRE_COMMIT_KEYS=1` 且未给
  `--require-signature/--strict-keys` 时只报告原因、exit 0。显式严格模式（env/旗标）才 FAIL；
  签名强制再开 `--require-signature`（团队 key 与签名习惯稳定后）。
- **公钥投影**：CI 读不到公司外部 `docs/keys`；`scripts/ops/export-key-registry.mjs` 只导 `<工号>.pub`+`.json`
  到仓库 `ops/keys/registry/`（私钥永不入仓）。**导出器安全（722 v2/F1）**：`--out` 与 `--keys-dir`
  同目录/互相包含（realpath 规范化后）一律拒绝；清理旧投影**只删与本次导出 registry 工号匹配的 `<id>.pub`/`<id>.json`**（及按内容标记识别的本工具 README），
  其它任何文件（含 `.key`/package.json/data.json/子目录/隐藏文件）**一律保留并告警**；不按扩展名泛删、不递归。

### 11.3 分支保护（dev；配置由 Lead 窗口用 admin token 执行）

- **默认=务实模式（F3，制作人 2026-11-05 拍板）**：required status check=`required-checks`（`strict=false`）、
  **管理员可绕过**（`enforce_admins=false`）、**不强制线性历史**（兼容现 dev merge commit）、
  审批数=**0**（GitHub 单成员组织无法自我批准 PR，禁止设 1）、禁 force push/删除、对话解决；
- **严格模式（未来可选，附录）**：`enforce_admins=true`＋PR 审批≥1＋`strict=true`＋线性历史——
  需先加机器人/第二账号并统一 squash/rebase 流程；命令见 `ops/ci/github-protection.md` §7；
- merge queue：**默认不开**；启用条件=保护连绿 ≥10 次 + 团队 key registry 就绪 + PR 并发明显（≥5/日）；
- 权限：classic PAT `repo` 或 fine-grained `Administration: write`+`Contents: read`；token 只由 Lead 持有，不入仓库/workflow。
- 命令与回滚：`ops/ci/github-protection.md`（GET 备份 → PUT 保护 → 核对 → DELETE/关闭 mutation 回滚）。

### 11.4 回滚与影响面

- workflow 可逆：删除 `.github/workflows/required-checks.yml` 即不再触发；分支保护 `DELETE` 即撤销；
  merge queue `disableMergeQueue` 关闭。
- 本地脚本/钩子不影响运行时（无 daemon/部署面依赖）；已生成的公钥投影可删除（仅 CI 读取）。
- 与 §九 衔接：提交校验的 key/作者纪律；与 §七 发布控制面独立（CI 不部署）。

### 11.5 CI 平台边界（2026-11-05 裁决；不花钱、不假装绿）

- ubuntu runner 无法可靠运行 macOS 专属套件（seatbelt/dsh launch、localplatform EACCES、channel 权限等是
  **平台性差异**，不是代码缺陷）；强行在 ubuntu 跑全量 `verify:v2` 会长期红、掩盖真实回归。
- **分工**：CI required job=平台无关门禁（docs/scan/commit-keys，快速稳定）；ubuntu 全量 V2=信息性信号
  （`verify-v2-informational`，continue-on-error，非 required）；**macOS 本地/verifier 全量 verify:v2=真实质量门禁**
  （落仓前每次必跑，制度不变）。
- 分支保护 context 不变（`required-checks`）；以后若 GitHub 提供 macOS runner 再评估收编信息性 job。
- 变更只动 workflow/文档；`required-checks.mjs` 语义不变（`--only` 为既有能力）。
