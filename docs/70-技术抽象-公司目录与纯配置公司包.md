## 〇、纯配置到底约束什么

“纯配置”不是“没有行为”，也不是“只要不写代码就安全”。它同时约束三件事：包里有哪些字节、
宿主拿到字节后会不会自动执行、声明式规则按什么语义解释。

### 0.1 定义包里可以有什么、不可以有什么

可以包含声明、受限规则表达式、提示文本、验收口径、文档、模板、数据引用和依赖引用，但：

- 不可包含安装/激活脚本、宿主命令、可执行插件、隐藏下载、自动执行钩子或秘密值；
- 声明式规则只能按§0.3 的版本化求值语义解释，不能借“配置”名义执行任意宿主代码；
- 提示词可以影响模型，但不是授权、资格、验收通过或事实来源；
- 需要代码提供的工具、agent loop、插件、验证器或传输适配器，统一归为**能力包**，
  在包外声明、单独分发、单独审查和授权。

这是对 `docs/43`“公司包不含代码，唯一例外是 dsh 插件”的有意修订。理由不是代码一定恶，
而是“含可执行代码的纯配置包”在概念上自相矛盾，也使导入校验、能力授权与公司批准混为一谈。
若要一键分发公司定义及其依赖，可以使用§1.4 的**分发聚合体**，但不得再把聚合体简称为纯配置公司包。

### 0.2 字节惰性：导入、校验、物化都不执行包内任何文件

“不执行”必须是机制，不是纪律。取得、解包、结构校验、差异比较、渲染预览、物化到工作区，
一律不得执行公司包内任何文件。

| 通道 | 惰性要求 | 常见偷渡 |
|---|---|---|
| 脚本与 shebang | 不按可执行位或解释器行调用任何包内文件 | `setup.sh`、`postinstall`、`Makefile`、`.cmd` |
| 版本控制钩子 | 不因导入而激活 `hooks/`、改写 `git config` 或拉取子模块 | `pre-commit`、`post-checkout`、`core.hooksPath` |
| 包管理生命周期 | 不因解包触发 `install`/`prepare`/`postinstall` | `package.json` 脚本字段、构建后端钩子 |
| 编辑器 / CI / 任务 | 不自动加载包内任务、预览服务器或工作流定义 | `.vscode/tasks.json`、`.github/workflows/**` |
| 引导文本 | 不把 `AGENTS.md`、提示词、README 里的指令当作激活步骤 | “运行以下命令即完成安装” |
| 链接与归档 | 不解引用符号链接逃出根目录，不递归展开嵌套归档后执行 | 软链到宿主目录、归档炸弹 |

- 可执行位、shebang、钩子路径、CI 配置与符号链接按“需标记”资产处理：清单记录，策略要求时拒绝，不得“顺手跑一下看看”。
- 把定义资产放入宿主**可执行位置**（`PATH`、shell profile、钩子目录、任务调度、插件加载目录、被宿主自动读取的配置）
  是独立的部署动作，须另行授权并留痕：对象、位置、时间、授权依据、撤销方式与影响范围。它和“读一份定义”不是同一件事，
  不能由导入器代办，也不能由包内声明自授权。
- 校验器、参考求值器与预览器本身属于能力包，只能在受控沙箱内显式调用；不因“只读”免于授权与隔离。
- 惰性只排除宿主自动执行，不排除文本影响判断：提示文本仍可能改变模型行为，这类影响按§4.2 处理，不构成授权、资格或验收。

### 0.3 规则表达式只经版本化 `Rule Profile`

若公司包用表达式（谓词、阈值、触发条件、风险分档、异常政策、授权范围）表达可判定语义，必须满足：

| 要求 | 具体含义 |
|---|---|
| 版本化语言档 | 语言、算子集、类型系统、比较与错误语义打包为 `Rule Profile` 的不可变版本；包内声明所用 profile 标识与版本 |
| 求值封闭 | 只读包内声明的输入与求值时显式传入的记录字段；禁止宿主时间、环境变量、网络、随机、文件系统探测、模型调用等外部 IO |
| 未知即拒收 | 未识别算子、未识别类型、类型错误、越界、缺失必需输入，一律拒收该规则或该修订；不得默认允许、默认忽略或降级为文本 |
| 激活钉版本 | 激活记录钉住 profile 版本与求值器实现版本；升级 profile 属变更，须重新验证，不得静默改变既有判定 |
| 共同用例 | 随 profile 发布参考求值器与共同用例（含拒绝用例）；跨框架一致以用例为准，不以“看起来一样”为准 |
| 定性不受迫 | 只能定性判断的语义（信任、尊严、长期价值、损害可接受性）保留判断位置、证据、异议与复审，不因无法机械化被删除或伪造成表达式 |

两条边界：

- profile 只决定“怎样算出一个可判定结论”，不决定结论是否被授权采纳；判定仍须具名位置与证据（§3.4）。
- 同一规则同时有人读文本与表达式时，按§4.2 的同一标识与一致性验证处理；冲突不得由“表达式优先”或“提示词优先”单方消解。

`Rule Profile` 与核心规范、公司定义修订分别版本化，是§5.3 版本轴中的独立一条。

## 一、公司定义、记录、部署、权威与分发形态

### 1.1 公司同一性由什么组成

公司至少有稳定身份、定义修订谱系和记录谱系。显示名、slug、git 地址、平台项目号和本地路径
都是别名或绑定，不能独自承担公司同一性。权威“在哪里”不属于绑定，而是独立的公司决定（§1.2）。

| 对象 | 内容 | 是否属于纯配置定义包 |
|---|---|---|
| `Company Identity` | 稳定、不可因改名复用的公司标识与合法谱系 | 是，只声明标识与谱系主张；当前身份状态不属于定义包，不证明外部承认或已经激活 |
| `Definition Revision` | 某一版使命、组织、规则、能力需求与模板 | 是，内容寻址或等价不可变修订 |
| `Record Lineage` | 任职、授权、决定、工作、承诺、证据、修正、权威激活与清算历史 | 否，属于运行档案与移交档案 |
| `Deployment Binding` | 宿主、路径、账号、秘密引用位置、硬限额、能力安装状态 | 否，属于部署，默认不随公司传播 |
| `Authority Requirement` | 本公司哪些事实域需要权威，及独立性、可核验、可导出要求 | 是，只声明需求，不指定端点 |
| `Candidate Endpoint` | 本环境实际可连、可写、可读回的候选权威端点与限制 | 否，属于部署，只作候选 |
| `Authority Activation` | 公司有权位置对某事实域的端点选择、范围、生效与失效条件的具名决定 | 否，属于公司记录，须写入 `Record Lineage` |
| `Activation Generation` | 每次权威激活产生的治理代次，用于判定“哪一代被授权” | 否，属于公司记录；不是技术租约 |
| `Capability Lock` | 某次实际解析的能力版本、内容摘要、兼容和权限结果 | 声明需求属于；实际锁与安装状态不属于 |

复制一份定义只能证明“拿到了相同声明”。同一公司恢复、新公司分叉、只读镜像和运行迁移，
必须分别满足§6.3 的条件，不能都叫作“安装完成”。**当前身份状态只归 `Record Lineage`**（§6.3）：
定义包只承载身份标识与谱系主张，包内写 `active` 不能覆盖记录中的 `liquidated`/`dissolved`，激活与对账一律以记录为准。
终态身份不会因为有人拿到旧备份或包内声明就重新成为 `active`。

### 1.2 权威三段：需求、候选、激活

公司事实“存在哪里”不能由写文件、部署清单或某个服务自荐决定。三件事分开，顺序固定：

```text
定义：Authority Requirement —— 哪些事实域需要权威，满足什么独立性、可核验、可导出条件
   ↓ 只提出要求，不指认端点
部署：Candidate Endpoint —— 本环境实际能提供哪些候选端点、连接方式、硬限制与已知缺口
   ↓ 只提供候选，不宣告“当前权威”
公司：Authority Activation —— 有权位置选定端点、范围、生效/失效、代次，写入 Record Lineage
```

- **部署不能单方换权威。** 部署可以新增、替换或移除候选端点，可以收紧可用范围，但不能把某端点宣告为
  “公司当前权威”，也不能因为“新端点更方便”“旧平台要下线”就改变既有事实域的权威指向。
- **激活权不能由目录文本或凭据自授。** 包内写“本目录即权威”、`.studio-next.yaml` 的声明、平台管理员权限、
  API key、fencing token、租约或在线时长，都不构成激活。激活只能由公司宪制指定的位置（§3.4/§3.5，
  或最终责任位置的明示授权者）作出，并至少记录：事实域与字段范围、端点、`Activation Generation`、
  上一代次、生效时间与失效/复审条件、依据、冻结与迁移安排、异议位置。
- **兼容现状也不暗中迁移。** 沿用当前平台作为某事实域权威，本身是一次显式 `Authority Activation`（“沿用”），
  不是“没改所以不用记”。首次导入既有公司时，须声明哪些事实域沿用、哪些空缺、哪些无法表达（§7.2）；
  不得把“读取兼容”读成“新端点已是权威”。`69-§3.3` 所称“显式的**公司激活决定加迁移**”在本卷读作：
  部署决定候选与硬限制，公司决定激活与代次，部署侧无权单独处置事实归属。
- **状态前置与竞争冻结。** `Authority Activation` 前须核验 `Record Lineage` 中的当前身份状态：只有 `active`
  才可作普通激活；`suspended` 只能在冻结新承诺下完成 as-of 恢复与对账，恢复决定作出并转为 `active` 后才可激活；
  `liquidated`/`dissolved` 不构成任何激活依据（§6.3/§6.5）。若发现同一事实域存在竞争激活、活代次或两个位置
  各自宣告有效，须先冻结写入，交预设终裁位置裁决并记录；未决期间任何一方都不得启动新代次（§6.6）。
- **`Activation Generation` 是治理概念**：它是某次激活的编号与前后关系，回答“哪一代被授权”。
  它不由技术组件自增，也不因进程重启、部署复制、镜像刷新或租约续期而增加。
- **`Fencing Token / Fencing Epoch` 是技术概念**：由权威端在写入时签发并校验，只防旧写入者在切换后继续写。
  围栏不能证明业务授权、不能延长授权、不能替代接收确认或结清（`69-§3.2`）。上一代围栏凭据即使形式上仍有效，
  也只能被拒写，不能被解释为“仍然有权”。

跨框架并发只有两种合法形态：

| 形态 | 条件 | 禁止 |
|---|---|---|
| 互认围栏 | 权威端签发并校验围栏，或各方共同指定可引用的仲裁者；所有框架的写入携带同一围栏凭据，发现活代次即拒绝启动或退出 | 各自持有本地租约、各自围栏自己 |
| 独占交接 | 无互认围栏时，同一事实域同一时刻只有一个写入者；移交走§6.3/§6.6 的冻结、导出、核验、接收与代次切换 | 双方“格式相同”就并行写；双写后希望一致 |

- 互认围栏缺失不是“可以试试”的空白，而是“只能串行”的约束；双方本地租约都有效，不构成共同写入许可。
- 仲裁者须有指定程序、权限、失效与争议处理；“两边都同意用某个 daemon”不是仲裁者。
- 权威端不可达时按§6.6 的故障处置：冻结新承诺、保全证据、由有权位置判定失能并建立新代次，不得静默 fail-open 到本地副本。

### 1.3 四种容易混淆的包

| 形态 | 内容与用途 | 不得宣称 |
|---|---|---|
| **公司定义包** | 纯配置的不可变定义修订，供校验、分享、分叉或初始化 | 包含全部历史、已取得外部信任、已激活权威或可直接履职 |
| **分发聚合体** | 公司定义包 + 可选能力包 + 各自清单/来源/许可证明的传输组合 | 整体仍是纯配置；签名校验等于安全与授权 |
| **运行/迁移档案** | 定义修订引用、历史记录、未决义务与承诺、证据引用、权威激活与代次、结清与移交信息 | 可公开传播、可由当前配置覆盖或可无主认领 |
| **部署样例** | 无秘密的宿主与平台示例、候选端点与能力替代说明 | 可直接复制本机路径、账号、信任、权威与授权到另一环境 |

运行档案可以含敏感信息，公开公司定义不等于公开工作历史、个人记忆、秘密、客户资料或证据。
传播前必须按知悉范围拆分，不能用“开源公司”推导“一切记录公开”。

- 四类包都不携带可复活的身份：`liquidated`/`dissolved` 的终态不因取得、校验、物化或分发任何包而改变；
  运行/迁移档案只用于核验、承接与追责，不是重新激活原身份的依据（§6.3/§6.5）。
- 包内状态主张与记录冲突时以记录为准；聚合体、签名或“来源一致”都不构成身份延续或复活的证据（§1.5/§5.1）。

### 1.4 聚合体清单与纯配置子集

分发聚合体必须有顶层 manifest，按 part 列出：

| 列 | 内容 | 缺失或未知时 |
|---|---|---|
| part 标识 | 稳定名称与命名空间 | 无法定位，拒收 |
| part 类型 | `definition` / `capability` / `template-asset` / `evidence` / `license` / `unknown` | `unknown` 一律拒收 |
| 内容摘要 | 摘要值与规范化规则 | 无摘要不得进入分发 |
| 来源 | 发布者、上游引用、制作/构建谱系 | 无来源只能标“未核验” |
| 许可 | 该 part 的许可声明与适用范围 | 未声明即标“待有权者决定”，不默认继承仓库许可 |
| 可选性 | 对运行是否必需、缺失影响 | 缺必需 part 不得宣称完整 |

- 校验器必须能输出 **definition-only 子集**及其摘要：只含 `definition` 类 part，附被排除项与原因。
  只有这份子集可以被称为“纯配置公司包”。
- 含未知 part 的聚合体不得宣传为可安全导入，只能作为待审查材料隔离；不得“忽略后继续”。
- 聚合体签名只证明“谁对这份字节清单作过声明”，不证明 part 安全、许可清晰或已被授权激活（§5.1）。
- 分区由清单表达，不由目录约定猜测；路径布局不得暗示“某 part 自动是权威、已信任或可执行”。

### 1.5 导入不是激活

完整过程有六个不同结论：

```text
取得传输对象 → 字节惰性与结构/来源校验 → 公司身份主张与谱系核验
→ 公司语义与权源审查 → 能力、部署与权威候选核验 → 有权位置激活（含 Authority Activation）
```

- 任一步失败都可以保留“已取得/只读检视”状态，但不得自动进入下一步。
- 结构合法只说明可解析；不证明使命来源正当、身份连续、授权真实、能力可用或部署者接受风险。
- 身份主张与谱系核验：包内声明的 `Company Identity`、修订谱系、上游引用与（如有）状态主张，须与可取得的记录、
  回执或公示对账；仅凭包内自述不得宣称“同一家公司”，包内状态主张不得覆盖记录中的当前状态（§1.1/§6.3）。
  记录为 `liquidated`/`dissolved` 的身份不得经导入、迁移、承继或任何激活路径复活（§6.5）。
- 无并行权威核验：目标事实域若已有活代次，须先完成§6.3 的交接或§6.6 的失能判定，不得叠加第二个写入者。
- 缺能力时可导入供审阅，但激活只能缩小到经授权的可用范围，或如实拒绝；不能先全员运行再补依赖。
- 激活是对某定义修订、某部署、某些事实域权威与某代次的具名决定，不随文件变化自动继承；换文件、换目录、
  换平台都不自动重新激活。
- 激活不代替授权或资格：能力认定（`71-§一`）、本次授权（`71-§四`）与开工门禁仍各自成立。

## 二、设立、使命与相关方的配置语义

### 2.1 设立不是自我声明即正当

公司定义必须能表达初始公设：使命、边界、初始自主/保留/禁止范围、相关方基本权利、
最终责任及实质控制、清算与残余承接、失能后再指定，以及本规范的版本与修订权来源。

设立责任共同体可以是单一主体或有明确规则的集体，不强制是人类或某个内部工号。它的成员、
代表、决定方式、责任分配、继任和外部争议位置必须可识别。配置中写入一个名字只是主张，
还需要相应的外部承认、委托、契约或公共规则作为来源；公司不能凭自签名获得对他人的权力。

**失败出口**：来源无法核验、责任主体不可识别、残余承接缺失时，可以保存草稿或要求补正，
不得激活为符合本纲的自治公司。既有公司补正只能从合法元治理与独立确认后向前生效，
不能追溯洗掉历史缺陷。完全无法补正时，只能重新设立或终止，不能自封“设立者”。

### 2.2 使命与边界是机器可引用的，不必全部是机器可判的

- 每项使命与边界有稳定标识、来源、版本、责任位置、解释/异议路径和生效区间。
- 自主、保留与禁止要有适用范围、优先关系和未覆盖处置；新事项默认保留。
- 禁止优先于效率与授权，保留事项不能因紧急或“工具支持”自动转自主。
- 可机械检查的条件尽量结构化；若用表达式表达，须按§0.3 的 `Rule Profile` 求值，未知构造与类型错误即拒收。
  信任、尊严、不可量化价值等可以保留定性判据，但必须指定判断位置、证据要求、异议与复审，而不是因不可编码就删除。
- 文本解释与机器规则有同等重要性的，须声明一致关系和冲突裁决；不得让隐藏提示词覆盖公开规则。

### 2.3 相关方不是通讯录

`Stakeholder Relation` 至少区分：

| 角色 | 必须能表达的关系 |
|---|---|
| 委托主体 | 使命/意图来源、优先关系、可接受的交代与保留决定 |
| 受益者 | 价值反馈、使用结果与相应的验收/评价位置 |
| 受影响者 | 风险暴露、异议、代理、救济、不可放弃权利，以及损害可接受性的认定通道 |
| 监督者 | 检查范围、独立关系、信息获取与报告去向 |
| 承诺相对方/代表 | 承诺条件、异议、变更、同意或公共程序 |
| 异议受理 / 外部锚 | 受理范围、期限、答复、升级、报告去向；与被审查线无汇报、利益或同源关系 |

同一主体的多个角色分别记录，不合并成“相关方同意”。无法直接表达的主体需要事前代理立场
或禁止规则；公司不得自行指定一个受自己控制的代表来免除第三方权利。外部身份、平台账号
或开放 API 密钥不是相关方权利的完整来源。

- 异议必须有受理位置：受理范围、期限、答复、升级与报告去向都要可配置。无人受理不等于没有异议，
  只等于尚未被接收；静默丢弃按违规处理。
- 相关方直接表达不充分、或内部分离不足而风险较高时，按 `66-§9.3` 实例化外部锚（独立监督者、公共权威、
  受影响者代理）；其选任、更换与资源不得由被审查业务线单独决定。外部锚提供意见与证据，不替公司承担最终责任；
  拒绝其意见须给理由并留记录。
- 相关方论坛或代表席位不能由公司单方指派，也不能以“已经问过相关方”概括不同角色各自的结论。

### 2.4 承诺声明与公开承诺

承诺不是任务描述的附属文本。配置需要能定义承诺规则、授权位置和变更程序；每次实际承诺
则进入运行记录，至少有承诺者、相对方、内容、条件、期限、后果与版本。

面向分散或未来公众的公开承诺，在作出前就必须有相对方类别、独立代表或可检验异议/公共
程序及变更条件。无法确定这些安排时，可以发布非承诺性说明，但不得形成可执行公开承诺，
也不能日后以“公众无法逐一同意”为由单方降级。具体承诺变更与公开规则变更的路径不得互换。

公司合并、分立、迁移、新设承继或“换主体承接”都不减少相对方程序的必要性（§6.4/§6.5）：
承接者不能因为旧主体已不存在就单方改写承诺条件；无法取得程序的，只能维持原承诺主体或依法处理。

### 2.5 不可接受、不可补偿损害不由公司单方认定

`63-I-15` 的认定权不能留在公司内部，也不能留给受益委托方。配置与技术必须能表达：

- **认定通道**：公共规则、事前合法约定的受影响者代理、独立裁决三者至少一条可引用；不得只写“由公司评估”。
  代理的产生须依可检验程序或由公共规则确认，不得由承诺方或受益方指定。
- **前置禁止**：通道缺失、代理未产生、裁决未作出时，不得把某类损害登记为“可接受风险”；
  相关业务不得以此为依据开工或继续，也不得作为承诺或验收条件的默认前提。
- **争议期**：争议未决期间不得抵销，不得以责任结算、补偿承诺或“内部收益更大”代替停止影响、保全与说明。
- **记录**：认定结论、依据、异议、复审与失效进入 `Record Lineage`；价值与监控视图按 `72-§4.4` 呈现，
  不以绿色指标抵销。
- **新型损害**：按§3.6 剩余裁量的功能类别判断是否需要新通道；不得以“清单未列”排除，也不得因紧急转为自主。

拒绝认定或无法取得认定时的失败出口是：停止继续影响、保全事实、向受影响者与监督位置说明、请求有权决定；
不是自行降级为“可补偿”后继续。

## 三、组织、岗位与治理的配置语义

### 3.1 组织是责任关系，不是固定树

公司可以声明临时协作、单人、扁平、部门制或联合组织。只有满足 63-§三的条件才设岗位、
部门、职级和持续任职关系。配置规范必须允许：

- 临时责任主体直接承接事项，不为形式完整伪造长期员工；
- 岗位空编，但空编不能解释实际动作；
- 无部门/职级要求的扁平公司，不能暗中生成“默认级别即能力”；
- 一人多岗与集体任职，同时保留累计禁配、成员责任和独立判断；
- 外部主体以契约或有限任职参与，不因接入平台自动获得内部保留权。

`Position`、`Holder`、`Appointment`、`Department`、`Rank` 是不同对象。`role` 这类显示标签
不能替代稳定岗位；`login` 不能替代任职身份；`job` 只能表达唤醒或工作安排，不能定义岗位。

### 3.2 定义与运行关系的分界

| 定义包可以声明 | 必须进入运行记录的事实 |
|---|---|
| 初始岗位、组织与**拟任**安排 | 任命是否被有权者决定、被任职者接受并实际生效 |
| 权限/义务的规则与上限、义务定义 | 每次具体授权、转授权、行使、撤回和结清；每个义务实例的触发与到期 |
| 资格要求与认定程序 | 某任职者在某范围/期限内是否实际被认定 |
| 能力需求与兼容约束 | 实际能力、安装/加载结果、资格与本次执行计划 |
| 唤醒条件、义务触发与期限语义 | 某次是否触发、是否收到、如何处理、是否逾期与逾期去向 |
| 初始章程、治理位置拟任与修订程序 | 后续每次提案、批准、生效、异议、撤回和历史；位置的实际任命与退出 |

配置声明的是**拟任**（candidate appointment）、权源要求与禁配条件，不是任命本身。实际任命
由 `66-§5.2.1` 的治理配置责任者或有权位置决定，经任职者接受并生效后形成 `Appointment Event`；
直接改文件不产生任命、离职或结清。从新版配置读取“某员工当前在岗”不能覆盖历史任职事实；
合法人事变更须由决定与生效记录驱动，再形成新的可读快照。治理位置的“设置”同理：配置写的是
位置与拟任，任命、回避、替换与退出进入运行记录（§3.4）。

### 3.3 岗位、义务与权的必要语义

**岗位**至少能说明存在理由、持续责任、权责组合、能力需求、监督/协调关系、资源条件、
绩效接口、空编处置和撤销交接。岗位类型不宜用少数封闭枚举限制新的责任组合；可以用受控
能力标签帮助检索，但新增标签不能绕过概念审查。

**义务**必须分定义与实例，否则“章程写了要报告”会在技术上无声消失。

| 面 | `Obligation Definition`（定义包） | `Obligation Instance`（运行记录） |
|---|---|---|
| 类型 | 动作、维持状态、避免结果、报告、停止 | 本次的实际形态与范围 |
| 承担位置 | 哪类岗位/治理位置，含替补规则 | 具体任职或位置实例、权源与接受/接收状态；未接受不等于义务不存在（见下） |
| 对象与相对方 | 对内对象、相对方类别或受影响者 | 本次涉及的具体对象与通知结果 |
| 触发 | 事件、周期或条件（表达式走§0.3 的 `Rule Profile`） | 触发事实、时间、来源、是否送达 |
| 期限 / 复审 | 期限、复审条件、逾期语义 | 实际到期状态与复审记录 |
| 完成口径与证据 | 可定性；须写判断位置、证据要求与异议 | 完成口径引用的版本、证据、判断者与结论 |
| 违约去向 | 升级、问责、救济、终止 | 实际逾期/违约处置与去向 |
| 父链与转派 | 父义务、可转派条件、接受要求 | 父链实例、转派接受记录、结清或未结承接 |

- **不强制都变成工作单**：周期性报告、通知、维持与避免类义务可以直接以 `Obligation Instance` 管理；
  需要产物与验收的才形成 `Work Contract`（`71-§4.3`）。但“没变成工作单”不等于不必记录、不会逾期、不用承担。
- **未决义务必须可见**：进入移交清单（§6.5）与监控观察面（`72-§4.2` 的“义务与期限”行），
  具名到期处置与升级去向；不得只写在提示词或章程正文里靠人记得。
- **权源与接受/接收要分开记**：承担位置除记录具体任职或位置外，还须记录义务的权源（法律、章程、有效决定、
  合同或承诺）与接受/接收状态。依法或依章程已生效的义务，不因承担者拒绝履行或拒绝接受而视为不存在；
  拒绝履行按违约去向处理，而不是把义务从记录中抹掉。需要移交的义务，提交与接收是两件事：
  **未经接收方接受不算移交完成**，未接收项仍归原承担位置并按残余责任程序处理（§6.5）。
- 义务与授权互不派生：义务与授权不因单方存在自动创设或消灭另一方；具体授权可以明示相关义务，
  授权者的管理责任不因此消失。有义务不等于有权，有授权也不自动免除管理责任。
- 义务不能靠“尽力做好”充当完成口径，也不能通过改名、拆成多条“建议”、或转派给未接受的位置来消解。

**授权**至少有授权者、父链、对象、目的、范围、条件、期限、可否转授、撤回与在途处置。
求值时遵守：禁止优先、未覆盖不自动允许、子授权不超出父授权、部署只能收紧不能放宽。
授权范围若用表达式表示，必须按§0.3 的 `Rule Profile` 求值；无法判断包含关系时不得当作已获授权。
任意脚本不是权限系统的必要组成。权威激活、部署变更或能力升级都不自动扩大授权。

**禁配与利益冲突**跨任职者的全部任职、出工和仍产生影响的历史关系计算。不同账号、会话、
CLI、agent loop、名字、部署实例或框架都不能重置。公司合并、分立或新设承继后，同一任职者的
累计禁配按合并口径计算（§6.4）。补偿控制要说明风险、期限和独立复核，不能用“已披露”
自动免除冲突。

**责任类型与贡献可分性。** `Responsibility Assignment` 至少区分：

| 类型 | 技术对象关联 | 不能替代/豁免 |
|---|---|---|
| 运营责任 | 工作、出工、行动、结果与未决义务 | 不能用管理头衔代替实际履职归因 |
| 管理责任 | 岗位、授权、信息、资源与监督条件的设计、维持与纠偏 | 不因运营行动转派而消失 |
| 最终责任 | 使命、制度有效性、对外承诺与未分配剩余事项 | 不是对每个操作失误同等担责，也不是无实质控制的背锅位置 |
| 对外最终责任 | 跨公司联合承诺、实际控制、外部交代与止损 | 不替代各公司内部最终责任或实际法律关系 |
| 共同责任 | 共同决定、共同控制、贡献可分性与事先约定的责任形式 | 不随机选一人承担全部，也不得以集体名义免责 |

每项关联责任主体、对象、来源、范围、有效期间、实质控制、证据、争议与结清；其设置、判定与
争议仍按 `66-§6.3/§13.2`，这里只定义技术对象，不另立归责算法。工作提供行动与结果证据（`71`），
绩效与价值评价（`72`）不能改写当时的实际控制。**一般责任**（说明、接受评价并承担后果）不是
第六种责任类型，由 `69-§2.5(4)` 展开，并与上述类型共享 `Responsibility Assignment` 的对象语义。

**贡献可分性由独立位置判定。** 对共同成果形成 `Contribution Separability Assessment`，记录可分性
结论、判断者、证据、控制关系、异议与复审；被评价方或直接受益方不得单独判定。贡献可分时按分工
与实际控制分别负责；不可分时按事前约定的协调、共同决定与共同责任承接。不得为了精确绩效虚构
可分性，也不得以集体成果掩盖个体明知与故意行为。

### 3.4 治理位置与具名实例

公司配置声明**拟任**的治理位置、权源要求与禁配条件；实际设置、任命、回避与替换由
`66-§5.2.1` 的治理配置责任者按宪制办理并进入运行记录。配置里写下一个位置和名字只是拟任，
不是任命；上表末行的岗位/组织记忆处置位置另按下文指定的记忆治理配置责任者办理，不落入该十类。
位置空缺不能由“框架”自动补位，也不能由部署、管理员或导入器自动兼任。

| 位置 | 管什么 | 明确不能做什么 |
|---|---|---|
| 意图受理 | 来源核验、接受/拒绝/暂缓/转呈及期限 | 收到即承诺，或静默丢弃 |
| 派工 | 依有效合同分派、处理拒绝与改派 | 单方改写范围、承诺与验收 |
| 口径定义 | 主导形成可判定的验收口径 | 事后为既定结果降标 |
| 方法所有 | 维护工作方法与经验转化程序 | 用经验直接改写上位规则 |
| 验收 | 依风险、口径和证据作正式判断 | 验收自己控制下的交付 |
| 变更决定 | 批准非承诺任务要件变更 | 绕过承诺授权与相对方程序 |
| 承诺授权 | 承诺的作出、变更、解除及相对方程序 | 由承接者单方加码或降标 |
| 常态叫停 | 在预设范围内阻止继续影响 | 用叫停替代终局或无限冻结 |
| 恢复决定 | 按风险在条件满足后允许恢复 | 由被叫停交付方静默恢复 |
| 个人记忆处置授权 | 审查个人记忆修正/清除的权利与影响 | 清除历史、承诺、证据或救济材料 |
| 岗位与组织记忆处置授权 | 岗位/组织记忆的定密、访问、继承、修正、清除及争议；出工记忆的访问、继承、修正、清除及争议 | 由被记录方或被审查方担任、主导或单独控制；以清除消灭历史、承诺、证据或救济材料 |

十类工作治理位置（`66-§5.2.1`）不变；上表末行是把 `66-§9.4` 的要求实例化，不是新增平行权力。
末行位置不属于该十类，不能由十类位置的治理配置责任者仅凭该身份自动取得设置权。公司宪制只声明
**记忆治理配置责任者**的拟任与独立性条件；实际任命由最终责任位置或其明示上位授权者作出，
该责任者须独立于被记录方与被审查方，并回答权源、任期、替补、空缺、回避、争议与退出。
由该责任者依 `66-§5.1/§9.4` 设置、任命、回避与替换末行位置，实际决定进入运行记录。
分工是：个人记忆走个人处置位；岗位记忆、组织记忆与出工记忆的访问、继承、修正、清除与争议
走岗位/组织记忆处置位，二者不得互相替代，也不得由“管理员能读写文件”顶替。该位置须独立于
被记录方与被审查方，不得由二者担任、主导或单独控制；任职者可对该位置的处置提出异议。

还需要按职能明确风险/可逆性分类、独立记录、资格认定、整体资源、跨环趋势汇总、争议/申诉
（含相关方与受影响者异议受理）、元治理、继任与清算等位置。它们不新增一套平行权力，都是
63 既有责任的技术实例化。其中：

- **汇总不得自我兼任**：整体资源责任位置与跨环趋势汇总位置不得由被汇总的业务位置单独兼任；
  报告直达委托主体或独立监督位置（`63-§4.6`、`66-§8.2/§8.3`）。缺该位置时不得宣称整体可持续，
  也不得以某一环的局部数字充当整体结论。
- **异议与外部锚须可实例化**：相关方/受影响者异议的受理范围、期限、答复与升级可配置；需要外部锚时
  按§2.3 与 `66-§9.3` 指定，其选任与资源不由被审查业务线单独决定。

**禁配：**

- 同一主体不得同时承担同一事项的交付、验收与口径裁定；不得自审自批。
- 叫停与恢复不得由同一主体单独兼任；恢复决定须独立于被叫停的交付方。
- 同一控制者换账号、换进程、换模型名、换部门、换框架不构成独立；用多个身份会签也不当然满足独立性。
- 低风险可以按比例采用补偿控制，但须写明风险、期限、独立复核与失效信号；补偿不得取消不可自证原则，
  “低风险所以自证即可”不是例外。

每个位置都必须能回答权源、任期、替补、空缺、回避、争议和退出。

### 3.5 最终责任、集体与跨公司关系

最终责任位置需要与使命、制度、监督、资源和止损相匹配的实质控制。最高日常决定者与最终
责任者可以不同，但冲突终局、相互止损和不得架空必须事前定义。集体顶点必须有成员、代表、
议事、表决、异议、替换和责任分配规则；不得只写一个“委员会”就视为责任已承接。

跨公司联合承诺前，须以可引用的协议确定各方对外最终责任、实际控制、联合验收、信息共享、
争议、终止和剩余承诺。各方内部闭环不能替代联合外部交代。联合协议可由独立配置对象承载，
并受各方权源验证；把对方公司包作为子目录复制并不形成合法联合关系。联合组织的独立身份、
共同控制、对外最终责任与解散分配见§6.4。

### 3.6 资源、信息与剩余裁量

资源配置须区分公司总上限、事项预留、员工/岗位限制、执行部署硬上限和不可转移的外部条件。
额度声明不证明资源真实存在，实际预留和消耗由 71/72 处理。跨环共享资源不能只按部门局部
判断是否可持续，承诺变更不能被“资源优化”绕过；整体资源与汇总的独立性见§3.4。

信息配置须表达需求、来源、时效、知悉范围、可用目的与保留规则。公司需要某信息不等于有权
读取，部署能读取也不等于应注入执行上下文。

**秘密在定义里只有逻辑面。** 定义包可以声明秘密的逻辑类别（如“平台访问”“签名密钥”）、用途、
知悉范围、生命周期与轮换/吊销要求；具体句柄、路径、值、账号、令牌、密钥库位置与信任状态
一律归部署。导入须拒绝疑似具体路径与令牌样式的内容，并按§5.1 隔离而非放行。

剩余裁量须预授权**功能类别**、最高边界、持有位置、事后独立复核和终止路径；个案再确定范围、
期限、理由与证据。功能类别按事项所需决定的功能、风险与责任界定，不按部门名称或逐案白名单界定，
真正的新型个案不因名称未出现而被排除（`63-I-12`、`63-§6.2`）；但也不得借此把清单外事项转为自主。
没有相应裁量者只能保全和升级。未预见、清单外或紧急都不是自由授权。

## 四、公司定义包的逻辑结构

### 4.1 逻辑组成而非冻结目录

后续规范可以沿用多文件目录，也可提供等价交换格式，但至少能区分：

| 逻辑部件 | 作用 | 典型内容 |
|---|---|---|
| 包描述 | 识别公司、规范版本、修订、入口、谱系与必需扩展 | 稳定标识、版本、摘要、上游引用、所用 `Rule Profile` |
| 设立与宪制 | 正当来源、使命边界、相关方与元治理 | 初始公设、责任顶点、保留/禁止、清算与残余承接 |
| 组织与任职定义 | 岗位/部门/职级及**拟任**关系 | 权责、义务定义、能力需求、治理位置拟任、资源 |
| 工作规范 | 工作类型、合同要件、风险/验收规则、触发与异常政策 | 类型及时限、复审、结清；表达式引用 profile 版本 |
| 权威需求 | 哪些事实域需要权威、独立性/可导出要求、不可用时的行为 | `Authority Requirement`、候选可接受条件、故障处置 |
| 能力需求 | 中立能力及宿主绑定需求、兼容、权限和替代关系 | 需求引用、版本范围、依赖锁引用、已知不能 |
| 人读资产与惰性模板 | 帮助理解履职的说明、提示与素材，不暗含机器权能 | 章程说明、提示词、方法、模板、文档（按§0.2 惰性） |
| 扩展与词表 | 可选/必需扩展、受控词和命名空间 | 扩展版本、权能影响、兼容规则 |
| 验证与许可材料 | 作者提供的示例、来源证明与该 part 的许可声明 | 用例引用、证明引用、许可证标识与文本 |

这些部件可以合并到不同物理文件，不要求公司作者重复维护同一对象。规范应指定唯一索引和
引用完整性，防止“索引写一套、部门文件写一套、人事档案再写一套”却无法判断谁是权威。
物理布局不改变§1.1 的归属：权威激活、秘密、部署绑定与历史不得因“放在定义目录里”而变成定义内容。

### 4.2 人读与机读分离，但不能互相否定

- 自由文本用于解释使命、理由、判断维度和上下文；机器声明用于权限、版本、引用和状态语义。
- 同一规则同时有两种表达时，要有同一标识、版本与一致性验证；差异不能被“提示词优先”消除。
- 文档中的示例不自动成为授权；注释、模板与后缀说明不能携带隐藏指令，也不因“读起来像安装步骤”被自动执行（§0.2）。
- 验收命令、探针或脚本若需执行，引用外部受治理能力包及其版本，不以任何形式内嵌进定义包；“示例脚本”也是脚本。
- 文本中的链接、附件和引用按知悉范围与来源规则处理；可读不等于可用于所有任务。

### 4.3 依赖声明与能力包隔离

公司只声明“需要什么能力、为什么需要、在哪个范围、允许什么副作用、有哪些可接受替代”，
而不是“请在宿主执行这段安装逻辑”。依赖引用至少具有发布者/命名空间、能力或包标识、版本
约束、来源策略和内容锁定方式。实际解析、签名验证、安装、挂载和资格认定由 71 分别处理。
能力包在聚合体中是一个 `capability` part，须带自己的类型、摘要、来源与许可（§1.4），
不因与定义包同处一个归档而获得信任、授权或执行便利。

对当前 `dependencies@1` 的属性绑定只能视为**需求候选生成器**：属性命中不能单独产生插件
启用权，更不能证明能力资格。公司的部门、职级或预算额度也不能直接兑换更大宿主权限；
需要额外权限时必须有相应授权与风险程序。

### 4.4 扩展与未知语义

扩展必须声明命名空间、版本、是否必需、影响的语义面、所请求权能和知悉范围。以下扩展不得
静默忽略：使命/边界、授权/义务、承诺、验收、证据、工作语义、身份/任职、秘密、权威与外部影响。
纯展示或别名扩展可在明确标记后忽略。扩展不能通过嵌套 Markdown、模板字符串或外链接引入
未审查的可执行行为，也不能引入 `Rule Profile` 之外的求值语义（§0.3），更不能改写核心概念。
未知必需扩展与未知 part 同样按拒收处理，不因“只是多了一个目录”而放行。

## 五、传播、信任与版本

### 5.1 传输不是信任，签名不是安全

git、tarball、HTTP、可移动介质或内容寻址网络都只是传输方式。导入面须在不执行包内容的
情况下处理路径逃逸、符号链接、可执行位、活性版本控制元数据、归档炸弹、超大文件和嵌套
负载，以及§0.2 列出的自动执行通道。秘密与本机路径要在导入、变更和出站方向检查；
扫描有漏报可能，疑似内容须隔离并明示限制，不能声称扫描器证明“绝无秘密”。
向外部扫描服务发送内容本身也受知悉边界约束。

来源证明可以包含内容摘要、发布者声明、签名、透明记录或构建/制作谱系。它们分别回答
“内容是否一致”“谁声明”“何时被登记”“如何产生”，不证明内容合法、无恶意或已被独立验收。
聚合体的来源证明还须按 part 展开，不能让一份总签名替全部 part 背书（§1.4）。
信任决定须引用部署者认可的信任锚、作者身份、版本、权限差异和复审规则。

### 5.2 信任锚、秘密与失能处置

- 公司包可以携带公开验证材料或许可文本，不能携带私有密钥、访问令牌或宿主信任状态。
- 首次信任由有权部署者或合法设立程序确认，不能由包内同名文件自行声明“已信任”。
- 升级要比较新旧发布者、权限、依赖、外部端点、必要扩展和验收要求；显著变化进入重新授权。
- 信任可以按发布者、包、版本或用途限定；过期、吊销、回滚与密钥更替都须有明确状态。
- 本机信任记录不能随公开包传播；离线分发也需通过独立取得的摘要/信任材料建立来源链。
- 秘密只以逻辑类别与引用出现（§3.6）；具体句柄与值归部署，轮换与吊销须有记录。

#### 5.2.1 信任锚失效不是 fail-open

信任锚不可用、被攻破、唯一签名者吊销、透明记录不可达或验证材料过期时，默认动作既不是“继续”，
也不是“全部丢弃”，而是有状态、有具名决定、有通知与复审：

| 状态 | 默认效果 | 谁能改 |
|---|---|---|
| `trusted` | 按既有范围与用途可用 | 有权部署者 / 合法设立程序 |
| `unverified` | 已装内容标为未核验：不得扩大范围、不得新装、不得据其作对外承诺；在用工作按风险暂停或限范围 | 有权部署者与合规位置具名决定 |
| `suspended` | 停止新使用；保留内容与证据，等待复核 | 同上，须写明范围与期限 |
| `revoked` | 拒绝新获取与新激活；在用内容按撤销程序停止、导出与替代 | 有权位置，须通知受影响方 |

- **阻断新信任是默认。** 继续使用必须是具名决定，写明依据、范围、期限、复审与残余风险；
  不得由读侧组件、导入器或“签名看起来对”自行恢复 `trusted`。
- **标未核验，不标正常。** 依赖该信任的工作、承诺与视图一并标为 `unverified`/受损（`72-§4.1/§4.3`），
  不得显示为绿色或“无异常”。
- **通知与复审。** 受影响运行位置、依赖方与相关方须被通知；复审有期限与责任人，逾期按异常升级。
- **留痕。** 锚更换、密钥更替与回滚保留旧材料与核验记录；不得用“重新信任一次”抹去失效期间
  已发生的写入、承诺与外部后果。
- **无可用锚时**只能隔离、只读检视与请求授权；不得静默 fail-open 到本地缓存或未签名副本。

### 5.3 七条版本轴

| 版本轴 | 为什么独立 |
|---|---|
| 核心/公司规范 | 决定语义与不可削弱约束 |
| 规则语言 `Rule Profile` | 表达式语义与拒绝行为独立演进；改求值即改判定 |
| 公司定义修订 | 记录具体公司规则与组织的变化 |
| 绑定档案 | 同一语义在某平台/宿主上的适配变化 |
| 能力包与依赖锁 | 供给升级不等于公司授权或资格已更新 |
| 框架实现 | 修复或升级实现不自动改变公司语义 |
| 记录/导出格式 | 历史迁移与长期可读需要独立演进 |

升级须声明兼容与迁移范围。不能仅以“只增字段”声称所有客户端兼容：新增必需语义、枚举值
或更宽权限也可能使旧实现误判。未知主版本、未知必需扩展、未知 profile、无法证明的迁移和
破坏历史连续的降级必须拒绝。记录/导出格式须能表达身份状态（§6.3）、权威激活与代次、
义务实例与未决项，否则“导出成功”不构成可交换。规范可以约定支持窗口，但不在抽象层强写
所有实现永远 N/N-1。

### 5.4 迁移是带证据的新产物

迁移须保留原对象、原版本、转换规则、结果摘要、未转换项、差异、验证和授权。它不能改写
原始历史；需要改变解释时，保留当时语义并提供新视图。可重放不等于可任意重写到同一事实源，
重复导入须按稳定标识和幂等规则防止重复公司、重复授权或重复承诺。迁移不是恢复：需要 as-of
恢复点、外部对账、缺口清单与时效性再验证时，按§6.3 的恢复条件执行。

### 5.5 公开传播与许可的现状

公司作者应能查看包内包含什么、排除了什么、依赖什么、会请求哪些权限、哪些内容不可公开。
这是可检视性要求，不等于公开决定已经作出。

许可按客观现状陈述：

- 根仓库当前的 `LICENSE` 与 `package.json` 标为 MIT；各工作区子包的 `package.json` 目前均未单独声明
  `license` 字段。这一现状只说明本仓既存字节的声明，不自动分层决定规范文本、必要词表、符合性用例、
  模板、实例公司内容与第三方能力包各自的许可与公开条件。
- 上述分层的许可、公开范围、商标与对外承诺**尚待有权者（制作人）决定**，并须记录决定内容与日期；
  本文不替其选择，不给法律结论，也不把某个许可证当成技术兼容性证明。
- “别的框架可按规范运行”以规范、词表与共同用例的**可获取性**为前提。若规范不公开或仅受限获取，
  跨框架声明相应受限：只能对标已获授权获取的对象作互操作与符合性声明，不得以“公开可获取”为前提宣传，
  也不得把未公开内容当作公共语义。
- 决定作出前，聚合体 manifest 的许可列按§1.4 标“待有权者决定”，不得默认继承根许可。

## 六、变更、分叉、迁移、继任与清算

### 6.1 配置变更不是直接覆盖

正常路径分七个阶段，其中两道门：

```text
候选修订 → 实质分类 → 验证授权 → 独立验证 → 激活批准（相关方/承诺程序不省略）
→ 受控生效 → 后验
```

- **两道门不能合并。** “授权进行验证”与“批准激活”是不同决定：前者允许取得证据，后者允许产生影响。
  先验证后补授权、或以“已批准所以不必验证”都不成立；等待验证期间原规则继续有效。
  这与 `72-§5.1` 是同一条责任链（该处为主答）；本卷只把其中“分类与合法授权”明确拆成验证授权与
  激活批准两道门，不另立第二种流程。
- 一般变更、具体承诺变更、公开承诺规则和构成性变更必须分流。草案、已批准修订、实际激活修订是不同状态；
  热重载只描述实现如何观察，不改变授权。
- 涉及相对方权利、公开承诺或构成性规则时，相关方程序与承诺程序不因“技术性变更”“只是升级”“只是合并”
  而省略（§2.4），也不得由受益方单方分类降级。
- 在途工作默认保留其合同和授权版本，除非依变更程序明确迁移。回滚配置只停止相应未来影响，
  不能抹去已发生的行动、外部后果或责任。修复、补偿和相对方程序另行记录。
- 合并、分立、同一公司恢复、迁移与新设承继本身就是变更，须走同一链（§6.3/§6.4/§6.5），不得作为“结构调整”另行通道。

### 6.2 公司不能修改上位规范

公司元治理只能在本规范允许的范围内修改本公司宪制。公司层配置不得把 I-1–I-16 解释为可关闭
选项，也不得通过扩展改变根命题。修订修宪权本身须由更高或实质独立的位置确认；无此位置时，
只能取得合法上位授权、终止或依法重新设立，不能自我锁定。

框架自身的变化同样是变更对象。框架生成框架、公司生成框架时，其权限、验证、激活与退出语义
以 `72-§5.3` 为主答（工作产物边界见 `71-§6.3`），本文不复制该规则。此处只保留一条必要约束：
生成物不因“自己写的”获得生产权，也不获得修改本规范的特权。

### 6.3 身份状态与相邻操作的区分

当前身份状态只由 `Record Lineage` 保存。定义包可以声明身份标识与谱系主张，但不携带权威状态；
导入、对账与激活一律以记录为准，包内写 `active` 不得覆盖记录中的 `liquidated`/`dissolved`（§1.1）。

身份状态恰好四种，没有附加的再激活、复权或“已恢复”状态：

| 状态 | 含义 | 仍存续什么 | 可否普通履职 |
|---|---|---|---|
| `active` | 可被激活履职 | 全部记录、义务与承诺 | 可 |
| `suspended` | 暂停履职：不新增承诺、不新开工 | 记录、未决义务、承诺与救济期间；允许 as-of 恢复与对账 | 否；只做对账、保全与核验，具名恢复决定作出后才转 `active` |
| `liquidated` | 普通运营关闭：未结项由具名清算者或残余责任承接者接受，结清活动仅限清算范围 | 历史、证据、法定/承诺期间的记录与残余责任；未结事项按接受范围处理 | 否；不恢复普通履职，也不因结清完成而回到 `active`；后续可转 `dissolved` |
| `dissolved` | 身份终止 | 历史与残余责任材料仍存；已结清与未结事项都按原记录追索 | 否；不得再被激活履职，也不得在原名下恢复运行 |

状态迁移是具名决定（依据、范围、公示或通知、异议位置），写入 `Record Lineage`；
“停止进程”“删目录”“注销账号”“租约过期”都不产生状态迁移（`69-§3.2`、`63-I-16`）。
`suspended` 的恢复须由公司宪制指定的具名恢复位置作出，不得由原经营位置、部署者或框架仅凭该身份自任；
涉及原经营位置时还须核验其独立性与事前授权，恢复前保持冻结新承诺；`liquidated` 只能转为 `dissolved` 或保持，
`dissolved` 只能保持：两者都是终态，不存在回到 `active`、`suspended` 的迁移，也没有附加的已恢复状态（§6.5）。

| 操作 | 身份与历史 | 必须满足 |
|---|---|---|
| **只读镜像** | 不激活履职，不改变公司身份与状态 | 标明来源修订、游标与陈旧度；禁止作为第二权威写入，不构成 `Authority Activation` |
| **新公司分叉** | 新公司身份，记录来源谱系；不自动承接原公司承诺与资格 | 新设立关系、新授权/资格/秘密/部署；可继承资产须逐项依据与接收确认 |
| **同公司恢复** | 同公司身份，延续记录与未决义务；身份须为 `active`，或 `suspended` 且具名恢复决定已作出 | as-of 恢复点、外部对账、缺口清单、时效性对象再验证、冻结新承诺、接收者确认；`suspended` 期间只对账与保全，不解除冻结 |
| **运行迁移/移交** | 同公司连续（原身份须为 `active`），旧写入者必须退出；终态后的承接另按下一行走新设 | 冻结/围栏旧写、导出核验、承诺与义务交接（含未决 `Obligation Instance`）、资格重认、旧框架凭据/秘密撤销与重签、旧外部连接关闭、新 `Authority Activation` 与代次、迟到副作用对账、接收确认 |
| **终态后的新设承继** | 新公司身份、新谱系；原终态身份不复活、不改写 | 新设立决定与具名设立者；资产、未决义务与承诺逐项承继及接收确认；相对方程序；历史只追加联接（§6.5） |

`Authority Activation`（含迁移后的新代次）前置核验当前状态：仅 `active` 可作普通激活；`suspended` 只能在
冻结新承诺下完成对账与核验，转为 `active` 后才可激活；`liquidated`/`dissolved` 不构成任何激活依据。
发现竞争激活或活代次时，先冻结写入并交预设终裁位置裁决，未决前任何一方不得启动新代次（§1.2/§6.6）。

**恢复的五项硬条件**（缺一不得宣称恢复完成）：

1. **as-of 恢复点**：写明恢复到哪个时点、哪个记录版本与哪个外部游标；恢复点不能晚于“最后可靠对账”，
   也不能落在结清决定之前（见下）。
2. **外部对账**：与权威端回执、外部系统游标、平台活动流比对，列出恢复点之后的外部事实。
3. **缺口清单**：缺失记录、不可重建项、语义损失、仍可能在途的副作用，逐项标责任与处置。
4. **时效性对象再验证**：授权、资格、秘密、租约、围栏代次、信任锚、能力锁都按当前时点重新核验；
   过期即失效，不因“历史上有过”而复活。
5. **冻结新承诺**：对账与再验证完成前冻结新承诺与新开工，只允许保全、修复与核验动作。

**禁止以结清前快照抹去结清事实，也禁止以任何程序复活终态身份。** `liquidated`/`dissolved` 身份不得以旧备份
“正常激活”，恢复也不得指向结清决定之前的快照。终态之后只有一条路：依法**新设公司身份并建立新谱系**，
资产、未决义务、承诺与责任逐项承继（§6.5）；原身份、原终态与原历史都不改写，只追加联接与去向。
不存在同身份重新激活的路径，也没有终态后的治理例外。历史不删除：结清记录、结清后发生的
外部事实与对账缺口都必须保留。该禁止只针对身份与运行连续性：结论、责任与救济仍可按
`66-§6.7/63-I-11` 依新证据重开；重开只更正相应结论与救济，不复活身份，连续性走新设承继。

复制相同公司标识而没有连续记录，不得声称“同一家公司已恢复”。分叉也不自动复制员工账号、
个人记忆、秘密、客户承诺或外部代表权。需要继承这些内容时，逐项获得合法依据和接收确认。

### 6.4 合并、分立与联合组织

#### 6.4.1 连续性由具名决定，不由文件合并决定

合并（A+B）、吸收（A 吸收 B）、分立（A→A1+A2）与联合（合资/联合体）都改变“哪些历史、承诺与责任
由哪个身份承接”。这不因目录合并、repo merge、数据库合并或改名而自动发生。

- 必须有 `Continuity Decision`：由各方有权位置（含相关方程序）作出的具名决定，写明生效时间、
  身份安排（谁延续、谁新设、哪些标识退役）、承接与不承接的承诺类别、**未决 `Obligation Instance`**、
  记录联接方式、异议与救济通道。未决义务须逐项由接收者接受，不能只写“责任一并转移”。
- **存续方只能是 `active` 身份。** `liquidated`/`dissolved` 不得被列为存续方，也不得经“决定延续”并入新实体；
  终态身份只能作为资产、未决义务与责任的**承接对象**，逐项依据、经相对方程序与接收确认，或由新设身份承继（§6.5）。
- **任职关系随身份逐项分配。** 决定须列明 `Holder`、任职关系、`Appointment Event` 与接受状态：谁继续任职、
  谁转任新岗位并重认资格、谁终止；不接受转任者的保留、终止与结清路径须逐项写明，不得默认“人随业务走”。
- 身份存续或新设由该决定明确；不得默认“大的那方存续”“文件在谁仓里谁存续”“沿用同名 slug 即连续”。
- 决定作出前只能做只读镜像与保全；不得对外宣称合并完成，不得单方承接对方承诺或把对方历史并入自家谱系。
- 合并、分立是变更，走§6.1 的两道门；触及使命、禁止与相关方基本权利的部分走元治理。

#### 6.4.2 记录谱系怎样联接

- **双谱系联接**：新记录同时指向两条或多条父谱系；原记录不改、不删、不重写，只追加联接与去向。
- **去重不靠删除**：同一对象在新谱系重复出现时，用稳定标识 + 来源 + 映射/别名表去重；不得“保留一份删一份”。
- **一个事实域一个权威**：合并后每个事实域须重新 `Authority Activation`（§1.2）。过渡期可保留两个只读源，
  写入只能一个；需要双写时必须有互认围栏或共同仲裁者，否则只能独占交接。
- **冲突保留**：同一对象两份不同事实并存时，保留冲突标记与裁决记录，不静默选一边（`72-§1.3`）。
- **可回溯导出**：消费者须能按父谱系回到原始记录；只导出合并后的“当前视图”不算移交。

#### 6.4.3 承诺、授权、资格与秘密

- **承诺不随合并自动转移**：须相对方程序（通知、同意或依原承诺条件）；公开承诺另按§2.4。无法取得程序的，
  只能维持原承诺主体或依法处理，不得以“公司已合并/分立”为由单方降级。
- **授权、资格、秘密重认重签**：旧授权不因合并自动延续到新身份；资格按新岗位与新执行配置重认；
  秘密须重新签发引用，旧框架凭据与旧句柄在交接完成后失效；旧外部连接须逐项关闭或经相对方
  授权的显式接管，未决连接不得默认续用；能力锁按新部署重新解析。
- **累计禁配按同一任职者合并**：跨合并各方、跨部署、跨框架、跨账号累计；不得以“不同公司”重置。
- **在途工作**保留合同版本或经变更程序迁移，不得静默改归属或改验收口径。

#### 6.4.4 分立时的分配

分立决定须逐项分配：在途工作与合同、未兑承诺、未决 `Obligation Instance`、资源与预留、秘密与访问、
四层记忆、证据与救济材料、问责未结事项，以及 `Holder`、任职关系、`Appointment Event` 与接受状态。
任职分配须写明谁继续、谁转任并重认资格、谁终止；不接受分配者的保留/终止与结清路径逐项写明。
分配不成立的部分由分立后的关联关系或残余责任承接者承接，并在决定中写明；不得以“随业务走”默认。

#### 6.4.5 联合组织

联合组织（合资、联合体、共同体）先分清对象类型：

- **作出承诺、持有义务/秘密/记忆的联合组织**：必须有 `Company Identity`、`Definition Revision`（可引用各成员的
  联合协议与章程）、`Record Lineage`、`Authority Requirement` 与身份状态（记录于 `Record Lineage`，§6.3），
  按公司级规则承担承诺、义务、记录与清算；不得因“只是联合”而免于身份、谱系与权威要求。
- **仅为协议对象的联合体**：不作出独立承诺、不持有独立义务/秘密/记忆时，成员仍是承诺与责任主体，
  联合体只是成员间的协议对象；不得把它说成公司，也不得借它形成共同顶点或对外单一责任主体。

作出独立承诺或持有独立义务时，联合组织须有独立的对象承载：

- **独立身份与成员关系**：成员、贡献/出资、共同控制规则、议事与表决、异议与僵局、退出。
- **对外最终责任**：按约定由一方、按份或共同承担，须与实际信息、监督、救济与止损位置相称；
  内部闭环不能替代联合对外交代（`63-§6.4`）。
- **联合验收与争议**：联合验收、信息共享、争议终局与终止程序事前约定；无法约定时不得作出联合承诺。
- **不假定法律人格**：技术对象只表达约定关系；是否具有法律人格由外部法律与登记决定，本文不替其认定。
- **不假定共同顶点**：联合组织不自动产生高于成员的统一顶点。无共同顶点时，冲突按预先约定的共同权威
  或联合程序处理；无法形成合法决定时拒绝或依法解除，不得由某一成员单方代表全体。
- **独立记录域**：至少一个由成员共同认可的权威（互认围栏、共同仲裁者，或共同授权且受制约的
  唯一写入服务，§1.2）。仅由一方控制、无法由成员共同核验与制约的账簿不是联合权威；
  唯一写入者可以是共同授权且受制约的服务，不能要求各方都写。
- **解散分配**：承诺、未决 `Obligation Instance`、证据、残余责任、记忆与资格的分配须在设立协议中
  事前约定并逐项接受；解散逐项结清，未结清不得宣称解散完成（§6.5）。

### 6.5 回收、移交与接收确认

公司、部门、岗位或任职终止时，移交材料按范围包含：

- 在途事项、合同版本、当前状态、最近可靠回执和可中断点；
- 未决 `Obligation Instance` 与未兑现承诺：承担位置、权源、接受/接收状态、触发、期限/复审、完成证据、
  违约去向、相对方、变更/争议状态与外部联系；
- 已消耗和预留资源、账号、秘密引用、未收回访问与外部连接；
- 资格重认结论（按接收方新岗位与新执行配置），旧框架凭据与秘密引用的撤销/重签记录，旧外部连接的关闭清单；
- 权源、任职/出工关系、决定依据、证据和未决问责/救济；
- 四层记忆的归属、知悉范围、保留/处置决定及未决异议；
- 权威激活与 `Activation Generation`、候选端点、围栏状态、迟到副作用与对账缺口；
- 当前能力/配置、规则 `Rule Profile` 版本、已知不能与后续复审安排；
- 身份状态建议（`suspended`/`liquidated`/`dissolved`）与结清意见及其依据。

移交方提交不等于移交完成；接收方须核验可读性、完整性与未决清单，并明确接受或附条件接收。
无人接收时进入残余责任程序，不能删除档案或宣称结清。技术校验通过也不能替代有权者接受。
**接管验证不只证明旧写入者被围栏拒写**：还须逐项处理其他外部副作用——旧凭据失效、旧连接关闭、
已排队动作与迟到写入对账、对第三方系统的通知或撤销；未处理的外部副作用按未结事项留账，不得视为已移交。

**公司层终态（`liquidated`/`dissolved`）的额外要求：**

- 终态决定由有权位置作出，逐项核对上述清单，写明未结项的承接者、接受范围与期限；
- `liquidated` 是普通运营关闭：未结项须由具名清算者或残余责任承接者**接受**，结清活动仅限清算范围，
  不恢复普通履职；后续可转 `dissolved`；
- `dissolved` 是身份终止：历史、证据与残余责任仍存，已结清与未结事项都按原记录追索；
- 对外公示或通知相对方与受影响者的程序不因“技术下线”省略；
- 结清后仍保留历史、证据、承诺与救济材料，不以“已删除”“已注销”替代记录；
- 结清写入 `Record Lineage` 并更新身份状态；结清前快照不得被用于恢复到 `active`，也不得作为重新激活的依据（§6.3）。

**终态不复活：只能依法新设并逐项承继。** `liquidated`/`dissolved` 之后，原身份不重新进入运行，
没有附加的状态迁移，也没有同身份重新激活的程序：

1. **新设**：由有权设立程序建立**新的 `Company Identity` 与新的记录谱系**，写明与原身份的关系
   （全部承接、部分承接或不承接）；
2. **逐项承继**：资产、未决 `Obligation Instance`、承诺、秘密、四层记忆、证据与救济材料逐项列明依据、
   承接者与接收确认；需相对方程序或外部登记的，先取得程序；未承接项写明归属与残余处理（§6.4）；
3. **历史不改写**：原身份、原终态、原结清记录与结清后发生的外部事实全部保留，只追加联接与去向；
4. **新身份各自激活**：新身份在自己的 `Authority Activation` 与代次下运行，不得沿用原身份的代次、
   凭据或围栏；
5. **对外表述**：只能称“新设并承继”，不得称“原公司恢复”“复权”或“原身份重新启用”；可以保留谱系与责任承接关系，但不得把新身份说成原身份本身。

**终态后谁能动作。** 处理未决义务、认可新设与承继的，只能是预设残余责任承接者、外部受托者或法定程序。
它们不能占据原经营位置，不能由原经营位置、部署者或框架自任，也不得据此把原身份重新激活（§3.4/§6.6）。
承接者空缺或失能时，按§6.6 的再指定程序处理并公示；未完成前不得宣称承继完成。
`Continuity Decision` 不得把终态身份列为存续方（§6.4.1）；终态身份只能作为资产与义务的承接对象出现。

### 6.6 防双写、围栏与失能

运行迁移必须区分授权决定、`Activation Generation`（治理代次）与 `Fencing Token / Fencing Epoch`
（技术围栏），三者不可互替（§1.2、`69-§3.2`）。

- 围栏只防旧写：旧宿主仍可能产生迟到副作用，切换后须对账，而不是假设它已经停了。
- 旧宿主不可达时，不能假装已经收到它的停机确认；应按预设故障处置冻结新承诺、保全证据，
  由有权位置判定失能并建立新代次，随后对账旧宿主可能产生的迟到副作用。
- 围栏签发与轮换须由权威端或被共同认可的仲裁者执行；单方轮换只在本方有效，不构成跨框架互斥。
- 租约过期本身不是业务授权、失能判定或清算完成；镜像不得因此被提升为权威。
- 顶点、清算者或残余承接者失能时，按预设继任和再指定程序处理。全部主体同时失能是自治失效
  与未结清状态，须向预设外部受托/法律关系提交并公示未决义务，不能以“终止进程”关闭责任（`63-§6.5`）。
  外部受托与法定程序只处理未决义务、认可新设与承继，不取得原身份的经营位置，也不构成复活原终态身份的授权（§6.5）。
- 发现竞争激活或活代次时，冻结写入并交预设终裁位置裁决；未决前任何一方不得启动新代次，也不得自称权威（§1.2）。
- 失能期间新承诺默认冻结；解冻须具名决定，写明范围、期限与复审。

## 七、与当前公司目录的关系

### 7.1 可继承与需要补足的面

下表是目标映射，不表示本阶段已经修改现行格式。事实细节与代码证据见 73。

| 当前对象 | 可继承 | 目标抽象需要补足/纠正 |
|---|---|---|
| `org-config.yaml` | 公司索引、部门/人员/工作流/资源等声明入口 | 不能独自承担完整公司语义；需设立、治理、承诺、任职、义务实例、权威需求与迁移等分型 |
| `departments/**/config.yaml` | 多文件组织资产与部门人读规则 | 与索引的唯一权威和引用一致性；关系不能只在 schema 收下后丢弃 |
| `departments/**/people/*.md` | 任职者档案与人读说明 | 岗位、任职、资格、员工身份分离；档案不是全部任职史 |
| `charter.md` / `charter/` | 宪制和章程资产 | 上位不可削弱约束、元治理与相关方权利的机器可引用性 |
| `prompts/` | 上下文和方法资产 | 不是权源；生成 `AGENTS.md` 是运行产物，不反向定义员工，也不得含自动执行指令 |
| `workflows` | 类型状态与语义锚点的绑定思路 | 不能代替合同、独立验收、失败、结清、新设承继与终态不复活（§6.5）的完整语义 |
| `jobs[]` | 定时唤醒与资源声明 | 不是岗位定义；触发耐久、收到与履行结果要另行记录，不能直接充当义务实例 |
| `dependencies.yaml` | 版本化依赖和属性候选绑定 | 中立能力需求、宿主兼容、来源/权限/锁和按出工生效语义 |
| 包内 `plugins/` | 可提取为独立能力包的候选内容 | 不属于纯配置定义包；不能因历史例外自动获得信任与授权 |
| 包内脚本 / 钩子 / 可执行位 / CI 配置 | 若存在，属执行内容或宿主自动化入口 | 不属于定义包；导入须标记并禁止自动执行（§0.2），不得借模板或钩子偷渡 |
| `.studio-next.yaml` | 本地挂载元信息的候选 | 不是源公司信任证书，更不是 `Authority Activation`；挂载状态与公开定义/运行档案分离 |
| `.git` | 传输、修订和 diff 工具 | 不是公司同一性或历史完整性的充分条件，也不是规范必需依赖 |
| `.AIWS/` / `var/` | 运行期工作区和部署状态的候选位置 | 不随定义包传播；权限、秘密、证据与迁移语义另行保证 |

### 7.2 兼容迁移必须诚实标损

现行 `org-config` 可以先通过**兼容绑定**提供只读投影，不必立即更换文件名。但若原格式无法
表达某责任位置、资格范围、承诺相对方、历史谱系或独立验收，就必须显示“未表达/不支持”，
不能由默认值虚构完整。迁移时要区分：

1. 原文已有且语义等价的字段，可直接映射；
2. 原文有名字但语义较弱的字段，只能标为候选，不得自动升格；
3. 原格式没有的概念，须新增受版本治理的表达，不得塞进自由提示词；
4. 与新理论冲突的旧默认，须走显式修订和迁移，不利用解析器偷偷改变；
5. 运行历史不能从当前目录快照凭空补造，缺失部分要标记不可重建及其责任；
6. 沿用当前平台作为某事实域权威，是一次显式 `Authority Activation`（“沿用”），须声明事实域、空缺与
   不可表达项；不得以兼容默认值代替，也不得读成“部署已经改了权威”（§1.2）；
7. 身份状态与谱系（是否 `active`、是否已结清、修订谱系能否对账）只从记录读取；原格式无法表达时必须显示“未表达”，
   不得默认 `active`，不得把旧备份当作可激活来源，也不得用包内状态声明覆盖记录（§1.1/§6.3）。

### 7.3 本卷闭合判据

- 公司定义可以纯配置独立校验、传播与分叉；导入、校验、物化不执行包内任何文件，聚合体能输出
  definition-only 子集及其摘要（§0.2/§1.4）。
- 权威由“需求→候选→激活”三段构成；部署不能单方换权威，激活权不能由目录文本或凭据自授；
  激活前核验当前状态，竞争激活与活代次先冻结再终裁；无互认围栏时只能独占交接，不支持多框架并发（§1.2/§6.3）。
- 同一公司迁移时历史、承诺与义务可移交；不能把新公司复制冒充原公司连续；接管须处理旧凭据、旧连接与外部副作用（§6.5）。
- 义务有定义与实例，权源与接受/接收分开记；未决义务进入移交与监控接口，不因未变成工作单或未经接收而消失（§3.3/§6.5）。
- 合并、分立与联合组织由具名 `Continuity Decision` 与相关方程序决定；终态身份不得列为存续方，
  任职关系与接受逐项分配；联合组织按是否承诺/持有义务区分对象类型，不假定法律人格或共同顶点（§6.4）。
- 身份状态恰好四种，`liquidated` 是运营关闭、`dissolved` 是身份终止，两者都不回到 `active`；恢复须 as-of 点、
  外部对账、缺口清单与时效性再验证，`suspended` 下只对账与保全；终态之后只能新设身份并逐项承继，
  原身份、原终态与原历史都不改写（§6.3/§6.5）。
- 每个治理位置有权源、任命、回避、空缺与退出；岗位/组织记忆处置不得由被记录方或被审查方担任、主导或单独控制，
  汇总不自我兼任，交付/验收/口径与叫停/恢复禁配不可用低风险例外取消（§3.4）。
- 不可接受、不可补偿损害不由公司或受益委托方单方认定；剩余裁量按功能、风险与责任分类，
  不按逐案白名单（§2.5/§3.6）。
- 变更有“验证授权”与“激活批准”两门；信任锚失能不 fail-open；许可与公开分层待有权者决定，
  跨框架声明随公开条件受限（§5.2/§5.5/§6.1）。
- 公司层不能削弱上位规范，能力依赖不能直接赋权，公开承诺不能由承诺方单方降级。
- 框架生成框架按 `72-§5.3` 主答；公司定义、历史与部署的分离不被合并、分立、迁移或新设承继破坏。
- 其他框架在规范与共同用例可获取的前提下能按公开语义实现，不必复制本仓目录、Node 运行时、DSH 或 git；
  若公开范围最终受限，该声明相应收窄（§5.5）。
- 当前格式只作为候选绑定，不以兼容为名虚构语义或宣称已经完成迁移。
