## 〇、定位与阅读指引

**为什么需要这份清单**：四家适配器与 yt 适配器均已「对 fake CLI harness / fake fetch 全绿」，
但 fake 全绿只证明「适配器对冻结口径的实现正确」，不证明「冻结口径本身与真机一致」。所有
口径性假设（变量名、旗标形态、路径公式、求和假设、API 形态）都以头注「拟稿」形式沉淀在
源码里，从未对真机核实。v0.6 验收（16-§四）要求「同一探针单派四家、证据格式一致、成本
可对账」——**过不了真机，就过不了 v0.6**。本文把散落在 8 个文件头注里的全部待验证项收拢
成一张总账，并给出验证的组织形式（探针集）与执行前置。

**读法**：§一 是总账（哪来/是什么/怎么证/证伪改哪）；§二 是 YouTrack 侧的独立验证线（与
探针集并行，GET-only 零授权先行）；§三 是探针集 v0 设计（v0.6 验收的直接施工面）；§四 是
执行前必须备齐的条件；§五 是全部拍板项汇总。

**探针 runner 的定位**（18-§1.3，冻结）：在适配器层（`packages/adapters` 独立测试套件内），
「适配器写完先过探针集才注册」——探针集是注册门槛，不是可选回归。fake harness 管「口径
实现」，探针集管「口径真伪」，两层互补。

### 2.2 updatedSince 开区间语法（F6）

```bash
# 假设：query `updated: <iso> .. *` 被接受（03 白名单只实测过 created 闭区间）。
# GET-only 变体：先用只读面拿一张现有单的 updated 值当边界 T，再发开区间查询

  "$YT_BASE/api/issues?fields=idReadable,updated&\$top=1" | jq -r '.[0].updated')
sleep 2

  --data-urlencode "query=updated: $T .. *" \
  --data-urlencode "fields=idReadable,updated" \

# 客户端严格后滤（现实现）必须保留；不含＝开区间严格大于，后滤是冗余保险（留）。
```

**判读**：400＝语法证伪 → issues.ts 查询构造改（候选退路：`updated: <iso>` 单值形或

### 2.3 links POST 形态（F8）——需写授权

## 三、探针集设计 v0（16-§四 v0.6「同一探针单四家全绿」）

### 3.0 统一证据格式（「证据格式一致」的落法）

每次探针运行产出一份 **ProbeRecord**（JSON 落盘，四家同构——这就是 v0.6「证据格式一致」
的可验面）：

```
ProbeRecord = {
  probe: 'P-01',                     // 探针单 id
  family: 'dsh'|'claude'|'codex'|'kimi',
  runId: string, startedAt, endedAt, // 一跑一档
  detect: { version, ok, gaps },     // 跑前必过（18-§一 detect 前置纪律）
  briefHash: string,                 // 任务书内容哈希（对账锚点）
  handle: { executor, sessionId, pid },
  events: StreamEvent[],             // 归一事件序列（收割要件①②的断言面）
  rawPath: 'raw/<runId>.ndjson',     // stdout 原文逐行留痕（证据，不解析）
  stats: ResultStats,                // { cost, tokens, duration, turns }（成本对账面）
  exitCode: number | null,           // 证据价值，不参与判定
  completed: boolean,                // isCompleted() 判定
  assertions: { name, pass }[],      // §3.2 各探针的断言明细
  verdict: 'green' | 'red' | 'gap',  // gap=能力不支持时明报（不算红）
  gaps: string[]
}
```

**对齐收割四要件**（17-§6：终态事件 completed + 输出非空 + REPORT 落盘 + 闸门 exit=0）：
适配器层天然断言前两件（`events` 序列）；后两件由探针 runner 补齐——探针任务书统一附带
「把结论写入 `REPORT.md`」指令、runner 统一附带固定验收命令（检查产物文件存在且非空，
exit 0 即闸门）。**四要件在探针面上完整成立，与生产收割同口径**，这是「同一探针单四家
证据格式一致」的实质。

**探针与 fake harness 的关系**：fake harness（test/fake-cli/）留在 CI 常跑（口径实现回归）；
探针集对真机跑（`packages/adapters` 独立套件内的 probe runner 子命令，18-§1.3 定位），
**不进 CI**（需真机与真金），以 ProbeRecord 存档 + 四家矩阵报表作为 v0.6 验收证据包。

green。**判据中 gap 的合法性清单随本设计冻结，禁自适应。**

### 3.2 探针与进化目标物理隔离（17-§11 落法）

17-§11 冻结口径：探针集物理隔离＝**一次性人工基建：专户持有题目，daemon 只持 id+期望
哈希**。落法（v0 形态，实现单照此施工）：

1. **题目库**（`packages/adapters/test/probe-bank/`，git 版本化）：每探针一份任务书模板
   （`P-0x-brief.md`）+ 期望指纹（`expected.json`：关键断言的期望哈希，如暗号串哈希、
   REPORT 内容哈希）。**建库是一次性人工动作**：题目与期望由制作人过目后冻结，后续改动
   走批示（防「考题跟着学生改」）。
2. **daemon/runner 侧只持 id+期望哈希**：probe runner 运行时读题目库渲染任务书，但运行
   产物（ProbeRecord）**只含 briefHash 与断言结果**，不含题目原文——executor 侧日志即使
   全量泄漏也无从预取下次考题。daemon 常驻面（调度/进化管线）**不 import 题目库**，只
   消费 verdict。
3. **与进化目标隔离的实质**：进化管线（F3，candidate 评分）若将来引用探针 verdict，只能
   拿「id+通过/未过」二值，拿不到题目与期望内容——candidate 无法通过改提示词「背题」。
4. **专户**：题目库的 git 写权限收制作人专户（一次基建时授予）；worker 泳道只读。生产
   泳道与探针工作区物理分离：探针工作区在一次性临时目录，不进公司 git 目录（公司目录
   是 daemon 唯一写入面，探针不得越界——06 职责边界）。

### 3.3 探针成本对账口径（16-§四「成本可对账」的落法）

- **三链成档**：每格 ProbeRecord.stats 记 `estimate`（预留，E1 模型）→ `tokens`（实测）→
  `cost`（claude=原生 usd；dsh/codex/kimi=v0 恒 0，**待价目表折算**——价目表在 models.yaml，
  17-§4，启用时点拍板见 §五-4）。
- **对账基线**：同一探针单四家并排可比的是 tokens/duration/turns（同任务书 briefHash 锚定）；
  claude 的原生 cost 与厂商账单抽样核对（一次人工）；三家折算成本在价目表启用后补算
  （ProbeRecord 已有 tokens，折算不丢数据）。
- **探针成本的台账归属**：探针跑真金，费用必须可归因。拟稿：探针 run 事件落 daemon 台账
  并标 `source='probe'` 维度（不混入公司交付成本口径「每成功交付」，C5 教训）——**归属
  拍板见 §五-5**。

### 3.4 注册门槛回写（18-§1.3）

探针集结果回写 agent.yaml 注册面：四家 executor 的注册条目在 v0.6 后附
`probeMatrixVerdict`（最近一次全矩阵 id+verdict+日期）；适配器改版（锁版本升级/旗标改形）
必须重跑受影响探针格再动注册。CI 仍只跑 fake harness（口径回归）；真机探针是晋升闸的
人工触发件。

### 4.3 execa 决策：killDescendants 二选一（★拍板项1，E2）

现状：锁 execa 9.6.1（`^9.4.0` 解析至 9.6.1），**无 killDescendants**；四家 kill 均为
「SIGTERM→宽限→SIGKILL 直杀子进程」，不覆盖子孙树——17-§6 表行的 killpg 语义实际未达成。
upstream 10.x（2025-11 起）已发布 killDescendants 选项（16-§二选型登记本意「唯一内建
进程组杀法」在彼处落地）。

| 案 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| **A（拟推荐）**：升级 execa 10.x | `killDescendants:true` + 既有 `forceKillAfterDelay:false`（升级链仍自持） | 官方内建进程树杀，四家同改一处 spawn 选项；16-§二选型本意落地；维护面最小 | 主版本升级回归：四家适配器+fake harness 全量重跑（adapters 独立套件本来就能单独跑）；execa 10 其余 breaking changes 需实现单过目 |
| B：留 9.6.1 自持进程组杀 | spawn 加 `detached:true`（POSIX 进程组），kill 改 `process.kill(-pid, SIGTERM/SIGKILL)` 杀整组 | 零依赖变更，回归面最小 | 自研杀链（四家重复或抽 util——adapters 内新增共享代码）；detached 进程在 daemon 先死时孤儿化，需 reap 纪律；Windows 无进程组语义（本仓 daemon 跑 macOS/Linux，可接受但须头注明示）；与 16-§二「唯一内建」选型理由分叉 |

**两案共同底**：升级链语义（TERM→graceMs→KILL）与「成功判定不认退出码」均不变。
拟推荐 A；拍板后走独立实现单（引用本节）。
