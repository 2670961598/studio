## 〇、本组文档要解决什么

69–72 已经回答“需要哪些技术语义”，73 已经区分目标与现状。本组继续回答：

1. 这些语义如何表达为版本化、可交换、可校验的公共工件；
2. Studio Next 如何用 TypeScript、Node、Bun、SQLite、CLI、平台和文件系统承载它们；
3. 每个目标包和文件里有什么，输入输出、状态、IO、失败、幂等、测试和迁移是什么；
4. 如何证明设计没有漏掉权责、失败、异常、恢复、退出与外部影响。

**交付深度是自然语言级代码设计，不是代码实现。** 本组可以写字段、类型、接口签名、状态迁移、配置示例和必要伪码；不创建生产 TS/JS、可执行 schema、迁移、构建或测试脚本，不安装依赖，不改变真实运行环境。

### 0.1 四类命题与四种状态

| 标记 | 含义 | 审查方式 |
|---|---|---|
| 〔事实〕 | 当前代码、配置、锁文件、官方资料或真实运行证据支持的事实 | 给路径、版本、URL 或证据；不得外推 |
| 〔结论〕 | 从 63–72 的概念和不变量推出的必要约束 | 找反例；不得用产品选择冒充逻辑必然 |
| 〔选择〕 | 本组选定但可以替换的工程方案 | 比较替代、成本、失败与退出；不得冒充公司规范 |
| 〔假设〕 | 关于性能、易用性、成本或现实效果的判断 | 给基线、任务分布和停止条件；未证前不得当事实 |

| 状态 | 本组用法 |
|---|---|
| **已有** | 当前源码和调用链真实存在；只限已证明范围 |
| **库级存在/未接运行链** | 类型或函数存在，但生产链未接或没有运行证据 |
| **目标** | 本组新设计；文件、字段、接口和行为尚未实现 |
| **未证** | 当前无法确认；必须给探针、负向结果和拒绝路径，不能写成支持 |

“必须”若用于目标语义，表示实现该目标时不可省略，不表示当前代码已经满足。“推荐/默认”只用于实现选择，不能削弱 63–72 的核心语义。

### 0.2 不可混淆的四种文档效力

1. **公共规范**：删除 Node、TS、DSH、SQLite 和本仓路径后仍成立的语义。
2. **绑定档案**：某种平台、宿主、传输或存储怎样承载公共语义，及其损失与退出。
3. **实现说明**：Studio Next 选择的 TS 类型、包、文件、依赖、默认参数和构建方式。
4. **审查与决策记录**：为什么这样选、哪些已证、哪些待决；不能反写成公司义务。

实现说明不得使用“公司必须采用本实现”的措辞。其他框架可以实现相同公共规范，而不复制本仓的目录、语言或进程结构。

## 三、工程决策记录

### D75-01 公共规范、绑定与实现分卷〔选择〕

公共语义放 76/77，宿主绑定放 78，TS 实现放 79–81，验证与决策放 82。理由是防止把 Node/TS/DSH/SQLite 的结构反写成公司规范。代价是跨卷引用增加，因此所有对象必须使用 §2 的稳定 ID 和唯一主表，禁止复制定义。

### D75-02 完整目标与发布覆盖分离〔结论〕

本组设计完整的 R1–R31 与核心对象，不把它们裁成“v1 可选”。具体发布可以限制组织、平台、宿主或工作类型，但必须标“不完整实现”、报告损失、拒绝覆盖外事项。首版真实任务分布、时间窗、阈值和首批用户仍由制作人决定，不在本组虚构。

### D75-03 保留有效分层，按职责迁移〔选择〕

不新设平行的 spec/core/engine 包，不推倒重写。保留 contract/core/store/company/prompt/gateway/adapters/平台/panel/api/studio-tools/daemon/boot 的现有方向；先解除类型环和职责错位，再拆超大文件。所有新边和阈值变更仍是独立提案，不由文档自行生效。

### D75-04 定义包、能力包、部署与运行档案分开〔结论〕

定义包只含惰性配置与人读材料；能力包可含经过审核的可执行内容；部署绑定含宿主、账号、路径、秘密逻辑引用和硬限额；运行档案含历史、承诺、证据和未决责任。聚合体可以一键传输，但必须逐 part 标类型、摘要和来源，不得称整体为“纯配置公司”。

### D75-05 权威采用需求—候选—激活三段〔结论〕

定义声明 `Authority Requirement`，部署提供 `Candidate Endpoint`，公司有权位置作出 `Authority Activation` 并进入记录。部署确认不是公司授权，激活代次不是技术 fencing。缺少互认围栏时只能冻结旧写者、独占交接、核对迟到副作用，不能并发双写。

### D75-06 事实、记录与投影分开〔结论〕

原始事实、外部回执、公司决定、台账事件、SQLite 镜像、监控视图各自标来源与证明边界。记录缺失不证明事实未发生。面板不得把未知、陈旧、冲突或缺口显示成零、空或健康。

### D75-07 Node 开发态与分发态分开〔选择〕

仓内继续 Node 24 原生可擦除 TS + ESM + NodeNext，Bun 只做 workspace 和脚本壳。对外 npm/DSH 能力包必须提供 JS 与 `.d.ts`，不能让 Node 加载 node_modules 下的 TS。默认采用独立 `tsc` 发射配置并验证产物；`bun build --compile` 会切换运行时与 SQLite，只能另审，不是默认等价分发方式。

### D75-08 冻结交换工件，拒绝双事实源〔选择〕

公共结构以冻结的 JSON Schema draft 2020-12、词表和共同用例交换。Studio Next 用受限 Zod 子集作参考 authoring/binding，生成并冻结 JSON Schema；不把 Ajv 引入为第二运行时事实源，不使用 `z.fromJSONSchema()` 的实验能力反向生成规范。

必须验证：冻结 schema 自校验、生成漂移、Zod 与冻结 schema 的正反样本等价、非 TS runner。官方没有承诺生成字节永远确定，所以运行时不得重新生成权威工件。语义摘要与原始字节摘要分开，摘要算法和规范化规则版本化。

### D75-09 版本精确锁与结构化兼容界〔选择〕

公共声明只使用 SemVer 完整版本（含预发布/build）的精确锁、包含下界、排除上界和显式预发布策略，不把 npm range 语法变成跨框架规范。`0.2.0-rc.2` 必须可表达。锁不满足区间或策略即拒绝，不取“最新”。DSH 的 peer/range 只在绑定边界映射，不要求其他实现复刻 npm 全部边角语义。

### D75-10 依赖最小化与证据优先〔选择〕

优先使用仓内已有依赖和 Node 标准库；不因流行、最新版本或作者熟悉而加包。每个依赖必须写用途、版本范围与实锁、运行时/开发归属、许可、限制、替代、退出、是否进入公共规范。默认不新增 Ajv、semver、axios、express、dotenv、uuid、日期库、tsx/ts-node 或 Drizzle RC。

### D75-11 现有组件按真实职责归位〔选择〕

`api` 承担目标对外 API，panel 聚焦监控与公司概览；`panel/external` 的现有职责必须给出迁移与兼容路径。公共 CLI 只认 `cli/main.ts`。`src/index.ts` 先改为无侧效果且仅再导出 `assembly/serve.ts` 的过渡出口，包根 `main`/`exports["."]` 与根 daemon 脚本同步改为 CLI 入口；确认无消费者后退役占位文件，不以 root 引用 cli 或 engine。`RunServeOpts` 以 `assembly/hrsync/run-serve-opts.ts` 为唯一来源并补全通知注入；`ServeConfig`、EngineConfig/Inflight 也先有唯一定义，再拆运行链。

### D75-12 能力替换默认走交接，不假定原地热更〔结论〕

安装、挂载、加载、探测、资格、授权和实际生效各有记录。包版本安装与源码 HMR 不是同一件事。更换 CLI/agent loop/插件时默认暂停、保全、冻结旧写者、资格重认、交接和恢复；H0a–H4 只有取得对应证据才可声明，不把 `--dump-config`、配置热重载或进程重启分别冒充加载成功、插件热更或无损切换。

### D75-13 安全边界进入每个文件契约〔结论〕

秘密只以部署逻辑引用存在，不进入定义包、提示词、历史、快照或日志。路径必须 containment + realpath + 符号链接检查，写入采用临时文件与原子替换；归档有数量、大小、深度和膨胀上限。监听地址和认证采用最小暴露面，当前 loopback/LAN 文档漂移只登记呈审，不暗中开放网络。

### D75-14 所有版本引用钉住身份与代次〔结论〕

执行计划必须引用定义修订、合同版本、资格认定、能力描述、执行配置和绑定档案的 ID+版本，不引用“当前最新”。历史出工段只能按当时版本解释；更换配置不重置身份、历史、禁配或承诺。

### D75-15 验证分层，不用测试绿替代能力证明〔结论〕

V0/V1 是文本、结构和语义；V2 是行为契约；V3 是跨实现互操作与独立验收；V4 是迁移/故障/安全；V5 是特定版本真机探针；V6 是指定任务分布的自治评估。文档可读性、作者判定器、多 agent 一致、fake 全绿、现有项目回归各自不能替代另一层。

## 四、公共工件与纯配置的工程约束

### 4.1 公共工件的最小集合

76/77 必须为下列未来工件给出完整自然语言契约，但本阶段不创建可执行文件：

1. 规范版本、命名空间、术语与对象关系；
2. 公司定义包、记录与移交档案的语义 schema；
3. 封闭 Rule Profile、默认目录、扩展与诊断；
4. 核心共同用例 R1–R31 与绑定补充 E/W 的字段、初始事实、动作、预期和禁止副作用；
5. 绑定档案、能力广告、符合性声明与损失报告；
6. 版本迁移、规范摘要、来源证明与重放规则。

### 4.2 版本与扩展

- 每份工件带 `$schema`、稳定 `$id`、规范版本和自身版本；引用必须指版本，不指“最新”。
- 扩展采用可枚举记录，至少含命名空间、名称、是否必需、值、来源与可选 schema 引用。未知必需扩展拒绝；未知可选扩展只能按声明的惰性规则保留，不得自动获得语义。
- 结构校验通过不等于授权、资格、事实真实、验收、结清或符合全部公司规范。
- 原始字节、规范化语义和签名是不同材料；每份记录说明各自证明什么、不能证明什么。

### 4.3 纯配置的否定约束

定义包不得包含：可执行脚本、安装/激活钩子、秘密值、本机绝对路径、宿主环境插值、网络请求、任意模板求值、隐式当前时间或随机结果。人读 Markdown 不得藏另一套机读规则；人读与机读冲突必须显式拒绝或按已声明规则处理并留记录。

## 九、审查与验收口径

本组完成只表示技术细节可以提交审核，不表示实现已经批准或可行。审查至少检查：

- 公共规范是否技术中立，每个概念是否有唯一主归属；
- 每个字段是否有类型、来源、空值、默认、身份、版本、失败与退出；
- 每条工作路径是否有拒绝、异常、返工、恢复、终止和承接；
- 每个绑定是否有损失、负向探针、替换和退出，是否把未证写成支持；
- 每个 TS 文件是否有职责、接口、IO、依赖、并发、错误、测试和迁移；
- 每个第三方依赖是否有真实版本、官方限制、许可、替代与退出；
- R1–R31、E/W、I-1–I-16、11 类治理位置、H0a–H4、V0–V6 是否完整追溯；
- 每个目标文件是否落入实际允许边、目录和行数预算，测试目录是否超限；
- 文档级结论是否限定检查范围，不用“P2=0”冒充全卷无瑕。

P0/P1 必须清零；P2 如实记录和处置。后续 V2–V6 未执行时必须明确写未执行，不能以“文档很详细”替代验证。
