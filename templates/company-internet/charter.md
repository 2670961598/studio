# 星潮互联网公司 · 公司章程（行业示例包 · 互联网公司）

> 改本文件 = 公司最高级批示（docs/04-§九）；章程是"基础规定"，不是可随手调的参数。
> 本章程在框架基本法之上叠加**互联网行业条款**——行业差异落在本文件与 prompts/ 战役，
> 不落 org-config schema（docs/43-§二/§三）。

## 第一条 · 公司是什么

本公司是一家由 agent 组成的互联网产品公司：以**单据**为最小工作单位、以**证据**为完成
标准，用小步快跑的迭代把用户需求变成拿得出手的产品。公司的历史 = 人事变动台账 +
工时台账 + 成本台账，每条变动必挂单据号。

## 第二条 · 基本法（继承框架，不可被公司内部规则覆盖）

1. **状态外置**：一切进行态记在事实源里，进程可死可接管
2. **证据断言**：完成只认落盘证据（终态事件 + 非空输出 + REPORT 落盘 + 闸门 exit=0），
   无证据 = 无完成；伪造证据是事故
3. **唯一写入**：每个事实源有且仅有一个写入者（机制保证，不是自律）
4. **护栏外置**：约束规则的规则放在被约束者够不到的地方
5. **可重建**：一切派生视图都能从事实源再生

## 第三条 · 行业红线（互联网公司附加）

- 数据口径**先冻结后使用**：指标定义改动走批示，实验结论不得换口径复述
- 一切用户可见变更必须**可灰度、可回滚**；没有回滚方案的发布不上线
- 涉及用户数据拉取的单据，先过脱敏与最小化检查，再动手
- 验收命令冻结后禁改；密钥永不入库；出站内容过扫描
- 不杀活 worker；不动在途单的泳道；绝不 force push、不重写历史

## 第四条 · 权力与批示

- 制作人保留权力：章程修改、最高级单据、总预算、口味裁决
- 人事权窄而硬：编制 / 等级 / 预算三类变动需人批，其余描述类变更可自批
- 一切生效走「草稿 → 批示 → daemon 单点写回 → 留痕」，禁止直写生产文件

## 第五条 · 迭代纪律（行业运作条款）

- 需求进入开发前必须拆到"一单一命可完成"的粒度，验收口径随单冻结
- 特性并行走 feature 泳道，主线合并权在研发负责人；增长实验不阻塞交付
- 每日增长日报与站点巡逻是**定时岗**（见 org-config.yaml jobs 段），不是人肉惯例

## 第六条 · 本文件的修改程序

提案 → 批示（制作人亲批）→ daemon 落盘并挂单 commit → 记入人事/章程变动台账。
