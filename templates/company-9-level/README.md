# 示例公司（公司自述）

> 本文件是**公司自述**：使命 / 当前方向 / 战役。人会读它，agent 的身份包也会取它的摘要（提示词 L1 层）。
> 与 `charter.md` 的区别：章程是"规则"（改它要走最高级批示），本文件是"我们在干什么"（可随方向更新）。

## 使命

用一条可验证的交付链，把需求变成有证据的产出。

## 当前方向

把第一条端到端交付链跑通：需求 → 拆单 → 派发 → 干活 → 证据 → 关单。

## 战役（近期）

| 战役 | 目标 | 结束条件 |
|---|---|---|
| 交付链打通 | 最小闭环可用 | 一张真实单据走完全程并留下证据 |
| 台账可用 | 看得见发生了什么 | 面板能回答"在干什么 / 谁干的 / 花了多少" |

## 单据类型流（workflows.types[]）

> 分发口径：`company-2-level` 随附 `workflows`/`hooks`/`yt` 示例段；`company-3-level`..`9-level`
> 骨架**不随附**这些可选段（缺省走框架兜底流，需要时按 2 级模板增补——模板骨架最小面口径）。

`org-config.yaml` 的 `workflows.types[]` 按单据类型声明状态链（引擎 `T:<type>` 流表键——
类型优先于等级查表）。内置两样例：

- `proposal`：呈批位流——部长在「待批」审批，批准后派发（130-P1）。
- `devtask`：**策划验收位**流（202-P1）——复验通过的完工件由派单策划在「待验收」批示
  验收；合法批示人=部门 leader∪组织锚∪制作人∪本单 dispatcher（镜像列）；验收位「批准」
  不查派单律（R3——对象是已完工复验件）；验收位「打回」走声明回退边 `待验收→已派发`，
  机器随即回新单重做位并物化 resume 意图（cause=策划验收打回）——F1-15 既有消费门唤起
  原 worker 带打回理由前情续跑重做（attempt 续号、causation 链上次工时单）。

生产部署按需增删类型段——类型流声明是部署面配置，不是框架代码；声明规则（W-1..W-9）
见 `docs/51-公司仓库规范正文.md`。
